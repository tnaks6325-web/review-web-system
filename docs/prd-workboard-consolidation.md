# 작업표·작업보드 통폐합 PRD / 단계별 작업지시서

## 목적

사용자에게 보이는 `가상 무시트 작업표` 개념을 제거하고, 작업보드를 작업 설정·행 데이터·운영 화면의 단일 업무 단위로 만든다. 구매양식 원장은 최초 제출값과 감사 이력을 유지하며, 반영대기열은 작업보드 DB 반영의 유일한 비동기 전달 경로가 된다.

대상은 승인된 무시트 작업 120건과 이후 신규 작업이다. `4/27(메이커스)좋은상황_상황버섯진액 98건` 및 시트 유지 선언 작업은 대상에서 제외한다.

## 최종 구조

`구매양식 원장(order_submissions) → sync_queue(workboard_apply) → 작업보드 행(campaign_participants) → 리뷰 인덱스·리뷰 내역·정산 조회`

작업오더와 모집공고는 `workboard_id`로 같은 작업보드를 참조한다. 기존 `sheet_id/tab_name`은 외부 API·첨부·정산의 호환키로만 남기며, 새 로직의 소스 오브 트루스가 아니다.

## 불변 조건

1. 작업보드 행·구매양식 원장·리뷰 인덱스의 주문 연결은 하나의 `order_submission_id`로 추적한다.
2. 일반 구매양식은 정원을 넘겨 빈 행을 만들지 않는다.
3. 직원 수정값은 늦게 소비된 큐가 덮어쓰지 않는다.
4. 결제금액은 같은 작업보드·같은 주문 연결일 때만 원장에 역반영한다.
5. 입금·리뷰첨부·수정요청이 참조하는 과거 행은 하드삭제하지 않는다.
6. 기존 120건은 sealed 백업 없이 새 경로로 전환하지 않는다. 정책 확정 뒤 생성되는 신규 작업은 생성 트랜잭션 안에서 새 작업보드 ID를 부여한다.

## 단계별 작업지시

| 단계 | 작업 | 쓰기 범위 | 통과 기준 | 롤백 |
|---|---|---|---|---|
| 0 | 백업·롤백 모드와 `workboard_id` 가산 스키마 배포 | 신규 테이블·nullable 열만 | 기존 경로 변경 0, 상태 `legacy` | 즉시 `legacy` 유지 |
| 1 | 120건 목록을 확정하고 대상별 sealed 스냅샷 생성 | 백업 테이블만 | 원장·행·리뷰·입금 참조 수 기록 | 스냅샷 폐기 없이 다음 단계 중지 |
| 2 | `workboard_id` 연결을 복사 방식으로 생성 | 새 ID 열만 | 기존 키와 새 ID의 1:1 대응, 누락 0 | 변경 저널 기준으로 ID 연결을 제거 |
| 3 | `workboard_apply` 큐 소비자와 변경 저널 구현 | 새 큐 타입·새 행 반영 | 멱등·정원·충돌·재시도 테스트 통과 | 새 워커 중지, legacy 처리 재개 |
| 4 | 내부 읽기 경로를 pilot 작업 1건에만 전환 | pilot 읽기 라우팅 | 원장/보드/리뷰/입금 수 완전 일치 | control mode를 legacy로 변경 |
| 5 | 승인 120건으로 확대 | 승인 대상만 | 작업별 대조와 오류 0 | 대상별 legacy 라우팅 + sealed 백업 참조 |
| 6 | 화면 용어·호환 참조 제거 | 화면 및 미사용 코드 | 30일 관측·오류율 기준 충족 | 호환 해석기 재활성화 |

## 운영 중단 기준

아래 하나라도 발생하면 해당 대상의 확대를 중단하고 `rollback-mode`로 legacy를 복귀한다.

- 원장 주문 수와 작업보드 연결 주문 수 불일치
- 주문 1건이 둘 이상의 활성 작업보드 행에 연결
- 작업보드 행이 있으나 리뷰 내역 또는 입금 참조가 사라짐
- 정원 초과, 큐 재시도 급증, 작업보드별 잠금 대기 증가
- 직원 수정값을 큐 처리로 덮어쓴 충돌

## 백업·롤백 규칙

- 전환 전 `POST /api/workboard-consolidation/backups`로 대상별 sealed 스냅샷을 만든다.
- 스냅샷에는 설정, 작업오더, 공고, 작업보드 행, 원장, 리뷰·첨부·수정요청·참여연결·입금항목과 RAW 메타가 포함된다.
- `POST /api/workboard-consolidation/rollback-mode`는 명시 확인 문자열이 있어야 하며 새 경로를 즉시 차단한다.
- `POST /api/workboard-consolidation/mappings`는 sealed 백업과 정확히 동일한 대상일 때만 실행되며, `rollback-mappings`가 이 단계에서 만든 ID 연결만 제거한다.
- 실제 데이터 복원은 이후 3단계의 변경 저널을 함께 사용한다. 0~2단계는 기존 데이터를 덮어쓰지 않으므로 legacy 복귀만으로 되돌릴 수 있다.

## 3단계 로컬 구현 규칙

- `legacy`에서는 기존 무시트 즉시 반영을 유지한다.
- `pilot` 또는 `enabled`여도 `tab_configs.workboard_id`가 연결된 작업만 `workboard_apply` 큐에 넣는다.
- 큐를 넣은 주문은 작업보드 행과 장부 재생성이 성공한 뒤에만 `written`이 된다.
- 제어 모드가 legacy로 돌아가면 미완료 `workboard_apply`를 `workboard_legacy_apply`로 바꿔 기존 무시트 기록 경로에서 이어서 처리한다.

## 운영 전환 순서

1. 마이그레이션과 코드를 `legacy` 상태로 먼저 배포한다. 이 단계에서는 기존 주문 경로가 바뀌지 않는다.
2. 이전 버전 서버가 모두 종료된 것을 확인한 뒤에만 승인목록 120건을 고정한다.
3. sealed 백업과 ID 연결을 완료하고, 작업 1건만 `pilot`으로 시작한다.
4. 원장·작업보드·리뷰내역·입금 조회가 일치할 때만 120건 전체로 확대한다.
5. 이상 시 즉시 `rollback-mode`를 실행하고, 복구 큐 완료 뒤 필요할 때만 연결 ID를 제거한다.

현재 상태는 로컬 구현·검증 완료이며 운영 배포와 실제 pilot은 아직 수행하지 않았다.
