# 2026-08-19 (2차) 입금일 오염 — 오버레이 번짐 차단 + 8/12 진단

1차(#839)는 **재료화된 8/11**(`manual_payment_marks` → `row_json`)의 번짐을 막았다.
2차는 **8/12 계열**, 즉 `participant_edits` 오버레이가 번지던 경로를 막는다.

## 8/11 과 8/12 는 경로가 다르다

| | 8/11 (대부분) | 8/12 (및 미재료화 8/11) |
|---|---|---|
| 어디에 있나 | `campaign_participants.row_json[입금]` 에 **실제로 박힘** | `participant_edits(col:입금)` **오버레이** |
| 원장까지 갔나 | `payment_records`·`payment_batch_items(#0)` 생성됨 | 없음 |
| 번진 이유 | `rehydrateManualPaymentMarks` 가 앵커 매칭 **모든 줄**에 기록 | 합성 시 **order 앵커에 중복 게이트가 없었음** |
| 집계 영향 | `review_index.is_submitted2='PAID'` | `col:입금` 편집이 `is_paid` 로 연동 → `counts.paid` |
| 정리 방법 | **데이터 정리 필요** | **코드 게이트로 즉시 해소(이번 배포)** |

## 원인 — order 앵커에 중복 게이트가 없었다

`_deriveAnchor` 는 `order_submission_id` > `manual` > `identity_key` 순인데,
중복 게이트는 **identity 에만** 있었다(`trackB.service.js` 합성 루프).
그런데 `order_submission_id` 는 **유니크가 아니다**(`sheetlessOrder.service.js:154`) —
8/18~19 무시트 사고의 부팅 복구 잡이 같은 주문원장 행을 배포마다 새 슬롯에 다시 써서
**여러 줄이 같은 `order_submission_id`** 를 갖게 됐다.

→ 입금칸 수기 표기 1건과 그에 연동된 `is_paid` 오버레이가 **중복 줄 전부에 적용**되어
리뷰 미작성 줄에 입금일이 보이고 `counts.paid`(입금완료)가 부풀었다.

## 조치 (이번 배포 · 비파괴)

- **합성 게이트를 order 앵커까지 확대**(`workdeskTab` · 마감자료 `closeout` 합성 **두 곳 모두**).
  한 앵커가 2줄 이상을 가리키면 **어느 줄에도 오버레이를 적용하지 않는다**(identity 와 같은 규율).
  → 8/12 표시·집계 오염이 **데이터 조작 없이** 사라진다.
- **write-back 계획기**(`_computeWritebackPlan`)도 order 중복이면 `__ambiguous` —
  종전엔 `byOrder.set` 이 마지막 행으로 조용히 덮어 **어느 줄인지 모르는 채 시트에 쓸 수** 있었다.
- **편집 시점 게이트**(`editWorkdeskRow`) — order 앵커도 유일성 확인, 중복이면 `ambiguous_order` 거부
  (새 번짐을 만들지 않는다).
- 화면 문구 정정: `중복 신원` → **`중복 줄`**(같은 주문·신원이 여러 줄), 툴팁에 "입금일 포함 오버레이 미적용" 명시.
- **[입금일 점검] ④ 추가** — 오버레이로 남은 입금 표기를 **날짜별**(`8/11 N건(번짐 M) · 8/12 …`)로 집계.

## 곁다리로 고친 것 — `participantEdits` 가드가 배포 전부터 빨간 상태였다

입금·리뷰 칸이 시스템 전용으로 잠기면서(`status_column_locked`) `is_paid`·`col:리뷰제출` 편집을
전제로 하던 단언 3묶음이 드리프트해 있었다. **잠금을 푸는 방향이 아니라** 현재 계약
(= 상태칸 편집·되돌리기 모두 거부, 쓰기 0)으로 갱신했다.
★ 빨간 가드는 새 변경도 못 지킨다 — 그래서 이번에 함께 고쳤다.

## 남은 일 — 재료화된 8/11 데이터 정리 (별도 승인)

이 배포로도 **`row_json` 에 박힌 8/11 은 지워지지 않는다.** 순서와 판정 규칙은 아래와 같고,
되돌릴 수 없는 조작이라 [입금일 점검] 숫자를 확인한 뒤 별도 승인으로 진행한다.

1. **중복 줄 정리**(기존 도구) — 근본 원인. ★ 입금 회차에 담긴 줄이 있는지 먼저 확인
   (`uq_payment_items_active` 는 `(sheet,tab,row_index)` 라 중복 줄은 별건으로 잡힌다).
2. **남길 줄 판정** — 정규 입금 대상은 `is_submitted=TRUE` 였으므로 **실제 이체된 줄은 리뷰 제출된 줄**이다.
   그룹에 제출 줄이 정확히 1개면 그 줄을 남기고, **0개 또는 2개 이상이면 사람이 고른다**(자동 금지).
3. **나머지 줄 회수** — `removeDepositStamp` 로 그 날짜만 제거 + `payment_records`(`source_key='manual-811:*'`)
   · `payment_batch_items`(#0) 회수 + `review_index.is_submitted2` 해제.
4. **`manual_payment_marks` 축소** — 실제 이체 1건당 1줄.
