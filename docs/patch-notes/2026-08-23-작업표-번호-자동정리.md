# 2026-08-23 — 작업표 번호 어긋남 자동 정리(줄 삭제 즉시 + 5분 스윕 백스톱)

## 적용 대상
- 본섭 `main` (PR: claude/row-deletion-number-reset-yadxos)
- 서버 `utils/rowNumbering.js` · `services/rowNumbering.service.js` · `services/trackB.service.js` · `services/sheetlessLedger.service.js`
- 프론트 `workdesk.html`([🔢 번호 정리] 전체 목록)
- 스키마 변경 0 · 마이그레이션 0 · 시트/Drive 무접촉

## 배경(신고)
「웰스앤헬스 국내산 천기 약도라지…500건」에서 **1번 줄을 지웠는데 표의 번호가 2번부터** 시작한 채 남았다.
"5분마다 자동 정리되니 그대로 둬도 되는가?" 확인 요청 → **아니었다.**

원인 두 겹:
1. 주기 스윕의 신호가 셋(**번호 빈칸 · 중복 번호 · 짝 빈 줄**)뿐이라, **"번호는 다 찼는데 `1..N` 이 아니다"**
   는 상태가 어느 신호에도 걸리지 않았다(다음 주문이 들어올 때까지 그대로).
2. **번호 칸이 없는 탭**은 재번호가 `no_target_column` 으로 아무것도 못 하는데 스캔에서 **빈칸 수 = 전체 줄 수**로
   잡혀 정렬(`blankNumber DESC`) 맨 앞을 **영구히** 차지했다 → 사이클 상한(12탭)을 매번 먹어 진짜 대상이 뒤로 밀렸다.

## 변경
1. **판정 단일 출처** `utils/rowNumbering.hasNumberGap` 신설 — 스캔 SQL 은 **원재료만** 센다
   (숫자 번호 개수 · 최솟/최댓값 · **번호 칸 유무**). 조건은 순수함수 한 곳에서만 판정한다.
   - 재번호 상한(`MAX_RENUMBER_ROWS` 5000) 초과 표는 **대상에서 제외**(매 주기 다시 쓰는 무한 루프 차단).
   - 빈칸·중복이 있으면 이 신호는 켜지 않는다(같은 사실을 두 번 세지 않는 가산적 신호).
2. **스캔이 대상 판정(`need`·`seqGap`)을 항목마다 실어 준다** — 스윕·화면이 그 값을 그대로 쓴다(사본 0).
   번호 칸 없는 탭은 `need=false`(위 ②의 starvation 해소).
3. **줄을 지우는 경로가 그 자리에서 다시 매긴다**(스윕은 백스톱):
   - 행 삭제 `_hideParticipantInTx` — 보충 슬롯 INSERT **뒤**, 장부 재생성 **앞**, `renumberTabInTx`(SAVEPOINT 격리·절대 throw 없음)
   - 줄 정리·중복 정리·수동 중복 정리 3경로 — `sheetlessLedger._renumberAfterRetire` 공용 훅
4. **화면**: 목록에 **[번호 어긋남]** 칸(헤더 7 ≡ 행 7 ≡ colspan 7), 안내 문구를 사실에 맞게 갱신.
   구버전 백엔드(`need` 부재)는 종전 세 신호로 접고 어긋남은 `?`("모른다"와 "없다"를 구분).

## 검증
- `tests/rowNumbering.test.js` **161케이스**(신규 [K] 27) + **변이시험 10종 전부 검출**
- 전체 회귀가드 **357개 파일 전건 통과**
- 실 http 오리진 브라우저 실측: 대상 1개만 잡힘(정상·번호 칸 없는 탭 제외) · 칸 수 7 · body 직속 · JS 오류 0
- 배포 스큐(구버전 백엔드) 실측: 종전 세 신호로 폴백 + `?` 표기

## 운영 함의
배포 후 **"번호가 1부터가 아닌 무시트 작업"이 순차로 자동 보정된다**(사이클당 최대 12탭 = 5분마다).
이미 인쇄·공유한 번호와 달라질 수 있다 — 종전 수동 [🔢 번호 정리]와 같은 성질이다.

## 롤백
- 전체: Railway `WORKTABLE_AUTO_NUMBER=0`(재번호 기능 전체) 또는 `WORKTABLE_RENUMBER_SWEEP=0`(주기 스윕만)
- 코드: 이 PR revert(스키마 변경 0 · 시트 API 0)

## 남은 한계(문서화)
번호가 **1부터 빠짐없이** 채워져 있고 **순서만** 어긋난 표는 여전히 스캔에 드러나지 않는다
(날짜 파싱이 필요해 전 탭 스캔에서 비싸다) — 그건 주문이 들어올 때 그 자리에서 다시 매겨진다.

# 후속(같은 날) — 재번호가 장부까지 다시 만든다(핑퐁 차단)

## 배경(프로덕션 실측)
배포 후 관측하니 스윕이 고친 것이 10분 뒤 그대로 되돌아왔다.

```
17:22 UTC  대상 35 · 빈칸 308줄   기준선
17:27      대상 23 · 빈칸   2줄   ← 5분 스윕이 12탭 정돈
17:32      대상 35 · 빈칸 308줄   ← 되돌아감
17:37      대상 23 · 빈칸   2줄   ← 스윕이 다시 정돈 (무한 반복)
```

## 원인
무시트 탭의 진실원본은 작업표(`campaign_participants`)인데
`participants.importTabFromIndex` 가 `row_json = EXCLUDED.row_json` 로
**`review_index` 값을 작업표에 덮는다**(`TRACK_B_PROJECTION` / `PARTICIPANTS_AUTO_SYNC` 10분 크론).
무시트 작업표에 row_json 을 쓰는 다른 실행부는 전부 쓴 뒤 장부를 재생성하는데
**재번호만 예외**여서, 다음 투영이 옛 번호(빈칸)를 도로 밀어 넣었다.

파급이 더 컸다 — 되살아난 빈칸 탭이 매 사이클 정렬 앞자리를 다시 차지해
**정렬상 맨 뒤인 "번호 어긋남" 14개 탭은 영영 차례가 오지 않았다**(관측 내내 14 고정).

## 변경
`renumberTab({ rebuild })` — 쓴 뒤 `sheetlessLedger.rebuildLedgers` 호출.
- 켜는 곳: 주기 스윕 · 전체 정리 · 수동 [🔢 번호 정리] 라우트
- 끄는 곳: 트랜잭션 안(주문 기록) · 줄 정리 훅 — 호출부가 곧바로 재생성한다(중복 금지)
- 미리보기·변경 0줄은 부르지 않는다 / 실패해도 throw 없이 `ledgerError` 로 사유를 싣는다

## 검증
회귀가드 [L] 13케이스 추가(총 175) + **변이시험 6종 전부 검출**(가드는 호출부가 아니라
`renumberTab` 안에 있어야 함을 변이시험이 잡아냈다) + 전체 357개 파일 전건 통과.

## 남은 과제(후속 검토)
`importTabFromIndex`(review_index → 작업표)는 **무시트 탭에서는 방향이 반대**다.
지금은 장부를 맞춰 무해화했지만, 근본적으로는 투영이 무시트 탭을 건너뛰는 것이 맞다
(단 `_reconcileSeen` 이 함께 걸려 있어 별도 설계가 필요 — 이번 범위에서 제외).

# 후속 2 — 투영이 무시트 탭을 건너뛴다(핑퐁의 근본 수정)

## 배경
직전 수정은 "장부를 맞춰" 되돌림을 무해화한 것이고, 근본은 **복사 방향이 반대**라는 것이었다.
`review_index → 작업표` 복사는 시트 시절 흐름의 마지막 화살표인데, 무시트 탭에서는
작업표가 원본이고 review_index 가 결과물이다.

## 변경
- 게이트를 `importTabFromIndex` **안**에 둔다 — 호출부 4곳(투영 크론·동기화 크론·수동 import·수동 sync)이 모두 덮인다
- ★ `projectTab` 은 건너뛴 탭에서 `_reconcileSeen` 도 건너뛴다
  (임포트 없이 돌리면 `source='import'` 활성 줄이 전부 비활성화된다)
- `_enrichTab` 은 계속 돈다(row_json 무접촉 · identity_key·주문 링크만 blank-only)
- 동기화 크론은 건너뛴 탭을 "동기화했다"로 세지 않는다

## 효과
무시트 탭 113개에서 10분마다 돌던 불필요한 복사가 사라진다(되돌림 위험 + DB 부하 제거).

## 검증
`tests/projectionSheetlessSkip.test.js` 17케이스 + **변이시험 5종 전부 검출** + 전체 358개 파일 전건 통과.
