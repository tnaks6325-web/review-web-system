# 2026-08-19 (5차) 보류건 판단 기준 — 증거 사다리 + 사람이 고르기

4차(#864)는 "리뷰 제출된 줄이 정확히 1개"인 그룹만 자동 복원하고 나머지는 **보류**로 뒀다.
이번은 그 **보류건을 어떻게 판단할지**의 기준이다.

## 기준 = 증거 사다리 (위에서부터, 정확히 1줄로 좁혀질 때만 인정)

| 순위 | 근거 | 왜 이게 근거인가 |
|---|---|---|
| ① | **입금 원장이 있는 줄**(`payment_records` / `payment_batch_items paid`) | 실제로 돈이 나간 줄이면 그 줄이 직원이 표기한 줄이다 |
| ② | **리뷰 캡처 업로드 기록이 있는 줄**(`review_submissions`) | `is_submitted` 는 `row_json` 파생이라 장부 재생성에 흔들리지만, **파일 업로드 사실**은 흔들리지 않는다 |
| ③ | **직원이 적은 시각보다 먼저 채워져 있던 줄** | 8/18~19 사고로 생긴 중복 줄은 8/11 에는 **화면에 없었다**. 채워진 시각 = `review_submissions`·`participation_links`·`order_submissions` 중 가장 이른 것 |

★ **어느 단계도 1줄로 좁히지 못하면 추천하지 않는다** — 억지로 고르지 않는다.

## ★★ 사다리는 추천까지만 — 자동 확정은 하지 않는다

- **자동 확정 규칙(리뷰 제출 1줄)은 한 글자도 바꾸지 않았다.** 사람이 이미 미리보기로 확인한 결과가
  배포 한 번에 달라지면 안 된다. 사다리는 **보류건에만** 붙고, **자동 확정 건에는 추천조차 붙이지 않는다**
  (같은 화면에 "확정"과 "추천"이 섞이면 무엇이 판단된 것인지 흐려진다).
- 보류건은 화면이 **줄별 근거를 나란히** 보여주고(리뷰제출/입금원장+날짜/캡처/채워진 시각),
  추천 줄에 미리 체크해 둔 뒤 **사람이 확정**한다. `고르지 않음(그대로 보류)` 선택지도 항상 있다.

## 서버가 최종 검증한다

`decisions:[{editId,rowId}]` 로 받되, **그 그룹의 실제 줄일 때만** 적용한다.
화면이 보낸 `rowId` 를 그대로 믿으면 **남의 줄에 입금일을 새길 수 있다**.
그룹 밖 값은 조용히 무시하고(쓰기 0), `not_sheetless`·`deposit_column_missing` 은
**사람이 골라도 열리지 않는다**(그 사유는 선택으로 해소되는 성질이 아니다).

## 창구

**[입금일 점검] → ④ [직원이 적은 입금일 복원하기] → 하단 「보류」 블록**
그룹마다 줄 목록이 라디오로 뜨고, 각 줄 옆에 근거가 붙는다:

```
◉ 60번   리뷰제출 ✓ · 입금원장 ✓(8/11) · 캡처 ✓ · 채워진 시각 8/5
○ 178번  리뷰제출 ✕ · 입금원장 ✕ · 캡처 ✕ · 채워진 시각 8/18
○ 고르지 않음(그대로 보류)
```

확인창은 `자동 N건 + 직접 고른 M건` 을 나눠 말하고, 결과 토스트도 `직접 고른 M건 포함` 을 표기한다.

## 남은 보류 (사다리로도 안 좁혀지는 경우)

말한다. 이때는 **은행 이체결과 파일**(예금주·금액·계좌끝 4자리·이체시각)과 대조해 사람이 고른다.
