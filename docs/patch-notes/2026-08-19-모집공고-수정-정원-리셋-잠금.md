# 2026-08-19 — 모집공고 수정에서 총인원·일건수가 리셋되던 문제

## 증상 (사용자 신고)

총 200건 · 일건수 10건으로 조절해 둔 공고를 [모집공고 수정]에서 저장하면
**총인원이 비어(무제한) 리셋되고 일건수가 다른 값으로 바뀌었다.**

## 원인

수정 모달의 진행상품 표에 있는 총인원·일건수는 **캠페인 정원(`recruit_total`·`daily_limit`)의
파생 입력**이다(`_syncPreviewFromOptRows` 가 표 → hidden 정원을 매번 다시 계산).

그런데 **옵션 없는 작업**은 옵션 원장(`campaign_options`)이 비어 있어, 표를 서버 값이 아니라
**작업내용 상품 원문(`work_detail.productLines`)을 다시 파싱**해 만든다
(`renderOptRowsWithProduct` 의 fallback). 원문이 **두 줄 이상**이면 그 줄들에 인원 정보가 없어
`recruitTotal`/`dailyLimit` 이 **0** 으로 떨어지고, 파생 규칙("하나라도 0이면 합계도 0=무제한")에
따라 캠페인 정원이 0 이 된 채 저장된다. 실브라우저로 재현했다(총 200/일 10 → 화면 0/0 → 저장).

## 변경 — 정원 변경 창구를 [📅 모집인원 조절] 하나로 (사용자 확정)

**수정 모드 + 옵션 없는 작업**에서 캠페인 정원을 잠근다(`_rfQuotaLocked`).

- 표의 **총인원·일건수 입력칸을 읽기 전용**으로 두고, 값은 **캠페인 원장 그대로** 표시한다
  (프리필도 상품 줄 수와 무관하게 첫 행에 원장 값을 싣는다 — 종전 `singleProduct` 조건이 0 리셋의 입구였다).
- 잠금 상태에서는 **표에서 캠페인 정원을 다시 계산하지 않고**, 저장 payload 에도
  `recruit_total`·`daily_limit` 을 **싣지 않는다**(미전송 = 서버 COALESCE 유지).
  화면 잠금만으로는 부족하다 — 낡은 화면·파생 계산이 다시 0 을 만들어도 원장이 흔들리지 않는다.
- 표 아래 안내 줄(`#rf_quota_lock`)이 **지금 값 · 바꾸는 곳**을 말한다:
  "총량은 [📅 인원]의 차수 추가, 그날 인원은 날짜별 조절로".

### 탈출구 — [🔓 직접 수정]

기본 일건수(`daily_limit`) 자체를 바꿀 다른 창구가 없으므로([📅 인원]은 날짜별 조절·차수 담당),
confirm 을 거친 **[🔓 직접 수정]** 을 남겼다. 열면 안내 줄이 빨갛게 바뀌며
**"저장하면 총 N · 일건수 M 상태로 덮어씁니다"** 를 입력과 함께 실시간으로 보여준다(조용한 리셋 금지).
모달을 다시 열면 잠금으로 되돌아간다.

### 잠그지 않는 경우

- **신규 발행** — 여기가 초도 정원을 정하는 유일한 창구다.
- **옵션 있는 작업** — 옵션 원장이 서버에서 그대로 오므로 파생이 정확하고, 옵션별 정원은
  [📅 인원]에서 바꿀 수 없다(잠그면 막다른 길).
