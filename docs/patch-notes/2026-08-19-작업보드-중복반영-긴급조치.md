# 2026-08-19 긴급 조치 — 작업보드 구매양식 중복 반영

## 증상

무시트(탈 구글시트) 작업의 작업보드에 **같은 리뷰어·같은 주문번호 줄이 반복해서 쌓였다.**
`0722)장수산업_쿠팡_탄소매트 900건`(참여자 901/900), `8/3(쿠팡)위프_블랙 탈취제 800건`(870/800) 등
정원을 넘겨 반영됐고, 같은 쌍이 규칙적인 간격으로 되풀이됐다.

## 원인 (2건)

### ① `writeOrderToWorktable` 의 `seq` 스코프 오류 — 직접 원인

`server/src/services/sheetlessOrder.service.js` (`642c33c4`, 8/18)에서 `let seq` 를 **try 블록 안**에
선언했는데, 커밋 이후의 완결 표시·신원 링크·로그가 **블록 밖**에서 그 값을 쓴다.

결과적으로 **모든 무시트 구매양식 제출**이 이렇게 흘렀다.

1. 작업표 행 기록 · 장부 재생성은 **정상 완료**(COMMIT)
2. `markOrderWritten` → `ReferenceError: seq is not defined` (경고만)
3. 신원 링크(`recordParticipationLink`/`recordReviewIdentity`) 실패 → 리뷰어 검색·리뷰 내역에서 그 행이 안 열림
4. 마지막 로그 줄에서 **함수 밖으로 예외**가 던져짐
5. 호출부가 잡아 `markOrderMirrorFailed` → 주문이 **`failed` 로 강등**, 화면엔 **제출 실패**로 표시
6. 리뷰어가 **다시 제출** → 새 주문원장 행 → 새 빈 슬롯 소비 → **작업보드 중복 줄**

### ② 부팅마다 도는 자동 복구 잡 — 증폭기

`server/src/app.js` 가 기동할 때마다 `recoverUnwrittenSheetlessOrders({ limit: 1000 })` 를 실행했다.
이 잡은 "실물 주문"이 아니라 **주문원장 행(os) 단위**로 멱등이라, ①로 생긴 중복 주문 각각이
"아직 반영 안 됨"으로 판정돼 **배포할 때마다 빈 슬롯을 하나씩 더** 가져갔다. 8/18~19 배포가 40여 회였다.

## 조치

- ①: `seq` 선언을 try 밖으로 올렸다. 제출 1건 = 작업표 1줄로 정상 완결되고 주문이 `failed` 로 강등되지 않는다.
- ②: 부팅 자동 복구를 **기본 OFF** 로 바꿨다(`SHEETLESS_RECOVER_ON_BOOT=1` 일 때만 실행).
  기능은 그대로 남아 있고, 필요할 때 `POST /api/diag/sheetless-worktable-recover`(admin·master)로 사람이 실행한다.

## 남은 위험 · 후속 (별도 승인 필요)

1. **이미 생긴 중복 줄 정리** — 같은 (탭, 주문번호, 연락처) 중 가장 이른 줄만 남기고 나머지 soft delete.
   ★ **입금 회차에 담긴 줄이 있는지 먼저 확인할 것** — `uq_payment_items_active` 는
   `(sheet_id, tab_name, row_index)` 기준이라 **중복 줄은 서로 다른 건으로 잡혀 이중 이체가 가능**하다.
2. **구조적 중복 방어 복구** — 무시트 경로는 `sheet_row_claims` 의 `(sheet_id,tab_name,dedup_key)`
   유니크를 건너뛰는데(`skipSheetMirror`), `campaign_participants.order_submission_id` 도 유니크가 아니다.
   → "주문 1건 = 줄 1개" 를 강제하는 제약이 없다.
3. **당일 중복 가드 확대** — 지금은 ㉮ 오늘(KST) 제출분만 ㉯ 15개 필드 완전 일치 ㉰ `campaign:<id>` 스코프라,
   어제 건 재제출·표기 차이·차수 재발행이 전부 새 주문이 된다.
