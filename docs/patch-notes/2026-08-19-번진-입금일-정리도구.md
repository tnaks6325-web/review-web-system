# 2026-08-19 (3차) 번진 입금일 정리 도구 — 미리보기 → 확인 → 실행

1차(#839)는 재생산을 막았고, 2차(#842)는 오버레이 번짐(8/12 계열)을 코드로 해소했다.
3차는 **이미 `row_json` 에 박힌 8/11 을 회수**하는 도구다.

## 판정 규칙 (사용자 확정 2026-08-19 · 완화 금지)

정규 입금 대상은 `payment.service.js` 가 `is_submitted = TRUE` 를 강제했으므로
**실제 이체된 줄 = 리뷰 제출된 줄**이다.

| 그룹의 제출된 줄 수 | 처리 |
|---|---|
| **정확히 1개** | 그 줄만 남기고 나머지에서 **그 날짜만** 회수 (자동) |
| **0개** | **보류** — 어느 줄이 실제 이체인지 사람이 판단 |
| **2개 이상** | **보류** — 사람이 고른다 |
| 시트 기반 탭 | **보류** — 작업표 값을 지워도 다음 빌드가 되돌린다 |
| 입금 컬럼 미상 | **보류** |

★ 서버가 임의로 한 줄을 고르지 않는다. 고르는 순간 그 추측이 곧 입금 원장이 된다.

## 실행이 하는 일 (한 트랜잭션)

1. 회수 대상 줄의 작업표 입금칸에서 **그 날짜 토큰만** 제거(`removeDepositStamp`) —
   같은 칸의 다른 입금일(`8/3, 8/11` → `8/3`)은 **보존**한다.
2. 칸이 비면 그 줄의 `review_index.is_submitted2` 를 `'NONE'` 으로(장부 재생성도 같은 결과를 만든다 — 즉시 반영용).
3. **수동 이력 회차(#0)** 의 해당 항목만 `cancelled` 로 회수 —
   ★ `historical_key='manual-811'` 로 한정한다. **실제 이체 회차 항목은 절대 건드리지 않는다.**
   `cancelled` 는 `uq_payment_items_active` 에서 빠지므로, 그 줄이 정말 입금 대상이면 다음 회차에 정상으로 담긴다.
4. 마커를 **남긴 줄에 정확히 재고정**(`anchor_type='manual'`, `anchor_value=<그 줄 id>`) —
   앵커가 다시 여러 줄을 가리키지 않게 한다(1차 게이트가 계속 건너뛰는 상태를 해소).
5. 회차 #0 의 `item_count`/`total_amount` 재계산 — 회수분을 빼야 "이체 1건 = 원장 1건"이 맞는다.
6. 무시트 장부 재생성(실패해도 작업표 값은 이미 정리됨 — 다음 재생성에 자동 반영).

## 창구

**입금관리 → [입금일 점검] → ① 아래 [번진 입금일 정리하기 →]**
미리보기(정리 대상·보류를 표로) → **확인창**(되돌릴 수 없음 명시) → 실행.
대상 날짜는 기본 `8/11` 이고 화면에서 바꿔 다시 계산할 수 있다.

- `GET  /api/trackb/payment/repair/deposit-fanout-cleanup`(adminOrMaster, 읽기 전용)
- `POST /api/trackb/payment/repair/deposit-fanout-cleanup`(adminOrMaster, `confirm:true` 필수)

★ **미리보기와 실행이 같은 판정 함수(`_fanoutGroups`)** 를 쓴다 — 사본을 두면 "미리보기 ≠ 결과"가 되고,
되돌릴 수 없는 조작에서 그건 가장 나쁜 실패다. 화면은 서버 계획을 **그대로 그리기만** 한다(프론트 재판정 0).
