# 2026-08-19 (4차) "직원이 최초로 적은 입금일" 복원

## 사용자 요구

> 최초로 우리 직원이 8/11과 8/12 입금일을 수동으로 입력한 버전이 필요해. 번진 값은 전부 다 없어져야 해.

## 2차 배포가 만든 부작용 — 원래 줄에서도 사라졌다

2차(#842)의 게이트는 **"앵커가 2줄 이상이면 어느 줄에도 오버레이를 적용하지 않는다"** 였다.
번짐은 멈췄지만, 그 결과 **직원이 적은 8/11 이 원래 줄에서도 안 보이게** 됐다.
요구는 "원래 줄엔 남고 번진 줄에서만 사라지는" 상태다.

## 왜 오버레이만으로는 안 되나 (구조적 제약)

합성은 **행에서 파생한 앵커**(`_deriveAnchor`: order > manual > identity)로 편집을 찾는다.
중복 줄은 같은 `order_submission_id` 를 가지므로 **구조적으로 같은 키**가 된다 —
편집 쪽 앵커를 아무리 바꿔도 "둘 중 한 줄에만" 붙일 방법이 없다.

→ **원래 줄에는 값을 실제로 새기고(`row_json`), 오버레이는 이력으로 내린다(`reverted_at`).**
그러면 그 줄에만 남고 번진 줄에서는 사라지며, 앵커 모호성 자체가 소멸한다.

## 판정 (사용자가 이미 확정한 그 규칙)

| 그룹의 리뷰 제출된 줄 | 처리 |
|---|---|
| **정확히 1개** | 그 줄 = 원래 줄. 값을 새기고 나머지에서 지운다 |
| **0개 / 2개 이상** | **보류** — 사람이 고른다 |
| 시트 기반 탭 / 입금 컬럼 미상 | 보류 |

★ **입금 원장(`payment_records`·`payment_batch_items paid`)이 있는 줄은 지우지 않는다** —
실제 이체된 줄일 수 있다(fail-closed). 미리보기가 그 줄을 `원장 있어 보존` 으로 따로 보여준다.

## 실행이 하는 일 (한 트랜잭션)

1. 원래 줄 `row_json[입금칸]` 에 **직원이 친 값 그대로** 병합 기록 + `is_paid = TRUE`
   (`8/11`·`8/12` 는 물론 `계좌 오류` 같은 메모도 해석하지 않고 그대로 — "최초 입력 버전"이 목적)
2. 번진 줄에서 **그 값만** 제거(같은 칸의 다른 입금일은 보존). 칸이 비면 `is_paid=FALSE` +
   `review_index.is_submitted2='NONE'`
3. 그 오버레이와 **짝 `is_paid` 토글**을 함께 `reverted_at` 처리
   (짝을 안 내리면 입금완료 집계가 어긋난 채 남는다)
4. 무시트 장부 재생성

## 창구

**입금관리 → [입금일 점검] → ④ 아래 [직원이 적은 입금일 복원하기 →]**
(④ 의 "여러 줄에 번지는 것"이 1건 이상일 때 노출) → 미리보기 → 확인창 → 실행.

- `GET  /api/trackb/payment/repair/deposit-overlay-fix` (adminOrMaster, 읽기 전용)
- `POST` 동일 경로 (adminOrMaster, `confirm:true` 필수)

★ 미리보기와 실행이 **같은 판정 함수(`_overlayGroups`)** 를 쓴다. 화면은 서버 계획을 그대로 그릴 뿐이다.

## 3차(#843) 도구와의 관계

3차 [번진 입금일 정리하기]는 **`manual_payment_marks` 기반**이라 8/11 복구(#0 회차)를 실행한
경우에만 대상이 생긴다. 실제 운영 데이터에서는 ①이 **0건**이라 그 버튼이 뜨지 않았고,
오염의 실체는 ④ **오버레이 번짐**이었다. 이번 도구가 그쪽을 담당한다. 두 도구는 대상이 겹치지 않는다.

## 범위

- 마이그레이션 0 · 신규 테이블 0 · 시트/Drive 무접촉
- 쓰기 표면 3곳: `campaign_participants`(그 칸 + is_paid) · `review_index.is_submitted2` ·
  `participant_edits.reverted_at`(이력 보존, 삭제 아님)
- 주문 원장·회차·`payment_records` **무접촉**
