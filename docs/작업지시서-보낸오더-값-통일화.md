# 작업지시서 — 보낸오더 ↔ 리뷰웹 값 통일화 (1~8)

> **이 문서 하나로 다른 개발도구가 그대로 이어서 진행할 수 있게** 쓴 인수인계 문서다.
> 작성 2026-08-25 · 1~6 구현 완료 · **7~8 미착수**.

---

## 0. 목표와 이유

### 목표 (사용자 확정, 원문)

> "지금 끊겨있는 값들을 통일화한다. 하나씩 이어붙히자 — **보낸오더를 수정하면 리뷰웹에서도 수정된 값이 적용되고 실제 모집공고와 작업표까지 반영되도록**, 반대로 **리뷰웹시스템에서 수정하면 보낸오더까지 수정 반영되도록**."

### 왜 필요한가

같은 작업 하나의 값이 **네 군데**에 흩어져 있고, 그 사이 화살표가 군데군데 끊겨 있었다.

```
인트라넷 리뷰오더(원본)  →  리뷰웹 작업오더  →  모집공고  →  작업표 / 리뷰어 화면
   review_orders            work_orders        recruit_campaigns   campaign_participants
   (Cloudflare D1)          (PostgreSQL)
```

끊긴 자리마다 증상이 달랐다 — 어떤 값은 **조용히 버려졌고**(저장했다고 답하면서), 어떤 값은 **옛 값과 새 값이 한 화면에 섞였고**, 어떤 값은 **아예 수정이 막혔다**. 담당자는 고쳤다고 믿고 넘어갔고, 두 시스템의 값이 갈린 채 작업이 진행됐다.

### 지켜야 하는 제약 (사용자 확정, 원문)

> "**한번에 하나씩 구현 할거야** 라이브서비스중이기 떄문에 한번에 모두 구현했을때의 충돌이나 부작용을 감당하기 어려워"

> "작업하나를 할때마다 **표를 업데이트해서 나열해**"

- 항목 하나 = PR 하나 = 병합 하나. **묶어서 진행하지 말 것.**
- 매 항목 완료 후 아래 진행표를 갱신해 사용자에게 보여줄 것.
- 채팅 보고는 **개발을 모르는 사람이 읽고 이해할 수 있게**(파일명·표 이름·브랜치명을 날것으로 던지지 않는다 — `CLAUDE.md` 「채팅 보고는 12살이 읽어도 이해되게」).

## 2. 두 저장소 · 값이 흐르는 길 (필수 배경)

| | 인트라넷 | 리뷰웹 |
|---|---|---|
| 경로 | `/home/user/inadd-webapp` | `/home/user/review-web-system` |
| 기술 | Cloudflare Pages + D1, Hono, TypeScript | Node/Express + PostgreSQL(Railway) |
| 연결 | **HTTP 뿐** — 두 DB 는 서로 못 본다 | |

### 값이 가는 길 (원본 → 리뷰웹)

1. 인트라넷 리뷰오더 저장 → `review_orders.payload_json`(D1) + `review_order_outbox` 적재
2. `deliverReviewOrderOutbox` 가 리뷰웹으로 전송
   - 신규: `POST /api/order/intake`
   - **원본 수정: `PUT /api/order/intake/source/:sourceReviewOrderId`** ← 5·6번이 손댄 자리
3. 리뷰웹 `work_orders` 갱신
4. 사람이 **접수** → `tab_configs`/`campaigns` 등록 + 작업표 생성(`worktablePlan`)
5. 사람이 **모집공고 발행** → `_woCampaignPrefill` 이 오더 값을 **복사**해 `recruit_campaigns` 생성 ← **7번이 손댈 자리**

### 값이 오는 길 (리뷰웹 → 원본)

- 인트라넷 "보낸 오더" 목록은 `GET /api/order/intake/list` 를 **실시간 조회**해 표시한다.
- `reviewOrderSourceListItem(row, remote)` = `{...payload, ...remote, <명시 키>}`
  - `payload` = 인트라넷 원본(항상 최신)
  - `remote` = 리뷰웹 목록 **19칸만** ← **8번이 손댈 자리**

### 반드시 알아야 하는 함정 (실측)

- ★★ **개정 순번은 되돌릴 수 없다** — 인트라넷은 저장할 때마다 `source_revision`+1, 리뷰웹은 `현재+1` 만 받는다. 전송이 실패해 리뷰웹이 1에 머문 채 재저장하면 3이 되어 **재시도로도 영구 거부**된다. (2번이 이 사실을 화면에 말하게 했다.)
- ★★ **`GET /api/review-order/:id`(인트라넷) 는 리뷰웹의 지금 값이 아니다** — `review_order_cache`(D1)는 **오더를 만든 시점의 보관본**이고 **TTL 이 없다**. `PUT /review-order/source/:id` 는 그 캐시를 갱신하지 않는다. 그래서 그 경로로 폼을 열면 **처음 만들 때 값으로 되돌아간다**(3번에서 실제로 밟았다 — 되살리지 말 것).
- ★★ **`GET /api/order/intake/:id`(리뷰웹) 는 `work_orders` 행 전체를 준다** — 8번은 이것으로 충분하다. **신규 엔드포인트를 만들 필요가 없다.**

## 3. 1~6 구현 완료 내용

### 1 — 전달 여부 확인 (조사)
인트라넷 원본 수정이 리뷰웹까지 도달하는지 전 경로를 훑고 표로 보고. 코드 변경 없음.

### 2 — 전송 실패를 화면이 말한다 (인트라넷 #401)
- 저장은 됐는데 전송이 실패(202 · `delivery.ok === false`)해도 **작은 글씨 한 줄**만 남고 창이 닫혔다 → 담당자는 저장된 줄 알았다.
- `reviewOrderDeliveryFailMessage(delivery)` **한 곳**이 사유 + 다음 행동을 만든다. 저장·재전송 두 경로가 같은 함수를 쓴다(사본 금지).
- ★ **409(내용 거부)는 재시도로 유도하지 않는다** — 틀린 조치다. "리뷰웹시스템에서 직접" 으로 안내.
- ★ **"다시 저장"이 위험하다**는 것을 문구가 말한다(위 순번 함정).
- 가드: `tests/review-order-delivery-failure-notice.test.mjs`

### 3 — [원본 수정]이 옛 값으로 열리던 것 (인트라넷 #399 → #404 정정)
- 처음엔 "리뷰웹 상세를 강제로 다시 받아 연다"로 고쳤는데(#399) **그 응답이 만든 시점 보관본**이라 오히려 되돌아갔다.
- 정정: **목록 항목(`_reviewOrders[index]`)이 이미 `{원본 payload + 리뷰웹 현재 상태}` 를 합친 최신값**이므로 그것으로 연다. **상세 재조회를 되살리지 말 것.**
- 가드: `tests/review-order-edit-prefill-latest.test.mjs` — 스파이로 **폼에 실제로 넘어간 객체**를 본다(`_reviewOrders[index]` 만 보면 `populate(order)` 회귀를 놓친다).

### 4 — 카드 값 섞임 (인트라넷 #404)
- `{...payload, ...remote}` 에서 리뷰웹 19칸이 인트라넷이 쓴 칸을 덮는데, 긴 칸은 원본 값이 남아 **한 카드에 옛 값과 새 값이 섞였다**(개정이 한 번 전달된 뒤 다음 개정이 거부·실패했을 때).
- `REVIEW_ORDER_LOCAL_AUTHORED_FIELDS = ['title','recruit_count','start_date','inflow_type','work_kind']` — `status !== 'sent'` 이고 원격 행이 있으면 **서버가 이 5칸을 원본 값으로 통일**하고, 리뷰웹 현재값은 `source_pending` 에 실어 보낸다.
- 화면은 `reviewOrderPendingMark` / `reviewOrderPendingBanner` 로 **"아직 전달 못 한 수정"임을 말한다**(조용한 통일 금지).

### 5 — 접수 후 수정 전면 거부 완화 (리뷰웹 #1197)
- `SOURCE_EDIT_AFTER_ACCEPT` **8칸**만 접수 뒤에도 수정 허용:
  `title` · `manager_name` · `product_url` · `inflow_keyword` · `inflow_guide` · `guide_images` · `review_guide` · `special_notes`
- **왜 이 8칸만** — 접수 뒤에는 **아무 계산에 안 쓰이는** 칸이다. 작업표 줄 수·날짜·열 구성·정원·금액·시트 연결을 하나도 건드리지 않는다.
- ★ `inflow_type` 은 **일부러 제외** — `_lookupInflowType` 이 리뷰어 화면 폴백으로 살아 있어, 바뀌면 이미 발행된 공고의 리뷰어 화면이 흔들린다.
- ★★ **잠긴 칸이 하나라도 섞이면 요청 전체를 거부**(절반 저장 금지). 409 문구는 `SOURCE_FIELD_LABELS` 로 **사람이 읽는 칸 이름**을 말한다(코드명 노출 금지).
- ★ 저장은 **실제로 바뀐 허용 칸만** UPDATE, 값은 `_sourceContentNextValues` 에서 가져온다(계산 사본 금지). 계약 전용 요청의 SQL·응답은 **바이트 그대로**.
- ★ 인트라넷 변경 0 — 막힌 칸 이름이 409 본문 → 기존 전송 실패 알림(#401)으로 그대로 나간다.
- 가드: `server/tests/reviewOrderContentEditAfterAccept.test.js`(26), 변이시험 8종 검출 확인

### 6 — 회수·혼합 부속정보가 조용히 사라지던 것 (리뷰웹 #1198)
- `delivery_type_mix` · `recall_courier` · `recall_product` 가 **전체 저장 UPDATE 에는 있는데 바뀐 칸 판정(`_sourceContentNextValues`)에는 없었다** → 접수된 오더에서 그 칸만 고치면 "바뀐 게 없다"로 읽혀 계약 전용 경로로 흘러가고 **값은 버려진 채 200 ok**.
- 판정에 넣되 **허용 목록에는 넣지 않는다** — `worktablePlan` 에서 작업표 **열 구성과 줄마다 채우는 값**을 정하는 칸이라 이미 깔린 표가 따라오지 않는다(정원·일정과 같은 부류). 이제 409 + `회수 택배사` 로 말한다.
- ★★ **보내지 않은 요청은 비교하지 않는다(fail-open)** — 이 칸을 안 보내던 옛 payload 가 문장 파싱 폴백 때문에 "바뀐 것"으로 읽히면 **계약 후속 매칭이 새로 막힌다**(2026-08-20 실장애 자리).
- ★★ **재발 방지 본체 = 드리프트 가드** — 전체 저장 UPDATE 의 **SET 칸**(계약·광고주·기록 칸 제외) ≡ **판정 목록 키**. 앞으로 칸이 늘 때 한쪽에만 들어가면 그 자리에서 빨개진다.
- 가드: `server/tests/reviewOrderRecallMixEditDetect.test.js`(15), 변이시험 7종 검출 확인
- Codex 리뷰(P1)가 #1197 에 같은 문제를 지적했고 #1198 이 그대로 해결(혼합 개정의 원자적 거부 포함).

## 4. ⬜ 7번 작업지시서 — 고친 값이 모집공고와 작업표까지 반영되게

### 문제

모집공고는 **발행 시점의 스냅샷**이다. `_woCampaignPrefill`(`frontend/js/work-order-detail.js`)이 작업오더 값을 `recruit_campaigns` 로 **복사**하고, 그 뒤 오더를 고쳐도 **공고는 따라가지 않는다.** 그래서 5번으로 8칸을 열어 놨는데도 **리뷰어가 보는 화면은 안 바뀐다.**

### 이미 있는 선례 (그대로 따를 것 — 새 방식을 만들지 말 것)

리뷰웹은 이미 같은 문제를 **네 번** 풀었고 패턴이 굳어 있다:

| 값 | 방식 | 단일 출처 |
|---|---|---|
| 정원(총건수·일건수) | 공고 값이 0(미설정)이면 **작업오더 값이 실제 정원** | `linkedRecruitQuota.displayRecruitTotal` |
| 유입방식 | 공고 저장값 **없을 때만** 오더 값 프리필 + **출처를 문장으로 말함** | `_lookupInflowType` |
| 혼합 리뷰 조합 | 공고 저장값 → 연결 작업오더 → 없으면 입력 요청 | `linkedRecruitQuota.linkedWorkOrderForCampaign` |
| 시작일 | **표시 전용 안내** — 다를 때만 한 줄, 값은 안 덮음 | `orderStartDate` |

**공통 규율**
- ★★ **공고 저장값이 언제나 이긴다** — 사람이 정한 값을 오더가 덮지 않는다.
- ★★ **조용한 자동 적용 금지** — 화면이 "작업오더에서 불러왔습니다 / 확인 후 저장하면 반영됩니다" 라고 **말한 뒤 사람이 저장**한다.
- ★ **경고(빨강)로 칠하지 않는다** — 차수 재발행 등 정상적으로 다른 경우가 있어 상시 경고가 되면 진짜 신호가 묻힌다.
- ★ **짝짓기 규칙 사본 0** — 역방향 링크(`work_orders.linked_campaign_id`) 우선 → 정방향(`recruit_campaigns.source_work_order_id`), 같으면 최근 수정 오더, **소프트삭제 제외**. 반드시 `linkedWorkOrdersForCampaigns(db, ids, columns)` **배치 1회**(N+1 금지).
- ★ **조회 실패는 fail-soft** — 화면은 그대로 열린다.

### 착수 전 반드시 할 것

1. **`CLAUDE.md` 사전 충돌 점검 7축**을 먼저 수행하고 사용자에게 보고한다(생략 불가).
2. **어느 칸을 이을지 사용자에게 확인받는다.** 후보와 성격이 다음처럼 갈린다:

| 오더 칸 | 공고 칸(`_woCampaignPrefill` 기준) | 성격 | 제안 |
|---|---|---|---|
| `review_guide` | `wd_review` + `wd_review_images` | 리뷰어 안내 문구 | **잇기 쉬움** — 화면 표시용 |
| `special_notes` | `wd_notes` | 리뷰어 안내 문구 | 잇기 쉬움 |
| `inflow_guide` / `guide_images` | `wd_inflow_html` / `wd_inflow_text` | 리뷰어 안내 문구 | 잇기 쉬움 |
| `product_url` | `product_url` | 리뷰어 진입 경로 | 잇기 쉬움 |
| `inflow_keyword` | (공고에 별도 칸 없음) | 표시 | 확인 필요 |
| `title` | `title` (상품명 우선) | **공고 제목은 관리자가 다시 쓴다** | ⚠ 덮으면 안 됨 |
| `manager_name` | (담당AE — 공고 필드 아님) | 내부 | 대상 아님 |

3. **작업표까지 반영하는 범위를 확정한다.** 안내 문구는 작업표에 안 들어가므로 대개 **모집공고까지**면 충분하다. 열·줄에 닿는 값(정원·일정·옵션·배송 부속)은 **7번 범위 밖**이다(6번에서 잠근 이유와 같다).

### 권장 구현 (최소 위험)

- **A안(권장)** — 모집공고 수정 모달이 열릴 때 **공고 저장값이 비어 있으면** 연결 작업오더 값을 프리필하고 **출처를 말한다**. 사람이 저장하면 반영. → 혼합 조합 프리필(`reviewMixOriginPrefill`)과 **글자 그대로 같은 패턴**이므로 그 구현을 그대로 베끼면 된다.
- **B안** — 값이 다르면 **안내만**(시작일 방식). 덮지 않는다.
- ★ 자동 덮어쓰기(오더가 바뀌면 공고를 즉시 갱신)는 **하지 말 것** — 관리자가 리뷰어용으로 다시 쓴 문구가 소리 없이 사라진다.

### 손댈 자리

- 서버 재료: `server/src/routes/campaign.routes.js` 관리자 상세 응답에 **가산 필드**로 실어 보낸다(예: `orderReviewGuide`). ★ **`work_detail` 을 고쳐 내려보내지 말 것** — 저장 시 그 값이 굳는다(`reviewMixOriginPrefill` 규율).

## 5. ⬜ 8번 작업지시서 — 반대 방향(리뷰웹 → 보낸오더)

### 문제

리뷰웹 [관리자 수정](`PUT /api/order/admin/edit`)으로 값을 고치면 `work_orders` 는 바뀌지만, 인트라넷 보낸오더 카드는 **긴 칸에서 옛 값을 계속 보여준다.**

이유: 인트라넷 카드 = `{...payload(인트라넷 원본), ...remote(리뷰웹 목록)}` 인데 **`remote` 가 19칸뿐**이다. 그 19칸에 없는 값(`review_guide`·`special_notes`·`inflow_guide`·`product_url`·`purchase_time`·`delivery_type`·`review_type`·`pay_amount`·`daily_count` 등)은 **인트라넷 원본 값이 그대로 이긴다.**

즉 **4번(카드 값 섞임)의 정확한 거울상**이다.

### 이미 있는 것 (새로 만들지 말 것)

- ★★ **`GET /api/order/intake/:id` 가 `work_orders` 행 전체를 준다** — 인증은 같은 `X-Intake-Key`, 인트라넷은 이미 이 URL 로 PUT/DELETE 를 하고 있다(`src/routes/api.ts`). **신규 엔드포인트·신규 저장소 0.**
- 리뷰웹 관리자 수정은 이미 diff 요약을 인트라넷 처리메모 webhook 으로 push 한다(`intranetMemo.service`) — **알림은 이미 있고, 값이 안 올 뿐이다.**

### 두 갈래 (사용자에게 고르게 할 것)

| | (가) 목록 칸 넓히기 | (나) 카드 펼칠 때 상세 조회 |
|---|---|---|
| 방법 | `/intake/list` SELECT 에 긴 칸 추가 | 카드를 펼칠 때 `/intake/:id` 1회 조회 |
| 장점 | 카드가 처음부터 최신값 | 목록 응답 크기 불변 |
| 단점 | **200건 × 긴 텍스트 = 응답 폭증** | 펼치기 전에는 옛 값 |
| 권장 | 짧은 칸만(예: `purchase_time`·`delivery_type`·`review_type`) | **긴 칸(가이드·특이사항)은 이쪽** |

> 권장: **(가)+(나) 혼합** — 짧고 자주 보는 칸은 목록에, 긴 칸은 펼칠 때. 단 **한 번에 하나씩** 규율에 따라 **(나)부터** 하고 (가)는 별도 항목으로 나눌 것.

### 완화 금지 규율

- ★★ **아직 전달 못 한 내 수정을 리뷰웹 값으로 덮지 말 것** — `source_outbox_status !== 'sent'` 이면 **원본 값이 이긴다**(4번이 세운 규칙 그대로 · `REVIEW_ORDER_LOCAL_AUTHORED_FIELDS` 와 같은 판정). 덮으면 담당자가 방금 친 글이 사라진다.
- ★★ **`review_order_cache` 를 최신값으로 착각하지 말 것** — 만든 시점 보관본이다(3번 함정).
- ★ **[원본 수정] 폼은 여전히 목록의 최신값으로 연다** — 상세 재조회를 되살리지 말 것(`review-order-edit-prefill-latest` 가드가 부재를 고정).
- ★ **리뷰웹 값을 인트라넷 `payload_json` 에 써넣지 말 것**(1단계에서는). 원본은 인트라넷이 소유한다 — 표시만 최신으로 맞춘다. 원본 자체를 갱신하려면 순번 규약을 건드려야 해 **별도 항목**이다.
- ★ 조회 실패는 **fail-soft** — 카드는 종전대로 뜬다.

### 손댈 자리
