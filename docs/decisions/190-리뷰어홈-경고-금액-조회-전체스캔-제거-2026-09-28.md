# ★★ 리뷰어 홈 「리뷰 미작성 경고」·「받을 예정 금액」 조회 — 표 전체 읽기 제거 (migration 168, 2026-09-28)

- **증상(운영 실측)**: `/api/reviewer/overdue-review-warning` 약 **50%**(하루 약 1,400건), `/api/reviewer/review-earnings` 약 **9%** 가 503. 리뷰어 화면에서는 경고 팝업·받을 예정 금액이 **조용히 안 뜬다**. 원인 코드 57014 = `boundedReviewRead` 의 1.5초 조회 제한(statement_timeout) 초과.
- **원인**: 후보를 모으는 조회가 "계정ID **또는** 전화번호(OR)" 한 조건이라 인덱스를 못 타고 **주문·참여·신청 표 전체**를 읽었다. 특히 주문표는 전화번호 정리식(regexp)을 모든 행에 계산했고, 경고 조회는 후보를 찾은 뒤에도 **주문표 전체(행이 큼)를 읽어 합쳤다**. 전화번호 인덱스(051)는 조건(`deleted_at IS NULL AND mirror_status IN …`)이 글자 그대로 같아야 쓰이는 부분 인덱스라 이 조회에서는 쓰이지 않았다.
- **수정(결과는 한 행도 안 바뀐다)**:
  - OR 을 **갈래별 UNION** 으로 나눴다(OR 의 합집합과 같은 집합) — 경고 `warning_candidate_ids`, 금액 `reviewEarningsCandidates.service`(단일 출처).
  - 주문은 **후보 ID 로만** 읽는다(`WHERE id IN (후보)`).
  - ★★ **조건을 좁히지 않았다** — 후보 단계에 삭제 여부 등을 새로 넣으면(인덱스를 태우려고) 금액 조회가 "삭제된 주문의 작업표 줄"로 찾던 좌표가 빠진다. 그래서 인덱스 쪽을 조건 없이 만들었다.
  - migration 168: 갈래별 인덱스 7개(주문 전화번호식·주문 계정ID·참여 계정ID·참여 전화번호·참여 명의·신청 소유자번호·참여링크 계정ID). 비-CONCURRENTLY(기존 관례) — 표가 수만~십만 행이라 생성 중 해당 표 쓰기가 1초 안팎 대기할 수 있다.
- **검증**: 운영 규모 합성 데이터(리뷰어 2만·주문 8만·명단 12만·보관 20만, 타계정 명의·삭제·역방향 신청 연결 섞음)에서 **구 코드 vs 새 코드 응답 1,200건 전부 동일**(경고 있음 197명·금액 600명 포함). 경고 조회 84ms → 5ms, 금액 후보 조회 80~190ms → 9ms, 전체 응답 시간 약 3.4배 단축. 실행 계획에서 큰 표 전체 읽기 0.
- 회귀가드 `tests/reviewerHomeLookupIndexes.test.js`(후보 조회에 OR 재등장 금지 · 후보 ID 로만 주문 읽기 · 조건 좁히기 금지 · 인덱스 7종·식 일치) + 기존 `reviewEarningsCandidatesPg`(원래 계산과 동일성)·`reviewerOverdueReviewWarningPg` 통과.
