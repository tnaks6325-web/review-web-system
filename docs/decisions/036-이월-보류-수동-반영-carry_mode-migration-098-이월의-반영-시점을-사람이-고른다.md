# ★★ 이월 보류·수동 반영 (carry_mode, migration 098) — 이월의 반영 시점을 사람이 고른다
- **배경(사용자 요청)**: 자연 미달분(이월)이 무조건 다음날 자동으로 얹혀(066), 업체가 "미달분은 나중에 몰아서"를 원하면 매일 아침 손으로 줄여야 했다. 시안 = `frontend/docs/이월보류_수동반영_와이어프레임.html`(사용자 확정 3건: 기본=자동·옵트인 보류 / 반영 창구=카드 원클릭+[📅 인원] 팝업 / 홈 인라인 수정은 허용명단 리뷰어도 설정 가능).
- **모델**: `recruit_campaigns.carry_mode` TEXT 기본 `'auto'`(백필 0 = 기존 공고 현행 불변, DB CHECK 없음 — 087 규율). `'hold'` = **자동 이월 가산만 멈춤**(`dailyQuota`의 carry 분기 앞 `isCarryHold` 게이트) — 계획표(095)·조절일 규칙·총량 clamp 불변이라 **물량 소실 0**(반영 안 하면 종료일만 뒤로). 킬스위치 `CAMPAIGN_CARRY_HOLD=0` = 전건 자동 복귀.
- ★★ **판정 단일 출처 = `isCarryHold` / 잔량 = `heldCarry`**(campaignState.service — 게이트·잔량·목록 칩이 같은 판정): 잔량 = 어제까지 계획누적(095 계획 반영) − 확정(`counts.hold` 창) − 반영누적(`campaign_plan_events` `carry_apply` 합 — `fetchCarryAppliedSums` fail-soft). **null = 계산 불가**(기준선 없음·보류 아님) — 화면은 칩 미표시·"조회 실패"로 말하고 **0으로 꾸미지 않는다**.
- ★ **기준선 2종(066 carry + 098 hold, `campaign_carry_hold_start` 시드 = 소급 차단)은 한 쿼리**(`_baselines`) — 따로 읽으면 fetchCampaignCounts 쿼리 순서가 밀려 **"카운트 쿼리는 두 번째"라는 066 가드 계약이 깨진다**(실측 — 스텁 행에 `key` 컬럼 필요).
- **반영 = 날짜별 계획(095)에 얹기(신규 정원 경로 0)**: `savePlans`의 `carryApply`(hold 공고만 — auto면 `carry_not_hold`)가 `carry_apply` 이력을 남겨 잔량에서 차감. 창구 둘 = ① 카드 **⏸ 보류 N 칩**(`pg-hold` 보라 — 클릭 = `CampaignDailyPlan.quickApplyHeld` 확인창 3택[오늘 반영/세부 선택/그대로 두기] 후 즉시 저장) ② [📅 인원] 팝업 상단 **보류 블록**(오늘/내일/분산 스테이징 → [확정 저장]).
- ★ **설정 세그먼트 = 공고 수정 모달(`rf_carry_mode`) + 홈 인라인 모달(`cae_carry_mode`)**: UI 있는 화면에서만 전송(미전송 = COALESCE 유지 — $40 센티널, auto/hold 외 값 무시). **보류를 직접 고른 순간에만** 고지문 펼침(silent 프리필) — "오늘 정원 복귀 + 물량 불소실"을 문장으로(원칙 ⑤). ★ **스코프 편집(`_scopedCampaignEdit`)도 carry_mode 만 추가**(확정 ③ — 일건수를 이미 수정 가능한 신원) — **반영(carryApply)은 adminOrMaster 전용 API라 스코프 토큰이 보류분을 열 수는 없다**(인라인 모달이 "반영은 관리자"를 문장으로 안내).
- ★★ **코드리뷰 반영 5종(완화 금지)**: ① **B1** — 공개 `GET /list` SELECT에 `carry_mode` 명시 동봉(빠지면 목록·apply가 서로 다른 정원을 봐 "카드는 열렸는데 참여 거부" — counts 깔때기 규율의 SELECT판) ② **M1** — 생성(create) INSERT에도 carry_mode(발행 시 선택이 조용히 auto로 낙하 방지) ③ **M2** — `savePlans`의 carryApply는 **캠페인 행 잠금 안에서 잔량을 재계산**(SAVEPOINT `cap_check`): 초과 = `carry_stale`(409, e.held 동봉 — 동시 원클릭 이중 반영 차단), 재계산 실패 = `carry_unknown`(503, **fail-closed** — 모르는 채 원장에 기록하지 않는다) ④ **M3** — `fetchCarryAppliedSums` 실패 = **null**(빈 Map로 접으면 반영분이 0으로 세어져 잔량이 부풀고 이중 반영을 유도) → admin/list도 합계 null이면 carryHeld null ⑤ **M4** — `REQUIRED_SCHEMA`에 `recruit_campaigns.carry_mode` 등록(082 규율 — 없으면 발행·수정·목록 42703).
- ★ **carryApply 단독(계획 미동반)은 `empty` 거부가 맞다** — 정원을 안 늘리고 반영 이력만 남기면 그 인원이 어디에도 안 열려 **물량이 소실**된다(원클릭은 항상 오늘 계획 set을 동반).
- ★ 원클릭 확인창은 **시트 일정 공고면 "이월 보류가 적용되지 않습니다 — [📅 인원]에서 날짜별로 조절하세요"**(2026-08-07 — 종전 "시트에서 조절" 문구 대체)와 **게시 꺼짐 고지**("반영 후 게시 토글을 켜야 재개" — 차수 추가 M1과 같은 규율)를 문장으로 말한다. 판정 실패(`unknown`)는 서버가 잔량을 null 로 내려 잔량 검사에서 걸린다.
- ⚠ **병합 유실 실측**: main 병합 과정에서 `repairRecruitTotalFromRounds`가 module.exports에서 빠져 **경합 자가치유가 TypeError→fail-soft로 조용히 무력화**돼 있었다(이번에 복구 + 가드가 export 존재를 고정). **여러 세션이 같은 파일을 병합할 때 exports 목록은 유실 단골**이다.
- ★ **시트 일정 공고에는 보류가 적용되지 않는다**(2026-08-07 — 위 095 항목 참조): `heldCarry`가 일정 인자를 받아 null 을 돌려주고 화면이 사유를 말한다. 그 공고의 이월 조절 창구는 [📅 인원]의 날짜별 조절.
- 잔여(문서화): 카드 ⏸ 칩은 admin/list 응답 재료라 **스코프 토큰(리뷰어앱) 화면에는 잔량이 없다**(설정 세그먼트만 — 반영은 어차피 adminOrMaster 전용이라 막다른 길 아님, 모달이 "반영은 관리자"를 안내). 킬스위치 복귀(`CAMPAIGN_CARRY_HOLD=0`)는 보류 중이던 이월이 **한꺼번에 자동 이월로 되살아나므로**(066 상한 2×dl가 버스트를 억제) 낮은 트래픽 시간대에 끄는 것을 권장. 잔량 기준선은 전역 1개(`campaign_carry_hold_start`) — 배포 이전 미달분은 세지 않는다(066 소급 금지와 동일).
