# ★★ 네이버예약리뷰 — 매장을 네이버 예약으로 방문하고 리뷰를 남기는 네 번째 체험단 종류 (`work_kind='booking'` · 사용자 확정 2026-11-23) — 1단계: 판정 단일 출처 + 안전핀 + 저장 입구 거절

## 무엇을 하는 작업인가
- 리뷰어가 업체 매장을 **네이버 예약**으로 예약해 방문하고, 방문 리뷰를 남긴다. 택배·상품 옵션·구매수량 단계·주소·주문번호가 없다.
- 같은 종류의 두 번째 갈래 **영수증리뷰는 나중에** 따로 만든다(이번에 넣지 않는다).

- ★★ 순서가 중요하다 — 리뷰웹이 `booking` 을 모르는 동안 인트라넷이 보내면 `normalizeWorkKind` 가 **조용히 review 로 접는다**(구매양식 + 상품 리뷰 AI 검수가 붙은 상품 리뷰 작업이 된다). 결정 321 Q&A 와 같은 함정.
1. **판정 단일 출처에 booking 추가 + 안전핀 + 저장 입구 거절** ← 이 항목
2. 날짜별 자리표(업체가 정한 날짜·인원) + 작업보드 칸
3. 모집 페이지·리뷰어 화면(날짜 고르기 · 예약내역 캡처 · 리뷰 캡처 · 방문일 + N일 기한)
4. 검수(예약내역·방문 리뷰 화면 기준)
5. 입금(환급형 = 결제금액 + 리뷰비 · 무료체험형 = 리뷰비만)
6. 인트라넷 리뷰오더 「네이버예약리뷰」 탭(코드값 `booking` 만 보낸다)

## 1단계 규율 (지금 지켜야 하는 것)
- **판정 = `utils/workKind.js` 한 곳.**
  - `WORK_KINDS` 맨 뒤에 `{ key: 'booking', label: '네이버예약리뷰' }` · `isBookingKind`.
  - `BOOKING_PATTERN` 은 **확실한 표기만** 잡는다: `네이버예약리뷰`(띄어쓰기 허용) · `예약자 리뷰` · `예약리뷰`(붙여 쓴 것) · 영문 낱말 `booking`.
  - ★ 맨 「예약」·띄어 쓴 `예약 리뷰` 는 잡지 않는다 — 예약구매·사전예약 상품 리뷰 글(`사전예약 리뷰체험단`)에 섞인다. `rebooking`·`bookings` 도 아님(낱말 경계).
  - ★ **블로그 → Q&A → 예약리뷰 순서**로 본다 — 예약리뷰는 「모르면 리뷰」로 떨어지던 표기에서만 가져오고 블로그·Q&A 답을 뺏지 않는다. 회귀가드가 결정 404 이전 판정 사본과 넓은 표본으로 대조한다.
  - 운영 저장값(2026-11-23 읽기 조회, `work_orders`·`tab_configs`·`recruit_campaigns`)은 `''`·`review`·`blog`·`qna` 뿐이라, 기존 작업이 booking 으로 바뀌는 일은 없다.
- **프론트 사본**: `work-order-detail.js` `WO_KIND_LABELS`·`_woIsBookingKind`·`_woHasNoReviewType`(블로그 ∪ Q&A ∪ 예약리뷰)·`_woWorkKindLabel`.
  - 서버와 판정이 일치하는지는 회귀가드가 실제 실행으로 대조하고, 표기 규칙은 글자 그대로 같은지 본다.
  - 프리필 사본은 `server/scripts/gen-wo-campaign-prefill.js` 로 다시 만들었다.
- ★★ **저장 입구 거절 (fail-closed · 완화 금지)** — 2~5단계가 없는 동안 booking 을 받아 두면, 날짜 자리표·리뷰어 화면·검수·입금 없이 **상품 리뷰 작업보드**(구매일자 줄·구매양식·상품 리뷰 검수)가 깔린다. 그래서 판정은 하되 저장하지 않는다.
  - 목록 = `workKind.NOT_READY_WORK_KINDS`(지금 `['booking']`) · 판정 `isWorkKindReady` · 응답 본문 `workKindNotReadyBody` — 409 `{ code:'work_kind_not_ready', blocked_fields:['work_kind'], error }`.
  - 거절하는 곳(전부 **읽기·쓰기 전에**):
    1. 인트라넷 새 오더 `POST /api/order/intake`(출처 계약 유무 무관) — 작업명 확인 바로 뒤.
    2. 인트라넷 원본 수정 `PUT /intake/source/:id` — 작업명 확인 바로 뒤. ★ 결정 332 종류 바꾸기(작업표·임시저장 공고 삭제)보다 **앞**이라 아무것도 지우지 않는다.
    3. 옛 수정 `PUT·PATCH /intake/:id` · `POST /intake/:id/update` — `work_kind` 를 보냈을 때만.
    4. 관리자 공고 만들기 `POST /api/campaign/admin/create` — 제목 확인 바로 뒤.
    5. 관리자 공고 고치기 `PUT /api/campaign/admin/:id` — `work_kind` 를 보냈을 때만, 맨 앞.
  - 안전벨트: 공고 신청(참여) — 공고 > 탭 종류가 booking 이면 잠금·자리 잡기 **전에** 409 `reason:'work_kind_not_ready'`(화면은 서버 문구를 그대로 보여 준다). 1단계엔 그런 공고가 생길 수 없지만, 생기면 상품 리뷰 홀드로 흘러가지 않게.
  - 거절하지 않는 곳(이미 막혀 있음): 관리자 작업오더 수정 창(`ADMIN_EDIT_FIELDS` 에 `work_kind` 없음) · 리뷰어앱 공고수정(화이트리스트에 없음) · 공유 저장(`work_kind` = 영구 잠금 칸 `permBlocked`) · 작업 종류(`tab_configs.work_kind`)는 접수 때 **저장된 오더 값**에서만 채워진다.
  - **왜 받아 두지 않고 거절하나**: 인트라넷은 거절 응답을 그 리뷰오더의 「실패」와 사유(`error`)로 보여 주고 거절 코드를 화면에 넘긴다(`deliverReviewOrderOutbox` → `markReviewOrderOutboxFailed`). **자동 재전송은 없고**(재전송 = 사람이 누르는 [재전송]·수정 저장), 실패한 오더를 다시 저장하면 **같은 번호**로 보낸다(`retryingFailed`) — 그래서 리뷰웹 번호(`source_revision` +1 규칙)가 어긋나지 않고 막다른 길도 아니다(종류를 바꿔 다시 보내면 된다). 인트라넷 코드는 2026-11-23 읽기 전용으로 확인했다(수정하지 않음). 반대로 받아서 조용히 리뷰로 깔면, 잘못 만든 작업보드를 사람이 찾아 지워야 한다.
  - ★ 이 거절은 그 종류의 2~5단계가 **모두** 생긴 뒤 `NOT_READY_WORK_KINDS` 에서 빼며 함께 푼다. 단계 하나만 생겼다고 빼지 않는다.

## 완화 금지
- **`NOT_READY_WORK_KINDS` 에서 booking 을 2~5단계가 다 생기기 전에 빼지 말 것** — 날짜 자리표·리뷰어 화면·검수·입금 없이 상품 리뷰 작업보드가 깔린다.
