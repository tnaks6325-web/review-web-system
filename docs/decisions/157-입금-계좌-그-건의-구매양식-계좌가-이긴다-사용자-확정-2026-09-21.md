- ★★★ **확정 = 그 건의 구매양식(작업보드) 계좌가 이긴다**(사용자 확정 2026-09-21). 해석 순서가 **① 그 건의 구매양식 → ② 등록DB(소유자 링크 → 연락처)** 로 뒤집혔다. ⚠ 112 의 "등록 계좌가 언제나 이긴다"는 **이 항목으로 대체됐다** — 되살리면 이 사고가 그대로 재현된다.
- ★★ **완화 금지 5종**:
  - **반쪽 값은 인정하지 않는다** — `_orderAccount` 가 은행·계좌·예금주 **셋이 다 있을 때만** 객체를 돌려준다(반쪽으로 만든 이체 파일은 은행이 통째로 거부한다). 반쪽이면 종전대로 등록DB.
  - **`reviewerId` 를 만들지 않는다**(112 규율 유지) — 양식 계좌는 지목할 등록 리뷰어가 없어 회차 스냅샷 대조에서 `unverifiable` 로 빠져야 **다운로드가 막히지 않는다**.
  - **신원 추적 필드는 등록DB 기준을 유지한다**(`ownerReviewerId`·`participantIdentityId`) — "누가 참여했나"는 "어디로 보내나"와 별개다. 여기까지 비우면 회차 항목의 소유자 추적이 끊긴다.
  - ★★ **두 계좌가 같으면 아무 말도 하지 않는다** — 양식 계좌가 기본 경로가 되면서 `accountSource==='order'` 가 대부분의 행에 붙는다. 그때마다 배지를 띄우면 **진짜 신호(불일치)가 묻힌다**(늑대소년). 서버가 `accountMismatch` 를 **다를 때만** 싣고, 화면은 그 값을 **그리기만** 한다(판정 사본 금지).
  - **비교는 숫자만**(`normalizeAccount`) — `725602-00-129824` ↔ `72560200129824` 를 다름으로 오판 금지.
- ★★ **보류시키지 않는다(사용자 확정) — 체크박스로 사람이 정한다**: 불일치는 `issues` 가 아니라 **`warnings`(`account_form_override`)** 라 `payable` 은 true 이고 **체크박스는 기본 체크**다(병목 방지). 행 바로 아래 안내줄이 **두 계좌를 나란히** 보여주고 마지막 줄이 `체크박스를 풀면 해당 건 입금은 보류됩니다` 를 말한다. 체크를 풀면 그 건만 회차에서 빠진다.
  - 안내는 **세 경우를 구분**한다: 예금주까지 다름(빨강 태그) / 계좌번호만 다름 / **등록 계좌가 아예 없음**(`registered: null` — 없는 계좌를 지어내지 않는다).
- ★ **되돌리기 = env `PAYMENT_FORM_ACCOUNT_FIRST=0`**(코드 변경 0). 판정은 `_formAccountFirst()` 가 **호출 시점에** 읽으므로 재배포 없이 즉시 종전 동작으로 돌아간다.
