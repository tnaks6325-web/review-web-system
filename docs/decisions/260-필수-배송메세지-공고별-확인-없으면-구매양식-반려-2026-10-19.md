# ★★ 공고별 「필수 배송메세지」 — 캡처 배송메세지에 없으면 구매양식을 받지 않는다, 두 번째부터 직원 확인 요청(🚩) (사용자 확정 2026-10-19 · migration 192)

## 사용자 결정
- "배송메세지 00 넣어서 구매 지시가 있던 작업은 시스템이 반드시 확인해줘야 해. 없으면 구매양식 제출을 반려할 수 있어야 해."
- 고른 안(모두 권장안):
  - ① 막는 방식 **가** — 제출 순간 막고 다시 캡처 안내. 같은 주문번호로 **두 번째부터** 막히면 리뷰어가 「직원 확인 요청」으로 제출할 수 있고, 그 주문은 작업보드 🚩 로 남아 직원이 캡처를 보고 반려(주문 취소)한다.
  - ② 지정 방법 **가** — 공고 설정에 「필수 배송메세지」 칸(직원이 00 입력). 공고 문구 자동 인식은 하지 않는다.
  - ③ 통과 기준 **가** — 그 글자가 **들어 있으면** 통과("00 부재시 문앞"도 통과).
- 배경 실측(2026-10-14~19 운영 읽기): "00" 지시 작업 3개 28건 중 00 이 읽힌 것 4건 · 빈칸 22건. 세 작업 모두 네이버라 캡처에 배송메모가 안 찍힌 경우가 많다(쿠팡은 96% 읽힘, 네이버 11%).

## 동작
1. **저장** — `recruit_campaigns.required_delivery_memo`(''=확인 안 함). 공고 생성·수정 라우트가 저장 직후 `_saveRequiredDeliveryMemo` 로 **이 칸만 따로** 쓴다(거대한 INSERT/UPDATE 자리표에 끼우지 않음 — 동시에 열린 다른 PR 의 자리표 변경과 번호가 어긋나지 않게). `undefined` = 유지(이 칸이 없는 화면·리뷰어앱 편집). 실패는 `requiredMemoWarning` 으로 응답 → 저장 안내 첫 줄.
2. **판정** — `/api/submit/order` 에서 `orderData` 를 만든 **직후 · 모든 쓰기 전**. 대상은 `orderData.deliveryMemo` **하나**(결정 245 서명에서만 꺼낸 값 = 원장에 남는 값). 공고 = 검증된 홀드 → `campaign:<id>` 범위 → 작업표 연결 공고(필수 글자 있는 가장 최근 것). `requiredDeliveryMemo.decide`:
   - 들어 있음 → 접수 + `order_submissions.delivery_memo_check='ok'`
   - 없음 → `DELIVERY_MEMO_REQUIRED`(접수·쓰기 0, 읽힌 메세지를 문구에 보여 준다)
   - 없음 + `deliveryMemoStaffReview` → 접수 + `'staff_review'` + 이상로그(warn)
   - 비교: 공백 무시·대소문자 무시·NFKC, **숫자만인 필수 글자는 영문 O 도 0** 으로 본다(AI 가 00 을 OO 로 읽는 경우).
3. **리뷰어 화면** — `search-app.js`(새 양식)·`index-app.js`(옛 양식) 같은 규칙. 같은 작업·같은 주문번호로 막힌 횟수를 sessionStorage(못 쓰면 메모리)로 센다. 1번째 = 안내만, 2번째부터 = "직원 확인 요청으로 제출할까요?" 확인 → 승인 시 플래그를 붙여 재전송. 거절하면 그 주문은 실패로 결과 목록에 남는다(조용히 빠지지 않음).
   - 처리 위치는 신원 확인 재전송(NEED_CONFIRM·NEED_SUB_REGISTER) **뒤** — 서버 순서가 상품 → 신원 → 배송메세지라, 신원 확인 후 재전송이 이 코드로 돌아와도 잡힌다.
4. **작업보드** — 명단 쿼리가 `purpose_order.delivery_memo_check` 를 읽어 **내부(showEdits)일 때만** `syn.deliveryMemoCheck='staff_review'`. 보기 표 배지 「🚩 배송메세지 확인 필요」 · 편집 표 이름 앞 🚩 · 제출물 미리보기 빨간 한 줄. 반려 = 기존 줄 메뉴 [주문 취소].

## fail 방향
- 공고 조회 실패 = 모름(null) → **막지 않는다**(fail-open + warn). 필수 글자 없는 공고 = 종전 그대로.
- 서명 없음·다른 주문의 서명·만료 → 배송메세지 '' → **막힌다**(필수 공고에서는 "모름"을 통과로 접지 않는다). 두 번째부터 직원 확인 요청이 탈출구.
- 직원 확인 요청 플래그는 화면 값이지만 결과는 🚩(직원 확인 대상)라 위조해도 얻는 것이 없다.

## 배포 스큐
- 새 서버 + 옛 리뷰어 화면: 막힘 문구가 일반 실패 알림으로 뜨고 제출이 멈춘다(직원 확인 요청 불가) → 새로고침하면 새 화면. 필수 글자를 적은 공고에서만 해당.
- 새 공고 창 + 옛 서버: 서버가 칸을 모름 → 응답에 `required_delivery_memo` 가 없으면 "저장되지 않았습니다" 안내.
- 마이그레이션은 칸 추가 2개뿐(기본 '' = 무변화).

## 완화 금지
- **판정 대상은 `orderData.deliveryMemo`(서명에서 꺼낸 값) 하나** — 요청 본문의 평문 배송메세지를 받으면 리뷰어가 "00" 을 적어 보내 통과한다. 결정 245 의 "제출 값은 서명에서만" 과 같은 규율. 회귀가드 `requiredDeliveryMemo.test.js`.
- **게이트는 모든 쓰기 전** — 막힌 제출이 원장·작업표에 남으면 "막았다"가 거짓이 된다(실 PG: 막힌 3건 후 원장 0건 확인).
- **🚩 는 내부에만** — 업체 화면에 "반려 대상" 을 보이지 않는다.
