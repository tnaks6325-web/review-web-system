# ★★ 인당 구매수량 단계 ①단계 — 오더 상품 구성이 수량 단계(qty_tiers)를 받는다 · 빈 단계 키는 지운다 (사용자 확정 2026-10-14 · 스키마 변경 0)

## 배경
한 작업 안에서 리뷰어마다 사는 개수를 다르게 받는다(예: 3개×10명 / 2개×40명 / 1개×50명 → 100명 · 160개).
설계는 사용자 확정(시안 시뮬레이터 2차, https://claude.ai/artifact/Rnuq6Qv7ANhTNGXNrJUPUE):
- 수량 구성은 **인트라넷 리뷰오더**에서 입력한다. 리뷰어는 신청 때 옵션 → 개수 단계를 고른다.
- 정원은 옵션 따로 · 단계 따로 지킨다. 마감은 계속 **사람 수**로 센다.
- 옵션 가격이 같으면 `common`(한 표), 다르면 `by_option`(옵션별 표). 리뷰비는 1인 고정.
- 단계별 1인 결제금액 = 인트라넷이 「단가 × 개수 + 배송비」로 자동 채우고 운영자가 고칠 수 있다(묶음가). **리뷰웹은 다시 계산하지 않는다.**
- `buy_method` = `qty`(수량 늘려 결제) | `option`(옵션에서 N개 선택) — 리뷰어 안내 문장에 쓴다.

순서: ① 리뷰웹이 받을 준비(이 항목) → ② 인트라넷 입력·전송 → ③ 리뷰어 신청·구매양식 → ④ 관리자·광고주 표시.
**①을 ②보다 먼저 배포한다** — 옛 리뷰웹은 검증 없이 단계를 저장한다.

## 모양 (상품 구성 `work_orders.product_options_json` 의 상품마다)
```
qty_tiers: { mode: 'common'|'by_option', buy_method: 'qty'|'option',
             rows: [{ option: <옵션 label>|null, qty: 1..99, people: 0.., amount: 0.. }] }
```
검증·표준형 단일 출처 = `server/src/services/productOptions.service.js` `normalizeQtyTiers`(정규화 `normalizeProductOptionsJson` 안에서 호출).
- 인원 합 = 모집인원(common: 상품 전체 — 옵션 있으면 옵션 count 합, 없으면 base.count / by_option: 옵션마다 그 옵션 count). 다르면 400.
- common 은 옵션 결제금액(`pay`)이 모두 같을 때만. by_option 은 옵션 있는 상품만, `option` 은 그 상품 옵션 label 과 정확히 같아야 한다.
- 같은 범위에서 같은 개수 단계 두 번 금지. 수량 1..99 정수, 금액 0 이상 정수.
- 구버전(라벨만) 배열에 단계가 실리면 400(단계형 v2 원본에서만 받는다).

## ★★★ 완화 금지
1. **빈 단계 키(null·''·빈 rows)는 지운다(표준형).** 인트라넷이 단계 없는 오더에 빈 값을 실어 보내도 저장 바이트와 접수 뒤 잠금 비교 모양(`_productOptionsLockedShape`)이 예전과 같아야 한다. 안 지우면 이미 접수된 모든 오더가 **무엇을 고치든 409**로 영영 잠긴다(결정 167 과 같은 구조).
2. **단계 금액 칸 이름은 `amount` — `pay` 로 바꾸지 않는다.** `pay` 는 접수 뒤에도 열린 키(`PRODUCT_OPTION_EDITABLE_KEYS`)이고 잠금 비교가 재귀로 걷어내므로, 단계 금액이 「잠금 밖 + 공고 전파 없음」 이 되어 값만 조용히 바뀐다. 단계 전체는 접수 뒤 잠긴다(정원에 영향).
3. **정규화를 안 거치던 옛 경로 3곳도 단계가 실리면 검증한다** — 출처 계약 없는 `POST /intake`, 옛 `POST /intake/:id/update`, 관리자 수정. 단계가 없으면 이 경로들은 지금처럼 원문 그대로(동작 불변).

## 이번에 하지 않은 것 (③·④에서)
- 공고·참여 기록·주문에 단계를 담는 표/칸(조사안: `campaign_qty_tiers` 표, `campaign_applications.purchase_qty`, `order_submissions.purchase_qty`) — 쓰는 코드와 함께 넣는다(필수 스키마 등록·이름 바꾸기 트랜잭션 합류 포함).
- 잘못 구매 판정(결정 230·236)의 기대 금액을 그 사람 단계 금액으로 바꾸기, 입금관리 이상금액 경고, 작업 조건 카드 총액(단가 × 사람 수 → 단계 금액 × 인원).
- 공고 밖 주문·수동 입력에는 단계 정보가 없다 → 단계 정원 셈 방법은 ③에서 정한다.
