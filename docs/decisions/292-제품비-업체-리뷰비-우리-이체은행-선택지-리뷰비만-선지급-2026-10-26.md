# ★★ 제품비 업체 · 리뷰비 우리 — 이체은행 선택지 「제품비 업체 · 리뷰비 케이뱅크/하나은행」(split) · 입금관리는 리뷰비만 · 리뷰 전 지급 (사용자 확정 2026-10-26 · 스키마 변경 0)

## 발단
- 사용자: "새 작업 건 구매대금 페이백은 업체입금 / 리뷰비는 인애드입금 — 입금관리에 제품비 제외한 리뷰비 1천원만 설정되게 하는 방법 필요".
- 종전 선택지는 둘뿐이었다: 우리 입금(금액 = 제품비 + 리뷰비, `payment.service` `amount = productPrice + fee`) / 업체입금(결정 247 — 업체가 **전부** 보내고 우리 입금관리에서 통째로 빠짐). 제품비만 빼는 길이 없어 직원이 이체 파일 금액을 손으로 고쳐 왔다고 한다.
  - ⚠ 운영 실측(2026-10-26, 대상 작업 「10/15(쿠팡)쟈니베어_군인핫팩 500건」): 은행 결과 파일 기준 110건 모두 **5,980원(제품비) 이체완료**로 반영돼 있고 1,000원 이체 기록은 없었다 — 사용자에게 통장 확인을 요청했다(기록과 실제 돈이 다를 수 있음).
- 사용자 확정: ① 그 작업에 적용 ② 업체가 제품비 입금일을 **적는다** ③ 리뷰비 1천원은 **바로 보내도 된다**("투입이 모두 끝난 시점에 한 번에 전원 입금이 제일 깔끔") ④ 이미 우리가 제품비까지 보낸 줄은 **그대로 끝**(리뷰비 추가 지급 없음 — 선택지 ②).

## 결정
1. **저장소 = 이체은행 하나**(결정 247 완화 금지 "두 번째 스위치 금지" 준수) — 리뷰비를 보낼 우리 은행을 값에 함께 담는다.
   - 공고 `recruit_campaigns.transfer_bank` = `split_kbank` | `split_hana` / 탭 `tab_configs.transfer_bank` = `제품비업체·리뷰비케이뱅크` | `제품비업체·리뷰비하나은행`(탭은 한글 라벨 관례).
   - 판정 단일 출처 = `payment.payoutModeFrom(공고, 탭)` → `ours | advertiser | split`(+ split 의 은행). 순서는 이체은행과 같다(공고가 은행을 명시하면 탭 값 무시). `advertiserPaysFrom` 은 **업체입금만** true 로 유지(우리 목록에서 통째로 빼는 판정), `advertiserGoodsFrom` = 업체입금 ∪ split(업체 계좌 공개·업체 입금일 기록·끄기 확인).
   - `normalizeBankChoice` 는 그대로 kbank|hana 만 — split 값이 이체 서식 은행으로 새지 않는다(`splitBankOf` 로만 푼다).
2. **입금 대상(`listPaymentTargets`)** — split 작업의 줄은
   - 금액 = **리뷰비만**. 회차에는 `product_price = 0` 으로 박제(인트라넷 페이백 장부 피드 결정 290 이 "돌려준 상품값"으로 읽지 않게 · `isFeeOnlyItem` 판별 근거).
   - **리뷰 제출·의무 대기 조건을 풀어** 구매가 끝난 줄부터 대상(결제금액이 없으면 `not_purchased` 보류 · 리뷰비 0 이면 `split_no_fee`).
   - 입금 칸 조건은 **통째로 풀지 않는다** — 채워진 입금 칸이 **모두 업체가 넣은 값**(활성 편집기록 `업체#…` 이고 지금 칸 값과 같음 = 업체 제품비 기록)일 때만 "우리 리뷰비 아직"으로 본다. 직원 [💰 입금수정] 날짜·8/11 수동 입금(우리가 보낸 돈)은 그대로 "이미 입금".
   - 회차 잠금(pending/paid)·우리 원장(`payment_records`) 잠금·미작성 종결 제외는 그대로. 원장 잠금의 "미입금 정정" 예외는 ⓐ 업체가 비운 기록(`업체#…`)은 정정으로 보지 않고 ⓑ split 후보 작업에서는 쓰지 않는다.
   - 구현: 후보 작업 키를 넓게 미리 읽어(`_splitCandidateKeys` — 공고 여럿·탭 값) SQL 에서 그 범위만 풀고, 행을 읽은 뒤 `payoutModeFrom` 이 split 이 아니면 `strictOk` 로 원래 조건을 다시 건다. 후보 조회 실패 = 풀지 않음(리뷰비가 늦을 뿐 잘못 나가지 않는 쪽).
   - 작업별 진행 `splitWorks`(지금 보낼 수 있음 N · 구매 전 M · 업체 미연결 경고) — 화면 한 줄 안내("투입 다 끝나면 한 번에").
3. **회차 만들기(`createBatch`)** — 화면이 본 입금 방식(`payoutMode`)과 다시 계산한 값이 다르면 회차를 통째로 만들지 않는다(계좌 지문 233 과 같은 규율). split 건은 그 값이 **필수**(모르는 옛 화면 요청은 담지 않음). 잠근 뒤 재확인: 방식이 바뀌었으면 `payout_mode_changed`, split 은 입금 칸(업체 제품비 기록)을 `already_paid` 로 보지 않는다.
4. **결과 반영(`paymentApply.recordDeposits` 외 네 경로)** — 리뷰비 전용 항목(`feeOnly`)은 v2 "리뷰 제출 전 입금 금지" 검사를 하지 않고, `review_index` PAID(= 리뷰어 "페이백 완료")·작업보드 입금 칸을 **건드리지 않고**, 우리 원장만 남긴다. 입금 칸 쓰기는 "처리됨"으로 센다(미기록 경고 없음). 금액 조정 후보에서 리뷰비 전용 항목은 뺀다. **회차 밖 이체 승인은 split 작업에서 거부**(그 돈이 제품비였는지 리뷰비였는지 시스템이 알 수 없다).
5. **업체 화면·기록(결정 247 창구 그대로)** — split 도 계좌 상시 공개 + 입금 칸 우클릭 기록. 리뷰비 전용 회차는 업체 기록을 막지 않고(`our_payout` 제외), 칸을 비워도 리뷰비 항목을 풀지 않는다. **우리가 제품비를 보낸(보내는 중인) 줄은 계좌 대신 "인애드가 제품비 지급 — 보내지 마세요"**(업체입금에도 적용 · 회차 조회 실패면 전부 숨김).
6. **리뷰어 참여정보 팝업** — 리뷰비 전용 항목은 페이백으로 보이지 않는다(작업보드 입금 칸 = 업체 제품비 기록이 페이백 날짜). **미작성 종결**은 리뷰비 전용 항목에 막히지 않는다(막다른 길 방지).
7. **이체은행 쓰기 규칙(`guardTransferBankWrite`)** — split 켜기 = 업체입금과 같은 검사(무시트 + 주인 업체). split/업체입금 → 우리 입금 = 확인 표시 필요(없으면 유지). **업체입금 ↔ split 직접 전환은 리뷰비 주체가 바뀌므로** 이미 그 방식으로 돈이 나간 줄이 있으면 거부(업체입금→split: 업체 입금 기록 있음 `advertiser_recorded` / split→업체입금: 리뷰비 전용 항목 있음 `fee_paid` · 조회 실패 = 거부).
8. 화면: 모집공고 창 세 모양 · 작업보드 작업 조건 › 이체은행 창에 두 선택지(칩 줄바꿈) · 입금관리 사유 문구·작업별 안내·"제품비 업체 · 리뷰비 N" 금액 칸 · 모집공고 저장 응답 `splitPayoutBank: true`(배포 시차 판별).

## 레드팀 반영 (2026-10-26)
- 템플릿 문자열의 `'\s'` 가 `s` 로 바뀌어 공고 코드값 split 을 못 알아보던 결함 → `[[:space:]]` + PG 시험으로 고정.
- 업체입금↔split 전환 이중 리뷰비 · 직원 수동 입금 줄 리뷰비 재지급 · 업체가 비운 기록으로 원장 잠금 풀림 · 회차 밖 승인 오분류 · 리뷰어 팝업 1천원 "페이백 완료" · 우리 제품비 지급 줄 계좌 노출 — 위 결정 2·4·5·6·7 로 막았다.

## Codex 리뷰 반영 (PR #1699)
- **이체은행 쓰기 규칙을 실제 입금 방식으로 판정** — `guardTransferBankWrite(slot, campaignId)` 가 그 탭의 가장 최근 공고 → 탭 순서로 지금/저장 후 방식을 계산해 비교한다(`_effectiveChoice`). 예: 탭 업체입금 + 공고 split 에서 공고를 「자동」으로 비우면 날값으론 "끄기"지만 실제론 split→업체입금 → `fee_paid` 검사. 호출부 네 곳(공고 생성 `campaign_new` · 공고 수정 `campaign`(연결 작업이 바뀌면 `campaign_new`) · 탭 이체설정·탭 설정 `tab`). 조회 실패 = 거부.
- **회차 만들기 잠금 안 재확인** — split 이어도 잠근 줄의 입금 칸에 값이 있으면 **업체가 넣은 값인지** 대상 SQL 과 같은 판정으로 다시 본다(목록 계산과 잠금 사이에 직원이 적은 날짜 = `already_paid`).
- **split 후보를 정확히** — `_splitCandidateKeys` 가 후보마다 가장 최근 공고·탭 값으로 `payoutModeFrom` 을 돌려 실제 split 작업만 돌려준다(공고가 은행을 명시한 작업의 리뷰 전 줄이 2,000건 상한을 먼저 채워 진짜 대상이 사라지던 문제).

## 남은 것 · 위험
- **split → 우리 입금으로 되돌리면** 리뷰비만 받은 줄은 영구 잠금(제품비를 우리가 보내지 않음), 업체가 기록한 줄은 "입금됨"으로 빠진다 — 끄기 확인 창이 경고한다. 되돌릴 일이 생기면 줄 단위 정리가 필요.
- 리뷰 전 지급이라 **다운로드(pending) 뒤 리뷰어가 취소**하면 리뷰비가 나갈 수 있다(우리 입금도 pending 은 같음 — 다만 그쪽은 리뷰 뒤라 드묾).
- 업체 입금일 기록은 종전 규칙대로 **리뷰 제출이 끝난 줄에만**(결정 247) — 업체가 구매 직후 보내는 운영이면 바꿔야 한다(사용자 확인 필요 시).
- 입금관리 2,000건 상한이 split 후보의 리뷰 전 줄로 먼저 찰 수 있다(지금 운영 규모에서는 무관 — 실측 안 함).
- 진단(`depositAnomalyReport` "리뷰 미작성인데 입금 기록")은 split 의 리뷰 전 리뷰비를 이상으로 셀 수 있다(읽기 전용 진단).

## ★★ 완화 금지
- **split 값을 `normalizeBankChoice` 가 은행으로 돌려주게 바꾸지 말 것** — 이체 서식 판정이다(247 과 같은 이유).
- **split 을 저장하는 두 번째 칸을 만들지 말 것** — 이체은행 하나(247).
- **split 에서 입금 칸 조건을 통째로 풀지 말 것** — 업체가 넣은 값일 때만(우리 직원 수동 입금 줄에 리뷰비 재지급). 8/11 수동 입금(`manual_paid`)은 풀지 않는다.
- **리뷰비 전용 결과 반영에서 PAID·입금 칸을 쓰게 되돌리지 말 것** — 1천원만 받은 리뷰어에게 "페이백 완료"가 뜨고 업체가 제품비 기록을 못 한다(`not_own`).
- **회차 박제의 제품비 0 을 실제 제품비로 바꾸지 말 것** — `isFeeOnlyItem` 판별과 인트라넷 장부 피드가 깨진다.
- **회차 밖 이체 승인을 split 에서 "지금 방식"으로 자동 분류하지 말 것** — 그 돈의 성격을 모른다.
- **우리 원장 잠금 예외에 업체가 비운 기록(`업체#…`)을 다시 넣지 말 것** · split 후보에서 예외를 되살리지 말 것.
- **업체입금 ↔ split 직접 전환 검사(advertiser_recorded·fee_paid)를 빼지 말 것** · 조회 실패를 허용으로 접지 말 것 · **날값이 아니라 실제 입금 방식(공고 → 탭)으로 판정**하는 `slot` 을 호출부에서 빼지 말 것.
- **회차 잠금 안에서 split 입금 칸을 무조건 건너뛰지 말 것** — 업체가 넣은 값일 때만.
- **회차 만들기의 입금 방식 대조(split 이면 필수)·잠금 안 재확인을 빼지 말 것.**
- **업체 화면에서 우리가 제품비를 보낸 줄의 계좌를 다시 보이게 하지 말 것.**
- **후보 SQL 에 `'\s'` 를 쓰지 말 것**(템플릿 문자열에서 `s` 가 된다 — `[[:space:]]`).
