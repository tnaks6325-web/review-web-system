# ★★ 구매양식 제출이 「선택 명의 확인 중…」에서 멈추지 않는다 — 제출 앞단 통신(명의 문맥·무캡처 확인·[내 주문이 맞습니다]·아이디 저장)은 시간 제한 + 쉬운 한국어로 실패 처리 · 제출 함수 밖으로 던져진 예외는 「제출 중」 표시를 반드시 푼다 · 죽은 「1회 재시도」 제거(결과 모르는 주문은 자동 재전송 금지) (2026-11-23 · 스키마 변경 0 · 서버 변경 0)

## 무슨 일이었나 (공고·구매양식 점검 2026-11-21 H2 · L6)
- 구매 캡처를 못 올린 리뷰어가 [캡처 없이 제출] → [제출완료하기]를 누른 순간 통신이 끊기거나 서버가 배포 중 오류 페이지(HTML 502)를 주면,
  버튼이 **「선택 명의 확인 중…」으로 바뀐 채 다시는 풀리지 않았다.** 아무 안내도 없었다.
- 위쪽 남은 시간은 00:00 이 돼도 만료 화면이 뜨지 않고 그대로 멈췄다 — 공고 화면은 틀 안의 「제출 중」 표시(`window._submitOrderFormInProgress`)를 보고
  만료를 미루는데(결정 351 「제출 중은 끊지 않음」 · `campaign.html` `_formSubmitting`), 그 표시가 영영 켜져 있었기 때문이다. 리뷰어는 새로고침밖에 길이 없었다.
- 원인
  1. 무캡처 확인(`/api/reviewer/order-identity-match/manual-confirm`)을 `fetch` + `response.json()` 맨손으로 불렀다 → 끊김 = `TypeError`, HTML 502 = `SyntaxError` 가
     `_prepareIdentityApprovals` 밖으로 던져졌다. 시간 제한도 없어 무응답이면 끝없이 기다렸다.
  2. `submitOrderForm` 본문에 `try` 가 없었다 — 진행 표시를 켠 뒤(`_submitOrderFormInProgress = true` · 버튼 「선택 명의 확인 중...」) 예외가 나면 끌 곳이 없었다.
     부르는 쪽(`confirmOrderSubmit` · `_proceedOrderSubmit`)도 실패를 받지 않는다.
  3. 같은 계열: 명의 문맥 조회(`order-identity-context`)는 실패를 잡긴 했지만 'Failed to fetch'·'Load failed' 영어를 그대로 보였고 시간 제한이 없었다.
     [내 주문이 맞습니다](`_manualConfirmIdentity`)와 주문 접수 뒤 아이디 저장(`_saveOrderShoppingIdIfRequested`)도 시간 제한이 없어 무응답이면
     「확인 중…」/「제출 중」이 끝나지 않았다.
- L6: 주문 전송의 「실패하면 1회 재시도」는 `gasPost` 가 예외를 던질 때만 돌았는데, `gasPost` 는 결정 359 이후 끊김·시간 초과를 예외가 아니라
  `{ ok:false, networkError }` 로 돌려준다 → **한 번도 실행된 적 없는 코드**였다.

## 바꾼 것 (`frontend/js/search-app.js` 만 · 서버·DB·campaign.html 무변경)
1. **`_ofPostJson(path, body, timeoutMs=20000, method='POST')`** — 예외를 던지지 않는 JSON 요청. 끊김·시간 초과(본문 읽기까지)·JSON 아님이면
   `{ response, data:null, error:'<쉬운 한국어>' }`, 서버가 답했으면 `{ response, data, error:'' }`(서버 판정·사유는 손대지 않는다).
2. **`_ofFriendlyErr(err, fallback)`** — 문구 단일 출처 `api.js apiFriendlyErrorMessage`(결정 359)를 부른다. 옛 api.js 가 캐시에 남아 함수가 없으면 fallback 한국어.
   서버가 준 한국어 사유는 그대로 돌려준다.
3. 위 도우미로 바꾼 곳(4곳): 명의 문맥 조회 · 무캡처 확인 · [내 주문이 맞습니다] · 주문 접수 뒤 아이디 저장(`PATCH`, 15초).
   명의 문맥 실패 토스트도 `_ofFriendlyErr` 경유.
4. **`submitOrderForm` 본문을 `try { … } catch (_sofErr) { _submitOrderFormEscaped(…) }` 로 감쌌다**(들여쓰기는 그대로 — 아래 가드들이 함수 끝을 첫 `\n}` 로 찾는다).
   `_submitOrderFormEscaped(err, { sent, okCount, resetBtn })`:
   - 이미 표시가 꺼져 있으면(완료 화면 이후의 예외 등) 아무것도 하지 않는다.
   - ㉮ 주문 요청을 보내기 전 → 버튼을 [제출]로 되살리고 쉬운 한국어 오류 토스트.
   - ㉯ 보냈지만 접수 0건 → **[재제출]**(종전 「전체 실패」 경로와 같은 모양 · 같은 참여 자리는 서버 멱등 게이트가 한 번만 받는다).
   - ㉰ 이미 접수된 주문이 있으면 **[제출]을 되살리지 않는다**(이중 제출 금지) — 표시만 끄고 버튼은 「접수됨」으로 잠근 채 「다시 제출하지 마세요 · 새로고침해 확인」.
5. **L6 = 죽은 재시도 분기를 지웠다**(살리지 않았다). 이유: 결과를 모르는 주문(요청은 갔는데 답을 못 받음)을 화면이 스스로 다시 보내면,
   참여 자리(홀드)가 없는 직접 링크 주문은 서버가 같은 주문을 가려 주지 못한다(`submit.routes` 홀드 멱등 게이트는 `holdCtx` 가 있을 때만 —
   레거시·비참여형·nc모드는 무영향이라고 코드 주석이 밝힌다). 또 30초 × 2 기다림이 참여 남은 시간을 갉아먹는다.
   그래서 종전 실제 동작 그대로 「실패 안내 + [재제출]」을 사람이 누른다. 주석과 동작이 이제 같다.
6. `search.html` 의 `js/search-app.js` 에 `?v=20261123-submit-unstick` 을 붙였다(전에는 쿼리 없음 · `_headers` 가 `no-cache` 라 새로고침이면 어차피 새 파일).

## ★★ 완화 금지
- **`submitOrderForm` 본문의 `try … catch → _submitOrderFormEscaped` 를 빼지 않는다** — 빼면 제출 앞단의 예외 하나로 「제출 중」 표시가 영영 남아
  버튼이 잠기고 공고 화면이 만료를 무한히 미룬다(H2 그대로 재현).
- **제출 앞단 요청(명의 문맥·무캡처 확인·[내 주문이 맞습니다]·아이디 저장)을 시간 제한 없는 맨 `fetch` + `response.json()` 으로 되돌리지 않는다.**
- **무캡처 확인을 받지 못했으면 제출하지 않는다(fail-closed)** — 통신 실패를 「확인됨」으로 접어 승인 없이 주문을 보내지 않는다(결정 174 우회 차단과 같은 방향).
- **이미 접수된 주문이 있는 상태에서 예외가 나도 [제출]을 되살리지 않는다** · **결과를 모르는 주문을 화면이 자동으로 다시 보내지 않는다**(L6) — 이중 제출 위험.
- 이중 제출 가드(`if (window._submitOrderFormInProgress) … return;` · 진행 표시를 켜는 곳 1곳)는 그대로다. 표시를 끄는 곳은 종전 셋(`_resetBtn` · 정상 끝 · 재진입) + 이번 `_submitOrderFormEscaped` 하나.

## 하지 않은 것 / 남은 것
- 캡처 판독 직후의 명의 대조(`_matchCardIdentity`)는 제출 버튼 경로가 아니고 `try` 로 이미 잡혀 있어 그대로 두었다(서버가 AI 를 쓸 수 있어 시간 제한 값을 정하지 않았다).
- 공고 화면(`campaign.html`) 쪽 통신 문구·시간 제한(점검 M2·M3·M4)은 다른 작업 범위.
- 정원 찬 상품 재확인(`_optionFullRefresh`)은 실패를 「지금 값 그대로」로 접는 설계(결정 252)라 그대로 — 다만 시간 제한이 없어 무응답이면 [제출]을 눌러도 반응이 늦을 수 있다(버튼·표시는 아직 켜지기 전이라 멈춤은 아니다).
