# 구매사진 제출 완료와 직원 확인 요청을 분리한다 (2026-11-13)

## 사용자 승인 및 배경

정상 구매사진을 제출한 리뷰어들의 C/S에 「구매 사진 확인을 요청했습니다.」가 반복 표시된다는 신고를 조사했다. 신고 화면의 6건은 원본 구매사진 저장 기록이 있고 추가사진 업로드와 연결되지 않은 별도 확인 요청이었다. 사진이 불량이라고 자동 판정한 기록이 아니다.

사용자는 다음 네 가지 변경을 승인했다.
1. 정상 저장은 「구매사진 제출 완료」로 표시한다. 별도 직원 요청이 없다는 의미의 「확인 요청 전」을 미완료처럼 노출하지 않는다.
2. 정상 저장의 추가·확인 요청 버튼은 「사진에 문제가 있나요?」 안에 둔다. 저장 실패·연결 확인 중·사진 미접수·직원의 보완 요청은 필요한 행동을 직접 보여준다.
3. 사진 추가 저장은 기본적으로 사진만 저장한다. 기본 꺼짐인 「사진 저장 후 담당자에게 확인 요청」을 선택한 경우에만 기존 C/S 확인 요청을 같은 트랜잭션에서 생성한다.
4. 새 문의 문구는 「리뷰어가 구매사진 확인을 요청했어요.」와 「추가사진을 제출하고 확인을 요청했어요.」로 구분한다. 저장된 기존 문의는 수정·해결·삭제하지 않는다.

결정 357의 추가사진 저장 후 자동 확인 요청 정책만 위 승인으로 대체한다. 원본 보존, 기존 C/S 연결, 소유권, 증빙 버전, 동시 삭제 잠금, 사진 재읽기 검증 및 지급 상태와의 분리 규칙은 유지한다.

## 구현 계약

- `POST /api/reviewer/purchase-captures/:orderId/supplements`의 `requestCheck=false`는 사진 저장만, true는 사진+확인 요청이다. 명시된 비불리언은 Drive·DB 접근 전에 거절한다. 생략한 구화면의 신규 저장은 소유권·이미 저장된 재시도 조회 후 `CAPTURE_REFRESH_REQUIRED`로 거절해 새로고침을 안내한다.
- `purchase_capture_supplements.check_request_id`는 migration 219부터 nullable이다. 추가 마이그레이션은 없다. 비어 있는 확인 요청 번호는 저장 실패가 아니다.
- 명시된 `requestCheck`를 요청 본문 해시에 포함해 재시도에서 동의 여부를 바꾸지 못하게 한다. 생략한 옛 요청의 3항 해시와 이미 완료된 옛 요청의 재조회는 그대로 지원한다.
- 저장만 한 요청의 재시도는 이후 다른 사진이나 별도 확인 요청이 생겨도 문의를 만들지 않는다. 권한 검증과 잠금은 재조회보다 앞선 기존 순서를 유지한다.
- 새 문구의 추가사진 여부는 서버가 조회한 해당 구매처의 `photos[].isSupplement`로 판단한다. HTTP 본문의 `source`나 `photos`를 신뢰하지 않는다. 다른 구매처에 추가사진이 있다는 이유로 현재 구매처의 문구를 바꾸지 않는다.
- 새 응답의 `capabilities.canSaveWithoutCheck=true`로 서버 지원을 알린다. 새 화면은 이 값이 없는 구서버에서 저장 버튼을 잠그고 업데이트 안내를 한다. 구화면+새서버는 신규 저장 성공을 돌려주지 않아 옛 「담당자 확인을 기다려 주세요」 안내가 허위로 나오지 않게 한다. 옛 화면이 이미 저장한 요청의 읽기 전용 재시도는 계속 허용한다.
- 사진 저장 성공은 직원 확인 완료·명의 승인·리뷰 완료·지급 승인과 다르다. 조회 실패·연결 확인 중 상태를 제출 완료로 바꾸지 않는다.
- 화면의 확인 요청 선택은 기본 false이고, 최초 저장을 시도한 뒤에는 같은 재시도에서 선택값을 바꾸지 못한다. 요청 유실 시에도 같은 요청 번호·본문을 다시 사용한다.

## 영향 및 검증

지도에서 요청·저장 함수 3개와 직접 연결 4개를 확인하고, 문자열 검색으로 HTTP 입구·재조회·기존 두 화면의 로드 지점을 대조했다. 관련 검사 14개를 확인했다. 기존 사진·구매·리뷰·지급 원장과 과거 문의를 변경하는 SQL은 추가하지 않았다.

- 새 실패 검사: 정상 저장을 미완료처럼 표시하는 화면을 Chromium/WebKit 모두에서 실패 재현한 뒤 수정했다.
- `purchaseCaptureRequestClarityFront.test.js`: 정상 완료, 숨겨진 요청 버튼, 기본 꺼짐 선택, false/true 전송, 보완 요청 행동 노출, 구서버 저장 차단.
- `purchaseCaptureOptIn.test.js` 및 실제 JWT HTTP 통합 검사: 일반/네이버/쿠팡 × false의 사진 저장과 메시지·미읽음·SSE 무변화, 생략한 신규 저장의 새로고침 거절, true의 요청 1건, 재시도·옛 요청 호환·원장 보존.
- 기존 브라우저 검사: 기존 실패·권한·명의 전환·늦은 응답·보존 단언은 유지하고, 바뀐 접힘 행동을 실제로 열도록 수정했다. 실제 연결 12가지(Chromium/WebKit × 390/1280 × 일반/네이버/쿠팡)는 명시적 확인 요청 선택 후 기존 C/S 방→카드→보완 사유→직원 확인→리뷰어 재조회를 실행한다.
- 실제 Drive와 운영 업무 쓰기는 시험하지 않는다. 로컬 가상 자료·외부 연결 차단·가짜 Drive를 사용한다. 전체 검사·독립 검토·커밋 및 배포 상태는 실제 완료 시 별도로 기록한다.

최종 로컬 검증: 기준 b3316dfc 위에서 전체 833개 검사 파일 통과·실패 0(exit 0), 실행 중 수정 소스 지문 불변을 확인했다. 첫 전체 실행은 공유 설치에 sharp가 없어 사진 변환 검사 2개만 실패했다. 이 작업폴더의 node_modules 연결만 분리하고 lockfile대로 npm ci로 설치한 뒤 해당 32개 시험과 전체 검사를 다시 통과했다. 원래 작업폴더·manifest·lockfile은 바꾸지 않았다. 브라우저는 Chromium/WebKit의 기존 25개, 추가 2개와 실제 연결 12경우를 별도로 무스킵 검증했다. 실제 연결의 각 경우는 사진만 저장할 때 문의/미읽음 불변과 사진 변경 뒤 과거 문의 카드 열람까지 포함한다.

## 독립 검토 후 추가 승인

독립 검토에서 두 문제를 확인하고 사용자가 「두 가지 함께 보완」을 선택했다.
1. 구화면은 사진만 저장되고 직원 확인 대기 문구를 보여줄 수 있다. 신규 생략 요청을 거절하는 위 새로고침 판정으로 해결한다.
2. 사진만 추가하면 증빙 해시가 바뀌고 기존 직원 문의가 현재 요청 목록에서 빠져 카드가 열리지 않는다. `getForStaff`는 선택한 옛 요청을 그 구매처에 명시해 반환하고 `evidenceChanged=true`를 붙여 조회를 유지한다. 직원 화면은 사진과 옛 문의를 읽을 수 있게 하되 「확인 요청 뒤 사진이 바뀌었어요」 안내만 표시하고 보완/완료 버튼은 만들지 않는다. 서버의 `STALE_EVIDENCE` 거절은 그대로 유지한다. 과거 문의를 고치거나 닫지 않는다.

두 문제는 `purchaseCaptureRefreshAndHistory.test.js`로 수정 전 각각 실패를 확인한 뒤 수정 후 통과했다. 사진 변경 뒤 옛 요청과 새 요청을 번갈아 조회해도 선택한 문의가 유지되고 옛 요청으로 새 사진을 승인하지 못하는 것을 검사한다. 크롬/사파리 실제 DOM에서 옛 문의가 열리고 처리 버튼이 없는 것도 확인한다.

추가 보완 뒤 독립 검토자는 위 두 경로를 다시 읽고 해당 회귀검사 2건을 별도로 실행해 통과했다. 최종 판정은 passed=true, 보안 우려/논리 오류 없음이다. 전체 833개 검사와 브라우저 시험은 부모가 실행했으며 독립 검토자가 모두 다시 실행한 것으로 세지 않는다.

## 미리보기와 반영 경계

화면 모양은 기존 부품을 유지하며 상태 문구·문제 행동 접힘·확인 요청 선택만 바뀐다. 로컬 가상 전후 비교는 저장소 밖 `~/Documents/리뷰웹-검토/2026-11-13-구매사진-확인요청/`에 보관한다. 사용자의 최종 화면 확인 전에는 운영 머지를 하지 않는다. 기존 문의의 소급 정리는 이번 승인 범위가 아니다.
