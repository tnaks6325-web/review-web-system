# ★★★ 명의 규칙을 한 곳에 — 관찰 모드로 시작 · 명의 돌려쓰기 금지 · "가족" 전제 제거 (사용자 확정 2026-10-11 · migration 183)

신원 기준 재정립(결정 221) **3단계 3-1**. 3단계 목표 = 명의 정보를 만들고 고치는 입구를 하나로, 규칙도 그 한 곳에.

## 사용자 확정 (2026-10-11)
- **A**: 구매양식이 명의 정보에 자동 저장하던 것(빈 주소·계좌 채우기, "타계정으로 등록해야 제출" 팝업) → **물어보고 저장**(체크한 경우에만). 3-4 에서 구현.
- **B**: 번호가 같아도 이름이 다르면 **그냥 다른 명의로 허용**. 단 "가족"이라는 전제는 리뷰웹시스템에서 **없앤다** — 이름이 다르면 다른 명의일 뿐, 가족 예외 규칙·문구를 두지 않는다. 화면 문구 2곳(campaign.html "타계정(가족·지인 명의)", workdesk.html 메모 예시 "가족이 한 폰을 씀")은 3-3 에서 바꾼다.
- **C**: **다른 리뷰어의 타계정에 이미 있는 번호를 내 타계정으로 저장하지 않는다** — 명의 돌려쓰기 금지로 작업 참여 명의의 신뢰성을 올린다. 기존 겹침(현재 76건)은 **새 저장만 막고, 담당자가 정리할 때까지 지금처럼 참여 가능**("가"). 정리가 끝나면 참여 단계에도 같은 규칙을 켠다.
- **라이브 무중단 원칙**: 24시간 서비스 — 잘못된 배포로 운영이 멈추면 신뢰를 잃는다. 모든 단계에 ① 관찰 먼저(막지 않고 "막았을 건수"만) ② 배포 없이 끄는 스위치 ③ 입구 하나씩 ④ 스키마는 추가만 ⑤ 배포 직후 감시 ⑥ 한산한 시간 배포(운영 실측: KST 18시~익일 06시 — 3주 합계 18시 46건 vs 17시 270건).

## 명의 규칙(한 곳 = `server/src/services/identityRules.service.js`)
1. 이름은 띄어쓰기를 무시하고 비교한다(종전 5가지 방식 → 하나).
2. 본인과 이름·번호가 같은 타계정은 두지 않는다(`same_as_self`) — 인소민 건의 근원.
3. 한 사람 안에서 이름·번호가 같은 칸은 하나만(`duplicate_in_list`). 번호가 같고 이름이 다르면 허용(B).
4. 다른 리뷰어의 본인 번호를 타계정으로 두지 않는다(`other_owner_self_phone` — 참여 단계의 사칭 차단과 같은 규칙).
5. 다른 리뷰어의 타계정 번호를 내 타계정으로 두지 않는다(`other_owner_sub_phone` — C).
6. 타계정 10개까지(`limit`, 종전 화면 10 / 서버 50). 7. 이름·번호 빈 칸 금지(`missing_name_or_phone`).
- ★ **이번 저장으로 새로 생긴 위반만** 센다 — 이미 있던 칸(내용만 바꾼 저장 포함)은 문제 삼지 않는다(기존 데이터는 담당자 정리, "가").
  - 새로 생긴 명의(이름+번호)는 번호가 내 목록에 이미 있었어도 다른 리뷰어 겹침을 본다(Codex P2). 그래서 **기존 겹침 칸의 이름만 바꾼 저장도 새 명의로 세어진다** — 차단 때 이것을 막을지는 관찰 결과로 정한다.
  - 빈 칸은 칸 순번이 아니라 값으로 센다(순서만 바뀐 저장은 위반 아님 · Codex P2).

## 3-1 구현 (관찰 모드 — 아무것도 막지 않는다)
- migration 183 `identity_rule_observations`(새 기록 표만 · 이름·전화번호 저장 안 함 — 입구·소유자·규칙·칸 순번·겹친 소유자).
- 공용 쓰기 창구 `mutateSubAccounts` 가 **COMMIT 뒤에** `observeSubAccountsWrite` 를 기다리지 않고 부른다 — 관찰 실패·지연이 저장에 닿지 않는다. 대상 입구: 내정보 저장(구매양식 "타계정으로 등록" 포함) · 가입 · 구매양식 자동보강 · 관리자 외부 주문.
  - 창구를 거치지 않는 직접 쓰기(쇼핑 아이디·주소 저장, 입금 계좌 보완, 합치기 InTx, 번호 변경)는 새 타계정을 만들지 않거나(번호 변경은 관리자 전용·드묾) 3-2 에서 창구로 옮긴다.
- 스위치: `app_settings.identity_rules_mode` = `off`|`observe`(기본 observe, 30초 캐시) — 마스터 전용 `GET/POST /api/trackb/settings/identity-rules-mode`(최근 14일 규칙별 건수 포함 — 기록을 못 읽으면 0건이 아니라 `available:false` "확인 불가" · Codex P2). 비상: 환경변수 `IDENTITY_RULES_MODE=off` 가 이긴다. 설정 조회 실패 = 관찰(막지 않음). `enforce` 는 관찰 결과 확인 뒤 3-1b 에서 추가.
- 기존 저장 규칙(내정보의 "같은 연락처 타계정 한 번만" 등)은 그대로 — 새 규칙으로 바꾸는 것은 차단(3-1b) 때 함께(B 의 허용도 그때 반영).

## 알려진 한계
- 본인 번호를 쓰는 다른 이름 타계정(현재 180건)은 B 로 저장은 허용이지만, 참여하기는 참여 자리를 번호로 구분해 "본인 번호 타계정 참여"를 막는다(`sub_shares_owner_phone`). 참여 자리를 카드로 구분하는 4단계에서 푼다.

## 3단계 나머지
- 3-1b 차단 켜기(관찰 결과 오탐 0 확인 후, 기존 규칙을 새 규칙으로 교체) · 3-2 직접 쓰기 5곳 + 본인 칸 11곳을 창구로(하나씩) · 3-3 내정보 거부 사유 안내 + "가족" 문구 제거(화면 — 미리보기 확인) · 3-4 구매양식 "물어보고 저장"(A) · 3-5 참여하기 로그인 확인(측정 후).

## ★★ 완화 금지
- ① 관찰은 **COMMIT 뒤·기다리지 않고·실패를 삼킨다** — 저장 트랜잭션 안으로 옮기거나 await 하지 말 것(관찰 장애가 저장을 깨거나 늦춘다). 차단(3-1b)은 별도 경로로 설계한다.
- ② "새로 생긴 위반만" 원칙을 빼지 말 것 — 빼면 기존 겹침 76건·중복 칸 리뷰어가 아무 수정 없이 저장만 해도 걸린다(사용자 확정 "가" 위반).
- ③ 관찰 기록에 이름·전화번호를 넣지 말 것.
- ④ 비상 스위치(환경변수)가 설정값을 이기는 순서를 바꾸지 말 것.
- ⑤ 관찰 건수를 못 읽었을 때 0건으로 보여 주지 말 것 — 차단을 켜는 근거가 거짓이 된다.
