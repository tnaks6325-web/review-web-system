# ★★ 이미지 교체요청 승인 대기 줄이기 — Drive 왕복 묶기 · 옛 파일 보관은 응답 뒤 · 처리 중 잠금 · 다음 요청 원본 미리 받기 (사용자 확정 2026-10-19 · 스키마 변경 0)

## 발단 · 실측 (2026-10-19 운영)
- 사용자: "리뷰어 이미지 교체요청을 관리자가 확인·승인하는 과정 로딩이 느리다 — 몇 초나 걸리나".
- **승인 1건 = 5.7~9.1초**(운영 서버 HTTP 기록 `POST /api/trackb/review-edit/approve` 오늘 12건: 5676·5775·6206·6380·6406·6450·6518·7135·7237·9129ms …).
  원인 = 승인 한 번에 Drive 를 **순차로** 6회 안팎 친다 — 새 파일 부모 조회·이동·이름 변경, 커밋 뒤 옛 파일 보관 폴더·부모 조회·이동·이름 변경.
- 같은 승인이 **거의 동시에 6번** 들어간 기록(15:44 KST — 5건 499 클라이언트 종료 + 1건 200). 서버의 `FOR UPDATE` 재검증으로 한 번만 처리됐지만 버튼이 잠기지 않았다.
- 비교 팝업 원본 두 장 = **장당 1.4~1.8초, 동시 두 장 1.66~1.71초**(`GET /api/drive/image/<id>` 실측 3회 · 20KB~450KB 무관). 서버 기본 응답 0.2초.
  ⚠ 이 자리는 [결정 008](008-Drive-이미지-프록시-왕복-1회-2026-08-24-실측.md) 에서 이미 왕복 1회로 줄인 뒤의 값 — Drive 지연이 지배라 서버에서 더 줄일 여지가 거의 없고,
  **대조는 원본**(008 완화 금지 — 썸네일 CDN 금지)이라 작은 이미지로 바꿀 수도 없다.

## 결정
1. **새 파일 이동 + 정식명 변경 = `files.update` 1회**(`drive.service.moveAndRenameFile`) — 실패하면 **종전 2단계로 폴백**: 이동 실패 = 승인 실패(종전과 같다) · 이름 실패 = 무시(종전과 같다).
2. **옛 파일 [리뷰교체보관] 이동은 응답을 보낸 뒤**(`_archiveOldFileAfterReply` · `setImmediate`) — 커밋 뒤 비치명적 단계라 종전에도 실패를 무시했다.
   - ★ 응답 뒤라 잡아 줄 곳이 없다 → **throw 금지 · 전부 try/catch**(회귀가드가 고정).
   - 실패 시 옛 파일이 [리뷰] 폴더에 남는다(링크는 이미 새 파일) → 고아 캡처 정리 A 대상(종전 실패 때와 같은 결과).
   - 보관 이동도 이동+이름 한 번에(실패 시 2단계).
   - 리뷰어 채팅 통지(csBridge)는 **종전대로 응답 전·커밋 뒤**(093 순서 규율 불변).
3. 승인의 `_resolveFolders` 는 **스테이징 폴더([리뷰수정대기]) 조회를 생략**(`{ withStaging:false }`) — 기본값은 종전대로 확보(요청 업로드 경로 불변).
4. **같은 요청 처리 중 재요청 차단** — `cs-inquiry.js` `csApproveReviewEdit`/`csRejectReviewEdit` 한 곳(`_reInflight`): 대화창 카드·교체요청 팝업·관리자 대시보드가 모두 이 함수를 지난다.
   네트워크 오류도 실패로 접고 **잠금을 푼다**(영원히 "처리 중"이 되지 않게).
5. 교체요청 팝업 — 처리 중 결정 버튼·이전/다음(방향키 포함) 잠금 + 버튼 글자 「처리 중…」 · 끝나면(실패 포함) 해제. 닫기는 열어 둔다(서버 처리는 그대로 끝난다).
6. **다음 요청 원본 미리 받기** — 팝업을 그릴 때 다음·이전 요청의 원본 두 장, 대기 큐가 보일 때 맨 앞 요청의 두 장을 `new Image()` 로 미리 받는다.
   ★ 팝업과 **같은 주소**(브라우저 캐시 `private, max-age=600` 를 그대로 쓰게) · 같은 주소 1회 · 상한 12 · 썸네일 주소 금지(008).

## 기대 · 확인
- 승인: 응답 전 Drive 왕복 6회 안팎 → 2회(부모 조회 + 이동·이름) 기대.
- **2026-10-20 테섭 실측(PR #1659 환경, 사용자 승인 후 시험 사진 14장 업로드 → 측정 뒤 전부 휴지통)** — 같은 행을 14번 교체요청→승인. 승인 단계별 소요는 이번에 넣은 한 줄 기록(`approve 단계별 ms`)으로 쟀다.
  - 테섭 합계 4.1~6.4초(7회 중 6회 4.1~5.1초). 그러나 **테섭은 DB 질의 1회 ≈ 166ms**(`/health` = 질의 1회: 테섭 167~170ms · **운영 4~5ms**, Railway HTTP 기록) — 승인의 DB 질의 약 15회가 테섭에서만 ≈ 2.5초를 더한다.
  - Drive 몫(부모 조회 + 이동·이름) = 1.65~3.4초(중앙값 ≈ 1.8초). 운영 DB 몫(≈ 0.1초)을 더한 **운영 예상 = 1.8~3.5초(보통 2초 안팎)** — 개선 전 운영 실측 5.7~9.1초.
  - ★ 운영 숫자는 아직 추정이다 — 배포 뒤 운영 기록의 `approve 단계별 ms` 줄로 확정한다.
  - ⚠ 테섭 DB 가 서버와 멀다(질의마다 ≈ 166ms) — 테섭에서 잰 응답 시간은 운영보다 부풀려진다. 테섭 속도 측정은 단계별 기록으로 DB 몫을 빼고 본다.
- 이미지: 첫 장은 그대로(1.7초 안팎), **넘긴 다음 요청은 미리 받아 두어 바로** 뜨는 것이 목표.
