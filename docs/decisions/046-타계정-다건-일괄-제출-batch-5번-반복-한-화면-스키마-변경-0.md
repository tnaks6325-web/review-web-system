# 타계정 다건 일괄 제출 (batch) — 5번 반복 → 한 화면 (스키마 변경 0)
- **배경(실사고)**: 리뷰어가 타계정 5건 참여를 시도하다 **30분 걸려 포기**(카톡 피드백 실물). 원인 ① 명의당 [참여→구매→캡처1장→양식→제출] 5회 반복 ② 작성 중 새로고침하면 화면이 되돌아가고 **첨부 캡처가 소실**. 개선 제안서·목업 = `frontend/docs/타계정_다건참여_일괄제출_개선안.html`.
- ★★ **묶는 것은 "제출"이지 "구매"가 아니다**: 홀드 TTL(본계정 `hold_ttl_min` 15분 / 타계정 `sub_hold_ttl_min` 10분)은 **그대로**다. "5건 다 사고 와서 한 번에"를 UI가 부추기면 후행 건이 전부 지각(`late_order_id`)이 되어 관제 수동확정이 폭증한다 → **만료 홀드는 스냅샷에서 제외 + 카드에서 잠금 + 페이로드에서 제외**, 참여가 2건 이상이 되는 순간 "구매를 먼저 끝내고 마지막에 한 번에 제출하세요" 경고. **TTL 상향은 하지 않았다**(서버 정책 = 사용자 결정 사항, 아래 잔여위험 ①).
- **서버 변경은 멱등 게이트 1개뿐**(스키마 0, 신규 엔드포인트 0): 요청 1건 = 홀드 1건이라는 기존 계약(`_campaignHoldCtx`+`_authoritativeHold`)을 그대로 쓰고 **카드마다 자기 홀드 문맥을 실어 순차 전송**한다. `_authoritativeHold`가 같은 왕복에서 `status`·`order_submission_id`·`late_order_id`(+주문 생존 LEFT JOIN)를 함께 읽어 **이미 접수된 홀드면 `{ok:true, alreadySubmitted:true, campaignHold:'confirmed'|'late'}`로 즉시 반환**(왕복 순증 0).
  - ★★ **`late` 경로를 반드시 포함**: `confirmHoldInTx`의 late UPDATE는 `late_order_id IS NULL` 조건이라, 지각 건을 두 번째로 재제출하면 **링크조차 못 남기고 주문만 새로 생긴다**(관제에 흔적 0인 고아 주문). `status='submitted'`만 보면 이 경로가 뚫린다.
  - ★ **`ok:true`로 돌려주는 게 핵심** — "실패"로 보이면 리뷰어가 또 누른다. ★ **fail-open 유지**(조회 실패 시 `doneKind` 없음 = 기존 경로). ★ 레거시·비참여형·nc모드·관리자 경유는 `holdCtx`가 null이라 게이트에 도달조차 안 함.
- **부팅은 fail-closed 7조건 AND**(`_batchBoot`, `search-app.js`): embed && **미리보기 아님** && **nc모드 아님** && `batch=1` && 스냅샷 존재 && `2 ≤ 홀드수 ≤ MAX_ORDER_CARDS(5)` && 전 홀드 `app`·`holdToken`·8자리 `phone8` 보유 && 활성 app이 스냅샷에 포함(stale 거부). 하나라도 어긋나면 `null` = **기존 단건 동작 100% 불변**. 어떤 예외도 단건으로 수렴.
  - ★ **배치 여부는 iframe이 보내는 `batch-mode` ack로만 인정**(campaign.html). 부모 HTML만 새 버전이고 iframe JS가 캐시된 구버전인 **배포 스큐**에서 부모가 혼자 "5건 냈겠지"로 화면을 정하면 리뷰어가 1건만 낸 채 이탈한다(= 이 사고의 재현).
  - 스냅샷 = `sessionStorage.camp_batch_<campId>`(부모가 iframe src 세팅 직전 기록, **만료 임박 오름차순**). 저장 실패 = batch 미설정 = 단건. **옵션 공고인데 `optionKey`를 모르는 홀드**(이 배포 이전 생성)가 섞이면 배치 금지(틀린 옵션을 사게 하느니 단건).
- ★★ **자동배정(순서 폴백)을 리뷰어 화면에 옮기지 말 것**: 관리자 `manual-order.js`의 `distributeStaged`는 이름/뒤4자리 실패 시 **붙인 순서**로 배정하는데, 그건 **표를 눈으로 대조할 사람이 있어서** 안전했다. 리뷰어 화면엔 없다. 캡처가 남의 홀드로 가면 **"남의 명의로 주문 접수"**이고 **서버는 이를 막지 않는다**(`resolveOrderIdentity`는 "내 계정 중 하나인가"만 봐서 같은 소유자의 타계정 A↔B 교차는 SUB로 통과, `detectIdentityDrift`는 warn만). → 일괄 첨부는 **고른 순서대로 위 카드부터 부착(화면에 명시)** 하고, AI 추출 수취인 ≠ 그 카드 명의면 카드에 경고 + [○○ 카드로 옮기기]/[제가 확인했어요] 중 **사람이 고르게** 한다. 확인 안 된 불일치가 남으면 `_batchIdentityGuard`가 제출을 막는다. `manual-order.js`의 순서 폴백은 **그대로 유지**(가드가 생존을 고정).
- **배치 전용 카드 보정 3종**(전부 실제 사고 예방): ① **삭제 버튼 제거** — 카드가 사라지면 홀드↔카드 매핑이 어긋나 그 명의가 조용히 누락된다. ② **"1번과 동일" 기본 해제** — 기본 체크면 2~5번 카드의 **주문자**가 1번 값으로 잠기는데 서버 신원게이트는 `orderer`를 검증하지 않아 잘못된 명의가 그대로 시트에 기록된다(대신 제출 직전 **빈 계좌칸만** 1번에서 복사 = 타계정 리뷰비를 본인 공통계좌로 받는 정상 흐름 보존). ③ **옵션 잠금 전용 경로**(`_lockEmbedOptionBatch`) — 전역 피커를 숨기는 것만으로는 부족하고 `_selectedOptKey`가 null이면 `submitOrderForm`이 **제출을 통째로 차단**한다.
- **결과는 명의별 배열**: `_embedLastCampaignHold`(루프마다 덮어써지는 단수 값) **삭제** — 5건 중 4건이 지각이어도 "참여 확정!"이 뜨던 경로다. `_embedPost({results})` → 부모 `renderDoneBatch`가 명의별 한 줄로 표시하고 **성공한 명의만 `clearHold`**(실패분만 [이어서 진행] CTA 대상 = 재제출 유도 차단). 부분 실패는 "실패한 N건 다시 제출" 버튼 + `_BATCH.done[app]`으로 성공분을 건너뛴다(서버 멱등이 최종 방어 — `done`은 sessionStorage라 탭을 닫으면 사라진다).
- **새로고침 복원은 명의(phone8) 앵커**: 기존 `_embedSaveForm/_embedRestoreForm`은 **배열 인덱스 위치** 기반이라 홀드 1건이 만료돼 카드 수가 줄면 **2번 카드 자리에 3번 명의의 수취인·주소가 들어간다**(= 남의 명의 주문). → 배치는 `_batchSaveForm/_batchRestoreForm`(키 `embedBatchForm_<campId>`)이 담당하고 **위치 기반은 배치에서 조기 반환**으로 끈다(단건 경로는 무수정·무변경). **텍스트와 사진은 다른 키**(`embedBatchCap_<campId>`) — 한 키에 담으면 사진 용량 초과가 텍스트 저장까지 죽인다. 사진은 첨부 시점에 **1회만** 축소(canvas 1080px/JPEG0.6)하고 2.5MB 예산 초과분은 **저장 시점에 `dropped`로 세어** 배너가 "사진 N장은 용량 때문에 복원하지 못했어요"라고 정직하게 말한다(`_ssWrite`가 저장 후 되읽어 조용한 실패도 잡는다).
- **find-slot 왕복은 배치에서 생략** — 서버가 항상 `{mode:'append'}`를 즉시 반환하는 no-op인데 카드당 최대 15초 타임아웃이라 총 제출시간이 홀드 TTL을 그대로 갉아먹는다.
- 회귀가드 `tests/campaignBatchSubmit.test.js`(**스텁 pool로 멱등 게이트 실제 실행**(확정/지각/soft-delete/applied/조회실패/레거시 6분기 + 원장 미호출 스파이) + 배선 + 자동배정 부재 + manual-order 무회귀) + **실제 http 오리진 브라우저 실행검증 시나리오**(카드↔홀드 결속·페이로드 홀드 분리·fail-closed 6조건·만료 제외·재제출 스킵·명의 앵커 복원). ⚠ 이 변경으로 기존 grep 가드 5종의 패턴이 드리프트해 함께 갱신했다(검사 의미는 불변) — **배선 형태가 바뀌는 변경엔 패턴을 함께 갱신할 것**.
- **잔여위험(문서화)**: ① 🔴 **TTL vs 일괄은 해결되지 않았다** — 10~15분 안에 5건 결제는 물리적으로 불가하다. 이 기능은 **이미 유효한 홀드들의 제출을 묶는 것**까지만 하고 만료 건은 잠근다 → 지각은 줄지만 0이 아니다. 근본 해결은 `sub_hold_ttl_min` 상향 또는 "구매 완료 신고 시 TTL 연장"이며 **서버 정책 변경이라 사용자 결정이 필요**하다. ② 새 창 폴백(`openFormWindow`)은 `sessionStorage`가 복제돼 batch가 켜질 수 있으나 `_embedPost`가 부모에 닿지 않는다(폴링→`renderDone`→CTA로 자가치유하되 그 사이 화면은 1건만 확정된 것처럼 보인다). ③ **일괄 참여(홀드 5개 한 번에 생성)는 만들지 않았다** — TTL 폭발기라 기각. ④ `orderer`는 서버 신원게이트의 검증 대상이 아니라 사용자가 명시적으로 잘못 입력하면 그대로 나간다(단건과 동일한 한계).
