# ★★★ 상품마다 유입방식 — 한 오더·한 공고에 가이드유입 상품 + 링크유입 상품 (migration 213 · 사용자 확정 2026-11-04 「가」)

- **발단(직원 요청 2026-11-04)**: "1개의 작업으로 상품 2개로 나눠서 21호 - 검색유입 / 23호 - 링크유입 — 이게 안 돼서 각각 했다."
  리뷰오더는 유입방식을 **오더 전체에 하나**만 고를 수 있어, 한 작업인데도 오더·공고를 둘로 쪼개 관리해야 했다(최근 60일 공고 63개 중 23개가 상품 2개 이상).
- **모델**
  - 오더: `product_options_json[*].inflow_type = 'guide' | 'link'` — **상품 단위**(옵션은 상품을 따른다). **상품마다 다를 때만** 인트라넷이 싣는다.
  - 공고: `campaign_options.inflow_type`(213 · 줄 단위). `''`·NULL·키 없음 = **공고 전체 값(`work_detail.inflowType` / `work_orders.inflow_type`)을 따름** = 종전 동작.
  - 오더·공고 전체 값은 종전처럼 `'guide' | 'link'` 하나(섞이면 `'guide'`). ★ `'mixed'` 같은 새 값은 만들지 않는다 — `=== 'guide' ? 'guide' : 'link'` 분기들이 섞인 공고를 링크유입으로 읽는다.
  - 규칙 단일 출처 = `server/src/utils/unitInflow.js`(값 정규화 · 실제로 쓰는 유입방식 · 가이드 필수 판정 · 옛 창 값 보존 · 능력 표시).

## ★★★ 가이드 필수 검사는 「그 줄이 실제로 쓰는 유입방식」으로 (완화 금지)
- 164 의 규칙(가이드유입이면 살아 있는 선택지 전부에 가이드)은 그대로다 — 다만 **링크유입 줄은 상품 주소가 곧 유입**이라 가이드가 필요 없다.
- 검사 4곳이 한 함수(`guideMissingUnits`)를 탄다: 공고 저장(`campaign.routes _validateActiveUnitInflowGuides`) · 옛 원본 수정 전파(`campaignPayAmountSync.syncCampaignInflowInTx`) · 공유 저장(`sharedPatch._guideMissingInTx`). 화면 사본(`index-recruit.validateActiveUnitInflowGuides`)은 공고 창 상품별 선택 단계에서 맞춘다.
- ★★ **유입방식을 먼저 쓰고, 가이드까지 다 쓴 뒤 한 번 검사한다** — 검사가 옛 유입방식을 보면 "가이드→링크" 전환이 가이드 없음으로 거부되고, "링크→가이드"는 가이드 없이 통과한다(레드팀 R5).
  - 공유 저장: 구조 반영 → **유입방식 투영(`_projectUnitInflowInTx` · 공고 전체 값 + 줄 값)** → … → 가이드 투영 → **최종 검사**. 구조 경로가 따로 하던 검사도 이 최종 검사로 옮겼다(같은 문구 · 최종 상태 판정 = 더 정확).
  - 옛 원본 수정: 줄 유입방식을 가이드보다 먼저 쓰고 전파가 끝난 상태로 검사(종전 구조 그대로).
- ★ 공고 저장에서 유입방식을 안 보낸 줄(옛 공고 창 · `null`)은 **저장된 줄 값**으로 판정한다(링크 상품에 가이드를 요구하지 않게).

## ★★★ 리뷰어 화면 — 링크 상품은 그 상품 주소로만 (완화 금지)
- `campaign-workdetail.js`: 실제 유입방식 = 고른 선택지 값 → 없으면 공고 전체 값(`effInflow`). 버튼 판정·옛 문구 호환·불명 폴백 세 자리가 모두 이 값을 본다.
- 링크유입 선택지는 **공고 공통 가이드로 접지 않는다** — 섞인 공고의 공통 안내는 가이드 상품 몫이라 접으면 링크 상품 리뷰어가 남의 상품 검색 경로를 따른다. 대신 "링크유입 — 아래 버튼으로…" 안내.
- ★★ 유입방식이 적힌 선택지는 **공고 대표 주소(`landing_url`)로 접지 않는다** — 섞인 공고의 대표 주소는 다른 상품일 수 있다(남의 상품을 사게 된다 · R8). 그 상품 주소가 비면 버튼 대신 "운영자에게 문의" 안내.
- 줄 값이 없는 공고(기존 전부)는 종전 판정 100% 그대로(124 규율 불변 — 회귀가드 `campaignGuideView` ④ 패턴만 새 변수명으로).

- 옛 창은 상품 객체를 화면 값으로 새로 만들어 보내 `inflow_type` 키가 빠진다. 그대로 받으면 "지웠다"로 읽혀 링크 상품이 가이드로 바뀐다(가이드가 없으면 그 오더는 옛 창에서 아무것도 저장 못 함 · R3).

- 화면만 먼저 배포된 틈(새 화면 + 1단계 서버): 수정 창은 서버 상세의 `unitInflow` 표시가 없으면 카드 선택을 숨긴다 · 새 공고 발행은 1단계 서버도 줄 값을 저장한다.
- 같은 이름의 상품이 둘이면 ⑨ 의 상품 짝짓기(이름)가 둘을 구분하지 못한다 — 인트라넷이 상품 이름 중복을 막는다(종전 금액·주소 계획과 같은 한계).
- 선택지 합치기로 참여 기록을 링크 줄에서 가이드 줄로 옮기면 구매 중인 리뷰어의 안내가 바뀐다(드문 조작 · R18).
- 옛 형식 오더(상품 모드 표시 없음 · 옵션 1개 이하)는 공고에 줄이 없어 상품별 값을 둘 자리가 없다 — 인트라넷 신형은 늘 모드를 싣는다(R17).
- 섞인 오더는 상품별 값이 있는 줄의 짝을 저장마다 확인한다 — 공고 줄 이름 하나가 어긋나면 구조·유입이 닿는 저장이 거부된다(가이드 투영보다 넓다 · 의도: 오더만 바뀌고 리뷰어 화면이 옛 유입방식이 되지 않게).
- 서버는 「섞이면 오더 전체 값은 guide」를 강제하지 않는다(인트라넷 규칙) — 전체 link + 상품 guide 가 오면 프리필이 줄 가이드를 버려 저장이 가이드 없음으로 거부된다(안전한 쪽).
- 같은 옵션 이름이 두 상품에 있으면 옛 원본 수정 경로의 짝짓기(옵션명)가 상품명 붙은 공고 줄을 못 찾는다 — 종전 가이드 전파와 같은 한계.
