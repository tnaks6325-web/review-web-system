# ★★ 인트라넷 페이백 장부 피드 — 지급이 끝난 건의 금액·시각·작업 키만, 읽기 전용으로 내보낸다 (사용자 확정 2026-10-26 · 스키마 변경 0)

## 발단
- 사용자: "인트라넷과 리뷰웹시스템을 연결해서 상품비용 페이백하는 과정을 더해서 재무관리를 해야겠어."
- 리뷰어 페이백(상품값 + 리뷰비)은 리뷰웹 입금관리(결정 108·109)에서만 기록되고, 인트라넷 재무는 그 돈을 몰랐다.
  인트라넷 계약에는 광고주에게 받은 상품값(대납)만 있고, 돌려준 상품값·리뷰비·통장 출금과 이어지지 않았다.
- 인트라넷 계획(사용자 승인 2026-10-26): ①연결 통로(이 결정) → ②계약별 받은·돌려준 상품값 대조 → ③월별 흐름 → ④통장 출금 짝짓기 → ⑤리뷰비를 계약 비용으로.

## 결정
1. **인트라넷이 끌어간다(pull)** — `GET /api/order/payback-ledger/summary`, `GET /api/order/payback-ledger/items?batch_ids=…`.
   인증 = 기존 `ORDER_INTAKE_KEY`(`X-Intake-Key` **헤더만** — 주소에 키를 싣지 않는다). 새 비밀값 0, 리뷰웹 쓰기 0.
2. **싣는 것 = `payment_batch_items.status='paid'` 건의 회차 박제값**(상품값·리뷰비·합계·실제 이체시각)과 작업 키(sheet_id·tab_name·row_index·campaign_id).
   대기(pending)는 회차 합계에 건수·금액만, 실패·취소는 싣지 않는다.
3. **개인정보는 싣지 않는다** — 리뷰어 이름·phone8·은행·계좌·예금주는 SELECT 하지도 않는다(결정 186 92번과 같은 이유).
4. **회차 지문(md5)** — paid 건의 id·금액·이체시각으로 만든다. 인트라넷은 지문이 바뀐 회차의 건만 다시 가져간다(매번 전부 받지 않는다).
5. **작업 → 계약 연결은 회차와 따로**(`summary.tabs`) — 연결은 지급 뒤에 생기거나 바뀌므로 지문에 섞지 않는다.
   판정 = 탭 ↔ 계약 링크(`trackb_settlement_links`, 지운 링크 제외) > 그 탭에 연결된 가장 최근 작업오더(`work_orders.sales_id`, 지운 작업오더는 마지막 수단). 둘 다 없으면 `sales_id: null`.

## 남은 것
- **업체입금 작업(결정 247)** 은 우리 회차가 없어 이 피드에 나오지 않는다(우리 돈 흐름이 아니다). 인트라넷에 "업체 직접 지급"을 따로 보이려면 별도 단계.
- 중복 입금 회수·환불(migration 124 `duplicate_payment_cases`)은 아직 반영하지 않는다 — paid 건 그대로 싣는다.

## ★★ 완화 금지
- **응답에 리뷰어 개인정보(이름·phone8·계좌·예금주·은행)를 더하지 말 것** — 인트라넷 재무에 필요 없고, 이 입구는 사람 로그인 없이 공유 키로 열린다.
- **키를 쿼리 문자열로도 받게 바꾸지 말 것** — 접속 기록에 키가 남는다.
- **금액을 여기서 다시 계산하지 말 것**(리뷰비 규칙·공고 값으로) — 회차 박제값이 실제로 보낸 돈이다(결정 108).
- 회귀가드 `server/tests/paybackLedgerFeed.test.js`.
