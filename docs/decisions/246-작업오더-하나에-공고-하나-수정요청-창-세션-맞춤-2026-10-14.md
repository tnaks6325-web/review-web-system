# ★★ 작업오더 하나에 살아 있는 모집공고는 하나 · 수정요청 창은 화면의 리뷰어로 세션을 맞춘다 (사용자 확정 2026-10-14 · 스키마 변경 0)

## 사고 ① 같은 작업으로 공고 두 장 (2026-10-13 신고 2026-10-14)
- "10/14 네이버 실배송 눈 or간 영양제 1BOX" 가 모집공고에 2장, 작업보드엔 1장.
- 운영 실측: 같은 오더 `wo_129486c43279` 로 14:47:02 담당자 A 가 생성·게시(`camp_da9e1876791f`), **1분 7초 뒤** 담당자 B 가 하나 더 생성해 임시저장(`camp_faf97b013ea3`). 둘 다 같은 작업표를 가리켜 카드 숫자(20/20 · 총 20/60)가 똑같이 보였다. 작업오더의 `linked_campaign_id` 는 A 공고 → 작업보드는 1장.
- 원인: 생성 라우트(`POST /admin/create`)에 "이 오더로 이미 공고가 있나" 검사가 없었다. 화면은 `linked_campaign_id` 가 있으면 만들기 버튼을 숨기지만 **열어 둔 옛 화면**은 못 막는다.
- 운영 전수: 오더 하나에 공고가 둘 이상인 경우는 이 1건뿐 — 정상 업무에서 같은 오더로 공고를 둘 만드는 쓰임은 없다.

### 규칙
- 생성 시 `source_work_order_id` 가 있으면 **같은 오더의 살아 있는(보관 안 된) 공고**가 있는지 확인하고, 있으면 **409 `WORK_ORDER_CAMPAIGN_EXISTS`** + 그 공고 이름으로 거절한다(저장 화면이 오류 문구를 그대로 띄운다).
- ★ 확인과 저장은 **같은 오더끼리 직렬화**한다 — `pg_advisory_xact_lock(hashtext('recruit_campaign_wo:'||오더))` 를 쥔 트랜잭션 안에서 확인 → INSERT → COMMIT. 잠금 없이 확인만 하면 이번 사고처럼 거의 동시에 누른 두 생성이 둘 다 통과한다(실 PG 3건 동시 → 1건 저장·2건 거절 확인).
- ★ 보관(`archived_at`)된 공고는 세지 않는다 — 다시 모집할 길을 막지 않는다(막다른 길 방지). 오더 없이 만드는 공고는 종전 그대로(검사·잠금 없음, pool 경로).
- ★ **보관 해제도 같은 검사**(Codex PR #1632) — 보관 → 같은 오더로 새 공고 → 옛 공고 해제 = 살아 있는 공고 두 장(생성 검사 우회). `unarchiveCampaign` 이 같은 잠금 키(`workOrderCampaignLockKey`, 단일 출처)를 쥔 트랜잭션에서 다른 살아 있는 공고를 확인하고 있으면 409 `work_order_campaign_exists`. 해제의 다른 게이트는 여전히 없다(비상구).
- 삭제 뒤 재발행(`openRecruitModal` 404 → 신규) 은 삭제된 행이 없으므로 그대로 통과한다.
- 사각지대: 수정(PUT)의 `source_work_order_id = COALESCE($31, …)` 는 검사하지 않는다 — 화면은 수정 때 이 값을 보내지 않는다.

### 바로 구매 판정 기준 공고 — 임시저장은 후순위
- 같은 작업표에 공고가 여럿이면 바로 구매의 기준 공고는 "구매 시점에 있던 가장 최근 공고"였다 → 위 사고처럼 **1분 뒤 생긴 임시저장 공고**가 기준이 될 수 있었다(위반 표시가 리뷰어에게 열린 적 없는 카드에 붙는다).
- 순서를 단일 출처 `campaignAtPurchaseOrderSql()`(directPurchaseParticipation.service)로 모으고 **구매 시점에 있던 공고 우선 다음**에 `(rc.status IS DISTINCT FROM 'draft') DESC` 를 둔다. ★ 상태를 맨 앞에 두면 안 된다 — 상태는 나중에 바뀌는 값이라 옛 공고를 임시저장으로 되돌리는 순간 지난 구매의 기준 공고(인기 참여권 소비/적립)가 소급해 바뀐다(Codex PR #1632, 실 PG 확인). 규칙 판정(directPurchaseRules)과 인기 참여권 이벤트가 같이 쓴다 — 둘이 갈리면 위반 표시와 참여권 기준 공고가 달라진다.
- 정렬일 뿐 거르지 않는다 — 임시저장 공고뿐이면 그것으로 본다(판정이 "모름"으로 남지 않게).

## 사고 ② 수정요청 창 "로그인한 리뷰어의 제출 내역만 조회할 수 있습니다" (2026-10-14)
- 리뷰 내역(제출완료)에서 리뷰를 눌러 이미지 수정 창을 열면 403. 서버 데이터는 정상(본계정·타계정 번호 모두 그 리뷰어 소유, 행 소유 확인 통과 조건).
- 원인: 리뷰 내역 목록은 이 탭의 리뷰어(`getSavedUser().reviewerToken`)로 직접 부르지만, 수정 창은 `gasGet/gasPost` → `api.js _getAuthHeaders()` 가 **공용 리뷰어 세션 `rapp_reviewer_auth`**(구매양식·공고 화면과 같이 쓰는 값)의 토큰을 붙인다. 같은 브라우저 다른 탭에서 다른 사람으로 구매양식에 로그인하면 그 값만 바뀌어 화면은 A, 서버가 받는 사람은 B → `phone8` 이 세션 번호 목록에 없어 403.
- 규칙: `_reEditSyncSession()` — 창을 열 때와 **모든** 서버 호출 직전(파일 조회·교체 요청·취소·내 요청 내역 — Codex PR #1632)에 이 탭의 리뷰어로 공용 세션을 맞춘다(만료면 `_refreshReviewerHomeSession`). `goToSubmit` 과 같은 관용구(`syncSearchSession`). 화면 변화 없음.
- C/S 문의함(`csReviewerThreads`)은 세션이 아니라 phone8 로만 조회해 이 갈림과 무관.

## 완화 금지
- 생성의 같은 오더 확인을 잠금 밖으로 빼지 않는다(빼면 동시 생성이 둘 다 통과 — 이번 사고 그대로). 보관 해제의 같은 검사도 빼지 않는다.
- 바로 구매 기준 공고 순서에서 상태(draft)를 "구매 시점에 있던 공고"보다 앞에 두지 않는다.
- 바로 구매 기준 공고 순서를 두 곳에 따로 쓰지 않는다.
