# ★★ 작업오더 하나에 살아 있는 모집공고는 하나 · 수정요청 창 파일 조회는 화면의 리뷰어 토큰으로 (사용자 확정 2026-10-14 · 스키마 변경 0)

## 사고 ① 같은 작업으로 공고 두 장 (2026-10-13 · 신고 2026-10-14)
- "10/14 네이버 실배송 눈 or간 영양제 1BOX" 가 모집공고에 2장, 작업보드엔 1장.
- 운영 실측: 같은 오더 `wo_129486c43279` 로 14:47:02 담당자 A 가 생성·게시(`camp_da9e1876791f`), **1분 7초 뒤** 담당자 B 가 하나 더 생성해 임시저장(`camp_faf97b013ea3`). 둘 다 같은 작업표를 가리켜 카드 숫자(20/20 · 총 20/60)가 똑같이 보였다. 작업오더의 `linked_campaign_id` 는 A → 작업보드는 1장.
- 원인: 생성 라우트(`POST /admin/create`)에 "이 오더로 이미 공고가 있나" 검사가 없었다. 화면은 `linked_campaign_id` 가 있으면 만들기 버튼을 숨기지만 **열어 둔 옛 화면**은 못 막는다.
- 운영 전수: 오더 하나에 공고가 둘 이상인 경우는 이 1건뿐 — 정상 업무에서 같은 오더로 공고를 둘 만드는 쓰임은 없다.

### 규칙 — 단일 출처 `linkedRecruitQuota.service`
- `liveCampaignForWorkOrders(db, woIds, exclude)` — 그 오더에 짝지어진 **보관 안 된** 공고. 짝짓기는 기존 단일 출처 `LINKED_WO_ON`(역방향 `work_orders.linked_campaign_id` + 정방향 `source_work_order_id`) — 정방향만 보면 역방향으로만 이어진 옛 공고(067 백필 이전 모양)를 놓친다(Codex PR #1632).
- `lockWorkOrderCampaigns(db, woIds)` — `pg_advisory_xact_lock(hashtext('recruit_campaign_wo:'||오더))`, 여러 오더면 정렬·중복 제거(교착 방지). 키는 `workOrderCampaignLockKey` 한 곳.
- **생성**: `source_work_order_id` 가 있으면 잠금 → 확인 → INSERT → COMMIT 을 한 트랜잭션에서. ★ 저장하는 값도 잠그고 확인한 **정규화 값**(`_srcWoId`, 앞뒤 공백 제거) — 원문을 저장하면 다음 확인이 못 찾는다(Codex PR #1632). 있으면 409 `WORK_ORDER_CAMPAIGN_EXISTS` + 그 공고 이름(저장 화면이 오류 문구를 그대로 띄운다). 오더 없는 생성은 종전 pool 경로(검사·잠금 없음).
- **보관 해제**(`campaignArchive.unarchiveCampaign`): 보관 → 같은 오더로 새 공고 → 옛 공고 해제 = 살아 있는 공고 두 장(생성 검사 우회, Codex PR #1632). 해제 대상 행을 `FOR UPDATE` 로 잠그고, **이미 해제된(재시도)·없는 공고는 즉시 끝낸다**(계속 가면 그 사이 보관+새 공고가 끼었을 때 무검사 해제가 맞아떨어진다 — Codex PR #1632). 그다음 오더(`workOrderIdsForCampaign`, 정·역방향)를 같은 잠금으로 쥐고 다른 살아 있는 공고가 있으면 409 `work_order_campaign_exists`. 해제의 다른 게이트는 여전히 없다(비상구).
- 보관된 공고는 세지 않는다 — 다시 모집할 길을 막지 않는다(막다른 길 방지). 삭제 뒤 재발행(`openRecruitModal` 404 → 신규)도 그대로 통과.
- 실 PG 확인: 동시 생성 3건 → 1건 저장·2건 거절 / 역방향만 연결된 옛 공고 감지 / 보관 해제 거절→새 공고 보관 뒤 해제 허용 / 오더 없는 공고 해제 무변경.
- **작업오더의 연결 공고(역방향 링크)를 바꾸는 쓰기**(`PUT /api/order/admin/update`·`/admin/status`, Track B 위임 포함)도 같은 트랜잭션에서 `guardWorkOrderLinkChange` — 값이 실제로 바뀔 때만 오더 행 잠금 → 같은 잠금 → 다른 살아 있는 공고 있으면 409. 같은 값 재전송·미전송은 종전 그대로(상태 변경이 막히지 않게). 실 PG 확인(Codex PR #1632).
- **수정(PUT)은 작업오더 연결을 바꾸지 않는다** — `$31` 에 항상 null(=유지)을 넣고, 연결 탭 보정도 저장된 값만 쓴다. 바꿔 끼우면 잠금·확인 없이 같은 오더에 살아 있는 공고가 둘이 된다(Codex PR #1632). 화면은 원래 수정 때 이 값을 보내지 않는다.
- 사각지대: 역방향 링크가 새 공고로 옮겨 간 뒤 정방향이 빈 옛 공고를 해제하면 오더를 못 찾는다(그 오더와 더는 짝이 아니다).

### 바로 구매 기준 공고 순서 — 바꾸지 않는다(단일 출처로만 모음)
- 처음엔 "임시저장 공고 후순위"를 넣었으나 Codex 가 두 번 지적(PR #1632): `status`·`published_at` 은 **나중에 바뀌는 값**이라 순서에 넣으면 공고를 임시저장으로 되돌리거나 게시하는 순간 지난 구매의 기준 공고(인기 참여권 소비/적립)가 소급해 바뀐다. → 빼고 기존 순서(구매 시점에 있던 공고 → 가장 최근 → id) 그대로 둔다. 같은 오더 임시저장 사본은 위 생성 규칙이 원천 차단한다.
- 두 곳(규칙 판정 `directPurchaseRules`, 인기 참여권 `loadDirectPurchaseCreditEvents`)에 따로 쓰던 순서를 `campaignAtPurchaseOrderSql()` 한 곳으로 모았다(의미 불변).

## 사고 ② 수정요청 창 "로그인한 리뷰어의 제출 내역만 조회할 수 있습니다" (2026-10-14)
- 리뷰 내역(제출완료)에서 리뷰를 눌러 이미지 수정 창을 열면 403. 서버 데이터는 정상(본계정·타계정 번호 모두 그 리뷰어 소유, 행 소유 확인 통과 조건).
- 원인: 리뷰 내역 목록은 이 탭의 리뷰어(`getSavedUser().reviewerToken`)로 직접 부르지만, 수정 창 파일 조회는 `gasGet` → `api.js _getAuthHeaders()` 가 **공용 리뷰어 세션 `rapp_reviewer_auth`**(구매양식·공고 화면과 같이 쓰는 값) 토큰을 붙였다. 다른 탭에서 다른 사람으로 구매양식에 로그인하면 그 값만 바뀌어 화면은 A, 서버가 받는 사람은 B → 403.
- 규칙: `_reEditFetchMyFiles(c)` — 파일 조회(`/api/review-edit/my-files`, 창에서 세션을 보는 유일한 호출)를 **이 탭의 리뷰어 토큰을 직접 실어** 부른다(gasGet 과 같은 30초 제한 — 응답이 끊기면 오류로 끝난다)(만료면 갱신, 401 이면 갱신 후 1회 재시도 — 리뷰 내역·참여정보와 같은 관용구). ★ 공용 세션을 A 로 덮어쓰지 않는다 — 덮어쓰면 그 탭이 반대로 틀어진다(Codex PR #1632). 신원도 공용 저장소(`USER_KEY`)를 다시 읽지 않고 **이 탭에 그려진 목록의 주인**(`_reEditTabUser`, loadReviewList 가 기록)을 쓴다 — 다른 탭이 리뷰 내역에 B 로 로그인하면 `USER_KEY` 가 B 로 바뀐다. 토큰 갱신(`_refreshReviewerHomeSession`)은 `{ syncShared:false, persist:false }` — 공용 세션도 홈 신원 저장소도 쓰지 않고 새 신원만 메모리에 둔다(기본값은 종전대로 저장·동기화 — 다른 화면 무변경). 교체 요청·취소·내 요청 내역은 phone8 기반이라 무관. 화면 변화 없음.

## 완화 금지
- 같은 오더 확인을 잠금 밖으로 빼지 않는다(빼면 동시 생성이 둘 다 통과 — 이번 사고 그대로). 보관 해제의 같은 검사도 빼지 않는다. 짝짓기를 정방향만으로 좁히지 않는다.
- 바로 구매 기준 공고 순서에 `status`·`published_at` 같은 나중에 바뀌는 값을 넣지 않는다.
- 수정 창에서 공용 리뷰어 세션을 덮어써 맞추지 않는다.
