# ★★ 리뷰 캡처 업로드의 Drive 왕복 줄이기 — 줄일 것은 파일 크기가 아니라 말 거는 횟수 (2026-09-23 실측)

- **배경**: [169](169-리뷰-캡처-1차-필터가-배포-이래-한-번도-실행되지-않던-사고-preCtx-프리변수-2026-09-22.md)(1차 필터 복구)·[170](170-리뷰-캡처-축소는-긴-변-기준-사용자-확정-2026-09-22.md)(긴 변 축소) 로 제출이 **p50 9~12초 → 4.1초**가 된 뒤 남은 4.1초를 쪼갰다(실제 제출 4건 로그 타임스탬프 차).

- ★★★ **사진은 이미 165KB 인데 3.1초가 걸린다 — 대역폭이 아니라 왕복 지연이다**([008](008-Drive-이미지-프록시-왕복-1회-2026-08-24-실측.md) 과 같은 결론: Drive 는 크기와 무관하게 **왕복 하나당 0.8~1.5초**). 그래서 **사진을 더 줄이는 것은 효과가 거의 없고**(1200px 로 낮춰도 0.3초), 줄일 것은 **말 거는 횟수**다. 업로드 경로의 왕복 3회(폴더 조회·업로드·공개) 중 2회를 뺐다.
- **① 서브폴더 위치 캐시**(`getOrCreateSubFolder`): 같은 (부모, 이름) 을 매 요청 다시 묻지 않는다. ★ `findFolderByName` 은 **SA 로 먼저 묻고 못 찾으면 OAuth 로 한 번 더** 묻는 구조라 최대 왕복 2회였다. TTL 5분(`DRIVE_SUBFOLDER_TTL_MS`) · 상한 500 · 오래된 것부터 폐기.
  - ★★ **폴더가 지워지면 캐시가 죽은 ID 를 붙잡는다** — 그래서 업로드 실패 시 `invalidateSubFolderById(parentFolderId)` 가 **그 자리에서** 그 폴더를 가리키던 캐시를 버린다(다음 시도는 다시 찾거나 새로 만든다 = 자가치유). 캐시가 없으면 애초에 `createFolder` 로 자동 복구되던 경로라, **무효화가 없으면 캐시가 새로운 영구 실패 모드를 만든다**.
  - ★ 소비처 6곳(리뷰 업로드 슬롯·옵션, 교체요청 3, 차수 폴더) 공통 이득.
- **② 업로드 뒷정리를 응답에서 분리**(`uploadFileBase64(..., { deferShare: true })`): 공개 권한(`permissions.create`)과 소유권 보정은 업로드 결과(파일 ID·링크)에 **아무 영향이 없는데** 리뷰어가 그 왕복을 그대로 기다리고 있었다.
  - ★★★ **둘을 함께 미룬다** — 한쪽만 미루면 남은 쪽의 `await` 사이에 미룬 쪽이 끼어들어 **결국 기다린 셈**이 된다(회귀가드가 실행으로 잡았다. 테스트의 SA 경로에서 소유권 이전이 실제로 왕복하며 드러났다).
  - ★★ **완화 금지 — 미루기는 옵트인이다.** 인자를 안 주면 종전대로 기다린다. `deferShare` 를 **다른 업로드 소비처(가이드 이미지·문의 첨부·교체요청 등)에 붙이지 말 것** — 그쪽은 업로드 직후 곧바로 링크를 화면에 그리거나 외부로 보내는 경로라, 공개가 늦으면 **깨진 이미지가 그대로 나간다**. 회귀가드가 사용처 1곳을 고정한다.
  - ⚠ 공개가 늦어지는 동안(수백 ms)의 영향은 **구글 CDN 썸네일이 잠깐 우리 프록시로 폴백**하는 것뿐이다(008 — 화면은 계속 뜬다). 서버가 그 사이 재시작되면 그 파일만 비공개로 남는데, 프록시로는 계속 보인다.
  - ★ **폴더 공개 상속은 쓰지 않았다** — `createFolder` 가 폴더를 공개로 만들지 않아, 그 방식은 **폴더 목록 전체를 링크로 여는 범위 확대**가 된다(파일 하나씩 공개하던 것과 노출 범위가 다르다).
- ★ **AI 검수 0.14초 = 캐시 히트** — 169 로 되살린 첨부 시점 1차 필터가 실제로 제출 때 재사용되고 있다는 실측 증거다(123 의 "AI 콜 순증 0" 전제 회복).
