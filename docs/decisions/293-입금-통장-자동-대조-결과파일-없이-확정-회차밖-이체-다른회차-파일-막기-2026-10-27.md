# ★★★ 입금 통장 자동 대조 — 케이뱅크 거래내역으로 회차를 결과 파일 없이 확정 · 맞지 않는 금액만 '확인 필요' · 회차 밖으로 나간 돈 · 다른 회차 결과 파일 막기 (사용자 확정 2026-10-27 · migration 203)

## 왜
- 담당자가 리뷰웹 회차 밖에서 케이뱅크 대량이체 파일에 줄을 직접 넣어 보내 왔다. 결과 파일의 '미확인 이체'를 대조하지 않으면 그 사람이 다음 회차에 또 담겨 **두 번 나간다**(인트라넷 요청서 2026-10-26: 같은 이름·같은 금액 의심 27건 899,200원 · 9/3 29회차 낮 직접 이체 → 같은 날 30회차).
- 실측(운영 읽기 전용 2026-10-27):
  - 화면의 '미확인' 1,098건 중 **696건은 다른 회차에서 이미 paid 된 같은 이체**(계좌·금액·시각 5분 안) — 결과 파일을 엉뚱한 회차에 올린 탓. 76회차의 최신 업로드 = 78회차와 같은 파일(가짜 미확인 251건).
  - 10/19~26 케이뱅크 통장 대량이체 vs 회차 paid: **회차에만 있는 건 0건**(회차 기록은 전부 통장에 같은 금액·같은 시각 ±2분) · **통장에만 있는 건 103건 856.8만 원**(회차 밖 — 회차 파일에 끼워 같은 시각에 보냄).
  - 실패 11건(74·80·82회차) 중 9건은 같은 회차에 같은 금액을 받는 다른 사람이 있었다 → **통장만으로는 누가 실패했는지 모른다**(통장 대량이체 줄에는 받는 사람이 찍히지 않는다).
  - 82회차 실패 2건은 이체한 **같은 분(12:39)에 '취소'로 반환**됐다.
  - 78회차는 이체(10/21 14:51) 뒤 결과 반영까지 **이틀**(10/23 12:17).
- 사용자 확정: A.1 직접 이체는 앞으로 리뷰웹 회차 안에서(후속 작업) · B.1 「이미 직접 보낸 것 같음」은 처음부터 빼 두기 · 30일 · 개편안 진행.

## 무엇 (리뷰웹)
1. **통장 받기** `paymentBank.service.syncBank` — 팝빌 중계 서버(inadd-finance-server)에서 케이뱅크 최근 7일 거래내역(`/api/bank/collect` allPages)을 `X-Relay-Key` 로 받는다. 입금관리를 열 때 3분에 한 번(`payment_bank_sync` 칸을 조건부 UPDATE 로 잡아 동시에 두 번 받지 않음) · 「통장 확인」 버튼은 즉시.
   - 저장 `payment_bank_rows`(migration 203) = **시각·금액·구분(bulk_out/refund_in/other_out/other_in)·잔액뿐**. 받는 사람 이름·계좌·적요는 버린다(즉시이체 줄의 상대 이름 포함).
   - 덜 받음(truncated)·옛 중계 서버(allPages 없음)·모으는 중(202)·기간 조정 → 저장하지 않고 실패로 알린다.
2. **회차 대조** `reconcileBatch`(순수 계산) — 회차 만든 뒤 3일 안의 대량이체 묶음(3분 안에 이어 찍힌 출금) 중 금액이 가장 많이 겹치는 묶음(절반 이상)을 그 회차 이체로 본다. 다른 회차가 이미 그 시각에 paid 인 묶음은 제외.
   - 금액마다: 통장 건수 − 취소 반환(묶음 끝 30분 안) = 받은 건수. 회차 건수와 같으면 그 금액은 확정 · 모자라면 모자란 만큼 실패(누구인지는 모름) · **통장에 더 많이 찍혔으면(회차 밖 같은 금액 줄) 통장으로 정하지 않는다**.
   - 묶음 끝 10분이 지나야 확정(취소 반환 대기).
   - 결과 파일로 처리된 건이 하나라도 있으면 `file` — 그 회차는 결과 파일이 기준(통장으로 덮지 않음).
3. **확정** `confirmBatchFromBank` — 깨끗한 회차는 통장 받기 직후 자동 확정. '확인 필요' 회차는 담당자가 [통장 대조]에서 못 받은 사람을 고른다(금액마다 정확히 부족 건수 — 다르면 거부). 고르지 않고 확정하면 맞는 금액만 기록하고 나머지는 pending('확인 필요')으로 남긴다.
   - ★ 기록은 **결과 파일 반영과 같은 단일 경로** `paymentResult._commitBatchOutcome`(applyResultFile 에서 뽑아냄): 조건부 `status='pending'` UPDATE · recordDeposits · 작업보드 입금칸 · 실패 안내. `paid_at`/입금칸 날짜 = 통장 거래 시각. `result_status='통장 확인'`.
   - 회차는 남은 pending 이 0일 때만 `applied`(`markApplied:'when_done'`). 결과 파일 반영은 종전대로 항상 `applied`(파일에 없는 건 실패).
   - 기록 줄 `payment_result_uploads`(file_format='bank', summary.source='bank', 파일 없음) — 회차 목록이 '통장 확인'으로 보여 준다(`_batchView.resultSource`). 파일 미리보기(`getLatestResultPreview`)는 이 줄을 고르지 않는다. 바뀐 게 0이면 줄을 남기지 않는다.
4. **회차 밖으로 나간 돈** `outsideTransfers` — 최근 7일 대량이체 묶음 − 회차 paid(같은 금액·묶음 시각 ±2분) − 취소 반환. 처리 전 회차가 차지한 묶음·이체 직후 10분 묶음은 세지 않는다(거짓 알림 방지). 입금관리 맨 위에 날짜별로.
5. **다른 회차 결과 파일 막기** `_assertFileBelongsToBatch`(`_analyze` 안 — 미리보기·자동반영·저장본 반영 모두) — 파일 줄(계좌+금액)이 이 회차와 절반도 안 맞고 앞뒤 14일 안의 다른 한 회차와 80% 이상 맞으면 `wrong_batch` 로 거부. 두 회차를 한 번에 이체한 파일(각각 절반쯤)은 통과 · 5줄 미만은 판단하지 않음.

## 검증
- 운영 실데이터 재현(읽기 전용, 결과 파일이 없었다고 치고 74~83회차): 실패 없던 6개(75·76·78·79·81·83) = clean · 실패 있던 3개(74·80·82) = review 이고 **부족하다고 짚은 금액이 실제 실패 11건과 전부 같음**. 회차 밖 합계 103건 8,568,000원.
- `tests/paymentBank.test.js`(스텁 26) · `tests/paymentBankPg.test.js`(진짜 PG 22 — 자동 확정·원장·PAID·이중 기록 0·고르기 거부·회차 밖·목록 표시) · 기존 결제 테스트 27묶음 통과(`paymentResultApply` 가드는 개수 4→3, 의미는 "상태를 바꾸는 UPDATE 는 전부 pending 조건"으로 강화).

## 🚫 완화 금지
- **통장 확정은 `_commitBatchOutcome` 으로만 기록한다** — 따로 UPDATE·recordDeposits 를 쓰면 원장·입금칸·안내가 결과 파일 반영과 갈린다(가드 6a).
- **같은 금액이 회차보다 통장에 더 찍힌 금액은 통장으로 정하지 않는다** — 회차 밖 같은 금액 줄과 실패가 겹치면 받지 않은 사람을 '이체 완료'로 기록하게 된다.
- **묶음 끝 10분 전에는 확정하지 않는다** — 실패는 같은 분에 '취소'로 돌아온다.
- **결과 파일로 처리된 건이 있는 회차는 통장으로 덮지 않는다**(`file`).
- **통장 거래의 받는 사람 이름·계좌·적요를 저장하지 않는다.**
- **모르면 확정하지 않는다** — 통장을 못 받음·묶음을 못 찾음·덜 받음은 전부 그대로 pending.
