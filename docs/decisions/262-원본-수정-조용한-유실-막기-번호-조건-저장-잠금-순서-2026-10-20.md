# ★★★ 원본 수정의 조용한 유실 막기 — 같은 번호·다른 내용은 409 · 번호 조건 저장 · 잠금 순서 L1 먼저 (사용자 확정 2026-10-20 · 양방향 1단계 · 스키마 변경 0)

## 배경
리뷰오더(인트라넷) ↔ 모집공고(리뷰웹) 양방향 동기화 설계(레드·블루·심판 검토, 2026-10-19~20)에서 **지금 이미 있는 고장 두 가지**가 확인됐다. 사용자 확정: 양방향 7단계 중 이 1단계만 전수 시험 뒤 먼저 반영한다.

1. **조용한 유실** — 인트라넷은 전송에 실패한 번호를 다시 쓴다(`api.ts` createReviewOrderSourceRevision). 첫 시도가 실제로는 리뷰웹에 반영됐는데(커밋 뒤 오류·15초 시간초과) 담당자가 내용을 고쳐 다시 저장하면, 종전 재시도 키(`원본ID:번호`)가 같아 리뷰웹이 "이미 처리됨 = 멱등 성공"으로 답했다 → **새 수정은 리뷰웹에 안 갔는데 인트라넷은 "전송됨"**.
2. **확인과 쓰기 분리** — 원본 수정은 잠금 없이 읽고, 번호 조건 없이 UPDATE 했다. 같은 번호 요청 두 건이 동시에 오면 둘 다 "+1" 검사를 통과해 나중 것이 앞 것을 덮었다.
3. **잠금 순서 반대** — 공고 쪽 인원 동기화는 공고 행 → 오더 행, 오더 쪽은 오더 행 → 공고 행 순이라 동시에 돌면 교착(40P01). 로컬 실 PG 실측: 두 처리를 40회 엇갈려 돌리면 **교착 6회**(수정 후 0회).

## 동작(리뷰웹)
- `PUT /api/order/intake/source/:id`·`POST /api/order/intake`: 같은 원본·같은 번호인데 키(=인트라넷이 내용 해시를 붙인 키)가 다르면 **409 `code:'revision_already_applied'`**(멱등 성공으로 접지 않는다). 더 옛 번호 = `revision_stale`, 건너뛴 번호 = `revision_gap`. 같은 번호·같은 키 = 종전대로 멱등 성공.
- 부분 수정·전체 수정 UPDATE 둘 다 `AND COALESCE(source_revision,0) = <읽은 번호>` 조건. 0행이면 `_sourceRevisionRaceResponse` — 다시 읽어 같은 시도면 멱등 성공, 아니면 409(`revision_already_applied`/`revision_race`). 0행을 성공으로 접지 않는다. 전체 수정은 0행이면 인원 동기화 전에 끝낸다.
- 잠금 순서 = **L1(`recruit_campaign_wo:<오더>` 오더 단위 권고 잠금) → 행 잠금**:
  `assertWorkOrderQuota`·`syncWorkOrderRecruitTotal`·`syncCampaignRecruitTotal`(잠그기 전 짝을 읽어 L1, 잠근 뒤 짝이 바뀌었으면 `recruit_quota_link_changed`)·`guardWorkOrderLinkChange`(같은 값은 잠그지 않은 선읽기로 빠른 통과 유지)·`unarchiveCampaign`(바뀌면 `link_changed_retry`)·`syncCampaignPayAmount`·`syncCampaignThumbnail`·`syncCampaignInflow`·`syncCampaignPurchaseWindow`.
- L1 을 쥔 트랜잭션(공고 생성·연결 변경·보관 해제)은 전부 커밋한 뒤에 위 함수들을 부른다(자기 대기 없음, 2026-10-20 호출부 전수 확인).

## 동작(인트라넷 — inadd-webapp 같은 날 짝 PR)
- 재시도 키 = `원본ID:번호:내용해시32`(요청자 칸 제외 정렬 직렬화 SHA-256). 리뷰웹 형식 검사(160자·`[A-Za-z0-9:_-]`) 통과.
- 409 `revision_already_applied` 를 받으면 **번호 +1 로 최신 내용을 한 번 다시 보낸다**(조용히 버리지 않는다). 아웃박스 'sending' 은 60초 임대(영구 고착 방지).

## 배포 순서·스큐
- 리뷰웹 먼저 → 인트라넷. 새 리뷰웹 + 옛 인트라넷: 키가 종전 형식이라 동작 종전과 같음(유실은 인트라넷 배포 뒤 해소). 옛 리뷰웹 + 새 인트라넷: code 가 없어 자동 재전송이 일어나지 않음(종전과 같음).
- 스키마 변경 0 → 코드 되돌리기만으로 복귀.

## 남은 위험(의도적으로 두는 것)
- 인원 동기화가 공고 행을 잡은 **뒤에** 작업표 탭 잠금(`sheetless_worktable:`)을 잡는 순서는 종전 그대로다(결정 182 「탭 잠금은 첫 잠금」 규칙과 어긋나는 기존 경로). L1 은 탭 잠금을 잡는 구매 기록 경로가 쓰지 않는 잠금이라 이번 변경으로 교착 고리가 새로 생기지는 않는다 — 양방향 3·7단계에서 다룬다.

## 완화 금지
- **같은 번호·다른 키를 멱등 성공으로 접지 않는다** — 접으면 "실패 뒤 고쳐 다시 저장"한 수정이 조용히 사라진다.
- **원본 수정 UPDATE 의 번호 조건과 0행 처리를 빼지 않는다** — 빼면 동시 요청이 서로 덮는다.
- **오더·공고를 함께 잠그는 트랜잭션은 L1 을 먼저** — 행 잠금 뒤에 L1 을 잡으면 교착한다.
