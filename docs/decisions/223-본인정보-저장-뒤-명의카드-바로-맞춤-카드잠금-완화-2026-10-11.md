# ★★ 본인 정보를 바꾸면 명의 카드도 바로 맞춘다 · 카드 맞추기 잠금 완화 (신원 기준 3-2 · 2026-10-11 · 스키마 변경 0)

## 왜
- 결정 221 기준: 명의 = 카드. 1단계부터 참여·주문이 카드 번호를 기록하고, 4단계부터 입금·내역이 카드를 읽는다.
- 그런데 **본인 정보(주소·계좌·소득명의)와 가입**은 카드를 바로 맞추지 않고 10분 거울(`reconcileCards`)을 기다렸다.
  - 새 가입자는 최대 10분 동안 본인 카드가 없다 → 가입 직후 첫 참여에 카드가 기록되지 않는다(결정 221 1단계의 빈틈).
  - 4단계에서 입금이 카드를 읽으면, 계좌를 바꾼 직후 10분 동안 옛 계좌를 읽을 수 있다.
- 3단계 계획의 "직접 쓰는 5곳을 창구로 옮기기"는 조사 결과 **4곳이 이미 창구와 같은 잠금·카드 즉시 맞춤**을 하고 새 타계정을 만들지 않아 옮길 이득이 작았다(손대는 코드만 늘어 위험) — 대신 **실제로 카드를 늦게 맞추는 5곳**만 고친다(사용자에게 보고한 조정안).

## 결정
- `reviewerIdentityCards.syncOwnerCardsSoon(ownerId)` — 저장이 확정된 **뒤** 그 리뷰어 한 명만 맞춘다. 기다리지 않고, 실패는 삼킨다(10분 거울이 맞춘다). 한 사람분 짧은 트랜잭션: 잠금 상한 2초 · 리뷰어 행 `FOR NO KEY UPDATE`(reconcileCards 와 같은 규율).
- 부르는 곳: 가입 INSERT(새 본인 카드) · `saveIncomeInfo` · `saveBankInfo` · `saveAddress`(`RETURNING id` — phone8 범위면 해당 행 전부) · 관리자 외부 주문의 빈 칸 채우기(트랜잭션 밖일 때만 — 커넥션이면 확정 전이라 건너뜀).
- **카드 맞추기의 카드 행 잠금 `FOR UPDATE` → `FOR NO KEY UPDATE`**: 182 이후 참여·주문 기록이 외래키로 카드 행에 `FOR KEY SHARE` 를 잡는다. `FOR UPDATE` 는 이와 충돌해 카드 맞추기와 참여 카드 기록이 서로 기다렸다(레드팀 7). 카드 맞추기는 키(id)를 바꾸지 않으므로 `FOR NO KEY UPDATE` 로 충분하다(카드 맞추기끼리는 여전히 줄을 선다).
- **참여하기의 안전망(Codex P2)**: 바로 맞추기가 늦거나 실패한 채 가입 직후 참여하면 참여 기록 카드가 비어 남는다 — 그래서 apply `card_bind` 가 카드를 못 찾으면 **그 자리에서 `syncCardsAfterWrite`(자체 SAVEPOINT · throw 없음)로 한 번 맞추고 다시 찾는다**. 실패하면 종전처럼 비워 두고 참여는 계속.
- 카톡 아이디·관리자 메모·리뷰어 번호는 카드 칸이 아니라 대상이 아니다. 직접 쓰는 나머지(쇼핑 아이디·명의 주소·입금 계좌 보완·번호 변경·이름 변경)는 이미 카드를 즉시 맞춘다.

## ★★ 완화 금지
- ① 카드 바로 맞추기를 저장 트랜잭션 안으로 넣거나 await 하지 말 것 — 카드 맞추기 장애·잠금 대기가 저장을 깨거나 늦춘다.
- ② 카드 행 잠금을 다시 `FOR UPDATE` 로 올리지 말 것 — 참여·주문의 카드 기록(외래키)과 서로 기다린다.
- ③ 외부 주문이 트랜잭션 커넥션으로 부를 때 바로 맞추기를 돌리지 말 것 — 확정 전 값을 읽고 그 행 잠금을 기다린다.
