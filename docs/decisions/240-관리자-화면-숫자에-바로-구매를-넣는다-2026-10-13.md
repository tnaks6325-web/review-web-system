# ★★ 관리자 화면 숫자에 바로 구매를 넣는다 — 공고 카드 회차 진행 · 홈 "오늘 참여 확정" · 참여 관리 머리줄 · 상품별 현황표 (사용자 확정 2026-10-13 · 스키마 변경 0)

## 배경
- 결정 238(참여 규칙)·239(하한) 다음 단계 ② 화면 숫자. 사용자: "커져 보이는 것보다 실제 숫자가 중요". 날짜 기준 = **구매양식 제출 시각(KST)** (사용자 확정).
- 조사(2026-10-13): 공고 카드 회차 진행("1차 6/700 · 총 6/750")·홈 "오늘 참여 확정"·참여 관리 머리줄/상품별 표가 `campaign_applications` 만 셌다.
  카드의 "총 N/정원"(작업표 채운 줄)·오늘 게이지(작업표)·날짜별 창(무시트 작업표 채움)은 이미 바로 구매를 포함했다.
  운영 활성 참여형 공고 12곳은 전부 무시트 작업표라 날짜별 창은 이미 실제 값 — 시트 작업용으로 누적 합계만 보완.

## 결정 — 셈은 정원 엔진 하나
- `quotaFloor.confirmedWithDirect(counts)`(순수 함수) — `fetchCampaignCounts` 결과로 `total = max(제출 확정, 연결 주문)` · `today = max(오늘 확정, 오늘 연결 주문)`.
  `attributable=false`(공유 작업표·연결 없음·조회 실패·원장 셈 꺼짐) 면 공고 참여만. 결정 239 하한(`campaignUsedFloor`)도 이 함수를 쓴다(+ 홀드).
- `quotaFloor.optionDirectOrderStats` — 상품별 바로 구매 {누적, 오늘}. 하한과 같은 셈(공고 참여 주문의 수동 중복 제외).

| 화면 | 서버 칸 | 화면 |
|---|---|---|
| 공고 카드 회차 진행·폴백 분자 | `ops.totalConfirmedAll` · `directCountable` · `directShared` (종전 `totalConfirmed` 유지) | 새 칸 우선, 없으면 종전(배포 스큐) · 공유 작업은 툴팁에 "나눌 수 없어 공고 참여만" |
| 홈 "오늘 참여 확정" | `ops.todayConfirmedAll` | 공고별 합산 — 공유 작업은 서버가 공고 참여만 실어 이중 합산 없음 |
| 참여 관리 머리줄 | `GET /admin/:id/applications` → `directSummary{countable, shared, todayDirect, totalDirect, totalConfirmed, byOption}` | "· 바로 구매 오늘 N / 누적 M (확정 합계 누적 K)" · 공유 = "나눌 수 없음" |
| 상품별 현황표 | `directSummary.byOption` | 오늘 제출·누적 확정 = 공고 참여 + 바로 구매, 옆에 "(바로 n)" |
| 날짜별 창 누적(시트 작업) | `getPlanOverview` `progressSource='applications_and_orders'` | 무시트 작업은 종전(작업표 채움) |

- 실패는 null/종전 값으로 접는다(화면은 공고 참여만 그리고, 머리줄에 바로 구매 문구가 없다 = "모름"을 0 으로 꾸미지 않음).

## 완화 금지
- ★★ 화면 숫자의 바로 구매 셈을 새로 만들지 않는다 — `confirmedWithDirect`/`optionDirectOrderStats`(= 정원 엔진)만 쓴다. 화면마다 셈이 갈리면 카드·하한·참여 판정이 서로 다른 숫자를 말한다.
- ★ 종전 칸(`ops.todaySubmitted`·`ops.totalConfirmed`)을 지우지 않는다 — 구버전 화면 호환과 "공고 참여만" 진단에 쓴다.

## 한계 · 남은 것
- 상품별 표의 "상태"(마감 등)는 참여 판정 엔진 값 그대로라, 공고 참여 주문을 수동으로 또 넣은 중복(운영 22건)을 두 번 센 상태일 수 있다(결정 239 참고). 엔진 쪽 정리는 별도 결정.
- 참여자 목록에 바로 구매한 사람 줄을 넣는 것(③)·관리자 인기 참여권 집계(④)는 다음 단계.
