# ★★ 구매양식 구매일자는 항상 서버의 오늘(KST) — 리뷰어 휴대폰 시계를 쓰지 않는다 (사용자 확정 2026-10-14 · 스키마 변경 0)

## 발단 (사용자 신고 2026-10-14)
- 「닥터메이트 비타민C 30포, 1개」(camp_d7c85f4e5d86, 하루 10명) 관리자 카드가 **"표 9 / 10 · 진행중 0"인데 "오늘 모집 완료"**.
- 운영 읽기 조회: 오늘 공고로 제출 확정된 신청 = **10건**(정원 도달 → `daily_done` 은 정상).
  카드 분자(작업표 오늘 채움 = `review_index.start_date` 가 오늘인 줄)는 **9**. 빠진 1건(신청 16109, 0시 14분 43초 KST 제출)의
  `order_submissions.date_str` 이 **`10 / 13 (화)`** — 전날로 적혔다(그래서 10/13 은 11줄).
- 원인: 구매일자 `dateStr` 를 **리뷰어 화면이 `new Date()`(기기 시계·기기 시간대)로 만들어 보내고**, 서버는 비어 있지 않으면 그대로 썼다(결정 215).
  기기 시계가 늦거나 시간대가 KST 가 아니면 자정 직후 제출이 전날이 된다. 같은 시각대 다른 9건은 정상.
- 최근 30일 리뷰어 제출 4,427건 중 불일치 1건(이 건). 드물지만 자정 오픈 공고에서 재발 가능.
- 실제 참여 게이트는 `max(공고 확정, 작업표 채움)` 이라 정원 초과·미달은 없었다. 틀어진 것은 표시 숫자·날짜별 줄 수·구매일 기준 일정(리뷰 미작성 알림 등).

## 결정
- `POST /api/submit/order` 의 구매일자 = **항상 `manualOrder.todayKstDateStr()`**(관리자 수기 주문과 같은 함수 · 사본 금지).
  화면이 보낸 `dateStr` 는 판정에 쓰지 않고, **다르면 로그만** 남긴다(`[submit/order] 화면 구매일자(...)가 서버 오늘(...)과 달라`).
- 하루 정원(`kstTodayStr`)·작업표 오늘 채움·구매일자가 **같은 서버 시계**를 본다.
- 프론트는 바꾸지 않는다(옛 화면·새 서버 모두 같은 결과 — 배포 스큐 무관).
- 이미 잘못 적힌 1건(신청 16109 / 작업표 55행)은 이 변경으로 고쳐지지 않는다(데이터 정정은 별도 판단).

## 입구 전수
- 리뷰어 구매양식 2곳(`search-app.js`·`index-app.js` → 둘 다 `submitOrderForm` → `/api/submit/order`) — 모두 "제출 시각의 오늘"을 보내던 것이라 의미 불변.
- 관리자 외부모집 수동제출(`manualOrder`)은 이미 `todayKstDateStr()`.
- 같은 날 중복 판정(`orderDuplicate`)은 원장 저장값(orderData)끼리 비교 → 서버 날짜로 일관.
