# ★★ 리뷰 캡처 축소는 **긴 변** 기준 (사용자 확정 2026-09-22)

- **발단**: [169](169-리뷰-캡처-1차-필터가-배포-이래-한-번도-실행되지-않던-사고-preCtx-프리변수-2026-09-22.md) 로 AI 검수 5초를 제출 경로에서 뺀 뒤에도 **Drive 업로드 3~9초**가 남았다. 원인은 사진 크기 — 축소 판정이 **가로 폭만** 봤다(`width > maxPx`).
- ★★ **리뷰 캡처는 세로로 긴 모바일 스크린샷**(예 1080×2400)이라 가로가 상한(1920)보다 작아 **축소가 한 번도 걸리지 않았다**. 1MB 초과면 JPEG 재인코딩만 되고 **해상도는 원본 그대로** 올라갔다.
- **확정**: **긴 변 1600px**(품질 0.75 는 종전 그대로 — 한 번에 두 축을 흔들면 화질 문제의 원인을 못 가린다).
- ★★ **축척 계산 단일 출처 = `ImageShrink._scale(w, h, maxPx, longest)`**(`js/image-shrink.js`). `fromDataUrl`·`fromFile` 이 같은 규칙을 쓴다.
  - ★★★ **`longest` 미지정 = 가로 기준 = 기존 동작 그대로** — 이 기본값이 무회귀의 근거다. **구매 캡처 소비처 3곳**(업로드 `1920/0.8` · 배치 축소본 `1080/0.6` · 리뷰어 홈 보완 `1920/0.8`)은 인자를 안 넘겨 **바이트 불변**.
  - ★★ **구매 캡처에 `longest` 를 붙이지 말 것(완화 금지)** — 그쪽은 주문번호·수취인·주소를 AI 가 읽는 경로다(EXTRACT_PROMPT 기준샘플 4종). 해상도를 낮추면 **돈·배송과 직결된 판독**이 흔들린다. 회귀가드가 세 호출에 `longest` 부재를 고정한다.
- ★ **바뀌는 것은 리뷰 캡처 첨부 경로 하나**: `compressImage`(= `addFiles`·`_mrAddFiles`·`_csAddFiles` 공용) → `ImageShrink.fromFile(file, 1600, 0.75, { longest: true })`. 값은 `REVIEW_CAPTURE_MAX_PX`/`_QUALITY` 상수 단일 출처.
- ★ **폴백(모듈 미로드)도 같은 상한·같은 긴 변 기준** — 축소가 통째로 빠지면 큰 캡처가 서버 본문 상한(10MB)에 걸려 **증빙만 조용히 빠진다**(`image-shrink.js` 주석의 그 사고). 축소 실패는 원본으로 접는다(첨부를 막지 않는다).
- ★ **1MB 이하 JPEG 는 손대지 않는다**(양쪽 유지) — 재인코딩은 화질만 깎고 그 크기는 이미 빠르다.
- **실측**(실 오리진에 수정본 주입 · 1080×2400 합성 스크린샷): PNG 782KB → 종전 규칙 **341KB(1080×2400)** / 새 규칙 **193KB(720×1600)** = **−43%**. `_scale` 검증 = 긴 변 0.667배 · 가로 기준 1.000배(종전 버그 재현) · 상한 안 1(확대 없음).
- ⚠ **이 값은 AI 판정의 입력 화질이기도 하다** — 1차 필터·2차 검수가 같은 이미지를 읽는다(상품명·리뷰 본문·채널 단서 OCR). **더 낮추기 전에 실물 캡처로 확인**할 것. 되돌리기는 `REVIEW_CAPTURE_MAX_PX` 한 줄.
- 회귀가드 `tests/captureLongestSideShrink.test.js`(12 — `_scale` vm 실행 · 긴 변 배선 · 폴백 동일 기준 · **구매 캡처 3소비처 `longest` 미부착** · 작은 JPEG 무손상, **변이시험 6종 검출 확인**). 관련 기존 가드 34개 전부 통과.
