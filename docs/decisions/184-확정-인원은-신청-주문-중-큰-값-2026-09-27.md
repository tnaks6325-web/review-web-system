# ★★★ 확정 인원 = 신청·주문 중 큰 값 — 남은 자리·이월·예상 종료일·작업표 날짜 (사용자 확정 2026-09-27)

## 발단
- [183](183-이월은-남은-자리를-넘지-않는다-2026-09-26.md) 조사 중: "이미 모집한 인원"이 두 기록에서 갈린다.
  - **신청 기록**(`campaign_applications`) = 공고에서 자리를 잡고 구매양식까지 낸 사람만.
  - **주문 기록**(`order_submissions`) = 공고를 거쳤든 안 거쳤든 구매양식이 제출된 모든 건(대신 제출·외부 모집·늦은 구매 포함).
- [031](031-모집-누적-정원의-표주문-원장-기준-전환-2026-08-20-작업보드-169-vs-카드-49-신고.md) 이후 **총원 마감**은 두 기록 중 큰 값(`table_over_total`),
  **하루 인원·이월·예상 종료일·작업표 날짜**는 신청 기록만 — 같은 공고의 숫자가 판단마다 달랐다.
  운영(2026-09-27, 보관 아닌 20개): 15개 공고에 차이(면마스크 신청 49 vs 주문 168 · 모집 중은 업소용 간장 39).
- 결과: 예상 종료일이 늦게 나오고, 작업표 날짜 맞추기가 "줄 모자람"을 말하고, 공고 밖 주문이 그날 인원에 안 들어가
  **연 자리보다 더 들어온 날**이 생긴다(시뮬레이터로 D·A·B·C 비교 후 사용자가 A 선택).

## 결정
- `fetchCampaignCounts` 깔때기(`_mergeCountBasis`)에서 **구간마다 신청·주문 중 큰 값**으로 합친다:
  어제까지 확정(`submittedBeforeToday`) · 이월 기준선 이후(`carry.submittedSince`) · 보류 기준선 이후(`hold.submittedSince`).
  → 남은 자리(총량 clamp)·이월·앞날 예상(`projectDailyQuotas`)·조절 창·작업표 날짜 맞추기가 같은 값을 본다(소비처 호출부 변경 0).
- ★★ **오늘 확정(`todaySubmitted`)은 합치지 않는다**(레드팀 · 완화 금지): 신청 게이트는 이미 작업표 오늘 채움(`tableTodayFilled`)으로
  공고 밖 참여를 오늘 인원에 센다. 합치면 ① 탭 공유 공고의 오늘 합산(`campaign.routes._groupedTableTodayCounts` · `trackB` 오늘 참여현황)이
  공고마다 합친 값을 **다시 더해** 같은 주문을 두 번 센다(보관했지만 active 로 남은 옛 공고가 같은 탭을 쓰면 18명째 하루 마감)
  ② 주문만 저장되고 홀드가 남은 건(홀드 확정 실패)이 주문·홀드 양쪽에서 오늘 두 번 세진다 ③ 카드에 "오늘 60 / 누적 49" 가 뜬다.
- ★ **표 기준 게이트가 켜졌을 때(`CAMPAIGN_TABLE_QUOTA=on`, 기본)만** 합친다 — observe 에서 합치면 총원 마감은 신청 기준인데
  하루 인원만 0 으로 잘려 매일 "내일 다시 오픈"으로 영구히 잠긴다(031 "on 은 사람이 결정" 우회).
- 주문 구간 수는 `_loadLinkedOrderCounts` 가 신청 집계와 **같은 시간 경계**(KST 오늘 0시 · 066 이월 기준선 · 098 보류 기준선)로 센다.
  주문 좌표 합집합·앵커(시작일)·삭제 제외는 031 그대로. 캐시(10초)는 같은 구간 키일 때만 쓴다(자정 경계).
- 원래 신청 수는 `counts.applications` 에 보존, `counts.countBasis='max'`.
- 끄는 스위치: `CAMPAIGN_COUNT_BASIS=applications`(env 만 — 즉시 종전).

## 바꾸지 않는 것(완화 금지)
- ★★ `submittedAll` 은 합치지 않는다 — soft_full(`usedAll`) 재료. 주문 기준 마감은 `table_over_total`(비영속) 경로가 맡는다(031 두 경로 분리).
- ★★ `maybePersistClosed`(마감 영속)는 자기 SQL 로 신청만 센다 — 주문 기준 마감은 **영속하지 않는다**(주문 취소 시 자동 재오픈 · 031).
- ★ 공유 작업표(한 탭에 활성 공고 둘 이상)·탭 없음·조회 실패는 합치지 않는다 — 주문이 어느 공고 것인지 모른다(정원을 좁히지 않는다).

## 잔여(문서화)
- 옛 공고가 마감(closed)된 뒤 같은 탭에 들어온 늦은 탭 주문(새 공고 시작일 이후)은 새 공고의 "어제까지 확정"에 들어간다 —
  총원 마감(`table_over_total`)이 031 부터 이미 같은 재료로 세던 것과 같다(공유 판정은 active 공고만 센다).
- 대신 제출(수동제출)은 주문 기록과 신청 확정이 다른 트랜잭션이라 자정 직전 1건이 구간이 갈릴 수 있다(하루 1건 이내·다음 날 해소).
