# ★★ 여러 명의 차례 타이머 — 한 명의씩 시간이 흐르고, 대기 명의도 자리를 잡아 둔다 · 본계정 기본 20분 (사용자 확정 2026-11-06·09 · migration 217·218)

## 무엇
- **R1 본계정 20분**: 본계정 제한시간 기본값을 30분에서 20분으로 바꾼다. 서버 기본값은 `campaignHoldChain.MAIN_HOLD_TTL_DEFAULT_MIN` 하나이고, migration 218 이 DB 기본값도 20으로 맞춘다.
  - 기존 공고 중 **30분(또는 비어 있음)인 공고만** 20분으로 바꾼다(답 20). 60분처럼 일부러 다르게 정한 공고는 그대로 둔다.
  - 바꾸기 전 값은 `campaign_hold_ttl_backup_218` 에 남긴다.
  - 운영 실측(2026-11-09, 참여형 공고 기준): 30분 155건(그중 모집 중 17건) · 20분 2건 · 60분 2건(마감) · 15분 1건(임시저장).
  - 관리자 화면의 시간 칸은 지금처럼 숨긴다(답 21).
- **R2 차례 타이머**: 「타계정 허용」 공고(블로그·Q&A·네이버+쿠팡 동시진행 제외 — 답 22)에서 새 화면이 `sequential:true` 를 보낸 참여만 차례 줄에 선다.
  - 진행 중인 명의는 한 번에 하나다. 나머지는 **대기 명의**다.
  - 대기 명의도 `status='applied'` 이고 **실제 미래 마감 시각**(예상 마감 = 앞 명의 끝 + 자기 시간, 마감 시각에서 자름)을 가진다. 그래서 살아 있는 자리를 판정하는 20여 곳은 하나도 고치지 않는다.
  - 칸은 두 개만 더한다. `turn_starts_at`(내 차례 시작)과 `chain_ttl_min`(참여 시점 내 시간)이다.
- **끝남 처리**: 제출 확정, 관리자 확정(같은 명의 선-취소 포함), 담당자 수동·외부 확정, 리뷰어 취소가 일어나면 `pullChainEarlierSafe` 가 뒤 명의의 시작과 마감을 **앞으로만** 당긴다.
  - 만료에는 훅이 없다. 다음 명의의 예상 시작이 곧 앞 명의의 마감이다.
  - R3: 대기 명의가 미리 제출해도 제때 제출로 받는다.
  - R4: 직원이 확정해도 다음 명의 시간이 시작된다.
- **R5 마감 기준(답 17·18·24)**: 기다리는 명의는 자기 차례가 시작될 때 마감까지 **10분 이상** 남아야 받는다.
  - 기준 = `min(상태 엔진 cutoffAt, closesAt − 10분)`.
  - `close_buffer_min` 이 0인 공고에도 최소 10분을 적용한다.
  - 지금 바로 시작하는 첫 명의는 종전 cutoffAt 만 본다.
  - 넘치는 명의는 `/apply` 가 409 `chain_after_close` 로 **그 명의만** 거절하고, 자리를 잡지 않는다.
  - 마감 시각이 되면 종전과 같이 모두 끝난다. 30초 처리 유예도 그대로다.
- 하루 종일(시간창 없는) 공고의 차례는 자정을 넘어도 이어진다(답 24②). 진행 중에 「1인 1회」로 바뀌면 대기 명의는 정해진 시각에 시작한다(답 24③).

## 왜 이렇게(레드-블루-심판 · scratch `stage3/`)
- "앞 명의 마감을 복사"하는 방식은 버렸다. 1분 스윕이 같은 틱에 뒤 명의도 만료시켜 자리를 잃고, 거짓 "지각"이 생긴다(RED-02).
- 마감을 NULL 로 두거나 자리표시 시각으로 두는 방식도 버렸다. 20여 곳이 자리가 없다고 보고 정원 초과가 생기기 때문이다(RED-01).
- 앞당기기만 하는 이유: 끝남 처리가 실패하거나 빠져도 예상 마감대로 흐르면 되고(넉넉하고 끝이 있다), 시간이 늘어나는 일은 생기지 않는다(RED-07).
- 옛 화면(`sequential` 없음)은 종전 동시 시간으로 처리한다. 옛 화면이 자기 시계로 토큰을 지우는 사고를 막기 위해서다(RED-05).
- 화면 쪽(차례 표시·예상 시간·잠금·토큰 삭제 규칙)은 별도 PR 로 켠다. 서버만 먼저 나가면 바뀌는 것은 본계정 20분뿐이다.

## 끄는 스위치(Railway 환경변수 · 재시작)
- `CAMPAIGN_HOLD_CHAIN=0` — 새 차례 줄을 만들지 않는다(`holdChain=false`).
- `CAMPAIGN_HOLD_CHAIN_PULL=0` — 앞당기기를 끈다. 차례는 예상 시각대로 흐른다.

## 되돌리기
- 코드 되돌리기 = 서버는 새 칸을 무시하고, 대기 행은 보통 홀드처럼 예상 마감에 끝난다. 굳는 행은 없다.
- 데이터 20분은 코드를 되돌려도 남는다. 원래 값 복원은 218 의 주석 SQL 로 하며, 사장님 확인을 받은 뒤에만 한다. 칸은 지우지 않는다.

## 완화 금지
- 🚫 대기 명의를 새 상태값이나 NULL·자리표시 마감으로 만들지 말 것 — `applied` + 미래 `expires_at` 이어야 한다.
- 🚫 끝남 처리에서 마감을 **늦추지 말 것**(앞당기기만). 당기기는 `SAVEPOINT hold_chain` 안에서만 하고, 던지지 않는다 — 실패가 제출 확정이나 취소 결과를 바꾸면 안 된다.
- 🚫 차례 줄은 `sequential:true` + 서버가 알린 `holdChain` 일 때만 만든다. 옛 화면 요청에 차례를 적용하지 말 것.
- 🚫 차례 거절 기준은 상태 엔진 `st.cutoffAt` 과 `closesAt − 10분` 이다. `close_buffer_min` 사본 계산을 따로 두지 말 것.
- 🚫 화면은 서버 판정 없이 로컬 시계만으로 홀드 토큰을 지우지 말 것(화면 PR).
