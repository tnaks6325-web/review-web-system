# ★★ 작업보드 문자 — 같은 참여건·같은 번호로 같은 글을 10분(설정) 안에 다시 보내지 않는다 · 키(결정 364)와 무관 · 두 담당자가 동시에 눌러도 공급자는 한 번 · 번호 advisory 잠금(lock_timeout 5초) 안에서 창 판정 → '대기' 줄 선점 → COMMIT → 공급자 호출(잠금 밖) · 막힌 사람만 빠지고 나머지는 나간다 (사장님 확정 2026-11-10 · 스키마 변경 0 · migration 171·222 재사용 · 결정 365 「하지 않은 것」 ㉯ 채택)

## 무슨 일이었나
- 작업보드 [문자·알림톡 보내기]의 **문자**(결정 196)는 결정 364 로 「같은 키」 다시 보내기만 막았다. 키가 다르면(두 담당자, 창을 새로 열어 새로 쓴 같은 글, 새로고침 뒤), 키가 없으면(구버전 화면) **같은 사람에게 같은 문자가 그대로 두 번** 나갔다(돈 두 번 · 받는 사람은 같은 문자 두 통).
- 결정 365 「하지 않은 것」이 이를 **정책의 부재**로 적고 ㉮ 그대로 / ㉯ 같은 사람·같은 글 N분 안 다시 보내기 막기 / ㉰ 경고만 을 물었다 → **사장님이 ㉯ 를 골랐다(2026-11-10).**

## 규칙
1. **같은 대상 = 같은 참여건(sheet_id·tab_name·participant_id) + 같은 받는 번호(숫자만)**. 번호가 같아도 **참여건이 다르면(본계정·타계정이 각자 참여한 줄 등) 따로 보낸다** — 사장님 확정 2026-11-10("타계정이라도 번호가 같다 → 참여건을 구분해야"). 잠금은 번호 단위 그대로(같은 번호 요청은 줄 세움). (같은 요청 안의 같은 번호 두 줄은 이 규칙과 별개로 종전처럼 「같은 번호에 이미 보냈습니다(한 번만 발송)」 — merged, 결정 196.)
2. **같은 글 = 실제로 나가는 최종 글**(`composeSms` 결과 = 안내 문구 포함 · 화면 문안의 상품명 자리까지 채워진 글)을 `trim()` 후 `/\s+/g → ' '` 로 본 것. 글자 하나라도 다르면 다른 글 → 보낸다.
3. **창 = 10분(기본)** · 환경변수 **`MANUAL_SMS_SAME_TEXT_WINDOW_MIN`**(Railway → 서비스 → Variables · 바꾸면 서비스가 다시 뜨며 반영). `0` = 규칙 끔 · 비었거나 잘못된 값·음수 = 10(보호를 끄지 않는 쪽) · 소수는 내림 · 상한 1440. 이 저장소의 발송 관련 조정값(`REVIEW_REMINDER_RETRY_HOURS` 등)과 같은 모양이다(`app_settings` 화면 없음).
4. **막는 앞선 기록** = 창 안의 `manual_message_sends`(kind='sms') 중
   - `send_state` = `sent`(보냄) · `pending`(보내는 중 — 2분 넘으면 「결과 모름」 문구) · `unknown`(시간 초과·끊김 — 받았을 수 있음)
   - 종전 경로 기록(`send_state` NULL · 배포 직전 기록)은 `accepted = TRUE` 만.
   - **막지 않음** = `failed`(공급자가 거절했다고 답함 · 요청 전 오류) · 종전 기록 `accepted = FALSE`.
   - 창의 시각 = `COALESCE(send_state_at, created_at)`(마지막 시도 시각).
5. **모든 수동 문자 경로에 적용** — 새 화면(키 있음) · 구버전 화면(키 없음) · 다른 담당자. 키 없음도 이제 **공급자 부르기 전에 '대기' 줄을 넣는다**(`client_send_id` NULL · 결과로 sent/failed/unknown). 키 없음의 화면 문구는 종전 그대로(결과 모름도 「문자 발송 실패 — 사유」).
6. **동시에 두 요청 — 한 번만** (`manualMessage.service` `_claimSmsTx` · 결정 364·365 와 같은 「선점 → 호출」 모양):
   - `BEGIN` → `SET LOCAL lock_timeout = '5s'` → `pg_advisory_xact_lock(hashtext('manual_sms_same_text'), hashtext(번호))` → (같은 키 줄 확인) → 창 판정 → '대기' 줄 INSERT(키 있음 = 364 `_claim` 그대로) → `COMMIT` → **공급자 호출은 COMMIT 뒤(잠금 밖)**.
   - 둘째 요청은 첫째의 COMMIT 을 기다린 뒤 그 '대기' 줄을 보고 보내지 않는다(「보내기 시작해 아직 처리 중」).
   - 잠금 대기 5초 초과(55P03) → 그 사람은 **보내지 않음** + `manual_sms_busy`. 창 조회·선점 실패(스키마 문제 아님)·연결 못 얻음 → 보내지 않음(364 ⑤ 「기록을 남기지 못해」 · fail-closed).
   - 두 키 advisory 잠금 = 한 키(bigint) 잠금(`purchaseCaptureLock`)과 키 공간이 겹치지 않는다. 같은 두 키 형태인 작업 잠금(`withJobLock` · 자체 해시)·증빙 해시 잠금(`hashtext('dual_evidence_sha')`)과는 **첫 키가 다르다**(가드가 확인 · 겹쳐도 5초 상한).
7. **같은 키 다시 보내기는 364 가 우선** — 자기 키 줄이 이미 있으면(`failed` 제외) 창 판정을 하지 않고 364 결과(보냄=`duplicate:true` · 결과 모름 · 처리 중)를 그대로 돌려준다. 자기 키 줄이 `failed` 면 창 판정을 한다(그 사이 다른 담당자가 같은 글을 보냈으면 막는다).
8. **여러 명** — 막힌 사람만 그 사유로 빠지고 나머지는 나간다(사람마다 판정).
9. **마이그레이션 222 전 DB**(칸 없음 42703 · 색인 없음 42P10) → 경고 로그 「발송 선점 색인 없음 — 종전 경로(같은 글 막기 없음)」 후 종전 경로(보내기는 살린다). 실제로는 222 칸이 `REQUIRED_SCHEMA` 에 있어 칸 없이 부팅하지 않는다.

## 화면에 나가는 말(결과 목록 `r.reason` · 화면 코드 수정 0)
- 보냄: `이 참여건에 같은 문자를 {N분 전에|방금} 보냈습니다 — 두 번 나가지 않게 이번에는 보내지 않았습니다. 꼭 다시 보내야 하면 {M}분 뒤에 보내거나 내용을 고쳐 주세요`
- 보내는 중: `이 참여건에 같은 문자를 {N분 전에|방금} 보내기 시작해 아직 처리 중입니다 — (같은 꼬리)`
- 결과 모름: `이 참여건에 같은 문자를 {N분 전에|방금} 보냈는데 결과를 확인하지 못했습니다(이미 받았을 수 있습니다) — (같은 꼬리)`
- 잠금 대기 초과: `같은 번호로 문자를 보내는 다른 요청이 처리 중입니다 — 두 번 나가지 않게 이번에는 보내지 않았습니다. 잠시 뒤 창을 다시 열어 확인한 뒤 보내 주세요`
- N = 지난 분(내림, 1분 미만 = 「방금」) · M = 남은 분(올림, 최소 1). 응답 가산 필드 `results[].code` = `manual_sms_same_text_window` | `manual_sms_busy`.
- 화면 키(364)는 「모두 보냄」이 아니므로 그대로 남는다 → M분 뒤 같은 창에서 다시 보내면 이미 받은 사람은 duplicate, 막혔던 사람에게만 간다.

## 소비처 전수
- 문자 공급자 호출(`solapi.sendSms`)은 `manualMessage.service` 한 곳(키 경로 1 · 종전 경로 1). **자동/크론 문자는 없다** — 크론(`/review-reminders/run`)은 알림톡(`sendReviewAlimTalk`)만. 알림톡은 이 규칙 밖(결정 365 가 회차로 막는다 · `kind='sms'` 만 본다).
- `manual_message_sends` 읽기: 키 경로 4문장(364) + 창 조회 1(이번) · 작업 삭제 보존 목록(`workTabDelete`) — 화면 0, `SELECT *` 0.
- `/workdesk/manual-send` 를 부르는 화면 = `_msSendConfirmed` 1곳 — `results[].reason` 을 그대로 그린다(새 필드 불필요).
- 기존 가드 갱신(검사 의미 불변): `manualMessageSend.test.js`(정규식 db 에 트랜잭션 연결 흉내 추가 — 발송 기록 1줄·누가·무엇을 그대로) · `manualMessageSendIdempotency.test.js`(PGlite 트랜잭션 줄 세우기 추가 · 「키 없음 = 두 번 발송」은 창 끔(0)에서 확인 + 창 켬이면 막힘 1건 추가 · 「새 키 = 새로 보냄」은 글을 다르게 · 정적 순서 가드는 `_claimSmsTx` → `_claim` 로).

## 배포 순서
- 구버전 화면 + 새 서버: 키가 없어도 서버가 막는다(이 변경의 목적) · 막힌 사람은 결과 목록에 사유.
- 새 화면 + 구버전 서버: 종전 그대로(화면 변경 없음).
- 스키마 변경 0 → 마이그레이션 순서 문제 없음. 되돌리기 = 코드만 되돌리면 종전(키 없음은 발송 뒤 기록 · 같은 글 막기 없음). 이번 코드가 키 없음으로 넣은 `send_state` 줄은 종전 코드가 읽지 않는다(무해).

## 완화 금지
- **창 판정을 번호 잠금 밖으로 빼거나, '대기' 줄 선점을 공급자 호출 뒤로 옮기지 않는다** — 두 담당자가 둘 다 「없음」을 보고 둘 다 보낸다(같은 문자 두 통 · 돈 두 번).
- **공급자 호출을 잠금(트랜잭션) 안으로 넣지 않는다** — 공급자 응답(최대 수십 초) 동안 그 번호의 다른 발송이 5초 뒤 전부 「처리 중」으로 떨어진다.
- **`pending`·`unknown` 을 막지 않는 쪽으로 접지 않는다 · 잠금 대기 초과·창 조회 실패를 「보냄」이나 「막힘 없음」으로 접지 않는다** — 받았을 수 있는 문자를 또 보낸다.
- **키 없음(구버전 화면)을 이 판정에서 빼지 않는다** · **같은 키 다시 보내기의 364 결과(duplicate)를 막힘 사유로 바꾸지 않는다**.
- 가드: `server/tests/manualSmsSameTextWindow.test.js`(PGlite 실제 SQL · 실제 라우트 · 공급자 흉내로 호출 수 · 정적 순서 가드 · `SMS_WINDOW_NATIVE_PG_TEST=1` 이면 실제 PostgreSQL 에서 둘째가 번호 잠금을 실제로 기다리고(`pg_blocking_pids`) 5초 넘으면 55P03 으로 「처리 중」).

## 하지 않은 것 · 남은 판단
- **조정값을 화면에서 바꾸는 곳은 없다** — Railway 변수로만(바꾸면 서비스 재시작). 담당자가 자주 바꿔야 하면 `app_settings` + 관리 화면이 필요(사업 판단).
- **같은 글 판정은 글자 그대로**(공백만 무시) — 문안의 상품명 한 글자, 마침표 하나만 달라도 다른 글로 보고 보낸다(「내용을 고쳐 주세요」 안내가 이 성질에 기댄다).
- **번호 색인 없음** — 창 조회는 표 전체를 훑는다(운영 약 250줄 · 1년이면 수천 줄 · ms 단위). 수만 줄이 되면 `regexp_replace(target_phone…)` 식 색인 또는 숫자 번호 칸을 더하는 migration 을 검토.
- 막힌 뒤 「그래도 보내기」 버튼은 없다(의도) — 꼭 보내야 하면 M분 기다리거나 글을 고친다.
