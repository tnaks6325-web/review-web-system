# ★★ 공유용 공고 목록(recruit.html) — 통신 실패는 실패로(15초 제한 · 쉬운 한국어 상자 + [다시 불러오기] · 「없습니다」는 진짜 빈 목록만 · 다시 받다 실패하면 보던 목록 유지) · 탭은 받아 둔 목록으로 다시 그리기만(카드 두 벌 없음) · 카운트다운 0 은 비우지 않고 바꿔 끼움(스크롤 자리 유지) (2026-11-27 · 스키마 변경 0 · 서버 변경 0)

## 무슨 일이었나 (모집안내 점검 2026-11-27 · H1 · M4 · M5)
- **H1** 공유용 공고 목록(`recruit.html`)만 결정 359(리뷰어 홈)의 통신 실패 규칙이 빠져 있었다.
  - 서버가 500·200+`{ok:false}` 를 주면 `json.data || []` 로 접혀 **「현재 모집 중인 캠페인이 없습니다 · 잠시 후 다시 확인해주세요」** — 공고가 열려 있어도 리뷰어는 「없구나」 하고 떠난다.
  - 서버가 대답하지 않으면 「캠페인 목록을 불러오는 중입니다...」가 끝나지 않았다(시간 제한 0).
  - 처음부터 끊기면 「불러오기 실패: Failed to fetch」(아이폰 「Load failed」) — 영어.
  - 한 번 뜬 뒤 탭을 눌렀을 때 끊기면 **탭 아래가 텅 빔** — 오류 문구를 첫 성공 때 숨긴 칸(`rcLoading`)에 썼다. 머리의 「진행중 12건」은 그대로 남았다.
- **M4** 탭마다 목록을 새로 부르고 늦게 온 응답도 지금 탭 기준으로 **덧붙였다**(`appendChild`) → [블로그]→[리뷰]를 빨리 누르면 13장이 26장(크롬·웹킷).
- **M5** 카운트다운이 0 이 되면 `container.innerHTML = ""` 로 목록을 먼저 비우고 응답을 기다렸다 → 문서가 짧아져 아이폰(웹킷)에서 스크롤이 **맨 위(0)** 로 잘렸다.

## 규칙
1. **목록 조회 도우미 `_rcFetchList`(recruit.html 안 하나)** — 리뷰어 홈 `_rhFetchJson`(결정 359)과 같은 판정: `AbortController` **15초**(공고 화면 결정 397 과 같은 값 · 본문 읽기까지) + `!res.ok || !json || json.ok === false || json.error` 면 던진다. 목록 주소(`/api/campaign/list`)를 부르는 곳은 이 도우미 안 한 곳뿐(가드가 센다).
   - `_rhFetchJson` 은 index.html 인라인이라 이 화면에서 닿지 않는다 — 같은 판정의 **사본**이다. 두 화면이 판정을 바꿀 때는 함께 바꾼다(장기적으로 목록 그리기를 홈과 한 벌로 — 점검 보고 H1 「고치는 방향」).
2. **문구는 api.js `apiFriendlyErrorMessage` 단일 출처**(결정 359) — `_rcErrMsg` 가 부르고, 옛 api.js 캐시면 「잠시 후 다시 시도해 주세요.」(무응답이면 「응답이 늦어지고 있어요…」)로 접는다. `e.message` 를 그대로 보이지 않는다.
3. **실패 상자 `#rcError`** = 「캠페인 목록을 불러오지 못했습니다」 + 쉬운 사유 + [다시 불러오기]. 「현재 모집 중인 캠페인이 없습니다」(`#rcEmpty`)는 **응답을 받았고 그 탭에 공고가 0개일 때만**. 실패 상자일 때 머리 건수는 비운다(빈 목록일 때도 비운다 — 종전 첫 화면과 같고, 다른 탭의 「진행중 N건」이 남지 않는다).
4. **받아 둔 응답(`_rcLastJson`)이 있으면 다시 받다 실패해도 보던 목록을 지우지 않는다**(카운트다운 0 · 신청 뒤 새로고침 — 남은 자리 수만 잠시 옛 값). 홈 결정 359 규칙 4와 같다.
5. **탭은 받아 둔 응답으로 다시 그리기만** — 서버를 다시 부르지 않는다(홈과 같은 방식). 첫 응답을 기다리는 중이면 「불러오는 중」 그대로 두고 도착하면 지금 탭으로 그린다(재요청 없음). 처음 불러오기가 실패한 뒤 탭을 누르면 다시 불러온다(불러오는 중 → 목록 또는 실패 상자 — 빈 화면 없음).
6. **요청 번호 `_rcLoadSeq`** — 마지막 요청의 응답만 그린다. 늦게 온 옛 응답(성공·실패 모두)은 버린다.
7. **그리기 `_rcRender` 는 새 내용을 조각(fragment)에 다 만든 뒤 한 번에 바꿔 끼우고**, 바꾸기 전 스크롤 위치가 달라졌으면 되돌린다. 카운트다운 0 콜백은 `loadCampaigns()` 만 부른다(먼저 비우지 않는다).

## 소비처 전수(grep)
- `loadCampaigns` 부르는 곳 4곳 — 첫 로딩(DOMContentLoaded) · `setRecruitKind`(이제 받아 둔 응답이 없을 때만) · 신청 뒤 새로고침(`submitApplication` — 먼저 비우던 줄 삭제) · 카운트다운 0(`CampCards.startTicker` 콜백). 다른 파일은 이 함수들을 부르지 않는다(index.html 의 `setRecruitKind`·mockups 의 `loadCampaigns` 는 각 페이지 자기 것).
- 응답에서 읽는 칸은 종전 그대로(`data[].participation_mode·status·state·work_kind` · `serverNow` · 옛 방식 카드 칸). 같은 날 공개 목록 칸을 줄이는 다른 작업(campaign.routes.js)과 겹치지 않는다 — 옛 방식 카드가 `manager` 등을 못 받으면 그 칸만 안 그려진다(종전 `_buildCard` 그대로).

## 완화 금지
- 🚫 공유 목록의 조회 실패(500·200+{error}·끊김·무응답)를 「현재 모집 중인 캠페인이 없습니다」로 접지 않는다 · 목록 조회 시간 제한(15초)을 빼지 않는다 · 영어 `e.message` 를 화면에 그대로 쓰지 않는다.
- 🚫 다시 받다 실패했을 때 보던 목록을 지우지 않는다 · 카운트다운 0·신청 뒤 새로고침에서 목록을 **먼저 비우고** 응답을 기다리지 않는다(아이폰 맨 위로 튐).
- 🚫 탭 전환 때 서버 응답을 목록에 **덧붙이지** 않는다 — 받아 둔 응답으로 다시 그리거나, 다시 부르면 마지막 요청만 그린다(`_rcLoadSeq`).
- 🚫 실패 문구를 숨겨진 칸에 쓰지 않는다 — 실패 상자(`#rcError`)는 그 자리에서 보인다.

## 하지 않은 것 / 확인 못 한 것
- 탭을 바꿔도 서버를 다시 부르지 않으므로, 오래 켜 둔 목록은 카운트다운 0·신청·[다시 불러오기] 전까지 옛 숫자다(홈과 같다 — 점검 M1 「자동 새로고침 없음」은 이번 범위 밖).
- 다시 받다 실패했을 때 「낡은 목록」 표시는 없다(홈과 같은 조용한 유지).
- 다시 그릴 때 카운트다운 칸이 첫 1초 동안 `--:--:--` 로 보이는 것은 카드 모듈의 종전 동작(이번 변경 무관).
- 실제 휴대폰(아이폰 사파리·안드로이드 크롬)에서는 돌리지 않았다 — 시나리오 작성 + `node --check` 만. 운영 서버의 502 페이지 CORS 머리 유무도 확인 못 함(그 경우 브라우저는 끊김으로 보고 → 「인터넷 연결이 불안정해요」).
- 운영에서 이 페이지를 누가 얼마나 여는지는 모른다(결정 186 50번 「판정 불가」와 같음).
