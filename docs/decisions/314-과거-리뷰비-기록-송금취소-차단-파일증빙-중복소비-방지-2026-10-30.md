# 과거 리뷰비 기록은 송금·취소 금지, 은행 증빙은 파일 지문+결과 행으로 한 번만 소비 (2026-10-30)

## 승인·범위
사용자 「안전장치보완 포함해서 진행해」 및 이미 지급한 누룽칩 1차 리뷰비 22건 정리 승인. 새 송금·이체 파일 생성/다운로드·알림·은행 동기화·제품비 기록 변경은 금지. 다른 8명, 2차 작업, 원본 결과 파일/기존 회차, 설정을 보존한다. 서버 전용 변경이며 화면/스키마/설정 추가는 없다.

## 사전 충돌 및 선택
기존 일반 미확인 승인 경로는 리뷰비 전용이 아니어서 제품비 완료 표시를 바꾼다. feeOnly 원장 함수만 두 번 호출하면 두 번 INSERT한다. 적용 완료 회차도 다운로드는 가능하다. 업로드 ID별 검토 유일키만으로는 동일 파일 재업로드를 막지 못한다. 따라서 기존 함수의 feeOnly 분기를 재사용하는 별도 기본 dry-run 운영 도구와 공유 증빙 가드를 함께 배포한다. 제품비/리뷰비 판정(292), 리뷰비 날짜 읽기(299), 은행 집계(293/302)는 복제하지 않는다.

## 서버 안전장치
- 기존 historical_key의 `historical-fee:` 접두 회차만 historyOnly. 잘못된 접미어도 차단한다. 기존 manual-811 및 일반 회차는 동일.
- 실제 다운로드 라우트가 영수증/계좌 조회·buildWorkbook 전에 거부한다. 직접 markDownloaded, 취소, 결과 업로드/반영, 수동 대조, 완료/실패 상태 변경, 날짜 백필도 거부한다. 작업표 제품비 비우기·pending 이름 변경 경로에서도 해당 항목은 건드리지 않는다.
- 「입금 기록까지 삭제」도 이 과거 증빙은 지울 수 없다(일반 작업의 기존 별도 확인 정책은 불변). 작업 삭제와 복구가 같은 두 칸 advisory 작업 잠금을 사용하여 삭제가 먼저면 복구가 현재 원본 부재로 거부하고, 복구가 먼저면 삭제가 history_only로 거부한다. 숨기려면 기존 마감 기능을 사용한다.
- `paymentProof.service`의 계약: lockUploadProof로 저장 원본 바이트/SHA 확인 → lockFileProof(기존 hashtext(SHA) advisory 잠금) → assertProofUnused → 원본 회차 행 잠금. 모든 돈 기록 소비자가 같은 잠금 순서를 사용한다.
- 같은 SHA의 모든 업로드에서 일반 검토 예약, 계좌/금액 불일치 대조, 실제 paid 결과 행, historical-fee source_key를 확인한다. 다른 결과 행을 소비했다는 이유만으로 이 행을 소비했다고 보지 않는다. 하나라도 충돌하면 일반 반영도 부분 쓰기하지 않고 전체 거부한다.
- 자동 업로드의 기존 파일 전체 중복 방지 정책은 유지한다. 직접 반영에도 행 단위 증빙 검사를 추가한다. 새 적용 이력은 원본 바이트·SHA를 보존한다.
- 통장 확인용 file_format=bank는 파일 증빙이 아니다. SHA 없는 옛 이력은 원본이 있을 때 해시를 유도한다. 원본도 SHA도 없는 관련 없는 옛 이력을 임의로 같은 파일로 간주하여 모든 새 지급을 막지 않는다. 그런 이력을 선택해 돈 기록을 만들려 하면 거부한다. 소실된 옛 파일의 동일성을 복구했다고 주장하지 않는다.

## 운영 복구 계약
`server/scripts/restore-historical-fees.js`: 기본 dry-run, 저장소 밖 private manifest·700 디렉터리·600 파일만 허용. 실제 쓰기는 정확한 manifest SHA, 최신 dry-run beforeHash, 실행 코드 release SHA, 지정 DB host를 요구한다. 자격은 환경으로만 전달하고 stdout은 건수/합계/해시/작업 ID만 출력한다.

`historicalFeeRestore.service`: 원본 파일 재해석, 정확한 참가자 ID→유일한 원본 주문→현재 행/전화/소유자, 당시 주문 계좌/예금주, 활성 직원 비고, 성공/금액/실제 이체시각을 모두 재검사한다. 원본 리뷰비 스냅샷이 NULL이면 NULL 그대로 대조한다. 현재 계좌로 당시 증빙을 덮어쓰지 않는다. 레거시 신원 NULL도 그대로 유지한다.

하나의 제한시간 있는 SERIALIZABLE transaction에서 SHA 잠금→원본 회차→대상 참가자/주문/검색행/비고 및 설정 잠금. 기존 기록·다른 곳의 같은 계좌/금액/시각 기록·모든 증빙 소비를 검사한 뒤, 최초 INSERT 직전 전체 보호 대상 snapshot을 fsync 백업한다. 적용 후 같은 snapshot에서 정확한 신규 항목/원장/예약만 제외한 보호 해시가 같아야 COMMIT한다. 부분 복구는 거부, 완전히 같은 복구만 건너뛴다. 커밋 후 새 transaction의 dry-run으로 다시 읽는다.

새 전용 applied 회차/paid 항목/feeOnly 원장/기존 검토 예약만 생성한다. 제품비 0, 리뷰비/총액 1000, paid_at은 은행 증빙 시각, 다운로드 0. 원본 업로드와 원본 회차 항목은 변경하지 않는다. `account_source` CHECK는 self/sub만 허용하므로 NULL 유지, 당시 ORDER 출처·파일 SHA·행·주문·참가자·새 항목·source_key를 review_note 구조화 감사기록에 명시한다. self/sub로 위조하거나 migration을 추가하지 않는다. 계좌 지문은 기존 canonical 함수를 쓴다.

## 검증
- 운영 읽기 전용 dry-run: 공식 파서 118 성공 행 중 정확한 22건, 합계 22,000원, 추가 INSERT 0. 개인 금융 자료는 저장소 밖에만 보존.
- 후보 검증: 삭제/명의/원본 계좌/금액/시각/중복/비고 철회/업체 비고 거부, 현재 계좌 변경이 옛 주문 증거를 바꾸지 않음.
- PGlite: 실제 SQL dry-run, 백업 전 쓰기 0, 네 쓰기 경계마다 전체 rollback, 적용·완전 재시도·부분 충돌·같은 파일 다른 업로드 거부, 보호 해시 유지.
- 별도 임시 PostgreSQL: SHA 잠금의 실제 다중 연결 대기(pg_stat_activity)와 동시 복구에서 한 번만 생성, 재시도 skip 확인. 운영 DB/자격 미사용. 임시 DB는 종료·제거.
- 실제 등록된 다운로드 handler: 파일 생성 전에 history_only, 직접 취소·다운로드 기록도 거부.
- 외부/실제 PostgreSQL 차단 전체 검사 663 passed, 0 failed (검증 로그는 private scratch). 독립 읽기 전용 보안·금전 검토 must-fix 없음. 운영 적용 전 최종 코드에서 재검사한다.

## PR #1727 추가 검토 보완
- 같은 회차에 서로 다른 파일이 적용됐을 때 줄 번호가 다시 1부터 시작한다. paid 항목을 회차+줄만으로 모든 파일의 소비로 분류하지 않고, 공식 파서로 해당 파일의 계좌·금액·이체시각을 대조한다. 다른 계좌/금액은 미사용으로 남긴다. 같은 계좌/금액인데 이체시각이 다르거나 없으면 다른 파일의 돈이라고 단정하지 않고 invalid_evidence로 보류한다.
- 여러 행의 증빙 검사는 `assertProofRowsUnused` 한 번으로 수행한다. 원본 바이트/해시 확인 1회, 예약/paid/원장 조회는 요청 행 수와 무관한 6개 쿼리. 500개 실제 파서 행으로 원본 조회 1회·쿼리 6개 이하를 검증했다. 단건 승인도 같은 실행부를 쓴다.
- 실제 fsync 백업의 Buffer JSON 되읽기를 복원하여 저장 전후 해시를 검증한다. 원본 파일 바이트는 백업에 남긴다. 임시 파일 실제 생성·600 권한·create-only·해시 왕복 시험을 추가했다.
- 보호 전체 검사 665 passed, 0 failed. 원래 결함 재현 RED 후 수정 GREEN, 일회용 PostgreSQL 경합·기존 회귀·운영 읽기 전용 22건 dry-run을 재확인했다.

## 완화 금지
- 기록 전용 회차에 송금 파일 생성·취소/잠금 해제·일반 결과 반영을 허용하지 않는다.
- 원본 파일 지문과 결과 행 소비 검사를 업로드 ID만으로 되돌리지 않는다. SHA→회차 잠금 순서 유지.
- 이미 지급한 리뷰비 복구에 제품비 PAID/입금 칸을 쓰거나 기존 이체 회차에 줄을 추가하지 않는다.
- 백업·동일성·소유자·beforeHash 실패/부분 복구를 성공으로 접지 않는다. 조회 실패를 0건으로 가정하지 않는다.
- 금융 기록을 코드 revert와 함께 자동 삭제/환불하지 않는다. 복구 취소는 별도 승인과 후속 변경 점검이 필요하다.

## 배포·롤백
main PR로 서버 안전장치를 먼저 배포하고 해당 머지 SHA의 Cloudflare/Railway 신호를 확인한 다음 별도 승인된 운영 복구를 실행한다. 화면 변경 없음. 코드 revert만 하면 영구 보존한 historyOnly 지급 기록의 다운로드 방어가 없어지므로 복구 후에는 이 방어를 보존하는 수정으로 대응한다. 실제 송금/알림/은행 동기화는 도구에 없다.
