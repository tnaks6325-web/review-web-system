# 리뷰검수 2단계 — 상품·옵션 의미 비교와 과거 판정 우회 차단

## 승인과 범위

- 2026-10-30 사용자의 「남은 2단계 진행해」로 기준 강화 승인. 500g 기준에 400g이 명확하면 불일치, 용량이 안 읽히면 미확인, 두 경우 모두 사진 제출은 허용한다.
- 일반 리뷰의 상품명 비교와 기존 관리자 상품명 자동후보가 같은 `utils/reviewProductEvidence.js`를 사용한다. 새 AI 호출·패키지·마이그레이션·새 worker는 없다.
- 구매 선택 검증(`productCaptureMatch`), 영수증 지급 조건, 업로드 입구, 반려·통지·사진 이동/삭제, 프론트 화면은 변경하지 않는다. 1단계(결정 310)의 unknown/RETURNING 계약을 유지한다.
- 최초 사전 점검: 기존 지도와 소스에서 비교·군집 관련 8호출, 규칙 1호출, 기준 조회 5호출, 저장 2호출을 계수하고 사용자에게 16곳을 보고했다. 서로 다른 용량/연식의 일반 pass, 선두 소수 손실, 역순 수량 거부를 격리 실행으로 재현했다.

## 재현한 문제

1. 일반 판정은 부분 포함/앞 6자 일치로 400g과 500g을 pass로 만들었다.
2. 선두 목록번호 정리에서 `0.5L`의 `0.`이 사라져 `5L`과 같은 군집·자동후보가 됐다.
3. 엄격 판정의 숫자열은 `50ml 2개`와 `2개 50ml`를 다르게 보면서 숫자 역할·모델 접미·포장 관계를 충분히 구분하지 못했다.
4. 기준과 별칭을 합친 후보에서 옛 별칭이 현재 용량 충돌을 회피할 수 있었다.
5. JS의 옛 pass 규칙과 SQL의 `product_resolution` 보존이 새 conflict/insufficient를 다시 정상 종결로 덮을 수 있었다.
6. 군집 첫 행만 확인해 같은 옛 키에 묶인 다른 소수 용량까지 승인할 수 있었다. 승인 이후 대상/증거가 바뀌어도 키만으로 token이 같았다.
7. 작업오더의 옵션 label을 버린 이름만으로 양쪽이 같으면, 실제 옵션이 없는 상품인 것처럼 확정할 수 있었다.

## 단일 의미 비교 계약

- `compareReviewProduct`는 `match / conflict / insufficient`, 사유, 원문 후보, 역할별 축, 버전, 원문 signature와 의미 signature를 반환한다. 버전은 `review-product-evidence-v2`다.
- 목록번호는 `1. `처럼 뒤 공백이 있는 경우만 제거한다. 소수·큰 정수는 숫자 변환의 반올림을 피하는 문자열 단위 환산으로 비교한다.
- 모델 전체 토큰을 단위 판독 전에 보호한다. `AB100ML`은 독립적인 100ml 용량으로 환산하지 않는다. 모델 접미 문자·연식·농도·단위 용량·개수는 별도 축이고 중복을 보존한다.
- 역할이 확정된 축의 순서만 무시한다. 총량을 곱해서 다른 포장을 같은 옵션으로 만들지 않는다. 포장 관계·잔여 숫자·불완전/음수/0·소수 개수가 애매하면 insufficient다.
- 정리된 본체명이 정확히 같고 전체 식별축이 증명돼야 match다. 긴 공통 문구의 96% 유사도가 무향/유향 등 실제 변형 차이를 가리는 것이 재현돼, 유사도만으로 본체 차이를 오타로 간주하는 통로는 제거했다. 유사도·길이비는 진단값으로 유지하며 별칭이나 홍보문구 제거가 식별축 누락·충돌을 상쇄하지 못한다.
- 숫자 역할만 정렬해 구성품 연결을 추측하지 않는다. 같은 역할의 여러 값 또는 여러 본체 조각 사이에 숫자·모델·연식·농도가 끼어 연결이 불명확하면 insufficient다. 다른 역할의 용량/질량·용량/개수 뒤바뀜도 포함한다. 하나의 연속된 본체 전후로 전체 용량·개수 역할만 재배치한 정상 사례는 유지한다.
- `score`는 정규화된 본체명의 실제 Dice, `rawScore`는 원문 정리 후의 실제 문자 Dice다. 같은 용량의 단위 환산·역순 표기를 문자 차이로 오해하지 않으며, 원문 유사도를 거짓 100%로 바꾸지 않는다.
- 일반 wrapper는 match만 pass, conflict는 warn이다. 다른 본체명은 기존 상품명 의심 흐름을 유지하는 warn+unknown, 누락·기준 부재 등은 skip+unknown이다. 명시적 불일치와 정보 부족은 구별하고 모두 제출을 막지 않는다.

## 기준 출처와 정보 손실

- `loadTabExpectations`는 구 소비처용 merged `productNames`와 수동/파생 우선순위를 유지하면서 `primaryProductNames`, `productAliases`, `productCriteriaIncomplete`를 분리한다.
- 수동 기준을 최우선으로 쓰고, 파생 시 구조화된 이름이 있으면 잘린 자유서술 조각을 새 canonical 근거로 추가하지 않는다. 별칭만 있으면 canonical은 빈 목록이다.
- 구조화 옵션 label이 본체명에서 사라졌거나 여러 상품/옵션인데 행별 선택 근거가 없으면 불완전 기준으로 표시한다. 선택한 옵션을 추측하지 않는다. 자유서술 추출에서 빠진 의미 있는 꼬리·깨진 JSON도 정상 증거로 쓰지 않는다.
- 공식 `orderProductSummary.productSummaryText`로 원문을 글자까지 재현한 경우, 머리글·모집인원·소계는 숨은 옵션이 아님을 확인해 제외한다. 요약 문장의 `/` 꼬리를 모두 옵션으로 오해해 정상 기준까지 미확인으로 만드는 경계를 실행 검사로 차단했다. 옵션 label이 없거나 변환할 수 없는 구성은 이 예외로 통과시키지 않는다.
- 독립 검토가 잡은 `0.5ml` 안의 `5ml`, `150ml` 안의 `50ml`, `11개` 안의 `1개` 포함 오인은 동일 비교 엔진의 축·중복 수량으로 검증한다. 구조화 옵션과 자유서술 꼬리가 같은 검증을 쓰며, 구분자 없이 붙은 용량·수량·의미 있는 옵션 단어와 높은 문자 유사도로 가려진 옵션도 손실로 감지한다. 이 보완은 실제 실패→수정→통과 4회 후 단위 환산·정상 옵션·공식 요약 예외를 함께 재검사했다.
- 명시적 옵션이 말줄임·URL·머리글뿐이면 빈 축 목록을 포함 증거로 인정하지 않는다. 단위만 있어도 실제 용량 축이 증명된 정상 옵션은 유지한다.
- 기존 설정 표시·구매 정책·`productNamesFromWorkOrder`의 구 반환 계약은 유지한다. 행별 선택 옵션을 연결해 이 미확인을 해소하는 작업까지 끝난 것은 아니다.

## 과거 사람 기록과 SQL

- 옛 `productClusterKey`와 정규화, 기존 규칙·별칭·원장은 일괄 재작성하지 않는다. 따라서 옛 소수 키 충돌은 남으며 새 자동판정의 근거로 사용하지 않는다.
- 새 comparison이 conflict/insufficient이면 옛 learned pass는 판정을 승격하지 못한다. 사유·축·버전·signature·unknown은 남긴다.
- UPSERT의 상태·checks·resolution·시각·주체 분기가 하나의 보존 조건을 공유한다. 새 미확인/충돌은 현재 checks/status로 저장하고, 옛 상품 checks 복원이나 새 resolved/ok/확인시각 생성은 막는다.
- 기존 사람·메모·판정·시각은 이력으로 남긴다. 현재 상태와 역사적 resolution은 구분한다. 이 때문에 이미 상품 판단이 있는 건은 기존 군집 목록에서 제외되지만 건별 확인 경로는 유지한다.
- 독립 재심과 실제 SQL로 `옛 상품 pass → 새 conflict + 다른 unknown → 의심 목록 표시 → 명시적 건 전체 확인`을 검사했다. 자동 정상 승격은 없고 새 증거와 이력은 유지된다. 이는 상품 축만 다시 판단하면서 다른 축은 열어 두는 기능이 아니다. 그 기능은 이번 변경에 추가하지 않으며, 필요 시 별도 설계·승인을 받는다. 옛 상품 fail을 일반 정상 버튼으로 뒤집지 않는 기존 보호도 유지한다.
- 사람이 명시적으로 pass/fail을 확인하면 해당 상품 축의 unknown은 해소한다. `machineEvidence`와 원래 comparison은 보존하며, 다른 축의 unknown은 전체 종결을 계속 막는다.
- 계산 결과와 실제 저장 결과는 계속 분리하고 실제 RETURNING만 persisted=true다. 영수증의 독립 정책과 옛 payload 호환도 유지한다.

## 기존 관리자 자동군집의 경계

- 버전은 `product-auto-v2`다. 기존 프론트 확인값은 호환하되, opaque snapshot은 버전·범위·선택 키·각 군집의 evidenceToken에 묶는다.
- 출처 없는 옛 expected-only JSON은 `legacy_evidence`로 제외한다. v2 canonical 출처와 원문/의미 signature를 다시 확인하고, 모든 행이 match이며 같은 의미 증거여야 자동후보다.
- 원문·기준·출처·파일ID의 정렬된 증거 digest를 사용한다. 행 순서가 바뀌어도 같지만 구성원·원문·기준이 바뀌면 다르다. 조회 상한 10,000행에 닿으면 부분 군집일 수 있어 자동후보로 삼지 않는다.
- 실행 트랜잭션에서 실제 대상 전부를 FOR UPDATE로 읽은 뒤 다시 비교한다. snapshot의 ID집합·증거 token과 다르면 UPDATE·학습 0. 검증한 그 ID만 갱신한다.
- 자동 경로는 기존 사람 exact 규칙을 덮어 학습하지 않는다. 수동 판단 경로는 유지한다. 새 무인 재검수·무인 대량 종결 worker를 활성화한 것이 아니다.

## 검증과 한계

- 순수 엔진의 소수·큰 수·역순 역할·단위 환산·모델 접미·연식·농도·포장·누락·별칭·복수 후보·URL 꼬리를 격리 실행했다. 부모가 모델을 용량으로 잘못 환산하는 추가 경계를 RED→GREEN으로 보강했다.
- 일반 비교, 별칭 분리 후 실제 inspectSubmission→저장, learned pass 차단, 실제 UPSERT의 새 충돌/미확인·과거 이력·영수증 호환을 검사했다.
- 군집은 옛 소수 키 충돌·행 순서·정상 의미 증거·snapshot 대상 변경·잠금 직전 추가 행·stale signature·조회 상한·명시적 사람 확인을 실행했다. 실제 SQL 구성과 전체/독립 검토의 최종 결과는 해당 패치노트에 기록한다.
- 10월 29일 읽기 전용 스냅샷 20,125행 중 미해결 7,650행에서 영수증 15·블로그 3·상품명 사람판정 65를 제외한 7,567행을 최종 엔진으로 오프라인 재생했다. 상품 축 match 25, insufficient 7,542이고 25행도 다른 사유가 남아 전체 pass는 0이었다. 1차 보완 시점의 match 37은 두 번째 보완 이전 기록이다. 기준 불완전 2,410·기준 없음 1,020 등이 포함된다. 현재 운영 정확도·실제 불량 수·즉시 자동종결 가능 수가 아니다.
- 옛 사진을 다시 읽거나 새 AI를 호출하지 않았고, 운영 판정행을 소급 변경하지 않았다. 현재 사진·현재 기준·동시 변경을 보호하는 유한 재검수는 3단계다.

## 검토 실패 이력과 사용자 추가 승인·최종 검증

- 두 차례 보완 뒤 전체 검사 670파일은 성공했지만 독립 최종 검토 09b11132는 실패했다. 식별축이 하나뿐일 때 구성품 연결이 아직 사라진다. `세트 토너50ml 로션`과 `세트 토너 로션50ml`, `세트 본체AB100 부품`과 `세트 본체 부품AB100`을 같은 것으로 판정했다.
- 부모도 격리된 가짜 입력의 실제 `inspectSubmission` 경로를 재실행해 계산 pass·저장 pass·자동후보 true를 확인했다. 운영 자료를 조회·변경하거나 실제 AI를 호출한 것은 아니다.
- 전체 검사 통과를 승인 근거로 대체하지 않는다. 자동 보완 2회 제한에 도달해 추가 코드 수정·커밋·푸시·PR·배포를 멈추고 사용자 판단을 받는다. 구성품 소속이 불명확한 단일 축도 미확인으로 남기면 잘못 정상을 막지만 일부 정상 표기도 보류될 수 있다.
- 사용자가 선택 질문에서 「추가 보완하고 전체 재검증까지 진행」을 명시적으로 승인했다. 단일 용량·모델 등의 소속이 불분명한 경우까지 미확인으로 남기는 보수적 보완 한 차례와 전수·독립 재검토를 진행한다. 이는 검토 실패 상태의 배포 승인이나 무제한 자동 수정 허용이 아니다.
- 승인된 추가 보완은 기존 파서의 구성품 연결 방어를 식별축 2개 이상에서 1개 이상으로 확대하는 한 조건이다. 용량·모델 이동의 일반/엄격/실제 제출→저장 오승인을 먼저 RED로 재현한 뒤 GREEN을 확인했다. 개수·연식·농도, 역방향과 동일 중간 표기는 후속 회귀 검사이며 별도 RED 횟수로 세지 않는다.
- 보완 후 순수 113케이스와 실제 제출→가짜 DB 저장 15조합에서 미확인 보존·persisted=true를 확인했다. 하나의 연속 본체 전후 전역 역할 재배치·단위 환산·URL/목록번호 정리는 일반/엄격 모두 유지된다. 옛 연식 검사 한 곳의 보류 사유를 새 정책으로 갱신하되 자동후보 false는 유지했고, 연속 본체 끝의 명확한 연식 불일치 검사를 추가했다(검사 의미 유지/강화). 전수·독립 최종 결과는 패치노트로 확정한다.

## 되돌리기

- 새 스키마·데이터 삭제가 없어 코드 revert로 되돌린다. 구 코드에서는 새 comparison을 무시할 수 있으므로 새 자동 worker를 별도로 켜지 않는다.
- 운영 장애가 확인되면 먼저 사용자에게 되돌릴지 묻는 저장소 절차를 따른다.

## 완화 금지

- 일반·엄격 비교에 숫자 사본 규칙을 다시 만들지 않는다. 소수·모델·수량 역할·누락을 부분 포함/앞 몇 글자로 우회하지 않는다.
- 별칭·옛 exact 키·과거 pass를 새 canonical 증거로 승격하지 않는다. source/signature 없는 옛 군집을 자동 승인하지 않는다.
- 첫 행·잘린 조회·키만 같은 snapshot으로 전체를 자동 처리하지 않는다. 잠금 후 전체 대상 증거 확인을 생략하지 않는다.
- unknown을 옛 SQL 종결 경로로 정상화하지 않는다. 직원 기록을 지우거나 자동 판정을 직원 정답 규칙으로 덮어 저장하지 않는다.
- 제출 허용·영수증 지급 정책·실제 저장 성공 계약은 그대로 둔다. 사진·반려·통지·새 worker를 이 변경에 끼워 넣지 않는다.
