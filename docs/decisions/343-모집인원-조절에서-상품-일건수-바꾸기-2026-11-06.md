# ★★ 모집인원 조절 창에서 상품 일건수 바꾸기 — 날짜별로 정한 인원이 상품 일건수에 막히면 알리고, 팝업에서 상품 일건수·공고·리뷰오더를 함께 바꾼다 (사용자 확정 2026-11-06 · 스키마 변경 0)

## 발단 (340)11/4(쿠팡) 쿠션 21호 200건 · camp_5a467c5e891a · 운영 읽기 전용 실측 2026-11-06)
- 업체가 "일건수 40으로 투입"을 요청 → 직원이 [📅 인원]에서 11/6·11/7·11/8 을 40으로 저장(4번).
- 실제로는 하루 20명만 열렸다. 공고 하루 몫은 **상품(선택지) 일건수 합을 넘지 않는다**(결정 210) — 상품 「1.본품+리필1p 세트 / 21호」 일건수 20.
- 조절 창은 이 상한을 알리지 않았다. 게다가 표의 숫자(`planFor` = 서버 예상 인원의 실제 여는 값)는 저장된 40을 **20으로** 보여 줘,
  직원은 "40이 저장이 안 된다"고 읽었다. 40을 넣을 자리를 만들려고 다른 날(11/9~11/25 등)을 0으로 바꿔 둔 흔적도 남았다(추정).

## 결정 (사용자 확정 2026-11-06 — 「2번 + 팝업에서 상품 일건수 수정 → 공고도 수정」 · 질문 3개 1.A 2.A 3.B · 권한 A)
1. 조절 창(예상 인원 방식 `renderProj`)은 **사람이 정한 값**(저장 전 바꾼 값 → 저장된 계획 → 규칙 값, `odWant`)이 상품 일건수 합(cap)보다 큰 날에
   「40명 중 20명만」을 그 줄에, 위쪽에 「11/7·11/8은 상품 일건수(하루 20명)를 넘어 실제로는 20명만 열립니다」 + **[상품 일건수 바꾸기]** 버튼을 보인다.
   팝업은 **버튼을 눌러야** 뜬다(3.B).
2. 팝업 1단계: 상품마다 「지금 N → [새 값]」 칸 + 하루 최대 합계(2.A — 직원이 직접 나눈다). 상품이 하나면 날짜별로 정한 가장 큰 값을 미리 넣는다.
   2단계 확인: 함께 바뀌는 곳 — 상품 일건수 · 공고 기본 일건수 · (리뷰오더와 연결된 공고면) **인트라넷 리뷰오더 일 진행 건수**(1.A).
3. [바꾸기] → `POST /api/trackb/campaigns/:id/option-daily` → 같은 창을 새 값으로 다시 그린다. **저장 전 조절은 그대로 둔다**(작업 연속).
4. 권한 = 조절 창과 같은 내부 직원(master·admin·staff — 사용자 확정 A). 공고 수정 창(관리자 전용)보다 넓다 — 차수 추가·가격 고치기와 같은 급.

## 서버 (`campaignOptionDaily.service.js` 한 곳)
- 화면은 줄마다 **본 값(from)** 을 같이 보낸다. 열린 줄 전부가 아니거나 · 본 값이 지금 값과 다르면 409 `option_daily_stale`(쓰기 0) — 그 사이 다른 사람이 바꾼 값을 덮지 않는다.
- **연결 공고**(`findBidirLink` · 스위치 `campaign_edit='on'`) = 공고 창 인원 수정과 **같은 길**: `planCampaignMoneyEdit` → `applySharedPatch`(origin `campaign`) → 공고 칸은 투영이 바꾼다.
  인트라넷은 7단계-② 수신(일 진행 건수 · 상품·옵션 daily)으로 받는다.
- 연결 아닌 공고 = 공고 창이 쓰는 두 칸만(옵션 `daily_limit` · 공고 `daily_limit` = 열린 줄 합) 한 트랜잭션(공고 행 잠금 후 다시 대조).
- 쓴 뒤 `relayCampaignWorktable`(작업표 빈 줄 날짜 다시 깔기) · 이력 `campaign_plan_events.action='option_daily'`.
- 조절 창 자료(`getPlanOverview`)에 `optionDaily: { cap, options[], linked }` — 상한이 실제로 걸리는 공고만(`optionDayCapacity` ≠ null · 순차진행 아님 · 열린 줄 모두 일건수 > 0). 조회 실패 = null(경고 없음 = 종전 화면).

## 지킬 것(완화 금지)
- ★★ **연결 공고는 옵션표 줄 전부를 보낸다** — 결정 280 그대로. 인원·금액은 기준(오더) 값, 상태는 공고 값, 일건수만 새 값. 한 줄만 보내면 다른 줄이 오더에서 지워진다.
- ★★ **계획에 일건수 말고 다른 변경이 끼면 쓰지 않는다**(`dailyOnlyViolation` — 허용 칸 `product_options_json`·`daily_count`·`recruit_count`(같은 값), 상품 구성은 일건수 칸을 뺀 나머지가 기준과 같아야). 오더·공고가 이미 갈라진 공고에서 구조·인원까지 바뀌는 것을 막는다(변이시험: 이 검사를 빼면 갈라진 공고에서 공유 저장이 실행돼 시험 실패).
- ★★ **연결 판정 실패·스위치 꺼짐 = 막음**(fail-closed) — 공고만 바꾸면 오더와 갈라지고, 다음 리뷰오더 수정 때 옛 값으로 되돌아간다.
- ★★ **본 값(from) 대조를 지우지 않는다** — 옛 화면으로 다시 누르면 남이 바꾼 값을 덮는다(변이시험으로 검출 확인).
- ★ 날짜별로 사람이 정해 둔 인원(`campaign_daily_plans`)은 건드리지 않는다(결정 275 사용자 확정 가). 0으로 바꿔 둔 날은 직원이 [기본으로]를 눌러야 새 일건수가 깔린다.
- ★ 경고 비교는 **사람이 정한 값**으로 — 표 숫자(`planFor`)는 실제 여는 값이라 저장된 40이 20으로 보여 경고가 안 뜬다(로컬 실브라우저에서 처음 이렇게 잡혔다).
- ★ 팝업 입력은 `input` 이벤트를 쓰지 않는다(조절 창 IME 규율 7w — `keyup`·`change`).

## 사각지대
- 리뷰웹 → 인트라넷 일건수 전송은 이 기능 전 2주간 운영에서 한 번도 없었다(2026-11-06 실측). 인트라넷 수신 코드는 있으나 실제 수신은 배포 뒤 첫 사용 때 확인한다.
- 시트 일정 방식 화면(`render` — 예상 인원 방식이 아닌 옛 화면)에는 경고·버튼을 넣지 않았다(지금 운영 공고는 예상 인원 방식).
