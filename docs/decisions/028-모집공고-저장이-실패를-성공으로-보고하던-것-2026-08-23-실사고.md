# ★★★ 모집공고 저장이 "실패를 성공으로" 보고하던 것 (2026-08-23 실사고)
- **신고**: 총인원이 공란인 공고에 **200 을 입력해 저장** → `✓ 저장됨` + 가운데 안내 `「…」 공고 수정이 반영되었습니다`(변경 목록에 **총 모집인원**까지) → **다시 열면 여전히 공란**.
- ★★ **원인은 총인원 로직이 아니라 저장 성공 판정이었다** — 이 API 의 `errorHandler` 는 **GAS 호환**으로 실패를 **HTTP 200 + `{ error }`** 로 돌려주는데(`error.middleware.js`: `res.status(200).json({ error })`), `saveRecruitPostImpl` 이 **`res.ok`(HTTP 상태)만** 보고 본문을 안 봤다. 그래서 서버가 거부한 저장이 그대로 성공 경로를 타고 **모달까지 닫혔다**. CLAUDE.md 가 이미 "이 API 의 errorHandler 는 200+{error} 라 **상태코드만으로 성공을 판정하지 말 것**"이라 적어 둔 자리인데 이 경로가 그걸 안 지키고 있었다.
- ★ **거부 사유의 대표 예** = `assertCampaignRecruitTotal` → `worktableSlotDelta` 의 `이미 참여자 또는 구매양식이 있는 작업보드 인원보다 낮게 목표 인원을 설정할 수 없습니다` — **총인원 0(무제한)에서 200 으로 "올리는" 조작이 작업보드 기준으로는 축소**라(무시트 작업표에 이미 200 줄 넘게 채워져 있으면) 거부된다. 사람은 올린다고 생각하는데 서버는 줄인다고 본다. ⚠ **이 예시는 신고 건의 원인이 아니었다**(본섭 실측: 그 공고는 시트 기반 탭이라 `assertWorktableSlotsInTx` 가 `not_sheetless` 로 즉시 빠져나가고, 차수도 0 이며, DB 에는 200 이 정상 저장돼 있었다) — 진짜 원인은 아래 절이다. **침묵 자체는 실재했고 그대로 고쳤다**(다음에 같은 계열이 나면 이제 화면이 사유를 말한다).
- **수정**: `saved.ok === false || saved.error` 를 실패로 읽는다. ★ 판정은 **역연결·성공 안내·모달 닫힘보다 앞** · ★ 기존 `!res.ok` 상태 검사는 **그대로 둔다**(두 갈래를 모두 막는다 — 본문 판정으로 대체 금지) · ★ **`data` 부재를 실패로 단정하지 않는다**(응답 shape 이 바뀌면 정상 저장이 실패로 보고되어 같은 저장을 반복하게 된다) · 실패는 종전 catch 가 **모달을 열어 둔 채** 사유를 그대로 보여준다(토스트로 흘리면 모달 덮개 아래로 깔린다).
- ⚠ **같은 계열을 의심할 자리**: `/api/admin/*`·`/api/campaign/*`·`/api/order/*`·`/api/manual-order/*` 는 사유가 마스킹되지 않을 뿐 **상태코드는 여전히 200** 이다 — 이 경로들에 `fetch` 하는 화면은 전부 **본문(`error`)으로 판정**해야 한다.
