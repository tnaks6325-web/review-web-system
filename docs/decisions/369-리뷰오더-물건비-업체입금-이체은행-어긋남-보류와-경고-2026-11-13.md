## 결정 — 세 겹으로 막는다
1. **판정 단일 출처** `payment.goodsCostSaysAdvertiser(물건비)` = `/업체\s*입금/`. 프론트 `index-recruit.js _rfOrderSaysAdv` 는 같은 정규식(회귀가드가 대조).
2. **입금관리 보류**(돈이 나가는 쪽 · fail-closed) — `listPaymentTargets` 에서 입금 방식이 우리(`payoutModeFrom().mode === 'ours'`)인데
   물건비(공고의 리뷰오더 → 탭 순)가 업체입금이면 막는 사유 `order_goods_by_advertiser`. `createBatch` 는 같은 계산을 다시 타므로 회차에도 안 담긴다.
   - 업체입금·제품비 업체(split) 작업은 해당 없음. 화면 라벨·작업 단위 보완(작업 조건 › 이체은행으로 가는 버튼)을 함께 둔다(막다른 길 금지).
3. **작업 조건 카드 경고** — 서버가 `condition.transferBankOrderMismatch`(같은 판정)를 싣고, 이체은행 칸 끝에 빨간 「⚠ 리뷰오더는 업체입금」 + 설명 툴팁.
   새 줄을 만들지 않는다(세 박스 높이 규율). 업체 렌즈(`_condAdvertiserLens`)는 화이트리스트라 나가지 않는다. 업체를 나중에 연결한 작업도 여기서 드러난다.
4. **모집공고 창** — 물건비 업체입금이면 이체은행 안내 줄이 「제품비 업체 · 리뷰비 …」/「업체입금」을 고르라고(업체 미연결이면 [자동]으로 두고 연결 뒤 변경) 말하고,
   케이뱅크·하나은행을 새로 고르고 저장하면 확인창(취소 = 저장 안 함). [자동]은 확인 없이 저장되지만 입금관리가 「이체은행 미지정」+ 이 사유로 막는다.

## ★★ 완화 금지
- **`order_goods_by_advertiser` 를 경고(warnings)로 낮추지 말 것** — 담당자가 체크한 채 내려받으면 제품비가 우리 돈으로 나가고, 업체도 보내면 되돌릴 수 없다.
- **판정을 화면·라우트마다 따로 쓰지 말 것** — `goodsCostSaysAdvertiser` 하나(프론트는 같은 정규식 + 대조 가드). 갈리면 카드는 조용한데 입금관리만 막히는 등 서로 다른 말을 한다.
- **이 판정으로 이체은행을 자동으로 바꾸지 말 것** — 업체입금(업체가 리뷰비까지)과 제품비 업체(리뷰비는 우리)는 돈의 주체가 달라 사람이 정한다.
