# ★★ 영수증리뷰 2단계 — 오더 계약(v2 상품 원본 안 `receipt` · 영수증 사진 파일 번호 목록) + 영수증 묶음 `receipt_pool`(한 장 = 한 자리 · migration 230) + 비공개 영수증 사진(`receipt_review_files` = 사진 통로 거절 목록 · 인증 통로만) + 작업보드 칸(참여일자·영수증·리뷰마감일 · 날짜를 지어내지 않음) + 작업표 자동 정리 격리 (2026-11-25)

> 1단계·사용자 확정 표·단계 계획 = [418](418-영수증리뷰-체험단-종류-receipt-1단계-판정-안전핀-2026-11-25.md). 본보기 = 예약리뷰 2단계 [407](407-네이버예약리뷰-2단계-날짜별-자리표-작업보드-칸-2026-11-24.md) · 사진 통로 [352](352-무인증-사진-통로-허용목록-DB에-기록된-번호만-2026-11-07.md).

## 무엇을 했나
- 리뷰웹이 영수증리뷰 오더를 **받을 모양(계약)** 을 정하고, 그 오더에 붙은 **영수증 사진 한 장 = 리뷰어 한 명 자리**를 작업표 줄과 함께 까는 길을 만들었다.
- 영수증 사진을 **비공개로 올리고(인트라넷 → 리뷰웹) · 직원만 보는** 길을 만들었다. 무인증 사진 통로·엣지는 영수증 번호를 거절한다.
- ★★ **운영에서 열린 길은 없다** — 1단계 저장 입구 거절(`NOT_READY_WORK_KINDS = ['receipt']`)을 그대로 두었다. receipt 오더·공고가 저장되지 않으므로 묶음·작업보드 칸은 시험(내부 함수 직접 호출)과 로컬 미리보기에서만 돈다. 영수증 올리기·보기 통로는 열려 있지만 receipt 오더가 접수되지 않아 쓸 곳이 없다(7단계 인트라넷이 쓴다).

## 오더 입력 계약 (단일 출처 = `server/src/utils/receiptPool.js` `receiptReviewSpecFromWorkOrder`)
- **v2 상품 원본(`product_options_json`) 안에 둔다** — 새 칸·새 접수 필드 없음(Q&A `qna` · 예약 `booking` 과 같은 자리 · 접수·원본 수정·잠금 비교·프리필이 이 글자를 그대로 나른다).
```json
work_orders: { "work_kind": "receipt", "workboard_schema_version": 2, "recruit_count": 4, "review_fee": 5000, "pay_amount": 0 }
product_options_json: [{
  "name": "<매장 이름>", "url": "<네이버 플레이스 주소>", "option_schema_version": 2, "product_mode": "none", "options": [],
  "base": { "pay": 0, "count": 4, "daily": 0, "review_type_mix": [] },
  "receipt": {
    "review_deadline_days": 3,
    "place_address": "<매장 주소 · 안내용 · 선택>",
    "receipts": [{ "file_id": "<POST /api/order/receipt-review-image 가 돌려준 번호>" }, { "file_id": "…" }, { "file_id": "…" }, { "file_id": "…" }]
  }
}]
```
- 매장 이름·주소 링크 = **상품 이름·상품 주소 칸 그대로**(따로 두면 두 값이 갈린다). 영수증 번호 = `receipts` 받은 순서(1..N). 리뷰비 = `work_orders.review_fee`. 결제금액은 언제나 0(매장 비용은 업체 부담 · 사용자 확정 1).
- `receipt` 키 이름은 캡처 칸 키(현금영수증 `slot_key='receipt'`)와 **다른 축**이다 — 이 값은 상품 원본 안에만 있고 현금영수증 칸·안내 판정(`captureSlots`·`cashReceiptContext`)은 읽지 않는다(418 「섞지 않는다」 그대로 · 회귀가드가 리뷰 오더 상품에 `receipt` 키가 실려 와도 계획이 그대로임을 지문으로 본다).
- 잠금(blocker — 그대로 깔면 반드시 틀린 묶음만 · 조용히 고쳐 깔지 않는다): `receipt_requires_v2` · `receipt_one_place`(살아 있는 상품이 정확히 하나 · 옵션 없음) · `receipt_place_name` · `receipt_no_qty_tiers` · `receipt_no_spec` · `receipt_no_files`(한 장 이상) · `receipt_too_many`(> 2000 · **펼치기 전에**) · `receipt_file_invalid`(드라이브 번호 모양 `^[-\w]{20,200}$` — 결정 352 통로와 같은 모양 · 주소째·객체 아님 거절) · `receipt_file_duplicate`(한 장 = 한 사람) · `receipt_total_mismatch`(총모집·`base.count` ≠ 장수 — 사용자 확정 7 「장수만큼만 받는다」 · 2026-11-25 Q2 부터 저장 입구가 장수로 맞추므로 맞춤을 건너뛴 값에서만 뜬다) · `receipt_has_pay`(1건 금액·결제합계 > 0) · `receipt_deadline_days`(1~30 · 없으면 3).
- 막지 않는 것: 리뷰비 0원(입금 5단계가 본다) · 매장 주소 없음(안내용).
- 계약 잠금은 작업표 계획 잠금(`buildWorktablePlan().blockers`)으로 올라온다 → 접수 미리보기·접수가 멈춘다.

## 영수증 사진 — 어떻게 들어오고 왜 비공개인가 (★★ 완화 금지)
- **들어오는 길** = 유입가이드 사진과 같은 인트라넷 → 리뷰웹 올리기(인트라넷 서버가 `X-Intake-Key` 로 리뷰웹을 부름)를 쓰되 **입구를 따로 둔다**: `POST /api/order/receipt-review-image`(인증 = 인트라넷 키 또는 내부 담당자 로그인 master·admin·staff · 업체·리뷰어·주소 토큰·인트라넷 SSO 토큰 불가).
  - 유입가이드(`POST /api/order/guide-image`)와 다른 세 가지: ① 드라이브 공개 권한을 주지 않는다(`shareAnyone:false` — 구글 썸네일 주소로도 안 열림) ② 공개 안내 사진 목록(`guide_image_files`)이 아니라 **비공개 영수증 목록(`receipt_review_files`)** 에 응답 전에 적는다(실패 = 올리기 실패) ③ 주소로 받아 오기(`imageUrl`)를 받지 않는다 · 사진(jpeg·png·webp·heic·gif)만.
  - 응답 = `{ ok, id }` — **주소를 만들지 않는다**. 폴더 = `RECEIPT_REVIEW_FOLDER_ID` 또는 루트 아래 `[영수증리뷰]`(유입가이드 폴더와 섞지 않음).
- **공개 통로 거절**: `receipt_review_files.file_id` 를 결정 352 의 **거절 목록(`imageAllowlist.PRIVATE_SOURCES`)** 에 더했다(이체결과 보관 파일과 같은 자리). 그래서 `GET /api/drive/image/:id`·`GET /api/order/guide-image/:id`·사진 엣지(354 · 같은 판정)는 영수증 번호를 **어느 공개 목록에 함께 적혀 있어도 404(드라이브 읽기 0)**. 시험이 「실수로 안내 사진 통로로도 올라간 영수증」까지 거절됨을 확인한다.
- **보는 길(인증 통로만 · 캐시 금지 `private, no-store` · 사진(image/*)일 때만 · 구글 썸네일로 돌리지 않음)**:
  - 직원 작업보드: `GET /api/trackb/workdesk/receipt-image?sheetId&tabName&seq`(`authMiddleware + internalMiddleware`) — **줄 번호로** 찾는다(화면에 파일 번호를 주지 않는다). 묶음에 없는 줄·비공개 목록 밖 파일 = 404 · 조회 실패 = 503(내주지 않음 · fail-closed).
  - 인트라넷 AE 미리보기(7단계용): `GET /api/order/receipt-review-image/:id`(인트라넷 키 또는 내부 담당자 · `Authorization` 헤더만) — 비공개 목록에 있는 번호만.
  - 리뷰어(3단계): 배정된 리뷰어만 자기 영수증을 보는 통로를 3단계가 만든다(신청 ↔ 자리 묶음으로 판정 · 이 통로들을 리뷰어에게 열지 않는다).
- **접수 때 확인**: 묶음 저장(`receiptPool.service.insertPool`)은 계약의 파일 번호가 **전부 비공개 목록에 있을 때만** 쓴다 — 하나라도 없으면 아무것도 쓰지 않고 던진다(`receipt_file_unregistered` → 접수 409 `receipt_pool_failed` · `reason:'receipt_file_unregistered'`). 그래서 공개 안내 사진·이체결과 파일 번호를 영수증으로 끼워 넣어 직원·리뷰어 통로로 꺼내 가는 길이 없다.
- **화면 응답에서 지움**: 작업보드 응답의 오더 원문(`workdeskTab` `detail.productOptionsJson` — 업체 화면에도 나간다)에서 영수증 파일 번호를 지운다(`receiptPool.redactReceiptFileIds` · **응답을 만드는 바로 그 줄**(`const _detail = …` → `res.detail`)에서 · `{ no: N }` 만 남김 · 영수증 목록이 없는 글은 **같은 문자열 그대로**). 작업표 「영수증」 칸에도 `N번` 만 적는다.
- 작업 삭제는 묶음(`receipt_pool`)만 지우고 비공개 목록(`receipt_review_files`)은 남긴다 — 남겨야 그 번호가 공개 통로에서 계속 거절된다(드라이브 파일 정리는 별도 · ⚠ 아래).

## 영수증 묶음 — 생성은 순수 함수, 저장은 별도 표
- **생성 = `receiptPool.buildReceiptPool`**: 받은 순서 그대로 한 장 = 한 자리(`seq`·`poolSeq`·`fileId`·`label='N번'`). 날짜를 만들지 않는다.
- **저장 = `receipt_pool`(migration 230)** — 한 줄 = 영수증 한 장 · 그 자리의 작업표 줄 번호(`seq`) · 유일 색인 (탭, 영수증 번호)·(탭, 줄 번호)·(탭, 파일 번호) + 파일 번호 색인(사진 통로 판정용이 아니라 조회용 · 판정은 `receipt_review_files` 기본키). 기동 필수 표(`REQUIRED_TABLES`)에 두 표.
  - 접수 때 작업표 줄과 **같은 흐름**(`sheetlessAccept.persistSheetlessWorktable` ①-d): 이미 있는 줄이 계획과 줄마다 같을 때만 붙이고(`verifyRowsMatchPool` — 매장·영수증 칸), 실패는 던진다.
  - ★★ 묶음 저장 실패 = **접수를 끝내지 않는다**(`receipt_pool_failed` 409 · 상태 전이 전) · 연결까지 끝난 재접수는 `repairPoolIfMissing`(줄과 같을 때만 되살림) — Q&A·예약과 같은 막다른 길 방지.
- ★★ **왜 표를 두나** — 3단계에서 참여하는 순간 「안 쓴 영수증 한 장」을 주고 **한 장이 두 사람에게 가지 않아야** 한다. 자리 한 줄 = 살아 있는 신청 하나를 유일 색인으로 묶어야(3단계 `campaign_applications.receipt_pool_id` + 부분 유일 색인 `status IN ('applied','submitted')` — 예약 228 과 같은 방식) 동시 참여에도 넘침이 구조적으로 막힌다. 작업표 줄 글자는 자동 정리·손 편집이 바꾸므로 진실원본이 될 수 없다.
  - **예약 자리표(`booking_slots`)·Q&A 자리표(`qna_slots`)를 같이 쓰지 않는다** — 그 판정(자리표 존재)이 영수증 탭을 자기 탭으로 읽으면 날짜 신청·캡처 기한 스윕·추가 모집이 붙는다(회귀가드가 서로 안 읽음을 실제 SQL 로 확인).
  - 남은 영수증 재료 = `receiptPool.service.poolCounts`(2단계엔 신청 묶기가 없어 open = 전체). 영수증 고르기·자동 마감은 3단계·6단계가 **잠금 안에서** 한다.

## 작업보드 칸 (`worktablePlan.ensureReceiptColumns`)
- `번호 · 참여일자 · 상품 · 영수증 · 리뷰마감일 · 수취인 · 은행 · 계좌번호 · 예금주 · 리뷰 · 입금일 · 비고`(표준 열에서 실측).
- 「구매일자」 자리 = **「참여일자」**(이름에 「일자」 → 매퍼가 같은 날짜 역할 `dateStr`). 표준 열에 날짜 칸이 없으면 번호 바로 뒤에 시스템이 만든다.
- ★★ **날짜를 지어내지 않는다** — 줄을 깔 때 참여일자·리뷰마감일은 비운다(리뷰어가 기간 안 아무 날 방문 · 참여일 + N일은 3단계가 채운다). 계획 줄 날짜 없음 · 날짜 요약 없음 · 미리보기 날짜/건수 조정 무시.
- 「영수증」·「리뷰마감일」 = 역할 없는 시스템 칸(리뷰어 구매양식 매퍼가 덮지 않는다). 리뷰마감일 이름은 예약리뷰와 같은 상수(`RECEIPT_DEADLINE_HEADER = BOOKING_DEADLINE_HEADER`) — 작업보드 날짜 표기(409)를 그대로 받는다.
- 없앤 칸: 주문번호·아이디(채널 ID 포함)·연락처·주소·결제금액·리뷰옵션·상품옵션·송장(택배발송대행이 켜져 와도). 리뷰타입을 행마다 정하지 않는다. 상품 칸 = 매장 이름(v2 선택 키).
- 계획 경고: 리뷰 날짜 경고·구매채널 모름·「상품이 여러 개」 안내 대신 `receipt_pool` 한 줄.
- 날짜 칸 찾기(`campaignSchedule.findDateColumnIndex`)에 「참여일자」를 **넣지 않았다** — 넣으면 기존 탭 판정이 바뀌고, 영수증 탭 보충 줄에 날짜가 붙는다(회귀가드가 -1 을 고정).
- 화면(`workdesk.html`): 서버가 내부 응답에만 `receiptPoolColumn`(영수증 묶음이 있는 탭 · 조회 실패 = 안 실음)을 실으면 「영수증」 칸을 읽기 전용으로 그리고 직원 [보기] 단추(헤더 인증 fetch → 화면 안 창 · blob · 닫으면 지움). 업체 화면엔 없다. 자동 열 너비에 단추 폭(44px)을 더했다 — 안 더하면 단추가 칸 밖으로 잘려 눌리지 않았다(미리보기 실측).
- 리뷰·블로그·Q&A·예약리뷰·현금영수증 리뷰 계획은 **180조합 바이트 동일**(회귀가드가 결정 420 이전 지문과 대조 · 표준 열에 「참여일자·영수증」이 있는 리뷰 표 포함).

## ★★ 작업표 자동 정리 격리 (완화 금지)
- 판정 `receiptPool.service.isReceiptPoolTab` = 묶음이 있거나 `tab_configs.work_kind='receipt'`. **조회 실패(표 없음 포함) = 영수증 탭**(fail-closed) · 트랜잭션 연결은 SAVEPOINT(`receipt_pool_tab_probe`·`receipt_pool_bound_probe`). 자리 줄 판정 실패 = 묶인 것.
- 막은 곳(예약 판정 뒤에 하나씩 덧붙임 — Q&A·예약 동작 불변):
  - 빈 줄 날짜 옮기기(`relayWorktableToProjection`) → 건너뜀 `receipt_pool`(날짜를 붙이지 않는다).
  - 총 건수 맞추기·저장 전 확인(`_assertQnaCalendarUnchanged` 하나) → `recruit_quota_receipt_locked`(409). 작업표 만들 때 모집인원만큼 빈 줄 맞추기(`campaignWorktable`)도 건너뜀.
  - 번호 겹친 빈 줄 정리(`cleanupPairedBlanks`) → 자리 줄 제외(`poolBoundRowSql`).
  - 번호 없는 주문 끼우기·옮기기 → `receipt_pool_required`(화면 문구 추가).
  - 줄 정리·중복 정리·짝 빈 줄 정리(`sheetlessLedger.retireRows`) → `receipt_pool_rows`(차수 단위도). 주문 행 삭제 → `receipt_pool_row`(409 · 「줄 삭제」로 안내).

  → `work_orders.recruit_count` 를 쓰는 order.routes 의 모든 곳(INSERT 1 · UPDATE 4: 원본 수정 전체·계약만·옛 경로·관리자 수정)이 맞춘 값을 쓴다. 모집 상한 확인(`assertWorkOrderQuota`)·공고 인원 맞추기(`syncWorkOrderRecruitTotal`)도 맞춘 `b.recruit_count` 를 받는다.
- 읽는 곳(그래서 모두 같은 수를 본다): `recruit_count` = 서버 20개 파일 95줄 · `base.count` = 9개 파일(공고 프리필·주문 요약·양방향 투영·공유 편집 등). 하나씩 고치지 않았다 — 저장되는 값 자체가 같아서다.
- ★★ fail-closed: 맞출 근거가 확실할 때만(살아 있는 상품 하나 · 옵션 없음 · 영수증 목록 1..2000장) 맞춘다. 영수증 없음·목록 아님·상한 초과·매장 둘·형식 깨짐 = **받은 그대로** → 계약 판정이 `receipt_no_files` 등으로 계획을 멈춘다(0명으로 접지 않는다). 장수 = 받은 줄 수(틀린 번호·중복은 계약 판정이 `file_invalid`·`file_duplicate` 로 따로 막는다).
- ★ 이미 같은 수면 원문 글자를 바이트 그대로 둔다(잠금 비교·양방향 지문 불변). 리뷰·블로그·Q&A·예약 오더는 손대지 않는다(같은 상품 원본 모양이 와도).
- **방어선 두 겹(선택)**: 계약 판정의 `receipt_total_mismatch` 는 **그대로 남겼다**(문구만 「다시 저장하면 장수로 맞춰집니다」). 맞춤이 저장 입구에서 같음을 보장하므로 정상 흐름에선 안 뜨고, 맞춤을 건너뛴 값(DB 직접·앞으로 생길 새 저장 경로)으로는 작업표 계획이 여전히 멈춘다 — 계약 단계에서 지우면 그 우회 길에서 장수와 다른 줄 수가 깔린다.
- 원래 요청한 수: 새 칸을 만들지 않았다(기존 관례에 「요청값 보관 칸」이 없다). 서버 기록(`logger.info` `[order] 영수증리뷰 모집 인원 = 영수증 장수 …(요청 총모집 · 상품 인원)`)에만 남긴다. 접수 응답(`data.recruit_count`)은 맞춘 값이라 7단계 인트라넷이 그 값을 보여 주면 된다.

### Q3 ① — 접수 뒤 영수증 **덧붙이기** 허용(모집 인원 = 늘어난 장수)
- 판정 = `receiptPool.receiptAppendDecision(이전 오더, 새 오더)`(둘 다 Q2 맞춤 뒤 값) → `{ append:[{poolSeq,fileId}], locked, invalid, fromTotal, toTotal }`.
  - 허용 = **뒤에 덧붙이기만**. 영수증 번호 = 받은 순서 = 이미 깔린 작업표 줄이라 새 장은 `이전 장수+1..` 번.
  - 잠금: 이미 있는 영수증 빼기·다른 사진으로 바꾸기·순서 바꾸기(`receipts_removed`) · 매장 이름(`place_name`) · 리뷰 마감 일수(`review_deadline_days`) · 총모집 ≠ 이전 장수 + 덧붙인 장수(`total` — 맞춤을 건너뛴 값) · 한쪽 계약을 못 읽음(`receipt_shape` · fail-closed).
  - 새로 깨진 사유만 `invalid`(덧붙인 사진이 기존 사진과 같음 = `receipt_file_duplicate` · 상한 초과 등) — 이미 있던 사유로 글 칸 수정까지 막지 않는다(414 규율). 잠금·사유가 하나라도 있으면 `append` 는 비어 있다.
  - ★ **아직 안 간 영수증 빼기도 막았다(보수적)** — 2단계엔 배정(신청 ↔ 영수증 묶기)이 없어 「안 간 장」을 판정할 근거가 없다. 3단계가 배정을 만든 뒤 사용자와 다시 정한다.
- ★★ **2단계 = 판정 함수만 · 연결은 안 했다**. 실제로 덧붙이려면 같은 트랜잭션에서 ① 작업표 줄(빈 자리 줄 · 영수증 칸 N번) 덧붙이기 ② 장부 다시 쓰기 ③ 묶음(`receipt_pool`) 줄 + 비공개 목록 확인(`insertPool` 규율) ④ 공고 총모집 맞추기(지금 영수증 탭은 `recruit_quota_receipt_locked` 로 막혀 있다)를 함께 해야 해서, 안전핀(`NOT_READY_WORK_KINDS`)을 푸는 단계(6단계 접수 뒤 잠금)가 원본 수정 경로에 이 판정을 잇는다.
  - 그때까지 접수된 영수증 오더에 영수증을 덧붙인 원본 수정은 **종전 잠금(총모집·상품 구성 = `accepted_worktable_locked` 409)** 이 막는다 — 조용히 저장되거나 반쯤 깔리는 길은 없다(지금은 receipt 오더 자체가 저장 입구에서 거절된다).

## 완화 금지
- **저장 입구 4곳의 모집 인원 맞춤(`_followReceiptRecruit` → `receiptRecruitFollow`)을 빼거나 저장·잠금 비교 뒤로 옮기지 말 것 · 계약 판정의 `receipt_total_mismatch` 를 지우지 말 것(두 겹)** — 영수증 장수와 다른 수의 자리·공고 인원이 깔린다. **영수증이 없거나 형식이 틀린 오더를 0명·임의 수로 맞추지 말 것**(fail-closed).
- **접수 뒤 영수증 덧붙이기에서 이미 있는 영수증 빼기·바꾸기·순서 바꾸기를 열지 말 것**(`receipts_removed`) — 이미 깔린 줄·배정된 자리의 영수증이 바뀐다.
- **영수증 사진을 유입가이드 통로(`guide-image`·`guide_image_files`)로 올리거나 드라이브 공개 권한(`shareAnyone`)을 켜지 말 것 · `receipt_review_files` 를 `PRIVATE_SOURCES` 에서 빼지 말 것 · 영수증 보기 통로를 무인증·주소 토큰·업체·리뷰어 전체에 열지 말 것 · 구글 썸네일로 돌리지 말 것** — 결제 카드·시각이 찍힌 영수증이 주소 하나로 열린다.
- **묶음 저장에서 비공개 목록 확인(`insertPool` → `unregisteredFiles`)을 빼거나 뒤로 옮기지 말 것** — 공개 안내 사진·이체결과 파일 번호를 영수증으로 끼워 넣어 직원·리뷰어 통로로 꺼내 간다.
- **작업보드 응답·작업표 칸에 영수증 파일 번호를 싣지 말 것(`redactReceiptFileIds` 유지 · 「영수증」 칸 = N번)** — 업체 화면으로 번호가 퍼진다.
- **영수증 탭 판정 조회 실패를 「리뷰 탭」으로 접지 말 것(fail-closed · SAVEPOINT)** · **격리(빈 줄 날짜 옮기기·총 건수 맞추기·번호 겹친 빈 줄 정리·번호 없는 주문·줄 정리·날짜 고치기·칸 편집·차수)에서 영수증 탭을 빼지 말 것** — 영수증 줄에 없는 참여일이 붙거나 영수증 자리가 지워진다.
- **줄 삭제 보충에서 영수증 탭을 날짜 갈래(`_slotTab`)에 넣지 말 것** — 지운 사람의 참여일·마감이 새 자리에 붙는다.
