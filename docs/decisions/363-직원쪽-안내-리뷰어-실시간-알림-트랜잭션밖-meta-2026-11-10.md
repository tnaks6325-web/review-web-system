# ★★ 직원 쪽 안내도 리뷰어에게 실시간으로 — `postAdminNotice` 실시간 알림이 트랜잭션 블록 안 `meta` 를 밖에서 읽어 조용히 0건이던 것 수정 · 저장 1 = 알림 1 · 다시 보내기·실패 = 알림 0 · 알림 실패는 경고 로그 (2026-11-10 · 스키마 변경 0 · 화면 변경 0)

## 무슨 일이었나
- 직원 쪽에서 리뷰어 문의방으로 보내는 안내는 전부 `csBridge.postInspectionReject`(= `postAdminNotice`) 한 벌을 쓴다(결정 013). 호출부 전수(`grep -rn "postAdminNotice\|postInspectionReject" server/src` — 6곳):
  1. 리뷰검수 반려(사진 카드) — `reviewInspect.service` `notifyInspectionReject`
  2. 입금 실패 안내 — `paymentResult.service` `_notifyFailures`
  3. 작업보드 [리뷰어에게 메시지] — `trackB.routes` `POST /cs/notify-participants`
  4. 리뷰어 주문취소 접수 안내 — `reviewerOrderCancel.service`
  5. 블로그 승인/반려 안내 — `campaign.routes` `_notifyBlogDecision`
  6. 작업보드 문자 수동 발송의 문의방 사본 — `manualMessage.service`(이 파일은 이번에 손대지 않는다)
- **저장은 됐는데 리뷰어 화면에 실시간으로는 한 번도 안 갔다.** 2026-08-21 「방 생성·메시지·방 갱신을 한 트랜잭션으로」(결정 013) 때 카드 값 `meta` 의 선언이 트랜잭션 `try { … }` 블록 **안**으로 들어갔는데, 커밋 뒤 실시간 알림 줄은 블록 **밖**에서 `meta` 를 읽는다 → `ReferenceError: meta is not defined` → 그 줄을 감싼 `try {} catch (_) {}` 가 **아무 기록 없이 삼켰다**(결정 362 때 블록이 `else { … }` 로 한 겹 더 들어갔을 뿐 같은 상태).
  - 실측(main · PGlite + 진짜 `utils/sse` 에 가짜 리뷰어 연결): 저장 1 · 리뷰어 연결에 써진 `cs_message` 0 · 경고 로그 0. 관리자 화면 갱신 방송(`broadcast`)은 다음 줄이라 나가고 있었다 — 그래서 관리자 쪽에선 이상이 안 보였다.
  - 리뷰어는 대화창을 다시 열거나, 20초마다 도는 미확인 숫자 안전망(`refreshUnread`)이 돌 때에야 알았다. 대화창을 열어 둔 채 기다리면 새 안내가 안 뜬다.

## 규칙
1. **실시간 알림이 읽는 값(`meta`·`_fid`)은 트랜잭션 블록 밖에서 만든다** — DB 와 무관한 순수 값이다. 블록 안에서 선언하면 커밋 뒤 줄에서 이름이 사라진다. 위치는 `senderName` 바로 아래(= `pool.connect()` 전).
2. **실시간 알림은 커밋 뒤, 저장된 메시지 하나에 정확히 한 번** — 순서와 갈래는 종전 구조 그대로다:
   - 새로 저장(COMMIT) → 그 리뷰어(phone8) 연결에만 알림 1 + 관리자 화면 갱신 방송 1.
   - 같은 키 다시 보내기(`duplicate:true` · 결정 362) → ROLLBACK 뒤 바로 반환 — **알림 0 · 방송 0 · 미확인 +1 0**.
   - 같은 키·다른 글(409 계열) · 저장 실패 → `null` — 알림 0.
   - 칸 없는 DB(migration 221 전)에서 키가 있으면 키 없이 한 번 더 부르는 갈래 → 첫 시도는 저장·알림 0, 두 번째에서 알림 1(합계 1).
3. **알림 실패를 맨 `catch (_) {}` 로 삼키지 않는다 — 경고 로그를 남긴다**(fail-soft 유지: 저장은 되돌리지 않고 throw 도 없다). 이번 사고가 석 달 가까이 안 보인 직접 원인이다.
4. **알림 모양은 답장(`POST /api/cs/reply`)이 리뷰어에게 보내는 칸을 전부 갖는다**(`id·threadId·senderRole·senderName·content·imageUrls·createdAt·campaignLabel` + 가산 `msgType·meta`). 보낸 사람 이름은 **리뷰어용 닉네임**(`toReviewerName` — 결정 015 fail-closed). 리뷰어 화면(`reviewer-cs.js`)은 `threadId` 만 보고 ① 그 방을 보고 있으면 대화를 서버에서 다시 읽고 ② 아니면 「관리자 답변이 도착했습니다」 안내 — 두 경우 모두 미확인 숫자는 **서버에서 다시 읽는다**(화면이 스스로 +1 하지 않는다).

## 리뷰어가 겪는 변화
- 위 6가지 안내가 **도착하는 그 순간** 리뷰어 화면에 보인다: 대화창을 열어 두었으면 바로 대화에 뜨고, 아니면 「관리자 답변이 도착했습니다」 알림 + 하단 1:1문의 숫자가 곧바로 갱신된다(종전엔 최대 20초 뒤 숫자만, 또는 다시 열어야).
- **미확인 숫자는 두 번 오르지 않는다** — 숫자는 저장 트랜잭션에서 한 번 오르고(`reviewer_unread_count + 1`, 종전 그대로), 실시간 알림은 화면에 「서버 숫자를 다시 읽어라」고 알릴 뿐이다.
- **문자·알림톡은 새로 나가지 않는다** — 이 수정은 앱 안 실시간 알림(SSE) 한 줄만 살린다. 문자·알림톡은 호출부가 따로 보내는 것이고 반환값(성공 객체 | `null`)·저장 쪽은 한 글자도 안 바뀐다.

## 완화 금지
- **`meta` 를 다시 트랜잭션 블록 안으로 옮기지 않는다** · **커밋 뒤 실시간 알림 줄의 catch 를 다시 맨 `catch (_) {}` 로 바꾸지 않는다** · **다시 보내기(`duplicate`)·실패 갈래에서 알림을 내지 않는다**(결정 362 그대로) · **알림을 COMMIT 전으로 당기지 않는다**(롤백된 메시지를 리뷰어가 보게 된다).
- 가드: `server/tests/csAdminNoticePush.test.js`(32건 — PGlite 실제 SQL + **진짜 `utils/sse`** 에 리뷰어 A·B·관리자 가짜 연결: 카드 없는 안내·카드 안내·키 첫 전송/다시/충돌/동시·저장 실패 주입·칸 없는 DB·실제 notify-participants 라우트·답장 알림과 칸 비교·COMMIT 뒤 순서·구조 고정 2건 · `reviewer-cs.js` vm 으로 화면이 알림을 받아 대화를 다시 읽는지). main 에서는 「그 리뷰어 연결에 실시간 알림 정확히 1」(n=0)에서 실패한다.
