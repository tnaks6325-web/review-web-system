# 리뷰 자동검수 — 1차 필터(첨부 즉시) + 2차 검수(제출 후), migration 081
- **설계 문서**: `frontend/docs/prd-review-auto-inspection.html`(기술) · `리뷰자동검수_와이어프레임.html`(화면 9종·채널 4종 판별 단서).
- ★★ **검수는 두 층**: **1차 = 캡처를 첨부하는 순간**(리뷰 화면인가·어느 채널인가) / **2차 = 제출 이후**(상품명·같은 파일·본문 겹침). 1차를 첨부 시점에 두는 이유 = 그때는 **Drive에도 원장에도 아무것도 없어 파일만 바꾸면 끝**이지만, 제출 후엔 교체요청→리뷰어 재제출 왕복이 생긴다. 상품명·중복·유사도를 1차로 올리지 않는 이유 = 기준 미등록 탭이 많아 오탐 위험이 크고, 중복·겹침은 **저장된 다른 제출과 대조해야** 나와 첨부 시점엔 비교 대상 자체가 없다.
- ★★ **AI 콜 순증 0**: `classifySubmissionImage` 캐시 키가 **이미지 해시**라 1차 판정이 제출 시 캐시 히트된다. 게다가 `review-upload`는 기존 `verifyCapture`가 같은 이미지로 이미 classify를 돌려 **캐시를 데워 놓으므로**, 2차 검수의 classify는 항상 캐시 히트다. 프롬프트는 **필드 추가만**(kind 판정 3줄은 한 글자도 불변 — 기존 슬롯 검수가 그대로 쓴다). 캐시 접두는 `classify:`→`classify2:`(옛 캐시가 새 필드 없이 히트하는 것 차단, 회귀가드는 `classify\d*:`로 버전 상향 허용).
- ★★ **차단은 한 갈래뿐**(완화·확대 금지): `kind='other'` AND 확신 ≥ `REVIEW_PRECHECK_BLOCK_CONFIDENCE`(0.9). **채널 불일치·상품명 불일치·중복·유사도는 절대 차단하지 않는다**(경고 또는 사후 분류) — 탭 채널은 상품 URL 호스트 **추정값**이라 우리 쪽이 틀릴 수 있고, 우리 오류로 리뷰어를 막으면 안 된다. **카카오메이커스는 채널 전체가 잠금 제외**(`REVIEW_PRECHECK_EXEMPT`) — 별점 있는 후기 화면과 **별점 없는 피드형**이 공존해 리뷰어가 어느 쪽을 캡처할지 통제할 수 없다.
- ★★ **우회로 제거 금지**: 같은 슬롯에서 2회 잠기면 "제가 올린 게 맞습니다" 체크가 열린다(`_PRE_BLOCK_LIMIT`). AI 오판으로 리뷰어가 **제출 자체를 못 하는 상태 = 참여 소각**은 불량 1건을 놓치는 것과 비교가 안 되는 사고다. fail-open 전면 적용 — AI 미설정·오류·타임아웃·저확신·네트워크 실패는 전부 **무판정 통과**(화면에 아무것도 안 뜸), precheck 라우트는 어떤 예외에도 200 통과 응답.
- ★ **첨부 경로 3곳 전부**에 1차 필터를 건다(`search-app.js`): 단일 행(`addFiles`) · 다건(`_mrAddFiles`) · 캡처 슬롯(`_csAddFiles`). 한 곳만 걸면 **대부분의 탭이 필터 밖**에 남는다(슬롯 모드는 현영 2슬롯 탭 전용). 제출 게이트도 2곳(`submitReview`·`_submitReviewSlots`). 관리자 미리보기(`_PREVIEW_MODE`)에서는 미실행. 안내문에 `stopPropagation` 필수 — 드롭존 onclick이 파일 선택창을 열어 **우회 체크를 못 누르는** 실측 함정.
- ★★ **본문 유사도 판정식은 `similarity` 단독이면 무력하다**(로컬 PG16 실측): 가장 흔한 복붙 수법인 "원문 + 문장 한두 개 추가"가 **0.859 / 0.718** 로 90% 기준을 빠져나간다. → `GREATEST(similarity, word_similarity 양방향)`으로 잡되(둘 다 1.000), word_similarity만 쓰면 **짧은 문구가 긴 글에 통째로 포함될 때 1.000 오탐**이 나므로 **길이비 가드**(`REVIEW_INSPECT_SIM_LEN_RATIO` 0.5) — 길이가 비슷할 때만 포함관계를 본다(오탐 케이스 길이비 0.29 → 0.298로 하락). 짧은 글(`REVIEW_INSPECT_MIN_TEXT` 30자 미만)은 애초에 비교 안 함(관용구 오탐).
- **중복 판정**: 업로드 시 SHA-256을 `review_submissions.file_hash`에 **INSERT와 함께** 기록(나중 UPDATE로 미루면 그 사이 올라온 파일이 대조 대상을 놓친다). ★ **같은 (시트·탭·행·리뷰어) 재업로드는 중복이 아니다** — Drive는 재업로드마다 새 file_id를 만들어 이걸 잡으면 정상 재제출이 전부 불량이 된다.
- **제출자명 검수는 하지 않는다**(수집만): 리뷰 화면 작성자는 `김**`·닉네임이라 실명 대조가 구조적으로 불가능 — 억지로 판정하면 멀쩡한 제출이 무더기로 의심 처리된다.
- **킬스위치**: `REVIEW_PRECHECK=0`(1차 전체) · `REVIEW_PRECHECK_BLOCK=0`(**판정만 하고 잠그지 않는 관측 모드 — 운영 초기 권장**) · `REVIEW_INSPECT=0`(2차 전체).
- **기대 상품명 공급(조건 ②를 살리는 재료)**: 우선순위 = ① 탭에 직접 적어둔 `tab_configs.inspect_product_names` → ② 연결된 작업오더에서 파생(`productNamesFromWorkOrder` — `product_options_json`의 `name` + `product_option` 텍스트 줄 단위, 가격 꼬리 제거, **"옵션 없음/단일/해당없음"류 서술 제외**). ①이 있으면 ②는 안 본다(관리자 명시가 최우선, 빈 값 저장 = 해제 → ②로 복귀). **후보는 넉넉히** 모은다 — 하나라도 맞으면 통과라 후보가 많을수록 오탐이 줄고 미탐만 조금 는다(이 기능의 실패 선호와 일치). 기대값이 없으면 대조 자체를 skip 하고 **화면이 그 사실을 알려준다**(조건이 죽어 있는 걸 모르면 안 된다).
- ★★ **작업오더 링크는 `ORDER BY`로 우선순위를 명시**(실측 버그): Track B 링크(`trackb_work_order_links`)와 `work_orders.linked_tab_*` 폴백을 **`OR`로만 묶으면** 링크가 있어도 `created_at`이 더 최근인 폴백 오더가 이겨 **엉뚱한 상품명으로 대조**한다. `CASE WHEN EXISTS(링크) THEN 0 ELSE 1 END`을 정렬 첫 키로 둔다. `work_orders`는 **읽기만**(Track A 승인 흐름이 `linked_tab_*`를 보고 분기).
- **관리자 화면(M3)**: 리뷰웹시스템[3버전] **"리뷰검수" 탭**(`/api/trackb/review-inspect/*` — list·resolve·product-names GET/POST). 권한은 **이미지 교체요청 탭과 동일**(`_reInternal`: master/admin 전체 · staff 담당 탭만 · **광고주 차단** — 검수 근거에 리뷰어 실명·본문 OCR이 실린다). 탭 미지정 staff는 `scopedActiveTabs`로 거르고 집계도 같은 기준으로 다시 센다. 기본 필터 = **의심+불량**(통과까지 나열하면 볼 것이 묻힌다), 카드에 **판정 근거를 문장으로**(어느 탭 누구 것과 겹쳤는지 — 열어보지 않고 판단되게), 중복 건은 **나란히 보기**, [확인 처리]는 `status='resolved'`로 종결하되 **원판정 `checks`는 보존**(오탐 누적이 임계값 조정의 근거).
- **상품명 군집판단·학습(migration 148)**: 상품명 의심은 `같은 sheet_id·tab_name + 같은 기대 상품명 후보 묶음 + 같은 OCR 표기`를 SHA-256 안정 키로 묶어 관리자 화면의 `[🏷 상품명 군집판단]`에서 한 번만 판단한다. 선택은 **통과 / 미통과 / 판단불가 / 기준 상품명 오류** 네 가지. ★★ 기존 `resolution`은 형식·중복 등 **건 전체 결론**이라 상품명 정답으로 재사용하지 않는다 — 상품명 축은 `product_resolution*`에 별도 기록한다. 통과·미통과만 `tab_configs.inspect_product_rules`에 **그 작업 exact 규칙**으로 저장하고, 판단불가·기준오류는 현재 군집만 종결해 미래 자동판정을 만들지 않는다. 같은 군집이라도 다른 형식·중복·본문 사유가 남으면 그 건은 open 유지. 다른 사유 재검수 시에도 같은 군집의 이미 끝난 상품명 판단은 보존하고, 마지막 다른 사유가 사라질 때 전체 건을 종결한다. ★ 과거 호환 `[정상]` 별칭 학습은 **상품명 warn 단독 건**만 허용 — 복합 사유 전체 종결을 상품명 정답으로 오해해 탭 별칭을 오염시키지 않는다. 조회·학습 API는 미래 판정 기준을 바꾸므로 `adminOrMaster` 전용. 회귀가드 `tests/reviewProductClusterLearning.test.js`.
- **판별 예시이미지(few-shot, 9슬롯)**: `utils/reviewSampleChannels.js` 단일 출처(채널 4종 × PC/모바일 + **`kakao_feed`**). 관리자가 등록하면 판정 시 프롬프트에 실물 예시를 동봉해 채널 판별 정확도가 오른다. ★★ **캐시 키에 예시 지문(`sampleSig`)을 반드시 섞는다** — 안 그러면 예시를 등록·교체해도 옛 판정이 히트해 등록이 무의미해진다. ★★ **호출부가 모두 같은 samples를 넘겨야 한다** — `review-upload`의 `verifyCapture`와 2차 검수가 다른 값을 쓰면 캐시 키가 갈려 **같은 이미지에 AI 콜이 두 번** 나간다(순증 0 전제가 깨짐). 그래서 예시는 **파일 루프 밖에서 1회** 준비해 양쪽에 같이 준다. ★ 채널을 모르면 **미동봉**(9장을 다 보내면 토큰·지연이 커져 첨부 즉시 판별의 응답성을 해친다), 등록된 예시가 없으면 빈 배열 = **오늘과 동작 동일**. 저장은 adminOrMaster(전사 설정), 조회는 내부인.
- **M2 배치 스윕**(cron `4-59/10`, `withJobLock('review_inspect_sweep')`): ① `pending` 재시도 ② **검수 이력 없는 과거 제출분**(최근 `REVIEW_INSPECT_BACKFILL_DAYS` 30일) 따라잡기. 건당 Drive 다운로드 1회 + AI 1콜, **사이클 캡** `REVIEW_INSPECT_BATCH`(20). **시트 API 무접촉**. ★ 재시도 상한 `REVIEW_INSPECT_MAX_ATTEMPTS`(3) 초과는 `unverifiable`로 종결(무한 재시도 금지 — 스마트빌드 실패 시트와 같은 규율). ★ 과거분은 원장에 지문이 없으므로 이번에 계산해 채운다(이후 중복 대조의 재료). ★ **절대 throw 안 함**(cron이 죽으면 안 된다). 수동 실행 `POST /review-inspect/sweep`(adminOrMaster, 같은 락).
- **M4 확장**: ① **전역 유사도** `REVIEW_INSPECT_SIM_SCOPE=global`(기본 `tab`) — 다른 캠페인에 같은 글을 돌려쓰는 것까지 잡지만 비교 대상이 전체로 늘어 무거워진다. ② **작성자 표기 재사용**(`findAuthorReuse`) — 실명 대조가 아니라 **같은 마스킹 표기가 다른 리뷰어 제출에 반복 등장**하는 패턴만 본다(한 계정으로 여러 명 대행 신호). **경고 전용·차단 없음**, 같은 리뷰어 본인 제출은 제외, 2자 미만 표기는 비교 안 함. ③ **검수 결과 CSV**(`GET /review-inspect/export.csv`, UTF-8 BOM, 판정사유 문장화).
- ★ **지각 해시(dHash)는 구현하지 않았다 — 도메인 부적합**: 같은 캠페인의 리뷰 캡처는 **상품 썸네일과 화면 레이아웃을 공유**해 픽셀 해시가 서로 비슷하게 나온다(구조적 오탐). 게다가 잡으려던 "크롭·밝기 조정한 재사용"은 **텍스트가 같아 본문 유사도가 이미 잡는다**. 순증 가치가 낮고 이미지 디코더 의존성까지 필요해 **의도적으로 제외**했다(다시 검토할 땐 이 두 가지를 먼저 반박할 것).
