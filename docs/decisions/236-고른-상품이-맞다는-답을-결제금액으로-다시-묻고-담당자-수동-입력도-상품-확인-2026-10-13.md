# ★★★ "고른 상품이 맞다"는 답을 결제금액으로 한 번 더 묻는다 · 담당자 수동 입력도 상품 확인을 거친다 (사용자 확정 2026-10-13 · 스키마 변경 0)

## 발단 — 위드프렌즈 사례 재현(2026-10-13, 로컬 가짜 데이터 + 당시 실제 AI 판독값)
- 결정 230 이후 실제 잘못 구매 3건(10/1 8000FS→HD1590 · 1450HM→8000FS / 10/8 탄소매트 퀸더블→킹)은 모두 경고 → 제출 불가로 막혔다(옛 코드는 셋 다 그대로 접수). 정상 40건 오경고 0.
- 남은 틈 두 개:
  1. **담당자 수동 입력**(외부모집 수동제출 · 결정 143·211)은 상품 확인을 거치지 않았다. 10/8 탄소매트 수동 입력(킹으로 넣었는데 결제 69,800원 = 퀸더블 가격)·
     조○○(10/12 탄소매트 미니싱글로 신청 → 명의 불일치로 막힘 → 담당자가 다른 공고 가습기 HD2200 으로 수동 등록)가 그대로 들어갔다.
  2. 리뷰어가 첫 경고에서 **사실과 다르게 "고른 상품이 맞다"**고 답하면 그냥 접수됐다(이상로그만).

## 결정 (사용자 확정 2026-10-13)
### ④ 리뷰어 — "고른 상품이 맞다" + 결제금액이 다른 상품 가격 → 한 번 더 묻는다
- 조건: 상품 가격이 2종 이상 · 결제금액이 고른 상품 가격과 다름 · **다른 상품 하나의 가격과 정확히 같음**(`priceOtherOption` — 결정 230 의 금액 규칙과 같은 함수, 단일 출처).
  가격이 같은 상품끼리·어느 가격과도 안 맞는 금액(쿠폰 등)은 근거가 없어 묻지 않는다("막을 방법은 없다" — 사용자).
- 서버가 `PRODUCT_PRICE_RECHECK`(쓰기 0) → 같은 창(`_pmvAsk(res, n, "recheck")`): 제목 "결제금액을 다시 확인해 주세요",
  "○○를 주문했다고 하셨지만, 결제금액 N원은 △△ 결제금액이에요. 잘못 구매한 것으로 보여요."
  - 「다시 확인할게요」(닫기) → 제출 안 함.
  - 금액이 같은 상품을 고름 → 그 키로 다시 보내 서버가 `PRODUCT_WRONG_PURCHASE` 로 막는다(결정 230 그대로).
  - 고른 상품을 다시 고름(「이 상품이 맞아요 · 제출」) → `priceRecheckAck:"true"` → **(가) 접수** + 이상로그 `capture_price_mismatch_confirmed`(신청 번호 포함 — 같은 상품 쌍이라도 사람마다 따로 남는다).
  - (가)인 이유: 운영 캡처 117건 시험에서 의류 5건이 3,000원 쿠폰 때문에 다른 상품 가격과 우연히 같았다 — 막으면 정상 구매자도 막힌다.
- 결정 230 의 「캡처는 다른 상품 — 리뷰어가 고른 상품이 맞다고 확인」 기록에도 신청 번호를 넣고 신청마다 따로 남긴다(같은 상품 쌍이 한 줄로 합쳐져 마지막 사람만 보이던 문제 — 아래 Codex 반영).
- 첫 창이 결제금액 근거여도 "맞다"고 하면 다시 묻는다(두 번 묻기) — "한 번만 묻기"(첫 창에 근거를 모두 적고 바로 접수) 시험판과 화면 비교 후 사용자 확정(2026-10-13).
  운영 캡처 117건에서 정상 구매자가 창을 본 경우 0 · 창은 잘못 산 4건에만 → 두 번 묻는 부담은 잘못 산 사람에게만 간다.

### ⑤ 담당자 수동 입력도 상품 확인
- `POST /manual-order/submit`(작업보드 경로 `/api/trackb/manual-order/submit` 포함) — 새 화면(`productCheck:true`)이면 배치를 시작하기 **전에**
  `productMismatchVerify.checkManualEntries` 로 줄마다 본다. 대상 공고 = 공고 화면 경로는 그 공고, 작업보드 경로는 탭에 연결된 공고(`tabOptionChoices`).
  - 결제금액 — `priceOtherOption`(④와 같은 규칙).
  - 붙인 캡처의 글자 — `capturedOtherOption`(결정 230 과 같은 규칙 · 화면이 캡처 판독 `productName/productOption` 을 보낸다).
  - 참여 신청 기록 — 그 연락처가 최근 **12시간** 안에 신청만 하고 접수되지 않은 신청(applied·expired)이 있는데 **이 공고·이 상품과 맞는 것이 하나도 없으면** 가장 최근 신청을 알린다(다른 공고 포함 — 조○○).
    - 12시간인 이유(운영 읽기 전용 실측 2026-10-13 · 지난 30일 수동 입력 145건): 3일이면 14건(10%)이 걸리고 그중 12건이 20~68시간 전 **무관한 공고의 만료 신청**(오경고).
      12시간이면 2건 — 1시간 전 다른 공고 신청(조○○)·4시간 전 같은 브랜드 다른 맛(자몽 신청 → 레몬 입력), 둘 다 확인할 만한 건.
    - 신청 기록만 걸린 줄뿐이면 확인창 첫 줄을 "방금 다른 상품·공고로 참여 신청한 연락처예요"로 쓴다("다른 상품을 샀다"고 단정하지 않는다).
  - 어차피 접수 단계에서 거절될 줄(필수 칸 빔·전화 자릿수)과 공고 목록에 없는 상품을 고른 줄의 금액·캡처 근거는 판정하지 않는다.
    공고 화면에서 신청을 골라 확정(`targetApplicationId`)하면 그 신청의 상품이 고른 상품이고, 신청 기록 대조는 하지 않는다.
- 걸린 줄이 있으면 **쓰기 0건**으로 `needConfirm:'product_check'`(재참여·오늘 몫 사전 판정과 같은 이유 — 부분 처리를 남기지 않는다).
  화면은 확인창: [확인] 그대로 접수(**(가)** — 결과에 "상품 확인 경고를 확인하고 접수(관리자 확인됨)" + 이상로그 `manual_product_mismatch_confirmed`) /
  [취소] 아무것도 접수 안 됨 → 그 줄에 "⚠ 상품 확인: …" 이유를 붙여 표로 돌아간다(상품·결제금액·연락처를 고치면 사라진다).
  - (가)인 이유: 리뷰어 화면은 잘못 구매를 "담당자에게 문의"로 보낸다 — 담당자까지 막으면 그 주문을 넣을 길이 없다.

## 코드리뷰 반영
- 공고에 없는 "확인한 상품" 값(`confirmedProductKey`)은 답이 아닌 것으로 보고 판정을 계속한다 — 종전(230)엔 그대로 통과해 경고·다시 묻기를 **기록 없이** 건너뛸 수 있었다.
- 금액 불일치 접수 기록에 캡처 상품도 함께 남긴다. 수동 입력 줄의 이유 표시는 신청을 바꿔 고르거나 캡처를 새로 붙여도 지운다.

## Codex 리뷰 반영 (PR #1615)
- 확인 기록 지문은 숫자를 지워(`fingerprint`) 신청 번호만으로는 사람마다 갈리지 않았다 → `logAbnormal({fingerprintKey})` — 숫자를 지우지 않는 key 를 지문에 더한다.
  **key 가 없으면 종전과 같은 입력**이라 기존 활성 기록의 지문은 바뀌지 않는다. 리뷰어 "맞다" 기록 = `app-<신청>` · 수동 입력 확인 = `os-<주문>`(잘못 구매 막음 기록은 종전대로 합침).
- 신청 기록 대조에서 늦게라도 주문이 붙은 만료 신청(`order_submission_id`·`late_order_id`)은 뺀다 · 12시간 창 전체를 본다(LIMIT 없음).
- 수동 입력: 캡처를 붙이자마자 제출하면 판독 전이라 캡처 근거가 빠졌다 → 제출 전에 판독을 기다린다(`awaitCaptureReads`, 최대 25초 · 1단계 보관함에서 판독 전에 배정된 줄도 다시 읽음).
- 수동 입력: 확인 단계(재참여 → 오늘 몫 → 상품 확인)를 **순서와 무관하게 반복 처리**(창이 열린 사이 앞 단계가 새로 돌아오면 그 창을 다시 띄운다 · 같은 단계는 한 번만).
  `repurchaseGuard`·`manualOrderExternal` 의 글자 검사는 새 재전송 줄도 받도록(의미 불변 — 받은 확인을 잃지 않고 다시 보낸다).
- 금액·연락처를 고쳐 이유가 지워지면 상품 칸의 문구도 함께 지운다.

## 완화 금지
- ★★ 금액 근거는 `priceOtherOption` 하나 — "다른 상품 **하나**의 가격과 **정확히** 같을 때만". 가격이 같은 상품이 둘이거나 고른 상품 가격과 같으면 근거 없음.
  넓히면(가까운 금액·여러 상품 중 하나) 쿠폰 할인 정상 구매가 걸린다.
- ★★ 다시 묻기(`recheck`)는 **아무것도 쓰기 전에** 돌려준다(신원 게이트·접수보다 앞). `priceRecheckAck` 는 `true`/`"true"` 만.
- ★★ 수동 입력 상품 확인은 **배치 시작 전 쓰기 0** — 루프 안에서 줄별로 거절하지 않는다(결정 143 의 부분 처리 금지).
- ★ 옛 화면(`productCheck` 없음)은 판정하지 않는다 — 배포 직후 캐시 화면에서 이미 산 주문이 기록되지 않는 쪽이 더 나쁘다(결정 211 규율).
- ★★ 화면이 보낸 `confirmedProductKey` 가 공고 상품이 아니면 **무시하고 판정을 계속**한다 — 통과(`none`)로 되돌리지 않는다.
- ★ 신청 기록 대조 창은 12시간 — 넓히면 무관한 만료 신청으로 수동 입력 오경고가 늘어 담당자가 습관적으로 [확인]을 누르게 된다.
- ★★ `fingerprint()` 의 key 는 **있을 때만** 지문 입력에 더한다 — 늘 더하면 기존 활성 이상로그 전부가 새 지문으로 갈라져 중복 행이 생긴다.
- ★ 판정 실패·조회 실패 = 걸지 않음(fail-open). 스위치 `CAMPAIGN_PRODUCT_VERIFY=0` 이면 ④⑤ 모두 즉시 종전.

## 배포 스큐
- 새 서버 + 옛 리뷰어 화면(230 판): 다시 묻기 코드를 몰라 서버 문구("…다시 확인해 주세요 (화면을 새로고침한 뒤 다시 제출해 주세요)")를 실패 알림으로 보여 주고 그 주문은 멈춘다 — 새로고침하면 창이 뜬다.
- 새 서버 + 옛 수동 입력 화면: `productCheck` 를 안 보내 종전대로 접수. 화면 파일 판 올림(`manual-order.js?v=20261013-prodcheck`).
- 옛 서버 + 새 화면: 서버가 `PRODUCT_PRICE_RECHECK`·`product_check` 를 안 보내므로 화면 동작 종전.
