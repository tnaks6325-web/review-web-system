# ★★ 리뷰어 홈 헛요청 줄이기 + 요청 제한은 실제 사용자 주소로 (사용자 확정 2026-09-28)

- **발단**: 리뷰어 홈을 열 때 요청 수를 줄이라는 요청(188 후속). 운영 로그를 떠 보니 줄일 것보다 **새는 곳**이 더 컸다.
- ★★★ **req.ip 는 사용자 주소가 아니었다(운영 실측)**: 서버 접속 기록의 주소가 전부 Railway 프록시(152.233.x) 몇 개로 모였다. `trust proxy 1` 로는 프록시가 한 겹 더 있어 실제 주소가 안 나온다. ⇒ 종전 "주소별 120" 과 이미지·로그인 등 **모든 요청 제한이 사실상 전 사용자 공용 통**이었다(이미지 분석 분당 10 을 모든 리뷰어가 나눠 씀). Railway 공식 문서대로 **`X-Real-IP`** 를 실제 주소로 쓴다(`rateLimit.middleware.clientIp` 단일 출처 — 전 제한기 7종이 이것 또는 사람별 신원으로 센다, 회귀가드가 개수로 고정). 형식이 주소가 아니면 `req.ip` 로 접는다 · 스위치 `RL_TRUST_X_REAL_IP=0`.
- ★★ **실시간 알림(1:1문의 답장) 연결이 3초마다 헛재시도**: 리뷰어 앱 서비스워커가 API 서버로 가는 요청까지 다시 보내면서 실시간 알림(EventSource) 요청에 `Cache-Control` 헤더가 붙었고, 서버 CORS 허용 목록에 없어 사전 확인만 반복됐다(운영 로그: 한 기기 43초에 사전확인 16번). **리뷰어는 사실상 실시간 답장을 못 받고 있었다.** 수정 2겹(어느 쪽만 배포돼도 풀린다): ① 서버 CORS 허용 헤더에 `Cache-Control`·`Last-Event-ID` ② 서비스워커는 **다른 주소(API) 요청과 event-stream 을 가로채지 않는다**(API 응답은 원래 캐시하지 않아 동작 차이 없음, 버전 v2).
- ★ 연결이 되살아나면 새 상시 연결이 생긴다 → 연결 수 상한(200)에서 밀려난 리뷰어가 3초마다 다시 붙어 서로 밀어내지 않도록 **리뷰어 재연결 간격 30초**(`retry:` 필드, 관리자는 종전 3초). 끊긴 사이는 기존 20초 미확인 수 갱신이 메운다.
- **홈 진입 헛요청 제거(화면 동작 불변)**:
  - 1:1문의 미확인 수 — 초기화와 세션 동기화가 동시에 불러 2번 → **합친다**(2초 안 재호출 합침). ★ 새 메시지 도착·방 열람·20초 주기는 `force` 로 즉시.
  - 공고수정 권한 확인 — 허용명단 밖(대부분)은 매번 401 → **같은 탭에서 10분 기억**(계정별). 새 로그인(`doLogin`)은 기억을 지운다 · 서버 오류는 기억하지 않는다. ⚠ 마스터가 허용명단에 새로 넣으면 최대 10분 또는 재로그인 뒤 반영.
  - 리뷰내역 — 새 조회가 아직 안 열린 리뷰어(대부분)는 "확인 1 + 옛 조회 1" 두 번 → **옛 조회 상태를 10분 기억**해 한 번으로. 옛 조회는 새 조회가 열린 뒤에도 정확하다.
  - 캠페인 화면 조회에 로그인 리뷰어 번호를 붙였다(188).
- 실측(브라우저, 서버 응답 스텁): 다시 열 때 13 → 10 요청, 자바스크립트 오류 0.
- ⚠ **남은 문제(별건)**: 「리뷰 미작성 경고」(`/overdue-review-warning`) 는 조회가 1.5초 제한을 넘겨 **약 절반이 503**(하루 1,400건) — 경고가 조용히 안 뜬다. 「받을 예정 금액」도 약 9% 503. 조회 최적화가 필요하다.
