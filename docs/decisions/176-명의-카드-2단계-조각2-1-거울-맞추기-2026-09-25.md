# ★★ 명의 카드 — 2단계 조각 2-1: 카드를 리뷰어 정보에 맞추는 거울 (스키마 변경 0, 2026-09-25)

- **배경**: 조각 1(175)로 운영 카드 4,317장(소유자 3,330명)이 만들어졌지만, 그 뒤 리뷰어 정보(`reviewers` + `sub_accounts`)가 바뀌어도 카드는 따라가지 않았다. 쓰는 곳이 19곳(그중 `sub_accounts` 쓰기 8곳)이라 한 번에 모두 바꾸면 위험이 크다(레드팀 지적 — 잠금 순서·경합·오래된 칸 순번·전화번호 기준 쓰기). 그래서 조각 2를 둘로 나눴다.
  - **2-1(이 기록)**: 쓰는 곳 19곳은 **건드리지 않고**, 10분마다 달라진 리뷰어만 골라 카드를 맞춘다.
  - **2-2(다음)**: 쓰는 곳을 창구 하나로 모으고, 그 과정에서 드러난 기존 버그를 고친다.
- ★★ **진실원본은 여전히 `sub_accounts`** — 카드는 그 거울이다. 아직 아무도 카드를 읽지 않는다(175 약속 ① 유지).
- ★★ **175 약속 ④("빈 칸만 채움")를 대체한다**: 거울이므로 목록의 값이 바뀌면 카드 값도 **덮는다**. 목록에서 사라진 타계정 카드는 **지우지 않고 내린다**(`removed_at`). 같은 이름·번호가 다시 생기면 **새로 만들지 않고 되살린다**(UUID 유지 — 조각 3 에서 주문이 이 UUID 에 묶인다).
- ★★ **완화 금지**:
  - ① **합친 카드(`merged_into`)는 다시 만들지 않는다** — 담당자가 합친 명의를 거울이 되살리면 합치기가 무효가 된다.
  - ② **본인 카드는 내리지 않는다** — 본인 이름·번호가 바뀌면 그 카드를 고친다.
  - ③ 적용 순서 = 내리기 → 본인 → 타계정 수정 → 되살리기 → 새로 만들기. 유일 인덱스(소유자·이름·번호, 본인 1장)와 부딪히지 않게 한다. 되살릴 때는 종류(본인/타계정)를 다시 정한다.
  - ④ 잠금 = 리뷰어 행 `FOR NO KEY UPDATE` → 카드 `FOR UPDATE`. `FOR UPDATE` 로 리뷰어 행을 잡으면 다른 표의 FK 자식 INSERT(참여·주문)까지 막는다.
  - ⑤ `lock_timeout` 2초 — 저장 중인 리뷰어와 부딪히면 기다리지 않고 `busy` 로 세고 다음 주기에 다시 한다(라이브 저장을 막지 않는다).
  - ⑥ 소유자마다 한 트랜잭션 · 표가 없으면(42P01) 성공으로 꾸미지 않고 멈춘다.
- **실행**: 크론 `7-59/10 * * * *` + `withJobLock('identity_cards_reconcile')`. 끄기 = Railway `IDENTITY_CARDS_RECONCILE=0`, 주기 = `IDENTITY_CARDS_RECONCILE_SCHEDULE`.
  - 수동: `GET /api/trackb/identity-cards/drift`(쓰기 0 · 달라진 리뷰어 수) · `POST /api/trackb/identity-cards/reconcile {confirm:true}`. 둘 다 adminOrMaster.
  - 조각 1 의 `applyCards`(백필)도 같은 `syncOwnerCards` 를 쓴다(규칙 사본 0).
- ⚠ **남은 한계**: 최대 10분 늦는다(아무도 안 읽으므로 무해). 리뷰어 전체를 매 주기 읽는다(약 3,300행 — 지금 규모에서는 가볍다).
- 회귀가드: `tests/reviewerIdentityCardsMirror.test.js`(22 — 계획 순수함수 11 · 배선 4 · 진짜 PG 7: 이름 맞바꿈·번호 변경·되살리기·합친 카드 유지·FK 자식 INSERT 가 막히지 않음·잠금 시 busy). `tests/reviewerIdentityCards.test.js`(17 — 빈 칸만 채움 → 값이 바뀌면 따라감으로 갱신).
  - 변이시험: 합친 카드 재생성 · 되살림 대신 새로 만들기 · 되살릴 때 종류 미지정 — 검출.
  - "적용 순서 정렬 제거"·"본인과 같아진 타계정 먼저 내리기 제거"는 검출되지 않았다. **같은 결과를 내는 변이**다 — 계획이 이미 그 순서로 쌓이고, 목록을 읽을 때 본인과 같은 타계정은 본인으로 접히기 때문이다. 정렬과 선제 제거는 쌓는 순서가 바뀔 때를 대비한 이중 방어로 남긴다.
