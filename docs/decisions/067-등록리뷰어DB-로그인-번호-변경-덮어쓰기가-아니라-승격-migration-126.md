# ★★ 등록리뷰어DB 로그인 번호 변경 — 덮어쓰기가 아니라 "승격" (migration 126)
- **배경**: `reviewers.phone` 을 바꾸면 파생 컬럼 `phone8`(GENERATED, 001:99)이 통째로 바뀌는데, 이 시스템의 참여·주문·문의·정산·차단이 전부 phone8 을 신원키로 쓴다. 그래서 번호 변경은 "칸 하나 수정"이 아니라 **신원키 교체**다. 종전에는 창구가 아예 없었고(등록리뷰어DB 는 `admin_memo` 만 수정), DB 직수정은 **그 사람의 참여 내역이 화면에서 통째로 사라지는** 조작이었다.
- ★★ **채택 방식 = 승격**: 새 번호 → `reviewers.phone`(본계정) / 옛 번호 → `sub_accounts` 항목(같은 이름). 그러면 아래 세 경로가 **기존 코드 그대로** 과거를 계속 본다(분기·사본 0) — 리뷰 내역·검색 `search.service._getReviewerPhoneList`(본인+타계정 phone8) · `/api/reviewer/review-earnings`(같은 phoneList) · 리뷰비 계좌 `payment.service._loadAccounts`(타계정 매핑 + 빈 계좌는 소유자 계좌 COALESCE).
- ★★ **방향이 계약이다(비대칭 함정)** — `_getReviewerPhoneList(p8)` 는 `reviewers WHERE phone8=$1` 로 소유자 행을 찾는다. **옛 번호를 본계정으로 남기면** 새 번호 세션이 소유자 행을 못 찾아(sub 로그인은 세션 phone8 이 타계정 값) 자기 번호 하나만 스코프에 담긴다. 그래서 반드시 **새 번호가 본계정**.
- ★★ **일부러 건드리지 않는 것**: `review_index`(시트 연락처 원문 = 진실원본, stale-pl 보안 게이트가 그 전제 위에 있다) · `participation_links` · `order_submissions` · `campaign_applications` · `payment_batch_items`(회차 스냅샷은 박제값). 승격이 조회를 살리므로 옮길 이유가 없다.
- ★ **이관하는 키**(옛 phone8 에만 매달려 승격으로 안 따라오는 것): `cs_threads.reviewer_phone8` · `campaign_reviewer_gates.phone8` · `reviewer_campaign_editors.phone8`. 셋 다 유니크 제약이 있어 **대상에 이미 행이 있으면 옮기지 않고 건수를 보고**한다(조용한 실패 금지 — 화면이 "옮기지 못한 N건"을 말한다). ★★ **블랙리스트는 옮기지 않고 새 번호를 추가**한다(`blacklist.phone` = 전체 번호 키) — 번호를 갈아 차단을 회피하는 길을 열지 않는다.
- ★★ **fail-closed 차단 4종(force 우회 없음)**: ① 새 번호가 다른 reviewers 행(UNIQUE 충돌 = 계정 병합 사고) ② **뒤 8자리가 타인과 겹침** — `phone8` 은 비유니크라 로그인·검색·계좌 매칭이 섞인다 ③ 새 번호가 **남의 타계정**으로 등록됨 ④ **유효 홀드 보유** — 홀드는 phone8+hold_token 이중 열쇠라 번호가 바뀌면 제출 확정이 막혀 참여가 소각된다(10~15분 뒤 저절로 풀리므로 막다른 길이 아니다). ★ 대상 지목은 언제나 **`reviewers.id`** — `WHERE phone8 =` 는 타인 행까지 함께 바꾼다.
- ★★ **리뷰어 내정보(무인증)에 두지 않는다** — `/api/reviewer/profile` 은 이름+뒤8자리가 전부이고 서버가 `WHERE phone8 = $1` 만 본다. 거기에 번호 변경을 열면 **뒤 8자리만 아는 제3자가 남의 계정을 자기 번호로 가져간다**(주민번호·계좌·리뷰비까지). 창구는 `POST /api/trackb/reviewers/phone`(**adminOrMaster** — 등록리뷰어DB 와 같은 게이트) 하나이고, confirm 없이 부르면 **쓰기 0 미리보기**(차단 사유 + 영향 건수)를 돌려준다.
- ★★ **집계·이관 프로브는 SAVEPOINT 격리**(진짜 PG16 으로 실측) — 프로브 하나가 42703/42P01 로 실패하면 그 뒤 전부가 **25P02(current transaction is aborted)** 로 죽어, "세지 못했을 뿐"이어야 할 fail-soft 가 **변경 전체를 무력화**한다(082 apply 규율과 같은 자리). ★ 변이시험이 이 자리를 뚫었다 — `previewPhoneChange`(pool 경로)만 검사하면 tx 경로 회귀를 못 잡는다.
- ⚠ **곁다리로 고친 무신호 버그**: `/reviewers/delete` 의 주문 집계가 **없는 컬럼**(`order_submissions.phone8` — 그 테이블엔 전체 번호 `phone` 뿐)을 봐 **항상 실패**했고, 확인창이 "구매양식 제출 0건"으로 조용히 속이고 있었다(진짜 PG 로 실행해야만 보인다).
- **화면** = 등록리뷰어DB 연락처 칸 [변경] → 팝업(**body 직속** · **바깥 클릭으로 닫지 않는다**(입력한 번호 보호) · Esc 리스너는 닫을 때 해제 · onclick 은 **인덱스만**). ★ **프론트 재판정 0** — 서버 blockers 를 그대로 그리고, 차단이 있으면 [이대로 변경] 버튼 자체를 만들지 않는다.
- 회귀가드 `tests/reviewerPhoneChange.test.js`(순수함수·스텁 db 차단 4종·라우터 스택 실검사·프론트 배선 + **진짜 PG16 end-to-end**: 승격 후 옛 번호 참여 2건이 실제로 조회되는지(`_getReviewerPhoneList` 실행) · 이관 충돌 보존 · 블랙리스트 승계 · 감사 이력 · 계좌 감사 트리거 통과 · 차단 시 쓰기 0 · 왕복 복구, **변이시험 검출 확인**) + 브라우저 실행검증.
- 잔여(문서화): ① **1:1문의방은 새 번호로 이미 방이 있으면 옮기지 않는다**(둘로 남는다 — 관리자 화면에서 확인) ② 리뷰어에게 "새 번호로 로그인" 안내는 **사람이** 한다(자동 통지 없음) ③ 옛 번호로도 로그인은 되지만(타계정 매칭) 그 세션은 새 번호 참여분을 못 본다 ④ `my-status`·`/cs/threads` 는 단일 phone8 스코프라 옛 번호 건이 그 화면에는 안 뜬다(타계정까지 넓히면 타인 명의 문의방 노출 위험 — 별건).
