# ★★★ 구매시간 글자는 24시간 보통의 한국시간으로 읽는다 — 「1~8시 = 오후」 규칙 제거 · 끝 00:00 = 24:00 · 못 읽으면 지어내지 않음 (사용자 확정 2026-11-18)

## 한 줄
리뷰오더 구매시간 글자 → 모집공고 시간창 해석기(`server/src/utils/purchaseTimeWindow.js` · 화면 사본
`frontend/js/index-recruit.js` `_parsePurchaseTime`)가 **적힌 숫자 그대로 24시간**으로 읽는다.
오후로 읽는 것은 `오후`/`PM`/`저녁`/`밤` 이 붙었을 때뿐이다. 사용자 지시 원문: 「시간읽기 수정해 이상한 규칙말고 24시간 보통의 한국시간으로」.

## 무엇이 터졌나 (2026-11-17 · 11-18 운영)
- 해석기에 `if (h >= 1 && h <= 8) h += 12` (「현장 표기 관행: 2시~5시 = 14~17시」)가 있었다.
  인트라넷 리뷰오더 구매시간은 **0~23시 24시간 고르개**가 만든 `HH:MM ~ HH:MM` 인데 이 규칙이 그 글자에도,
  `오전` 이 붙은 글자에도 그대로 걸렸다.
- 오더 `07:00 ~ 08:00` 으로 새 공고 창을 열면 프리필이 **19:00 ~ 20:00** 으로 들어가 그대로 저장됐다
  (camp_e4a143db7c60 · camp_d5cd506cbb3f — 오전 7시 공고가 저녁 7시에 열림).
- `07:00 ~ 09:00`(시작만 19시가 되고 끝 9시는 그대로 → 시작>끝)·`오전 7~9시`·`14:30 ~ 00:00` 은 **아예 못 읽어** 빈칸/자유시간대가 됐다.
- 게시 연결 검사(`CANON.time`)도 같은 해석기라 `07:00 ~ 08:00` 과 `19:00 ~ 20:00` 을 **같다고 봐서** 아무도 몰랐다.

## 규칙 (완화 금지)
| 글자 | 읽기 |
|---|---|
| `HH:MM` · `H:MM` · `H시` · `H시 MM분` · `H시반` | 적힌 숫자 그대로 0~23시 (`7시` = 07:00, `2시` = 02:00) |
| `오전`/`AM`/`아침`/`새벽` | 그대로, 12시 = 00시 (`오전 13시` = 못 읽음) |
| `오후`/`PM`/`저녁` | 1~11시 +12, 12시 = 12시, 13시 이상 그대로(`오후 13~20시`) |
| `밤` | 오후와 같되 `밤 12시` = 자정 |
| `낮` | 12시·1~6시만(12·13~18시), 나머지는 못 읽음 |
| `정오` / `자정` | 12:00 / 00:00 |
| 앞에만 오전/오후 | 뒤에도 같은 쪽 (`오후 2~5시` = 14~17시, `오전 10시~1시` = 시작≥끝 → 못 읽음) |
| 끝이 `00:00`·`0시`·`24시`·`자정` | **24:00 = 그날 끝** (`14:30 ~ 00:00` = 14:30~24:00) |
| 구분자 | `~` `-` `–` `—` `〜` `～` `부터…까지`, 공백 무관 |
| 시작 ≥ 끝 · 범위 밖 · 한쪽만 있음 | **null(못 읽음)** — 지어내지 않는다(`12시~3시` 도 null) |
| `자유`·`자율` | 종전대로 호출부가 먼저 「자유시간」으로 처리 |

- ★★★ **「표시 없는 1~8시 = 오후」 같은 추측 규칙을 다시 넣지 않는다.** 인트라넷은 24시간 고르개라 숫자가 곧 시각이다.
  애매한 글자는 null 로 두고 사람이 공고 창에서 고르게 한다(종전 「해석 못 하면 아무것도 바꾸지 않는다」 규율 그대로 — 164·168).
- ★ `저녁`/`밤`/`아침`/`새벽`/`낮` 은 사용자 지시 목록에 없지만 넣었다 — 운영 오더에 `저녁7~8시 한시간동안만` 이 실제로 있고,
  빼면 **07:00~08:00 으로 조용히 틀리게** 읽힌다(못 읽음보다 나쁘다). 보통의 한국어 읽기 그대로다.
- ★ 24:00 표현 = **DB `TIME '24:00:00'`** — 기존 관례 그대로(`campaignPayAmountSync` `win.end === '24:00' ? '24:00:00'`,
  `campaignState.timeStrToMinutes('24:00') = 1440`, `inflowSyncPg.test` ⑤). 23:59 로 바꾸지 않는다.

## 두 사본 (결정 164 규율 강화)
- 서버(`purchaseTimeWindow.parsePurchaseTime`)와 화면(`_parsePurchaseTime`)은 **함수 본문이 이름만 빼고 글자 그대로 같다.**
  가드가 ① 실행 결과 대조 ② **기대값 표**(종전엔 두 쪽이 같은지만 보고 값이 맞는지는 안 봤다 — 그래서 07시대 오류를 못 잡았다)
  ③ 본문 글자 비교 ④ `<= 8) h += 12` 재등장 금지 를 고정한다(`server/tests/inflowSourceEdit.test.js` ②).
- 기존 생성 방식(`woCampaignPrefill.generated.js`)은 **화면 → 서버** 방향이고 28개 함수 묶음용이다.
  함수 하나라 생성기 대신 글자 비교 가드로 같은 효과를 냈다.

## 운영 영향 (2026-11-18 21시 읽기 전용 실측)
- 해석 결과가 바뀌는 살아 있는 오더 18건 / 253 — 대부분 「못 읽음 → 바르게 읽음」(`07:00 ~ 09:00` ×6, `14:30 ~ 00:00` ×2, `오전 7~9시` 류 3, `자정 ~ 15시` ×2, `17:00 ~ 00:00`),
  「12시간 밀림 → 바르게」 3(`07:00 ~ 08:00`, `07:00 ~ 07:50`, `오전 6:00~7:15`), **「읽음 → 못 읽음」 1**(`12시~3시`, 6월 실험오더·제출 완료).
  표시 없는 `N시`(1~8) 오더 중 오전으로 뒤집히는 것은 위 `12시~3시` 하나뿐이다.
- 공고 글자 해석 변화 6건 / 180 — 전부 저장된 시간창과 **새 해석이 일치**하는 쪽으로 바뀐다(직원이 손으로 맞춰 둔 값).
  새 해석 ≠ 저장 시간창인 참여형 공고 0건(공고 공유 저장이 새로 409 로 막히는 공고 없음).
- 오더↔공고 맞추기 비교: 연결 쌍 179 중 **새로 「다름」 1쌍**(camp_d5cd506cbb3f — 보관된 초안, 실제로 12시간 밀린 공고라 맞는 판정), 새로 「같음」 0.
- ★ **배포만으로 공고 시간창이 다시 써지는 길은 없다** — 시간창을 쓰는 곳은 직원 저장(`campaign.routes`)·오더 구매시간이 **바뀔 때만** 도는 전파
  (`syncCampaignPurchaseWindow[InTx]`)·공유 맞추기(사람이 누를 때)·게시 연결(게시할 때)뿐이고, cron·시작 시 백필에는 시간 칸 참조가 0이다.
  ⇒ **다음에 그 오더 시간을 고치거나 새 공고를 만들/게시·맞출 때만** 새 규칙이 적용된다.
