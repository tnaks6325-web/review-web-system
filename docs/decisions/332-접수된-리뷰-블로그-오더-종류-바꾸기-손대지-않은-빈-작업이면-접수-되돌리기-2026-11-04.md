# ★★ 접수된 리뷰↔블로그 오더의 체험단 종류 바꾸기 = 손대지 않은 빈 작업이면 접수 되돌리기 (2026-11-04 · 스키마 변경 0)

## 무슨 일이었나
- 사용자 요청(2026-11-03 「2단계」): 오더를 리뷰로 올려 접수까지 했는데 블로그였어야 했다 → 지금은 인트라넷 수정 창이 종류를 영구 잠그고(`REVIEW_ORDER_LOCK_TARGETS`), 리뷰웹도 409 `accepted_kind_locked`(결정 327)로 막아 오더를 지우고 새로 올리는 수밖에 없었다.
- 접수가 종류대로 작업표(블로그 3열·리뷰 형태 배정·Q&A 자리표)를 이미 깔았고 작업표 종류(`tab_configs.work_kind`)는 다시 바뀌지 않는다 — 그래서 "종류만 바꿔 저장"은 오더와 작업표가 갈라진다(결정 327 이 막은 이유).

## 결정
- 종류 바꾸기 = **접수 되돌리기 → 리뷰웹에서 다시 접수**. 작업표를 고치지 않고 지운 뒤 새 종류로 다시 만든다 — 오더 종류 = 작업표 종류 불변식(결정 327)은 그대로 지켜진다.
- 대상: 리뷰↔블로그만(Q&A 는 자리표가 있어 제외) · 상태 `reviewing/revision/rejected/await_chatroom` · 작업표 연결 · 삭제 안 됨.
- 판정 = **결정 254 「손대지 않은 빈 작업」 그대로**(`workTabDelete._untouchedReasons`) + 돈 기록(`_moneyRows`) + 공고가 다른 작업을 가리키면 거부. 예외는 둘뿐:
  1. 바꾸려는 **그 오더 자신**의 연결(`untouched.selfOrderId`)
  2. **게시한 적 없는 임시저장 공고**(`status='draft' AND published_at IS NULL` · `untouched.allowDraftCampaign`) — 접수하면 공고 초안이 바로 생기는 흐름이라 이걸 막으면 바꿀 수 있는 오더가 거의 없다.
- 실행(`order.routes` 원본 수정 · Q&A 잠금·결정 327 잠금 **앞**): 번호가 **정확히 +1** 인 요청만 → `deleteTask({onlyIfUntouched:true, notifyIntranet:false, untouched, beforeCommit})`.
  - `beforeCommit` 이 같은 트랜잭션에서 오더를 `status='submitted'`·공고/광고주/양방향 연결 해제·삭제 표시 지움으로 되돌린다(읽은 번호 그대로일 때만 — 아니면 통째로 ROLLBACK).
  - 성공하면 오더를 다시 읽어 종전 전체 저장으로 새 종류를 쓴다(이제 잠기지 않은 오더). 실패하면 409 `kind_change_blocked` + 사유(아무것도 안 지움).
  - 오더 기록(memo_log)에 `kind:'kind_changed'` 한 줄.
- 수정 창 재료: `GET /intake/source/:id/shared` 가 `kind_change:{allowed, accepted, from, reasons}` 를 싣는다(조회 실패 = `allowed:false`, fail-closed). 인트라넷은 `allowed` 일 때만 리뷰↔블로그 탭을 연다. 옛 리뷰웹엔 이 칸이 없다 → 인트라넷은 종전 잠금.

## 검토 반영 (Codex PR #1758)
- **게시했다가 보관한 공고도 막는다** — 종류 변경 판정은 보관 여부가 아니라 게시 이력(`status<>'draft' OR published_at`)으로 본다. 판정·삭제 결과 검증 모두. 그 밖의 정리(결정 254)는 종전대로 「보관 안 된 공고」.
- **양방향 연결 오더는 창의 기준 버전 = 지금 버전일 때만**(`bidir.base_sync_version === sync_version`, 스위치 `in2rw=apply` 일 때) — 아니면 지우기 전에 409 `kind_change_stale`. 연결을 끊고 전체 저장으로 가면 공유 저장의 3방향 병합을 건너뛰어 리뷰웹에서 고친 가이드 등을 창의 옛 값으로 덮기 때문.

## 알려진 한계
- 작업표 삭제가 커밋된 뒤 이어지는 전체 저장이 다른 검증으로 실패하면, 오더는 「접수 대기」로 돌아갔는데 종류는 옛 값으로 남는다. 인트라넷이 같은 번호로 다시 보내면 잠기지 않은 오더라 그대로 저장된다(막다른 길 아님).

## 완화 금지
- **종류 변경의 삭제 판정에서 결정 254 판정을 빼지 말 것** — 사람이 들어온 작업표·게시된 공고·입금 기록이 종류 변경 한 번에 지워진다.
- **예외를 넓히지 말 것**(자기 오더·게시한 적 없는 임시저장 공고 두 가지뿐) — 게시했던 공고는 리뷰어가 봤다.
- **번호 +1 조건을 빼지 말 것** — 낡은·중복 요청이 다시 접수된 작업표를 지운다.
- **양방향 오더의 기준 버전 검사를 빼지 말 것** — 리뷰웹에서 고친 공유 칸이 조용히 옛 값으로 덮인다.
- **게시 이력 판정을 보관 여부로 되돌리지 말 것** — 게시했다 보관한 공고가 종류 변경 한 번에 영구 삭제된다.
