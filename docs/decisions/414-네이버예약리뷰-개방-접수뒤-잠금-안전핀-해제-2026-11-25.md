- ★ 장치(목록 · `isWorkKindReady` · `workKindNotReadyBody` · 저장 입구 5곳의 판정 위치)는 **다음 새 종류(영수증리뷰 등)를 위해 그대로** 둔다. 새 종류는 여기에 먼저 넣고 시작한다(404 와 같은 순서). 기존 시험(`bookingWorkKind` 2절 · `bookingReviewerFlow`)은 시험 안에서만 booking 을 목록에 다시 넣어 장치가 그대로 거절하는지 본다.

## ★★ 접수 뒤 수정 잠금 (완화 금지) — 판정 단일 출처 `bookingCalendar.bookingLockedChanges`
접수로 날짜별 자리표(`booking_slots`)와 작업표 줄(이용일자·리뷰마감일·결제금액 칸)이 **그 계약 값으로** 깔렸다. Q&A `_qnaCalendarLocked`(결정 321) 와 같은 규율로, 접수 뒤에는 자리표를 정한 값을 어느 출처로도 바꾸지 않는다.

- ★ **열린 칸도 고친 결과가 계약을 지켜야 한다** — 무료체험형에 결제금액, 환급형 1인 금액 0 등 `bookingSpecFromWorkOrder` 가 막는 모양이 **새로** 생기면 409(`booking_invalid`). 안 막으면 리뷰어 신청이 「예약 정보를 못 읽음」으로 막히고 입금이 「예약 설정 모름」으로 멈춘다. 이미 있던 사유로는 막지 않는다(글 칸 수정까지 영영 막는 막다른 길 방지).
- ★ 비교는 정규화된 계약 기준 — 키 순서·공백 같은 표기 차이로 막지 않는다. 같은 값 재전송은 통과.
- 잠금 시점 = 작업표가 연결됐거나(`linked_tab_name`) 자리표 줄이 있으면. 자리표 조회 실패 = **잠금**(fail-closed · 표 없음 42P01 만 열림). 예약 오더가 아니면 늘 종전 동작.
- 409 본문: `{ code:'booking_calendar_locked', blocked_fields, booking_locked, booking_invalid, error }`. 문구 = 무엇이 잠겼나 + 「원래 값으로 되돌려 저장」 + 「날짜·인원을 바꾸거나 늘리려면 새 리뷰오더로 접수(네이버예약리뷰는 접수 뒤 인원 늘리기·차수가 없습니다)」 + 열린 칸 목록. 문구 = `bookingCalendar.bookingLockMessage` 하나.
  - ★ 문구에 「추가 모집」이라는 말을 **쓰지 않는다** — 인트라넷 실패 안내(`reviewOrderDeliveryFailMessage`)가 그 말을 보면 Q&A 안내(「일정 끝 추가 모집으로 늘려라」)로 바꿔 보여 준다. 예약리뷰엔 그 길이 없다.
- 거는 자리(모두 같은 판정 · 같은 문구 · 쓰기 전):
  1. 인트라넷 원본 수정 `PUT /api/order/intake/source/:id` — Q&A 잠금 바로 뒤, 종류 바꾸기 판정·공유 저장보다 **먼저**(양방향 연결 오더도 여기서 멈춘다 · 원본 번호 미증가).
  2. 옛 수정 경로 `POST /api/order/intake/:id/update` · 관리자 작업오더 수정 창(`orderAdminEdit`).
  3. 공유 저장(`sharedPatch.service` — 공고 창·작업보드·발행 맞추기 출처) — 이 저장을 적용한 **다음 상태**(`applyWrites` 로 계산만)로 비교. 통과한 줄에만 `bookingOk` 를 붙여 예약 설정 칸(`booking`)을 통째로 옮긴다(표시 없으면 종전처럼 쓰지 않음 · 옵션에는 이 칸이 없다).
- ★ 공유 저장은 주말 제외·시작일·제외일을 **잠그지 않는다** — 예약 자리표는 그 값을 읽지 않는다(업체가 정한 날짜 그대로 · 407). 잠그면 발행 맞추기(오더 「정하지 않음」 → 공고 「주말 포함」)가 늘 실패한다(Q&A 와 다른 점).
- 원본 수정의 「접수 뒤 상품 구성 잠금」(`SOURCE_EDIT_AFTER_ACCEPT` · 발행 뒤)에서 예약 설정 안의 `place_address` 만 바뀐 것은 구성 변경으로 보지 않는다(`BOOKING_EDITABLE_AFTER_ACCEPT_KEYS` 단일 출처 · booking 키가 있는 오더에만 닿는다).

## 발행 폼 예약 안내 (결정 409 「불러오지 못했습니다」 해소)
- **작업 카드 [공고 발행]**: 그 응답(작업표별 작업오더 요약 행)에는 종류·예약 안내가 없어 예약 오더인데 **일반 리뷰체험단 폼**(종류 리뷰 · 상품·인원 빈칸)이 열렸다 — 그대로 저장하면 리뷰 공고가 된다. 요약 행에 `work_kind`(값만)를 싣고, 예약 오더면 홈 [공고 발행]과 같은 원본 행(작업오더 목록 · 서버가 붙인 `booking_spec`)으로 프리필한다. 원본 행을 못 받으면 요약 행으로라도 종류는 booking(카드는 「불러오지 못했습니다」). 다른 종류는 종전 그대로(목록 API 안 부름).
- **예약 공고 [수정]**: 공고 상세(관리자 보기)가 연결 오더 계약으로 `bookingSpec` 을 싣는다 — 기존 연결 오더 조회 **한 번**에 칸만 더 읽는다(조회 순증 0 · 기존 가드 그대로). 화면은 종류 복원(카드 그리기) **전에** 받는다.
- 변환 = `bookingCalendar.bookingSpecForScreen` 하나(작업오더 목록 `_bookingSpecOf` 도 이 함수로 바꿨다 — 사본 0).

## 인트라넷 계약 대조 (읽기 전용 · inadd-webapp `d7e4842f` · 머지 전)
- ✅ 인트라넷 수정 화면이 접수 뒤 잠그는 칸(날짜 줄·날짜 더하기·진행 방식·리뷰 마감·종류 탭) = 리뷰웹 잠금. 결제합계·총 모집은 화면 계산(날짜별 인원 합 · 1인 금액 × 인원)이라 날짜가 잠기면 같이 그대로.
- ✅ 하루 건수·주말·제외일은 예약 오더에서 싣지 않는다(`REVIEW_ORDER_BOOKING_OMIT_FIELDS`) · 시작일 = 첫 이용일(날짜가 잠기면 같은 값) → 맨 위 칸 잠금에 걸리지 않는다.
- ✅ 409 는 코드·문구를 그대로 넘겨 실패 안내로 보인다 — 잠금 문구는 「새 리뷰오더로 접수」 안내 갈래로, 계약 깨짐 문구도 「새 리뷰오더로 접수」를 담아 「작업보드에서 고쳐라」로 잘못 안내되지 않게 했다(실제 인트라넷 안내 함수를 vm 으로 돌려 확인).
- ⚠ 어긋남 1 — **매장 이름**: 인트라넷은 접수 뒤에도 매장 이름 칸을 열어 두고(공고 연결 뒤 `source_edit_locked` + 이름 바꾸기 허용이 없을 때만 잠금) 바꾸면 이름 바꾸기(`prev_name`)를 싣는다. 리뷰웹은 접수 뒤 매장 이름을 잠근다(412 캡처 검사·신청 선택 키) → 인트라넷에서 바꾸면 409 로 돌아온다(fail-closed · 안내 문구 있음). 인트라넷 `REVIEW_ORDER_BOOKING_LOCK_SEL` 에 매장 이름 칸을 접수 뒤 늘 넣는 것을 인트라넷 쪽에 제안(이 변경에서 인트라넷은 고치지 않았다).
