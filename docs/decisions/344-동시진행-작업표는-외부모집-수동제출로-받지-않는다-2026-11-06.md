# 네이버·쿠팡 동시진행 작업표·공고는 외부모집 수동제출로 받지 않는다 — 판정 실패도 막는다 (2026-11-06 · 스키마 변경 0)

## 무슨 일이 있었나

- 외부모집 수동제출(관리자가 카톡으로 받은 슬래시 양식을 대리 입력 — `POST /api/manual-order/{preview,submit}` 와 Track B 입구 `/api/trackb/manual-order/{preview,submit}`, 같은 핸들러)에는 동시진행 판정이 없었다.
- 그래서 네이버+쿠팡 동시진행 공고에 연결된 작업표에 **보통 주문 1건(한쪽 금액)** 이 들어갔다(운영 실사고 3건). 동시진행 주문은 구매처별 기록·두 리뷰·묶음 지급(결정 338·341)이 있어야 하는데, 보통 주문은 그 묶음 밖이라 지급·정원·검수가 어긋난다.
- 리뷰어 구매양식 경로(`submit.routes` 결정 338)는 이미 `409 dual_channel_bundle_required` 로 막고 있었다.

## 결정

- **서비스 맨 앞에서 거절** — `manualOrder.service.submitExternalOrder` 는 리뷰어 자동등록·원장·큐·작업표 쓰기보다 앞에서 `manualDualBlock` 을 부른다. 작업표 좌표(`sheetId`/`tabName`/`gid`)나 들어온 공고 id(`campaignId`·`optionCampaignId`) 중 하나라도 동시진행이면 **쓰기 0건**으로 돌려준다.
- **라우트 사전 판정** — `preview`(분해·AI 보정 전)와 `submit`(배치 시작 전)에서 같은 함수로 `409` 를 돌려준다. 미리보기 단계에서 바로 알린다.
- 판정 = 공용 lifecycle 발견기 `dualChannelLifecycle.discoverDualScope` 단일 출처(리뷰어 경로와 같은 함수 · 사본 금지).
- 응답: `{ ok:false, code:'dual_channel_manual_unsupported', error:<문구>, message:<문구> }` · 문구 「이 작업은 네이버·쿠팡 동시진행이라 수동제출로 접수할 수 없어요 — 리뷰어가 구매양식 링크로 두 곳을 함께 내야 해요.」 상수는 `utils/dualPhase1.js`.
  - ★ 화면(`frontend/js/manual-order.js`)은 서버 `error` 를 그대로 alert 한다(미리보기 `분해 실패: …` · 제출 `제출 실패: …`, 상태코드와 무관하게 `r.json()`). 그래서 `phase1ManualResult` 처럼 `error` 에 코드를 싣지 않고 사람 문구를 싣는다. 화면 파일은 바꾸지 않았다.
- **fail-closed** — 판정 자체가 예외면 `dual_channel_manual_check_failed`(「…확인하지 못해 접수하지 않았어요 — 잠시 뒤 다시 시도해 주세요」)로 막는다. 리뷰어 경로는 라이브 핫패스라 판정 실패를 종전 경로로 접지만(fail-open), 여기는 관리자가 대리로 넣는 **돈 걸린 경로**다 — 잘못 열리면 한쪽 금액짜리 보통 주문이 생기고, 막히면 사람이 다시 누르면 된다. 같은 이유로 들어온 공고 id 가 없는 공고(삭제됨)도 판정 실패 = 막음으로 접힌다.

## ★★ 완화 금지

- **동시진행 작업표·공고의 수동제출 거절을 풀지 않는다.** 관리자 대리 **묶음** 제출(구매처 두 곳을 한 번에 넣는 입구)이 생기면 **그 입구로만** 연다 — 이 경로에서 보통 주문 1건으로 받는 길을 다시 만들지 않는다.
- **판정 실패를 통과로 접지 않는다**(fail-closed 유지).
- 판정을 이 파일 안에 다시 쓰지 않는다 — `discoverDualScope` 를 태운다.
- 회귀가드 `server/tests/manualOrderDualBlock.test.js`: 동시진행 작업표·공고에서 리뷰어 등록·원장·큐·작업표 호출 0 / 판정 예외 시 거절 / 일반 작업표는 종전대로 / Track B 입구가 같은 핸들러.
