# 리뷰검수 1단계 — 미확인 정상처리 차단과 실제 저장 성공 계약

## 범위와 상태

- 2026-10-30 구현·로컬 검증 및 독립 검토 통과. 최신 main의 별도 변경을 충돌 없이 통합했으며 운영 배포는 별도 확인한다.
- 무인 자동화의 첫 단계이며, 기존 적체 자동 해소·새 자동 재검수 활성화를 뜻하지 않는다.
- 제출 입구, 사진 이동/삭제, 자동 반려·알림, 영수증 지급 조건, DB 스키마는 변경하지 않는다.

## 재현한 문제

1. AI 예외·불완전/저확신 응답이 `format.skip`으로 남아도 중복 대조 하나가 통과하면 전체 `pass`가 됐다.
2. 기준·행 리뷰타입·대조 조회 실패가 빈 값/적용제외와 합쳐져 검증된 정상으로 기록될 수 있었다.
3. `_upsertInspection`의 예외/반영 없음과 실제 저장 성공을 구별하지 않아 스윕 `done`과 영수증 재검수 성공이 부풀었다.
4. 상품명만 사람에게 확인받은 기존 SQL 보존·군집 판단이 다른 항목의 명시적 미확인까지 `resolved/ok`로 종결할 수 있었다.
5. 이미지 캐시가 앞 50,000글자만 해시하여 꼬리가 다른 두 이미지에 같은 키가 생겼다. 로컬 합성 입력 재현이며 실제 운영 발생 건수는 미확인이다.

## 계약

- 기존 `verdict: skip` 호환을 보존하고, 증거 부족에는 `evidence: unknown`과 `no_ai / low_confidence / no_expected / no_ocr / lookup_failed` 사유를 남긴다.
- 일반 리뷰 종합은 `fail → suspect → 명시적 unknown이면 unverifiable → 기존 pass/skip 규칙` 순서다. 이미 알려진 불량·경고를 미확인으로 감추지 않는다.
- 실제 비어 있지 않은 짧은 글, 별점·구매확정의 본문 불필요, 블로그의 리뷰 캡처 불필요와 작성자 검사 비활성/짧은 마스킹은 적용제외로 유지한다.
- 행별 리뷰타입 조회의 `strict`는 후검수만 켠다. 두 제출 입구는 기본 fail-open을 그대로 쓴다. 판정 규칙은 기존 `reviewType`·옵션 매퍼 단일 출처다.
- 기존 `{status, checks}`는 계산 결과다. `persisted`와 `storedStatus/storedChecks`를 추가하여 `RETURNING status, checks` 실제 행으로만 저장 성공을 확인한다. 저장 예외·0행은 false, 제출/교체 성공에는 예외를 올리지 않는다.
- 영수증 재검수 `ok`와 스윕 `done`은 `persisted === true`일 때만 증가한다. 영수증 교체 후 저장 실패는 기록하되 교체 성공을 되돌리지 않는다.
- 상품명 보존 SQL의 종합 상태 및 `resolution/resolved_at/resolved_by` 자동 종결 조건을 모두 보호한다. 군집 판단도 명시적 미확인을 종결하지 않는다.
- 영수증은 `receiptValidation`과 기존 별도 검증·지급 기준을 유지한다. 일반 리뷰의 unknown 정책을 지급 정책 변경으로 확장하지 않는다.
- 캐시는 전체 입력 SHA-256으로 식별한다. 기존 data 접두 정리, 용도·예시 접두, 캐시 재사용과 제출 원장 해시는 바꾸지 않는다.

## 검증

- AI 예외, 불완전/저확신, 기대값·행별 유형·중복·유사도·작성자 조회 실패, 본문 OCR 없음과 적용제외 분리를 실제 서비스 VM으로 실행했다.
- 저장 예외·0행·성공 반환행·계산/저장 판정 차이, 영수증 재검수·스윕 성공 집계·교체 후 실패 격리를 검사했다.
- 폐기용 PGlite에 기존 migration 081/092/148을 적용하고 실제 UPSERT SQL을 실행했다. 상품명 사람 판정을 보존하면서 다른 unknown은 종결하지 않고 확인 시각/주체를 만들지 않음을 검증했다. 다중 연결 경합 증명은 아니다.
- 최신 main(PR #1719·#1720 포함) 통합 후 전체 시험: 652파일 성공, 실패 0(135.7초), `stage1-latest-main-1720-full.log`. 앞선 통합본 650파일(112.3초)·최초 수정본 649파일(132.5초)도 통과했다. 최초 240초 호출은 집계 없는 시간초과로 별도 구분한다.
- 독립 검토는 보안/논리 차단 0으로 통과했고 변경 시험 8개를 별도로 실행했다. 비차단 권고였던 기존 종결정보 보존·영수증 예외도 실제 SQL 검사에 추가해 확인했다.
- 영수증·구매확정 성공 mock은 실제 RETURNING 행을 제공하도록 보강했고 행별 유형 가드는 strict 실패 분리까지 강화했다. 의미 없는 `|| true` 검사는 제거했다.
- 외부 통신·운영 PostgreSQL 연결은 차단하고 가짜 입력/폐기용 로컬 DB만 사용했다. 실제 AI 정확도나 운영 사용자 왕복 시험을 완료한 것은 아니다.
- 2026-10-29 읽기 전용 스냅샷 20,125행을 오프라인 확인했다. 사람 종결 1,447행·영수증 15행·블로그 28행을 제외하고, 명시적 `no_ai/no_ocr/lookup_failed` 기록이 있는 151행은 기존 `pass`였으며 새 실제 종합 함수에서 모두 `unverifiable`로 계산됐다. 상세 식별자는 출력하지 않았다. 이유 없는 옛 skip의 조회 실패는 추정하지 않았고, 현재 기준·사진·AI 재검수나 운영 변경도 하지 않았다. 이는 불량 사진 151장이나 전체 오판률을 뜻하지 않는다.

## 한계와 다음 단계

- 기존 판정행을 소급 갱신하지 않는다. 기존 미해결 적체는 남는다.
- 상품명·용량/개수/모델 의미 비교 통일은 2단계, 기준 변경 지문·유한 재시도·현재 제출 및 사람 판정 경합 보호·구신버전 혼재 gate를 갖춘 지속 재검수는 3단계다.
- 무인 정상종결을 활성화하기 전에 기존 `pass/resolved`, 교체 사진, 최신 기준을 늦은 결과가 덮지 않는 조건을 별도 검증한다.

## 되돌리기

- 코드만 되돌린다. 새 마이그레이션·데이터 삭제는 없다. 이미 남긴 unknown JSON은 구버전 코드가 무시할 수 있으므로 되돌린 상태에서 새 자동 종결을 활성화하지 않는다.
- 운영 장애가 확인되면 원인 조사보다 먼저 사용자에게 되돌릴지 묻는 저장소 절차를 따른다.

## 완화 금지

- unknown을 이유 없는 skip이나 보조 pass로 다시 합치지 않는다. JS 종합 함수만 고치고 SQL/군집 종결 우회를 남기지 않는다.
- 계산 성공을 저장 성공으로 주장하지 않는다. mock 성공도 실제 반환행 계약을 따르게 한다.
- 영수증 지급 기준과 제출 입구 허용을 일반 리뷰 자동화 수정에 끼워 바꾸지 않는다.
