# ★★ 공고 발행 때 값이 다르면 오더를 공고 값으로 자동 맞추고 연결 — 못 맞추면 그 자리에서 안내 (사용자 확정 2026-10-30 「1.가」·「A」 · 스키마 변경 0)

## 사고 경위
- 10/24 이후 인트라넷 리뷰오더로 새로 발행한 공고 13건 중 3건이 발행 직후 `bidir_state='diverged'`(연결 안 됨)였다 — 셋 다 발행 창에서 공유 칸을 고친 경우
  (상품 이름에 번호 「1.사우나」「1번 베개커버 40x60cm」「1. 마스크팩 … 포토리뷰」 · 구매시간 「자유시간대」). 고친 값은 공고에만 저장되고,
  발행 직후 `linkSharedOrder` 가 다름을 보고 **조용히** diverged 로 남겼다(발행 창은 `bidirLink` 를 버렸다). 그 뒤로는 양쪽 수정이 서로 안 맞춰지고,
  담당자 팝업(결정 284)이 뜰 때까지 아무도 모른다.

## 결정
1. **「1.가」** — 발행 때 다르면 오더를 **공고 값으로** 맞추고 연결한다 = 담당자 팝업 [공고대로 맞추기] 와 **같은 판정·같은 저장 길**
   (`sharedReconcile.reconcileOnPublish` → `planReconcile` → `reconcileSharedOrder`(applySharedPatch origin 'reconcile', opId `publish-<공고 id>`)).
   새 쓰기 SQL 없음 · 인트라넷으로는 맞춘 버전이 기존 보내기 대기열로 간다.
2. **「A」** — 상품 이름은 시스템마다 따로(결정 285 그대로). 리뷰웹 오더 사본은 공고 이름을 쓰고, 인트라넷 수신기가 「이름 서로 포함」 짝으로 인트라넷 이름을 지킨다.
   발행 안내의 칸 목록에서 상품 이름 칸은 뺀다(「이름도 맞췄다」 로 읽히면 틀린 안내).
3. **못 맞추면 아무것도 바꾸지 않는다(fail-closed)** — 접수 뒤 못 바꾸는 칸(`PERMANENT`: 체험단 종류·배송 혼합·회수 택배·회수 상품)이 다르거나 ·
   공고 쪽으로 못 옮기는 칸이 있거나 · 합계만 달라 고를 칸이 없거나 · 방금 만든 공고가 그 오더의 기준 공고(가장 먼저 만든 살아 있는 공고)가 아니면
   diverged 그대로 + 이유(`bidirLink.autoReason`). 맞추기 안에서 실패해도(값이 그사이 바뀜 `reconcile_stale` 등) 같다. 공고 발행 자체는 언제나 성공.
4. **발행 창이 그 자리에서 말한다**(`index-recruit.js` — 저장 안내 맨 위 한 줄): 맞춤 = 「✅ 인트라넷 리뷰오더도 이 공고 값으로 맞췄습니다 (칸…)」 ·
   못 맞춤 = 「⚠ … 아직 연결되지 않았습니다 (칸…) — 이유. 작업보드 「⚠ 오더·공고 다름」에서 맞춰 주세요」. 스위치가 꺼져 있어도 diverged 면 ⚠ 를 띄운다(사실이므로).
5. **즉시 끄는 스위치** — `app_settings.bidir_sync` 의 새 칸 `publish_reconcile`(off|on · 적지 않으면 off · fail-closed 그대로). in2rw 가 off 면 판정 자체를 안 한다(종전).

## 완화 금지
- 자동 맞추기는 **공고 쪽으로만**. 오더 쪽(공고를 오더 값으로)으로 바꾸면 발행 창에서 사람이 방금 고친 값이 리뷰어 화면에서 되돌아간다.
- 고를 칸이 하나라도 공고 쪽으로 못 가면 **통째로 안 맞춘다**(일부만 맞추기 금지 — 팝업 [공고대로 맞추기] 와 같은 규칙 · reconcile-prompt.js `sideBlock`).
- 판정·쓰기는 맞추기 한 곳(`planReconcile`·`applySharedPatch`) — 발행 라우트에 비교·쓰기 사본을 만들지 않는다.

## 배포 순서
- 스위치 off 로 배포(동작 불변) → 운영에서 `publish_reconcile":"on"` 을 더한다. 옛 화면 + 새 서버 = bidirLink 를 안 읽음(종전) · 새 화면 + 옛 서버 = autoReconciled 없음 → diverged 면 ⚠ 만(사실).

## 검증
- `server/tests/bidirPhase4Paths.test.js` ③(PG 실라우트): 구매시간만 다름 → on·오더=공고 값·공고 그대로·보낼 거리·`publish-` 기록 /
  체험단 종류 다름 → diverged·오더 쓰기 0·보낼 거리 0·이유 / 실제 사례 모양(번호 붙인 상품 이름+자유시간대) → on·안내 칸 = 구매시간만 / 스위치 off = 시도 안 함.
  발행 창 안내 블록을 그대로 떼어 vm 실행(맞춤·못 맞춤·옛 서버·말 없음·수정 저장 제외). 자동 맞추기를 끈 변이 → 실패로 잡힘.
- 인트라넷 수신기(`reviewOrderSharedPatchFromView`)에 실제 사례 이름을 넣어 「사우나」「마스크팩」 이름 유지 · 구매시간만 받음을 확인.

## 사각지대
- 발행 뒤 맞추기 사이에 다른 저장이 끼면 `reconcile_stale` 로 안 맞추고 안내만 한다(팝업·맞추기 화면으로 처리).
- 이미 diverged 로 남은 옛 작업은 대상이 아니다(새 발행만) — 담당자 팝업·맞추기 화면 그대로.
