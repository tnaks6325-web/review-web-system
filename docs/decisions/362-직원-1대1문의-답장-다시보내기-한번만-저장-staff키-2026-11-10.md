# ★★ 직원 1:1문의 답장 다시 보내기도 한 번만 저장 — C/S 대화창·작업보드 미니 C/S·작업보드 [리뷰어에게 메시지] 가 쓴 글마다 키 · 서버는 `staff:` 접두로 같은 칸(221)에 저장 · 같은 키·다른 글/보낸 사람은 409 · 다시 보내기에 리뷰어 알림·미확인 +1 재실행 0 (2026-11-10 · 스키마 변경 0 · 결정 361 의 직원 쪽)

## 무슨 일이었나
- 결정 361 은 **리뷰어 → 직원** 보내기만 막았다(그 「하지 않은 것」 첫 줄). 직원 쪽 화면 3곳은 실패하면 글·사진을 그대로 남기고(다시 누르면 된다) — 그런데 그 실패의 일부는 **서버엔 저장됐는데 응답만 못 받은** 경우다(시간 초과·끊김). 직원이 다시 누르면 **리뷰어에게 같은 답장이 두 번** 가고, 리뷰어 미확인 숫자도 두 번 오른다.
- 직원이 보내는 창구(전수 · `grep csAdminReply|/cs/reply|notify-participants|INSERT INTO cs_messages`):
  1. C/S 대화창 — `frontend/js/cs-inquiry.js` `csSendReply` → `POST /api/cs/reply`(작업보드 화면은 `/api/trackb/cs/reply` 로 같은 핸들러 위임 · 결정 270).
  2. 작업보드 미니 C/S — `frontend/js/workdesk-cs-mini.js` `send` → 같은 `csAdminReply`.
  3. 작업보드 [리뷰어에게 메시지](여러 명 한 번에) — `workdesk.html` `_rmSend` → `POST /api/trackb/cs/notify-participants` → `csBridge.postAdminNotice`(결정 013).
  - 그 밖의 직원 쪽 저장은 사람이 [보내기]를 다시 누르는 창구가 아니다: 검수 반려 통지·입금 실패 안내(`postAdminNotice` 의 다른 호출부 — 그 작업 자체의 처리 결과로 한 번), 구매사진 확인 결과(`purchaseCaptureCheck.decideForStaff` — 같은 결정·같은 메모면 이미 아무것도 안 하는 재실행 규칙이 있다, 결정 357). 이번에 손대지 않는다.

## 규칙
1. **키 규칙 단일 출처 = `server/src/utils/csClientMsgId.js`** — 키 모양(`^[A-Za-z0-9_-]{16,100}$`) · 내용 비교 · 직원 키 찾기 SQL. 리뷰어 보내기(361)도 이제 여기서 가져다 쓴다(정규식 사본 0).
2. **직원 키는 서버가 `staff:` 를 앞에 붙여 저장한다** — 리뷰어 키 모양에는 `:` 가 들어갈 수 없으므로 **같은 문의방 안에서도 리뷰어 키와 직원 키는 만드는 방식만으로 절대 겹치지 않는다**(부분 유일 색인이 문의방 단위라 두 쪽이 같은 범위에 산다). 화면은 접두를 모른다(두 쪽 화면이 보내는 키 모양은 같다).
3. **같은 키로 찾은 메시지가 「이 직원이 보낸 같은 글」일 때만 성공으로 돌려준다** — 역할 `admin` · 보낸 사람(로그인명 `req.admin.name`) · 종류 `text` · 글 · 사진이 모두 같아야 한다. 하나라도 다르면 **409 `cs_client_msg_conflict`**(답장) / 그 건 실패 + `failed[].code`(작업보드 여러 명) — 저장 0. 다른 직원의 답장을 「이미 보냄」으로 접지 않는다.
4. **답장(`POST /api/cs/reply`)** — 키가 있으면 한 트랜잭션: 「문의방 줄 잠금(`FOR UPDATE`) → 같은 방·같은 키 찾기 → 없으면 저장 + 방 갱신(리뷰어 미확인 +1·마지막 시각·미리보기)」. 있으면 ROLLBACK 하고 저장된 답장을 `{ ok:true, message, duplicate:true }` 로(응답 칸 = 첫 전송과 같음 + `duplicate`). **리뷰어 실시간 알림(`emitCsReplyToReviewer`)·관리자 화면 방송(`broadcast`)·새 저장 0.** 방 상태(열림/닫힘)는 답장이 원래 바꾸지 않는다 — 다시 보내기도 그대로.
   - 같은 방 동시 두 답장은 방 줄 잠금에서 줄을 서고 뒤쪽이 앞쪽 저장을 본다. 최후 방어선 = 부분 유일 색인(`23505` → 같은 연결로 다시 읽어 같은 처리). 없는 방 = 404 쓰기 0.
   - 키가 없거나 모양이 틀리면 **종전 경로 한 줄도 안 바뀜**(방 갱신 문장은 두 경로가 같은 상수 `CS_REPLY_THREAD_BUMP_SQL` — 사본 금지). 칸이 없는 DB(42703)면 경고 후 종전 경로.
5. **작업보드 [리뷰어에게 메시지]** — 화면이 키 하나를 싣고, 서버는 받는 사람(방)마다 같은 키로 `postAdminNotice({ clientMsgId })` 를 부른다(유일 범위가 방이라 방마다 한 번).
   - 첫 전송이 일부 방에만 저장되고 응답을 못 받았다면, 다시 보내기는 **받은 방은 `duplicate:true`(새 저장·실시간 알림·미확인 +1 없음)로 「보냄」에 세고, 못 받은 사람에게만** 보낸다.
   - `clientMsgId` 는 `postAdminNotice` 의 **가산 옵션** — 넘기지 않는 기존 호출부(검수 반려·입금 실패 안내)는 동작 불변. 카드(`card`)가 있는 통지는 키를 쓰지 않는다. 키가 있으면 기존 방을 `FOR UPDATE` 로 잠근다(새 방은 기존 upsert 가 잠근다).
   - 반환 계약(성공 객체 | `null`, 절대 throw 없음)은 그대로 — 충돌은 `onError(code)` + `null`.
6. **화면 키 = `frontend/api.js` `createCsStaffDraftKey()` 단일 출처** — 대화창마다 하나. `keyFor([방, 글, 사진 …])` 는 **로그인 계정(토큰 본문 id·username·name) + 초안**이 같을 때만 같은 키, 고치면 새 키(결정 262 원칙). **성공 확인 또는 409 에서 `settle`** — 통신 실패(결정 359 의 `ok:false`)에서는 키를 그대로 둔다. 작업보드 팝업은 응답을 받았으면(성공·부분 성공) 키를 버리고, 전부 실패·통신 실패면 둔다. 키 생성은 `randomUUID` → `getRandomValues` → `Math.random`(접두 `scs-`).
   - 작업보드 화면은 `api.js` 가 본문 스크립트보다 **뒤에** 실리므로 팝업 키는 처음 보낼 때 만든다(`_rmDraftKeyer`). 없으면 키 없이 종전 동작.
7. 화면 모양·문구는 그대로다(실패 문구는 서버 409 문장을 종전 「전송 오류: …」 틀에 그대로 보인다).

## 소비처 전수
- `cs_messages.client_msg_id` 를 쓰는 곳: 리뷰어 보내기(361) · 직원 답장 · `postAdminNotice`(키 있을 때) — 3곳. 읽는 곳은 각자의 키 찾기 SQL 뿐이고 대화 조회 응답들은 칸을 명시해 고른다(`SELECT *` 없음 — 가드가 확인).
- 응답 가산 필드: `duplicate`(답장 응답 · `sent[]` 항목) · `failed[].code` — 화면은 `ok`/`error`/`sent`/`failed[].reason` 만 읽던 그대로이고, 새 필드는 키 정리에만 쓴다.
- 가드 문자열 갱신(검사 의미 불변): `csAdminImageUpload.test.js`(「imageUrls 동봉」 정규식에 `, clientMsgId` 허용) · `workdeskCsMini.test.js`(같은 답장 API 호출에 imageUrls 동봉 — 오히려 좁혀 강화).

## 배포 순서
- 구버전 화면 + 새 서버: 키 없음 → 종전 경로(동작 불변).
- 새 화면 + 구버전 서버: 서버가 모르는 `clientMsgId` 를 무시 → 종전 동작(중복 방지만 없음).
- 마이그레이션 없음(221 칸·색인 재사용 · `REQUIRED_SCHEMA` 에 이미 있음). 되돌리기: 코드만 되돌리면 `staff:` 키가 남은 행은 아무도 읽지 않는다 — 무해.

## 완화 금지
- **직원 키에서 `staff:` 접두를 빼지 않는다** — 빼면 같은 방의 리뷰어 키와 같은 범위에서 겹칠 수 있고, 리뷰어 쪽 찾기(역할 필터)에 걸리지 않아 23505 → 500 이 된다.
- **같은 키 비교에서 보낸 사람·역할을 빼지 않는다**(다른 직원·리뷰어 글을 「이미 보냄」으로 접는다) · **같은 키·다른 내용을 성공으로 접지 않는다**.
- **다시 보내기에서 리뷰어 실시간 알림·관리자 방송·리뷰어 미확인 +1 을 다시 하지 않는다**(ROLLBACK 을 COMMIT 으로 바꾸지 않는다) · **키 확인을 방 줄 잠금 밖으로 옮기지 않는다**.
- **화면에서 키를 보낼 때마다 새로 만들지 않는다 · 성공 확인 전에 키를 버리지 않는다** — 둘 다 다시 보내기 중복이 그대로 돌아온다.
- 가드: `server/tests/csStaffSendIdempotency.test.js`(PGlite 실제 SQL · 실제 라우트 2개 · 화면 3곳 vm — 72건).

## 하지 않은 것
- **`postAdminNotice` 의 리뷰어 실시간 알림이 원래부터 안 나간다**(이번 변경과 무관 · main 에서도 같음): 실시간 알림을 만드는 코드가 트랜잭션 블록 안에서 선언된 `meta`(그리고 종전엔 `senderName`)를 블록 밖에서 읽어 `ReferenceError` 가 나고, 그 줄이 `try {} catch (_) {}` 로 감싸여 조용히 삼켜진다(실측: 저장 1 · 실시간 알림 0). 리뷰어는 대화창을 다시 열거나 목록을 새로 읽을 때 본다. 고치면 리뷰어 화면 동작이 바뀌므로 이번 범위 밖 — 별도 작은 수정 권장.
- 작업보드 **문자·알림톡 수동 발송**(`/api/trackb/workdesk/manual-send`)도 응답 유실 뒤 다시 누르면 두 번 나갈 수 있다(1:1문의가 아니라 외부 발송 · 비용 발생). 이번 범위 밖.
  - → **2026-11-10 결정 [364](364-작업보드-문자-알림톡-다시보내기-한사람-한번-clientSendId-선점-2026-11-10.md) 에서 처리**(받는 사람마다 공급자 부르기 전 선점 · migration 222).
- 다시 보내기 때 받는 사람 확인(`expect`)이 그 사이 바뀌면, 첫 전송에서 이미 받은 사람도 「받는 사람이 방금 바뀌었습니다」로 실패에 뜬다(드묾 · 종전 TOCTOU 규칙 우선).
- 사진 올리기 자체가 서버 저장 뒤 끊기는 경우의 고아 파일(361 과 같음).
