# ★★ 작업보드 문자·알림톡 다시 보내기는 한 사람에게 한 번만 — 화면이 「같은 줄 선택·방식·내용」마다 키(clientSendId) · 서버는 받는 사람마다 공급자 부르기 **전에** 발송 기록에 '대기' 줄을 선점(키·참여 줄 유일) · 다시 온 요청은 보냄=그대로 보냄 / 확실한 실패=다시 보냄 / 결과 모름·처리 중=보내지 않음 · 같은 키·다른 내용은 409 (2026-11-10 · migration 222)

## 무슨 일이었나
- 작업보드 우클릭 [문자·알림톡 보내기](결정 196)는 [N명에게 보내기]를 누르면 서버가 발송 업체(솔라피)를 부른다. 서버는 이미 보냈는데 **응답만 못 받은**(시간 초과·끊김) 경우, 화면은 「보내지 못했습니다」를 보이고, 담당자가 창을 다시 열어 같은 내용으로 보내면 **같은 문자가 한 번 더 나가 비용이 두 번** 든다(결정 362 「하지 않은 것」 둘째 줄).
- 알림톡은 더 나쁘다 — 첫 알림톡이 빨리 「도착」으로 확인되면 회차가 올라가고, 수동 발송은 날짜 전(not_due) 회차를 앞당겨 보내는 규칙이라 다시 보내기가 **다음 회차(2차)를 바로** 보낸다.
- 같은 화면에서 두 번 누르는 것은 이미 막혀 있다(보내는 중 버튼 잠금 · 보낸 뒤 [닫기]만). 문제는 창을 닫았다 다시 연 「다시 보내기」와, 첫 요청이 아직 처리 중일 때의 두 번째 요청이다.

## 규칙
1. **화면(`frontend/workdesk.html` `_msSendConfirmed`)** — 보낼 때 `clientSendId` 를 싣는다.
   - 키 = `createCsStaffDraftKey`(api.js · 결정 362 단일 출처) 의 `keyFor(['manual-send', 방식, 시트, 탭, 고른 줄(정렬), 문자면 글])`. 로그인 계정이 같고 위 값이 같을 때만 같은 키 — **창을 닫았다 다시 열어도** 같은 키(키 보관은 창 밖 `_msDraftKeyer`).
   - ★ 키는 **고른 줄(`_MS.ids`)** 기준이다 — 실제로 보낼 수 있는 사람 목록은 첫 발송 뒤 바뀔 수 있다(알림톡 「도착 확인 중」·회차 변화). 그 목록으로 키를 만들면 다시 보내기가 새 키가 되어 막지 못한다.
   - **키를 버리는 때 = 모두 「보냄」(이미 보낸 것 포함)이 확인됐을 때 · 409(같은 키·다른 내용)일 때뿐.** 통신 실패·서버 오류·일부 실패·결과 모름·처리 중이면 그대로 둔다 → 같은 내용으로 다시 보내면 이미 받은 사람은 건너뛰고 못 받은 사람에게만 간다. 창을 닫은 뒤 도착한 응답도 키를 정리한다.
   - `createCsStaffDraftKey` 가 없으면(구버전 api.js) 키 없이 종전 요청.
2. **서버(`POST /api/trackb/workdesk/manual-send` → `manualMessage.service`)** — 키(`utils/csClientMsgId` 모양)가 있으면:
   - ① 맨 앞: 같은 키로 **내용 지문**(방식·시트·탭·글·보낸 사람 로그인명의 해시 `client_send_fp`)이 다른 기록이 있으면 **409 `manual_send_conflict`** — 아무에게도 보내지 않는다.
   - ② 받는 사람(참여 줄)마다 공급자를 부르기 **전에** `INSERT … ON CONFLICT (client_send_id, participant_id) WHERE client_send_id IS NOT NULL DO NOTHING` 으로 '대기(pending)' 줄을 선점한다. 선점한 요청만 공급자를 부르고 결과로 `sent` / `failed` / `unknown` 을 적는다. 트랜잭션을 공급자 호출 동안 붙잡지 않는다(유일 색인이 한쪽만 이기게 한다).
   - ③ 선점하지 못한 요청이 본 상태:
     - `sent` → 공급자 0 · `{ sent:true, duplicate:true }`(화면은 「보냄」) · 문의방 기록도 다시 안 남긴다.
     - `failed`(공급자가 거절했다고 **답한** 경우 · 요청 전 오류) → `UPDATE … WHERE send_state='failed' RETURNING` 한 문장으로 다시 선점해 **다시 보낸다**(동시 재시도 중 하나만).
     - `unknown`(공급자 시간 초과·연결 끊김 — 받았을 수 있다) → **다시 보내지 않는다** · `code:'manual_send_unknown'` + 쉬운 한국어(「이미 받았을 수 있어 다시 보내지 않았습니다 — 꼭 다시 보내야 하면 리뷰어에게 확인한 뒤 내용을 조금 고치거나 새로고침하고 보내세요」).
     - `pending` → 앞 요청이 처리 중 → 보내지 않음 · `code:'manual_send_in_progress'`. 2분이 넘은 대기(처리 중 서버가 멈춤)는 `unknown` 안내로 바꿔 말한다(여전히 보내지 않음).
   - ④ 공급자 성공 + 결과 기록 실패 → 이번 응답은 「보냄」, 줄은 '대기'로 남아 다시 보내기가 **보내지 않는다**(이미 나갔으므로 맞는 방향).
   - ⑤ 선점 기록 자체가 실패 → 그 사람에게는 **보내지 않는다**(fail-closed · 「발송 기록을 남기지 못해 보내지 않았습니다」).
   - ⑥ **알림톡**: 선점한 줄만 `reminder.sendManual` 에 넘긴다(회차·원장·종결 흐름 = 종전 `sendOne` 그대로 · 수정 0). 공급자까지 안 간 줄(방금 제출함·기간 지남 등)은 선점을 풀어(이번에 넣은 줄은 지움 = 종전처럼 기록 없음) 다시 시도할 수 있다. `sendOne` 의 `uncertain` = `unknown`. `sendManual` 이 던지면 선점 줄은 '대기'로 둔다(공급자까지 갔는지 모르므로).
   - **키가 없거나 모양이 틀리면 종전 경로 한 줄도 안 바뀜.** (→ **2026-11-10 결정 [366](366-작업보드-문자-같은번호-같은글-10분-다시보내기-막기-번호잠금-2026-11-10.md)**: 문자는 키가 없어도 공급자 전 '대기' 줄 선점 + 같은 번호·같은 글 10분 막기를 탄다 — 키 판정만 빠진다. 알림톡 키 없음은 그대로.) 칸이 없는 DB(42703)·색인이 없는 DB(42P10)는 경고 로그 후 종전 경로(보내기는 살리고 중복 방지만 빠진다 — `REQUIRED_SCHEMA` 에도 넣어 실제로는 칸 없이 부팅하지 않는다, 이중 안전).
   - 응답 가산 필드: `results[].duplicate` · `results[].code` · 최상위 `code`(409). 화면은 종전처럼 `sent`·`reason`·`error` 만 그린다 — 새 안내 문구는 서버가 `reason` 으로 준다.
3. **migration 222** — `manual_message_sends` 에 `client_send_id`·`client_send_fp`·`send_state`·`send_state_at` (모두 NULL 허용·기본값 없음) + 부분 유일 색인 `uq_manual_message_sends_client_send (client_send_id, participant_id) WHERE client_send_id IS NOT NULL`. 더하기만 · IF NOT EXISTS · 두 번 돌려도 안전 · 기존 기록은 NULL 그대로.

## 소비처 전수
- `manual_message_sends` 를 쓰는 곳: 실행부 `_log`(종전 경로 · 칸 목록 명시 → 새 칸 NULL) · 키 경로 선점·결과·풀기 4문장 · 작업 삭제 보존 목록(`workTabDelete`) — 읽는 화면 0, `SELECT *` 0.
- `/workdesk/manual-send` 를 부르는 화면은 `_msSendConfirmed` 1곳.
- 기존 가드 `manualMessageSend.test.js` 는 키 없는 종전 경로라 그대로 통과(검사 의미 불변).

## 배포 순서
- 구버전 화면 + 새 서버: 키 없음 → 종전 경로(동작 불변).
- 새 화면 + 구버전 서버: 서버가 모르는 `clientSendId` 를 무시 → 종전 동작(중복 방지만 없음).
- 새 서버 + 마이그레이션 실패: `REQUIRED_SCHEMA` 가 부팅을 막아 직전 배포가 계속 돈다. 우회(`ALLOW_SCHEMA_DRIFT=1`)로 떠도 키 경로는 42703/42P10 에서 종전 경로.
- 되돌리기: 코드만 되돌리면 칸·색인은 남지만 아무도 쓰지 않는다(NULL 허용·기본값 없음) — 무해. '대기'로 남은 줄도 종전 코드는 읽지 않는다.

## 완화 금지
- **선점(대기 줄 넣기)을 공급자 호출 뒤로 옮기지 않는다** — 동시·다시 보내기 두 요청이 둘 다 「없음」을 보고 둘 다 보낸다.
- **`unknown`·`pending` 을 같은 키로 다시 보내지 않는다** — 받았을 수 있는 문자를 또 보내 비용이 두 번 든다(다시 보내는 길은 담당자가 내용을 고치거나 새로고침해 **새 키**로 의도적으로 보내는 것뿐).
- **공급자가 답이 없었던 오류(시간 초과·끊김)를 `failed` 로 접지 않는다** — `failed` 는 같은 키로 다시 보내는 상태다.
- **같은 키·다른 내용(글·방식·작업·보낸 사람)을 성공으로 접지 않는다** · **다시 보내기에 문의방 기록을 다시 남기지 않는다**.
- **화면에서 키를 보낼 때마다 새로 만들지 않는다 · 「모두 보냄」 확인 전(일부 실패·통신 실패·결과 모름)에 키를 버리지 않는다 · 키를 「보낼 수 있는 사람 목록」으로 만들지 않는다(고른 줄로)** — 셋 다 다시 보내기 중복이 그대로 돌아온다.
- 가드: `server/tests/manualMessageSendIdempotency.test.js`(PGlite 실제 SQL · 실제 라우트 · 공급자 흉내로 호출 수를 센다 · 화면 vm — 63건).

## 하지 않은 것 · 남은 판단
- **결과 모름 처리 정책(사업 판단 여지)** — 지금은 가장 보수적인 안: 같은 키로는 절대 다시 안 보내고, 담당자가 확인 뒤 내용을 고치거나 새로고침해 보내게 한다. 다른 안: ㉯ 결과 모름 줄에 [그래도 다시 보내기] 버튼(화면 변경) ㉰ 서버가 공급자 조회(`getMessageStatus` — 문자는 메시지 번호를 못 받았으면 조회 불가)로 확인 뒤 판정. 권장 = 지금 안 유지(드묾 · 돈이 두 번 드는 쪽을 막는다).
- **키가 다른 두 요청의 동시 알림톡**(두 담당자가 같은 줄에 동시에, 또는 구버전 화면 두 창) — `reminder.sendManual` 은 미리보기 판정 뒤 원장 줄을 넣기 전에 잠금이 없어 둘 다 보낼 수 있다(종전 그대로). 자동 알림 실행(`/review-reminders/run`)은 작업 잠금(`withJobLock`)이 있어 해당 없음.
  - **(2026-11-10 후속 → 결정 [365](365-리뷰미작성-알림톡-동시발송-한번만-상태줄-잠금-2026-11-10.md) 에서 고침)** — `sendOne` 이 주문의 상태 줄을 잠그고 다시 확인한 뒤 원장 줄을 넣는다(키와 무관 · 크론+담당자 동시도 포함). 위 「작업 잠금이 있어 해당 없음」은 크론끼리만 맞고, 크론과 담당자 수동이 동시인 경우는 해당이 있었다(365 에서 함께 고침).
- 화면 새로고침 뒤에는 키가 사라진다(메모리 보관 — 362 와 같음). 새로고침 뒤 같은 내용 = 새 발송.
- 발송 기록을 보는 화면이 없다 — 「처리 중」 안내가 「잠시 뒤 창을 다시 열어 확인」이라고만 말한다(다시 열면 알림톡은 회차·결과 확인 중으로, 문자는 같은 키면 「보냄」으로 보인다).
