# ★★ 구매캡처 재시도는 기존 사진을 지우지 않는다 — 완료 재점유 차단·늦은 실패 소유권·COMMIT 불명 보존 (2026-10-29)

## 발단·승인
- 결정 294의 깨진 구매사진 신고에서 전수 조사로 확장했다. 진행·마감·보관 작업 및 옛 첨부·교체 이력을 분리했다.
- 사용자는 확인된 551장부터 운영에 복구하고, 충돌·권한 문제 19건은 보류하며, 현재 코드의 재발 가능 오류도 수정하도록 승인했다.
- 운영 복구와 재발 방지 코드는 별개다. 복구는 원래 제출시각·배송메모·검수·정산을 보존하는 별도 절차이며 일반 사진 교체 기능을 재사용하지 않았다.

## 확인한 과거 결함과 한계
- 같은 이름 파일을 새 업로드 전에 휴지통으로 보내는 동작은 `f73ad7fac`(2026-04-27)에 들어갔다.
- 주문에 첫 업로드만 연결하는 `capture_uploaded_at IS NULL` 조건은 `327bd45e7`(#359, 2026-07-27)에 들어갔다.
- 이 조합은 재시도·재제출·동명이인 업로드가 첫 사진을 휴지통에 보내지만 주문은 첫 사진 ID를 유지하고, 새 사진은 연결되지 않는 현상을 만든다. 새 업로드가 실패해도 이전 사진부터 휴지통으로 가는 경우까지 실제 과거 코드로 재현했다.
- `0c8edbf36`(#1311, 2026-09-03)은 주문·세션별 이름과 완료 재사용·점유·주문 잠금으로 일반적인 재시도 충돌을 막았다.
- 그러나 최신 코드에서도 두 요청이 사전 조회 후 엇갈리면 `status <> 'uploading'`이 completed 재점유를 허용했다. 뒤늦은 요청이 이름 정리로 승자 사진을 지우고, 연결 경쟁에서 자기 사진도 지워 두 응답이 성공이어도 실물은 둘 다 휴지통인 경우를 재현했다.
- **개별 유실 파일의 삭제 시각·주체·경로는 미확인**이다. 결함 재현과 업로드 시기 집중이 모든 사진의 개별 삭제를 증명하지는 않는다. OAuth·서비스 계정 모두 404라는 것은 해당 계정에서 조회하지 못했다는 확인이며, 모든 파일의 영구삭제·복구 불가를 확정하는 말로 넓히지 않는다.

## 재발 방지 결정 — 스키마·프론트 변경 없음
1. `diag.routes`의 구매사진 업로드는 **두 장 모두 이름 기준 삭제를 하지 않는다**. 파일명은 `_2` 구분과 주문·세션 표시를 유지하되 `__pcv2_` + 요청별 암호학적 접미사를 붙인다. 구서버의 결정적 이름과도 분리한다.
2. `markUploading`은 prepared/failed 또는 오래된 uploading만 점유한다. 완료시각·세션 파일·살아 있는 주문의 첫 사진 유무까지 확인하며 `{ attemptCount } | null`을 반환한다. 실제 앱 소비처는 업로드 라우트 한 곳이다.
3. `markFailed`는 **이번 요청이 받은 attempt_count**가 현재 uploading과 같을 때만 쓴다. 늦은 실패가 새 시도를 failed로 바꾸지 않는다. 점유 전 오류·둘째 장은 실패 상태 쓰기 0이다.
4. 완료는 기존 `purchase_capture:<orderId>` 잠금과 원장 우선 판정을 유지한다. 최신 시도만 완료할 수 있게 바꾸는 새 fencing은 넣지 않는다. 오래된 정상 요청도 먼저 연결하면 이길 수 있고, 독립 파일 구조로 사진은 보존된다.
5. 점유 실패 뒤에는 세션을 다시 읽는다. 그사이 완료됐으면 업로드 없이 기존 ID·captureIndex만 반환한다. 실제 진행 중이면 종전 retryable 충돌 응답이다.
6. **다른 ID가 먼저 연결됐다고 확정된 이번 요청의 패자 파일만** 휴지통 정리한다. 패자 응답은 기존 early-completed 형식(ID·장 번호)만 쓰고, 지워진 패자 이름·URL·SSE를 승자 ID에 섞지 않는다. 완료 알림 실패는 저장 성공과 분리한다.
7. DB 연결 실패·세션 무효·COMMIT 응답 소실처럼 결과가 모호하면 업로드 파일을 보존한다. 직원 구매사진 교체의 catch도 새 파일을 지우지 않는다. 값 불일치가 확인되고 ROLLBACK이 성공한 경로의 자기 파일 정리, 정상 교체 후 사용하지 않는 옛 파일 정리는 유지한다.
8. 결정 288의 둘째 장 자기 칸·첫 장 세션/시각 무접촉, 직원 교체의 앞뒤 expectFileId 대조, 공통 주문 잠금은 불변이다.

## 운영 복구 결과 — 2026-10-29
- 동일 주문 사본 재연결 509건 + 휴지통의 동일 리뷰 원본 42장 = 551장.
- 18건은 후보가 다른 살아 있는 주문 기록에 이미 연결돼 있어 보류했다(동일 주문 중복 기록 귀속부터 판정). 옛 신청서 첨부 1장은 복구 권한이 없어 보류했다.
- 구매 사본은 원래 사진과 바이트까지 동일하다는 주장이 아니다. 주문번호와 원래 제출 작업의 구매폴더·실물 지문으로 확인한 **대체 사본 연결 정정**이다. 감사기록에도 원본 휴지통 복원과 구분했다.
- 운영 쓰기: 구매 `capture_file_id·updated_at`만, 복구 로그 append-only. 구매 제출시각·배송메모·둘째 장·검수·금액·입금·작업표·행 연결은 보존했다. 리뷰 원장·대표사진은 수정하지 않고 Drive `trashed:false`만 적용했다.
- 건별 변경 전 기록 저장·주문 잠금·기존 값 재대조·로그와 같은 트랜잭션·커밋 뒤 재조회. 기존 자동 연결 도구와도 공용 작업 잠금을 사용했다.
- 전수 재조회: 구매 509/509, 원본 42/42, 실패 0. 운영 이미지 프록시 실제 읽기 표본 40/40은 정상 응답과 바이트 지문까지 확인했다. 전수 메타데이터 검사와 표본 실물 읽기는 구분한다.
- 사진·주문 식별자·개인정보가 든 전체 명세·변경 전후 자료는 저장소에 넣지 않고 운영자 로컬 보호 보고 폴더에 보관한다. 코드를 revert해도 이 데이터 복구가 되돌아가지는 않는다.

## 완화 금지
- 구매사진 업로드에 이름 기준 삭제를 되살리지 않는다. 재시도는 먼저 연결된 파일의 삭제 권한이 아니다.
- 완료된 세션 재점유·점유 번호 없는 실패 쓰기를 허용하지 않는다.
- DB 결과가 모호한 예외에서 업로드 파일을 삭제하지 않는다. COMMIT 응답 오류는 롤백 확정의 증거가 아니다.
- 둘째 장이 첫 장 세션 상태·첨부시각을 쓰게 하지 않는다. 공통 주문 잠금·직원 expectFileId 대조를 빼지 않는다.
- 동일 주문 사본을 원본 동일성으로 보고하거나, 다른 주문이 쓰는 파일을 확인 없이 중복 연결하지 않는다.

## 남는 경계
- 롤링 배포 중 구서버끼리의 기존 경합과 구버전 실패 표시의 상태 오염까지 즉시 사라지는 것은 아니다. 새 이름은 구서버 삭제에서 격리되며 전체 배포 완료 뒤 재발 방지를 보고한다.
- 모호한 실패 파일은 남을 수 있다. 결정 064·272로 제거된 고아 자동 정리를 되살리거나 자동으로 치워진다고 약속하지 않는다.
- 서버 종료 뒤 남은 uploading의 5분 stale 대기는 유지한다. 브라우저 자동 재시도 창보다 길 수 있어 재실행이 필요한 경계는 이번에 바꾸지 않는다.
