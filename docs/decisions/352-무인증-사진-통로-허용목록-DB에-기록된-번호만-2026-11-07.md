# ★★ 무인증 사진 통로 2곳은 우리 DB 에 기록된 번호만 내준다 — 목록 밖·이체결과 = 404(드라이브 읽기 0) · 판정 = 인덱스 조회 1회 + 번호별 기억 · 조회 실패는 사진만 fail-open (사용자 확정 2026-11-07 · migration 216)

## 왜
- `GET /api/drive/image/:id` · `GET /api/order/guide-image/:id` 는 `<img src>` 가 헤더를 못 보내 **무인증**이다. 그런데 번호 형식만 보고 **소유자 계정으로 드라이브의 아무 파일이나** 읽어 내줬다 — 사진이 아닌 파일, 비공개 **이체결과 보관 파일(리뷰어 이름·계좌 전체, 결정 316)** 까지(사전 조사 실측 200).
- 사용자 확정: 「권장대로(방법 C 먼저) 진행, 단 사진 로딩은 매우 빨라야 한다」. 이번은 **1단계 = 허용 목록만**. 서명 주소(A)·드라이브 공개 권한 걷기는 별도 결정(결정 008 썸네일 구글 직결과 얽힘).

    | `review_index.review_file_id` | 대표 리뷰 이미지 폴백 · 리뷰어 제출 현황 썸네일(`reviewFileId`) |

  - **guide-image 허용 = 새 표 `guide_image_files`**(번호 기본키). 주소가 글 칸에 문장째 섞여 저장돼(오더 가이드·본문·선택지 가이드·썸네일·공고·C/S 첨부·설정·인트라넷 리뷰오더) 인덱스로 찾을 수 없어서다.
    - 올리는 3곳(`POST /api/order/guide-image`(+Track B 설정 프록시·인트라넷 키) · `POST /api/cs/upload` · `POST /api/reviewer/cs/upload`)이 **주소를 돌려주기 전에** `registerGuideImage` — 실패하면 올리기 실패(목록에 없는 주소를 돌려주면 영영 안 뜬다).
    - 지난 사진 = migration 216 의 DO 블록이 public 의 **모든 표·모든 글 칸**(text·varchar·json·jsonb·text[])에서 주소를 찾아 한 번 들여온다. bytea(이체결과 원본 등)는 읽지 않는다.
    - 인트라넷: 리뷰오더 사진은 인트라넷 서버가 우리 업로드를 대신 부르고(`/api/review-order/guide-image` → 우리 `POST /api/order/guide-image`, X-Intake-Key) 접수되면 오더 칸에 주소째 들어온다 → 앞으로 = 업로드 때 등록(`upload:intranet`), 지난 것 = 들여오기.
  - **두 통로 모두 거절이 우선**: `payment_result_drive_archive.drive_file_id`(이체결과 보관) 는 다른 칸에 같이 적혀 있어도 404.
- 라우트: 판정 → 거절이면 **404 + `Cache-Control: no-store`, 드라이브 읽기 0, 구글 썸네일 302 폴백도 안 함**(폴백하면 목록이 무의미). 허용이면 종전 그대로(캐시 헤더·CORP·썸네일 폴백 불변).
- migration 216: 인덱스 없던 출처 칸에 부분 인덱스(`IS NOT NULL`) 8개 + `guide_image_files` + 들여오기. 기존 관례대로 비-CONCURRENTLY(051·168). `REQUIRED_TABLES` 에 `guide_image_files` — 들여오기가 실패하면 표도 안 생겨(한 묶음) 새 배포가 거부되고 옛 배포가 그대로 돈다.

## 속도 (실측 — PGlite, 표당 10만~20만 줄, 같은 프로세스)
- 첫 판정(인덱스 조회 1회): 허용 중앙값 **0.38~0.43ms**(p95 0.8~1.5ms) · 목록 밖(모든 칸 확인) **0.47ms** · guide **0.19ms**. 두 번째부터(번호별 기억) **0.0007ms**.
- 운영은 여기에 DB 왕복(같은 Railway 망 1ms 안팎, 미측정)이 한 번 더 — 드라이브 왕복 1.7초(결정 008) 대비 0.1% 미만.
- EXPLAIN(seqscan 끄지 않고): 모든 칸 `Index Only Scan`/`Index Scan`, app_settings 만 Seq Scan(300줄 0.09ms).
- 기억: 허용 10분(브라우저 `max-age=600` 과 같은 길이) · 거절 5초 · 최대 2만 개(오래된 것부터 지움) · 같은 번호 동시 요청은 진행 중 판정 하나를 함께 기다림(썸네일 격자도 조회 1회).

## fail 방향
- **DB 조회 실패·1초 초과 = fail-open + 경고 로그(1분에 한 줄로 묶음), 이 판정은 기억하지 않는다** — 사진이 안 뜨면 검수·교체·보고가 다 막힌다.
- 단 fail-open 때는 **내려받은 파일이 사진(`image/*`)일 때만** 내준다 → 이체결과 파일(엑셀·CSV)은 조회 실패 중에도 거절(이 경우만 드라이브 1회 읽음).

## 🚫 완화 금지
- **목록 밖 번호를 드라이브로 읽지 않는다 · 거절을 구글 썸네일 302 로 돌리지 않는다** — 돌리는 순간 "아무 파일이나" 가 되살아난다.
- **이체결과 보관 칸(`PRIVATE_SOURCES`) 검사를 빼거나 허용 뒤로 미루지 않는다** · fail-open 의 `image/*` 제한을 풀지 않는다.
- **guide-image 주소를 새로 만드는 서버 자리는 주소를 돌려주기 전에 `registerGuideImage`** — 빠지면 올린 사진이 안 뜬다(회귀가드가 자리 3곳을 고정).
- **화면이 새 칸에서 사진 번호를 받기 시작하면 `DRIVE_IMAGE_SOURCES` 에 더하고 인덱스를 만든다** — 안 더하면 그 화면 사진만 조용히 404. 회귀가드가 ① 화면 주소 생성 자리 수(작업보드 9·리뷰어 검색 2·리뷰어 앱 1·C/S 카드 1·보고 1) ② 출처 칸 목록 ③ 칸마다 마이그레이션 인덱스를 대조한다.
- 결정 008 의 「드라이브 왕복 1회」「대조 자리는 원본」은 그대로다(허용 판정은 DB 만 본다).

## ⚠ 남은 것 · 사각지대
- **인트라넷에만 남은 지난 사진**: 리뷰웹에 접수되지 않은 인트라넷 리뷰오더(임시저장·미전송)에 붙은 옛 사진은 우리 DB 에 흔적이 없어 404 가 된다(앞으로 올리는 것은 등록됨). 필요하면 인트라넷 DB 읽기로 번호를 한 번 들여온다.
- 들여오기 시간: 운영 표 크기를 못 재 봤다(로컬 10만 줄 표 몇 개 = 1.2초). 120초 제한을 넘으면 새 배포가 거부되고 옛 배포가 유지된다(안전 쪽) — 로그 `216_image_allowlist.sql` 확인.
- 캡처 자체는 드라이브 「링크 있는 모든 사용자」 공개라 `drive.google.com/thumbnail?id=` 로는 여전히 열린다(조사 보고 ②) — 이번 범위 밖.
- 허용을 10분 기억하므로 지운 줄의 사진은 최대 10분 더 열린다(브라우저 캐시와 같은 길이).
