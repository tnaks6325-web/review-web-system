# ★★ v2 블로그 오더 접수 막힘 해제(리뷰타입·구매일자 없음) + 접수된 오더의 체험단 종류 변경 409 잠금 (2026-11-03 · 스키마 변경 0)

## 무슨 일이었나
- 블로그체험단은 운영에서 공고 0건·신청 0건이었다. 원인 조사(2026-11-03) 중 **v2 작업표(`workboard_schema_version=2`) 블로그 오더는 [접수]가 반드시 실패**함을 로컬 재현으로 확인했다.
  - 인트라넷은 블로그 오더의 리뷰타입을 지워 보낸다(`reviewOrderApplyBlogRule`). v2 계획은 행별 리뷰 형태를 정하려고 `variableWorkboard.reviewOptionAssignments` 를 부르는데, 리뷰타입이 비면 `invalid_review_type` 블로커 → "지금 구성으로는 작업표를 만들 수 없습니다".
  - Q&A 는 예외(`!isQnaPlan`)로 빠져 있었지만 블로그는 빠져 있지 않았다. 운영 최근 30일 오더 61건이 전부 v2 — 즉 오늘 인트라넷에서 블로그로 보내면 접수가 영영 안 된다.
- v2 도입(#1264) 때 결정 138·127 의 "블로그 표는 구매일자를 깔지 않는다" 가 `!isV2 && isBlogPlan` 으로 v1 에만 걸려, v2 블로그 표에는 날짜가 깔리게 돼 있었다(실제로 접수된 적이 없어 드러나지 않음).
- 별개로, `isSourceEditLocked` 는 공고·광고주 연결 뒤에만 걸려 **접수만 되고 광고주·공고가 없는 오더**(운영 실측 30건)는 인트라넷 수정으로 `work_kind` 가 그대로 저장됐다. 작업표 종류(`tab_configs.work_kind`)는 빈 값일 때만 채워져 다시 바뀌지 않으므로 오더와 작업표 종류가 갈라진다(운영 실측: 이미 갈라진 건 0).

## 결정
1. `worktablePlan.buildWorktablePlan` — 블로그는 v1·v2 모두 구매일자를 깔지 않고(`isBlogPlan`), v2 행별 리뷰 형태를 정하지 않는다(`!isQnaPlan && !isBlogPlan`). 리뷰 v2 는 종전대로(리뷰타입 없으면 막음).
2. `order.routes` — `_acceptedWorkKindChanged(order, nextKind)`: 작업표가 연결된(`linked_tab_name`) 살아 있는 오더에서 정규화한 종류가 달라지면 409 `accepted_kind_locked`.
   - 원본 수정(`/intake/source/:id`): Q&A 자리표 잠금 **뒤**, 담당자 분기 **앞**. 양방향(`bidir_state='on'`) 오더는 제외 — 공유 저장이 같은 요청을 `structure_new_order` 로 막아 온 응답을 그대로 둔다.
   - 옛 수정(`/intake/:id/update`): `work_kind` 를 보냈을 때만.
   - 문구는 "원래 종류로 되돌려 저장" — 인트라넷은 거절된 리비전을 `failed` 로 남기므로, 되돌리는 길을 알려야 막다른 길이 안 된다.
3. 접수 뒤 종류를 **바꾸는** 정식 경로(손대지 않은 작업만 접수 되돌리기 → 재접수)는 후속 단계에서 이 잠금 위에 따로 연다. 그 전까지는 409 가 맞다.
   - ★ 2026-11-04 열림 → [결정 332](332-접수된-리뷰-블로그-오더-종류-바꾸기-손대지-않은-빈-작업이면-접수-되돌리기-2026-11-04.md). 그 경로를 못 타는 요청(번호 어긋남·Q&A·게시·사람이 든 작업)은 여전히 이 409 다.

## 완화 금지
- **v2 블로그를 리뷰 형태 배정에 다시 태우지 말 것** — 블로그 오더 접수가 전부 막힌다.
- **접수된 오더의 종류 변경 409 를 풀지 말 것** — 오더와 작업표 종류가 갈라져 블로그 3열 없는 블로그 작업(또는 그 반대)이 생긴다. 바꾸려면 작업표를 다시 만드는 정식 경로로만.
