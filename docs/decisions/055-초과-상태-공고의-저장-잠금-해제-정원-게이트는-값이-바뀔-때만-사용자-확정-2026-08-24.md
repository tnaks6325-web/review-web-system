# ★★★ 초과 상태 공고의 저장 잠금 해제 — 정원 게이트는 "값이 바뀔 때만" (사용자 확정 2026-08-24)
- **신고**: 채워진 줄이 정원보다 많은 공고(41/40)에서 **제목·리뷰비만 고쳐도 저장이 실패**로 떴다. 실제로는 `UPDATE recruit_campaigns`·옵션·옵션 칸·리뷰비 구간이 **모두 커밋된 뒤** 맨 끝의 정원 동기화에서만 터진 것이라 **"저장은 됐는데 실패로 보고"** 였고, 담당자는 실패한 줄 알고 같은 저장을 반복했다(본섭 실측 **13개 작업**).
- ★★ **원인 = 게이트가 "전송 여부"로 돌았다** — 수정 모달은 진행상품 표 파생 hidden 값(`recruit_total`)을 **늘 재전송**하므로 같은 값에도 검사가 돌았고, `worktableSlotDelta`(1차 `next < fixed`)와 `syncWorktableSlotsInTx`(2차 `ids.length !== delta.retire`) **두 겹**에서 throw 했다. ⇒ **판정 함수만 완화하면 실패가 2차로 옮겨갈 뿐**(실행 증명: `current 41 / protected 41 / target 40` → `retire:1` 인데 빈 슬롯 0).
- ★★ **수정 = 호출부에서 "총정원이 이번 저장에서 실제로 달라졌을 때만"**(`campaign.routes` PUT `/admin/:id`): UPDATE 앞에서 이전 값을 읽어 `_rtChanged` 로 `assertCampaignRecruitTotal` 을 게이트하고, `syncCampaignRecruitTotal` 에는 `skipWorktable` 를 넘긴다. ★ **작업오더 경로가 이미 쓰는 관행**(`changes.find(... === 'recruit_count')`)의 대칭 적용 — 새 정책이 아니다.
- ★★ **완화 금지 5종**: ① **줄이려는 조작은 종전대로 막는다**(판정 함수 두 겹 **무접촉** — 값이 달라질 때만 게이트를 건너뛰지 않는다) ② **이미 초과된 인원은 초과 상태로 유지**(줄을 잘라 맞추지 않는다 — 초과 표시 정책 그대로) ③ **외부모집 수동제출로 초과가 더 늘어나는 것도 허용**(`manualOrder` 는 이미 총정원 초과를 허용하고 `모집 정원을 초과해 확정했습니다` 경고만 — 일 정원만 확인 게이트) ④ **정원이 찬 공고가 리뷰어에게 모집중으로 안 보이는 것은 정상**(상태엔진 `soft_full` — 게시 토글 `PUT /admin/:id/status` 는 정원을 보지 않으므로 토글 자체는 눌리지만 참여는 막힌다) ⑤ **이전 값을 못 읽으면 검사하는 쪽으로 접는다**(fail-closed).
- ★ **역방향 링크 백필은 건너뛰지 않는다** — `syncCampaignRecruitTotal` 은 정원 동기화 외에 `work_orders.linked_campaign_id` 도 채우므로, `skipWorktable` 는 **슬롯 맞추기만** 끈다(그것까지 빠지면 연결이 조용히 비는 별개 사고). ★ 비교는 **차수 보정(`repairRecruitTotalFromRounds`) 뒤 최종값**으로 한다. ★ **발행(create)은 이전 값이 없어 종전 그대로**.
