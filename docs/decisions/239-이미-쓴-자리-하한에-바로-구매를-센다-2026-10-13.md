- 결정 238(참여 규칙) 다음 단계 = "관리자 숫자에 바로 구매 넣기" 중 **① 안전장치**를 먼저 한다.
- 사용자: "지금보다 커져보이는거보다 실제 숫자가 중요해. 커져보이지 않은 다음 나중에 실제가 더 커서 일어나는 문제일때 수습이 어려워져."

  많은 공고는 **실제로 산 사람보다 정원을 낮게** 줄일 수 있었고, 바로 구매만 있는 **상품은 통째로 삭제**, 바로 구매만 있는 **공고는 삭제**
  (→ `payment_batch_items.campaign_id` SET NULL 로 입금 회차 연결 끊김)될 수 있었다.

## Codex 리뷰 반영 (PR #1625)
- **known 은 "주문 기록을 실제로 받았나"** — `totalQuotaUsage.known` 은 게이트 모드가 observe 면 조회 실패도 true 로 접는다. 하한은
  `!(참여형 && 연결 작업표) || CAMPAIGN_TABLE_QUOTA=off || linked.ok&&!noTab` 로 직접 판정한다.
  `off` 는 운영 킬스위치(주문 원장 셈 자체를 끈 상태)라 하한도 공고 참여만 — 줄이기를 영구히 막지 않는다.
- **레거시(참여형 아닌) 공고**는 연결 칸이 있어도 셀 바로 구매가 없다 → known(참여 0 이면 삭제 가능). 로컬 실측 삭제 200.
- **공고 삭제 확인은 체크아웃 커넥션**으로 — pool 경로의 주문 수 캐시(최대 10초)를 거치지 않는다.
- **모를 때 비교 기준 = 지금 적용 중인 정원**(`displayRecruitTotal(공고 값, 연결 작업오더 값)`) — 공고 값 0 · 작업오더 정원 공고도 줄이기를 막는다.
  작업오더 저장 3경로(`order.routes` 1044/1320/2144)는 이 검사를 작업오더 UPDATE 전에 부른다.
- **상품별 하한의 중복** — 공고 참여 주문과 같은 구매(주문번호+연락처)를 수동으로 또 넣은 바로 구매는 하한에서 뺀다
  (`fetchOptionCounts(…, { excludeApplicationDuplicates: true })`, 운영 전체 22건). 참여 게이트·화면의 상품별 셈은 종전 그대로(② 화면 숫자 단계에서 함께 볼 것).
  로컬 실측: 같은 구매 중복 1 + 별개 1 → 엔진 2(종전) / 하한 1.

## 완화 금지
- ★★★ **하한·삭제 가드를 다시 공고 참여만 세는 쪽으로 되돌리지 않는다** — 실제 산 사람보다 정원을 낮추거나, 바로 구매의 상품·공고(입금 연결)를 지우는 길이 다시 열린다.
- ★★ **새 셈법을 만들지 않는다** — 하한은 `quotaFloor.service`(= 정원 엔진 `fetchCampaignCounts`/`fetchOptionCounts`)만 쓴다. 결정 238 서비스(`directPurchaseParticipation`)는
  리뷰어 판정용 느슨한 규칙(시작일 절단·구매 키 중복 제거 없음)이라 하한에 쓰지 않는다.
- ★★ **주문 기록을 모를 때 줄이기·회차 빼기·공고 삭제는 막는다**(fail-closed). 늘리기·그대로 저장은 막지 않는다.
