## 판정 — 단일 출처 `payment.service.bookingPayoutOf`
- **금액 식은 종전 그대로**(`제품비 + 리뷰비` — 리뷰비는 082 `resolveReviewFee` 단일 출처, 제품비 원천은 `const productPrice = workboardPrice || orderPrice` = 작업보드 표시값 → 주문 원장). 이 함수는 **제품비 자리에 무엇을 넣을지와 막을지만** 정한다. 상품 리뷰용 계산기 사본을 만들지 않았다.
- 예약리뷰인가 = 공고 > 탭 종류(`resolveWorkKind`)가 `booking` **또는** 그 작업에 자리표(`booking_slots`)가 있음 — 종류 칸이 어긋나도 예약 규칙 쪽으로(fail-closed). Q&A 가 먼저.
- 예약 설정 = `bookingSlots.placeInfoForTabs`(새 묶음 조회) — `placeInfoForTab` 과 **같은 오더·같은 변환**(`_placeFromWorkOrderRow` → `bookingSpecFromWorkOrder`). 예약내역 창구가 결제금액을 묻는 근거와 같은 값이다.

## 회차 항목 표시 — 무료체험형 = 「0원 구매」 표시 재사용 (스키마 변경 0)
- 무료체험형 항목 모양(제품비 0 · 금액 = 리뷰비)은 결정 292 「리뷰비만 보낸 건」(split)과 값으로 구분되지 않는다. 표시가 없으면 결과 반영이 **입금일·지급완료를 안 남겨** 리뷰어 화면이 「미입금」으로 남는다(321·376 과 같은 함정).

- **새 칸을 만들지 않은 이유**: 무료체험형은 리뷰어가 실제로 0원을 낸 방문(업체가 현장 무료 처리)이라 「0원 구매」라는 칸 뜻과 맞는다(376 이 `is_qna` 를 빌리지 않은 이유 = 리뷰 작업에 「Q&A」가 박혀 뜻이 어긋나서 — 여기는 어긋나지 않는다). 새 칸이면 읽는 곳 3곳(결과 파일·통장 확인·입금일 다시 쓰기) + 판정 2곳(JS·SQL) + 기동 필수 칸 + 손으로 만든 시험 표 7곳을 함께 바꿔야 해 하나만 빠져도 376 의 통장 확인 구멍이 되풀이된다.
- 환급형은 제품비 > 0 이라 일반 입금과 같다(표시 없음).
- 이체 파일(케이뱅크·하나은행 서식)은 회차 항목 금액을 그대로 찍는다 — 바꾼 곳 없음(시험이 실제 파일을 열어 30,000 / 3,000 을 확인).

## 완화 금지
- **`bookingPayoutOf` 에서 1건 금액 초과·결제금액 없음을 상한으로 깎거나 0·상한으로 채워 지급으로 접지 말 것** — 과지급이거나 리뷰어가 낸 돈과 다른 금액이 나간다(되돌리려면 사람이 찾아 회수해야 한다).
- **무료체험형에서 결제금액 칸·주문 금액을 다시 읽지 말 것** — 업체가 현장에서 무료 처리했는데 상품값이 나간다.
- **예약 설정을 모를 때(조회 실패·계약 못 읽음) 지급으로 접지 말 것(fail-closed)** · 예약리뷰 판정에서 「자리표가 있음」을 빼지 말 것.
- **예약번호(예약내역) 확인을 빼지 말 것** — 예약하지 않고 리뷰만 낸 줄이 돈을 받는다.
- **회차 담기의 `bookingFree → zero_price_purchase` 박제를 빼지 말 것 · 모양 확인(제품비 0 · 금액 = 리뷰비)을 빼지 말 것** — 무료체험형 지급이 「리뷰비만 보낸 건」으로 읽혀 입금일·지급완료 없이 끝난다.
- **예약리뷰를 `zeroPricePurchaseOf`(결정 376)로 넓히지 말 것** — 두 판정이 섞이면 어느 쪽 조건이 이기는지 갈린다.
