# ★★ 발주 정원 폴백 — 공고 총인원·일건수가 0이면 발주서 값이 실제 정원이다 (2026-08-21, 스키마 변경 0)
- **신고**: 작업보드 [작업 조건]이 `총건수 0 건` 인데 바로 옆 진행 현황은 `참여자 99/100` — **한 화면에 두 숫자**. 공고 `recruit_total = 0`(=무제한/미설정)을 화면이 `0 건` 으로 그대로 그렸고(그건 "0건"이 아니라 "무제한"이라 **거짓 표기**), 참여자 게이지만 발주 총건수(`work_orders.recruit_count`, 없으면 탭 이름의 "100건")를 봤다.
- ★★ **단순 표시가 아니라 실제 적용(사용자 확정)** — 공고에 값이 있으면 그 값, **0(미설정)이면 발주서의 총건수·일건수가 그 공고의 정원이 된다**. 그래서 100건짜리 작업이 무제한으로 열려 있지 않고, 다 차면 `soft_full` 로 닫힌다.
- ★★ **판정 사본 0 = `linkedRecruitQuota.displayRecruitTotal`** (공고>0 이면 공고, 아니면 발주). 상태엔진은 `campaignState.effectiveQuota` 로 그것을 **그대로 태우고**, 작업 조건 재료(`trackB.tabConditionSummary`)도 같은 함수를 쓴다. 종전 `num(c.recruitTotal) != null ? … : …` 은 `num(0)` 이 참이라 **0을 값으로 취급**해 폴백이 영영 발동하지 않았다.
- ★★ **재료는 counts 깔때기**(`fetchCampaignCounts` → `counts.orderQuota`) — 목록·상세·apply 게이트·카드가 같은 정원을 본다(별도 인자로 흩으면 "카드는 100인데 참여는 무제한"). 로더 `_loadOrderQuota` 는 **plans·linked 뒤**(066 가드의 쿼리 순서 계약) · 잠금 tx 는 **SAVEPOINT `cs_order_quota` 격리**(082) · 10초 캐시 · **실패 = null = 미부착 = 종전 동작**(모른다고 정원을 좁히지 않는다).
- ★ **짝짓기 규칙도 기존 것 그대로** — 역방향 링크(`work_orders.linked_campaign_id`) 우선 → 정방향(`recruit_campaigns.source_work_order_id`), 같으면 최근 수정 오더(`displayRecruitTotalForCampaign`·067 과 같은 우선순위). **소프트삭제된 오더는 근거가 아니다.**
- ★★ **비영속(완화 금지)** — `maybePersistClosed` 는 여전히 DB 의 `rc.recruit_total > 0` 만 보므로 이 폴백으로 `status='closed'` 가 **굳지 않는다**. 발주 건수를 고치거나 공고에 총인원을 넣으면 그 순간 반영된다(표 기준 게이트와 같은 규율).
- ★ **적용 범위**: 총량 clamp · `soft_full` · `dailyQuota`(그날 정원) · 이월 기준 일건수(`pendingCarry`) · 표시 재료. **시트 일정(063) 경로는 무접촉**(시트가 총량의 진실원본).
- ★ **화면이 사유를 말한다**(조용한 대체 금지): 총건수에 `발주 기준` 칩(툴팁 = "공고에 총인원이 없어 발주서 총건수가 정원으로 적용 중"), 일건수는 사용자 확정 문구 **`발주 기준 10건/일 (공고 설정 오늘 16건)`** — 왼쪽은 계약상 기준선, 괄호는 모집인원조절·이월이 반영된 오늘 실제 정원. **없는 쪽은 지어내지 않는다**(한쪽만 있으면 그것만, 둘 다 없으면 [미설정]).
- 킬스위치 `CAMPAIGN_ORDER_QUOTA=0` = 전건 종전 동작 즉시 복귀(코드 변경 0).
- ⚠ **운영 함의**: 배포 즉시 **"공고 총인원 0 + 발주 건수 있음"인 공고들이 무제한에서 정원제로 바뀐다** — 이미 발주 건수를 넘겨 모집된 공고는 그 자리에서 `soft_full`(그게 사실이다). 되돌리려면 킬스위치 또는 공고에 총인원을 명시.
