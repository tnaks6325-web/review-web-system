# ★★ 오더를 지울 때 리뷰웹에 남는 모집공고·작업보드를 알려 준다 — 서버 부분(삭제 응답 `kept` + 삭제 전 미리보기 주소) (사용자 확정 2026-11-20 「가」 · 스키마 변경 0 · 화면 변화 0)

## 발단 (2026-11-18 세라모사이드 · 운영 읽기 전용 조사)
- 담당 AE 가 인트라넷에서 첫 오더(`wo_c2f91b87370d`)를 지웠다. 오더는 지워졌지만 그 오더로 **이미 게시한 모집공고**(`camp_e4a143db7c60`)와 작업보드는
  결정 254 설계대로 남았다(보관 안 된 공고가 있으면 자동 정리하지 않는다 `live_campaign`). 다음 날 07시 그 공고가 그대로 열려 204명 신청 · 194명 제출.
- 리뷰웹 삭제 응답은 `{ ok:true, id }` 뿐이라 「공고·작업보드는 남겼다」를 **아무에게도 알리지 않았다**. 인트라넷 확인창도 「작업오더도 함께 삭제됩니다」만 말한다.
- 최근 60일 지운 오더 23건 중 이런 「남는 공고」가 있던 오더 = **이 1건**(운영 읽기 2026-11-20).

## 결정 (이 PR = 심판 §8 PR 1번 「RW-B」 · 인트라넷 화면은 IN-B 별도 PR)
1. **읽기 함수 하나** `workTabDelete.orderDeleteImpact(q, workOrderId)` — 삭제 전 미리보기와 삭제 응답이 **같은 함수**를 쓴다(사본 0).
   - 남는 공고 = 보관 안 된 공고 중 `source_work_order_id = 오더` ∪ `id = 오더.linked_campaign_id` ∪ `오더 작업보드(linked_tab_sheet_id·linked_tab_name)에 연결된 공고`.
     칸 = `id · title · state · applicants(신청 기록 전부 — 취소·만료 포함) · submitted(제출)` **5개만**(신청자·담당자·삭제자 이름 없음).
   - `state` 4종(사용자 확정 Q6 ㉠ — 문구는 인트라넷이 상태별로): `open` 게시 중 · `draft` 임시저장 · `paused` 공고 전체 품절 멈춤(결정 259 칸 `soldout_paused_at` + 같은 스위치 `CAMPAIGN_OPTION_PAUSE`) · `closed` 마감(그 밖 상태).
   - 작업보드 = `predictCleanup(q, wo)` — **실제 자동 정리(`autoCleanupDeletedOrderTab` → `deleteTask onlyIfUntouched`)와 같은 입력·같은 판정을 그대로 부른다**:
     스위치 `INTAKE_DELETE_TAB_CLEANUP` · 직접 연결 작업만 · 결정 254 판정 `_untouchedReasons`(**글자 그대로 · 옮기거나 좁히지 않음**) · 돈 기록 `_moneyRows`.
     `outcome` = `will_remove`(정리 예정) · `remains`(남음 + `reasons`) · `removed`(이미 정리됨 — 같은 삭제를 다시 보낸 경우) · `absent`(등록된 작업 없음) · `none`(작업보드 없는 오더).
     삭제 전 미리보기는 곧 지울 **자기 오더**를 「살아 있는 오더」로 세지 않는다(결정 332 가 이미 쓰는 `selfOrderId` 예외).
     정리는 응답 뒤 비동기라 늘 **예정**(`predicted:true`) — 그 사이 주문·편집이 들어오면 실제 정리는 남긴다.
2. **삭제 응답에 `kept` 추가** — 새 삭제 `{ ok, id, kept }` · 이미 삭제 `{ ok, id, alreadyDeleted:true, kept }`. **기존 칸 불변**(옛 인트라넷은 `upstream.ok` 만 본다).
   `kept` 는 삭제 표시(UPDATE) 뒤 · 응답 **전**에 계산하고(상한 2.5초), 자동 정리는 **종전대로 응답 뒤 `setImmediate`**(순서 불변). 계산이 실패해도 삭제는 성공으로 답한다.
3. **삭제 전 미리보기** `GET /api/order/intake/:id/delete-impact`(`:id` = 삭제 경로와 같은 리뷰웹 작업오더 id) → `{ ok, id, deleted, kept }` · 쓰기 0.
   열쇠 = **`X-Intake-Key` 헤더만** + 시간 일정 비교 `_intakeKeyMatches`(`/shared`·`/payback-ledger` 와 같은 모양) — 주소(`?intakeKey=`)·본문 열쇠는 401.
   없는 오더 404 · 열쇠 미설정 503. 삭제 경로의 열쇠 방식(헤더·본문·주소 · `!==`)은 **바꾸지 않았다**(옛 인트라넷 배포 스큐 — 별도 보안 정리 과제).
4. **실패 = `{ known:false, reason }`**(`check_failed` · `timeout` · `not_found`) — 조회 하나만 실패해도 통째로 `known:false`. 부분 결과·빈 목록으로 내보내지 않는다(사용자 확정 ⑦ 「확인하지 못했습니다」).
5. **자동 보관·삭제 없음**(사용자 확정 ⑧ — 알리기만) · 화면 변화 0(직원 화면 문구는 인트라넷 IN-B · 공고 배지는 RW-C).

## 응답 모양 (IN-B 가 쓰는 인터페이스)
```json
{ "ok": true, "id": "wo_c2f91b87370d",
  "kept": { "known": true, "phase": "after",
    "campaigns": [ { "id": "camp_e4a143db7c60", "title": "11/19 오전7시 세라모사이드 이너뷰티캔디", "state": "open", "applicants": 6, "submitted": 4 } ],
    "worktable": { "outcome": "remains", "will_remove": false, "predicted": true, "name": "11/19 오전7시 세라모사이드 이너뷰티캔디",
                   "reasons": ["filled_rows", "live_campaign", "campaign_used"] } } }
```
- `phase` = `preview`(아직 안 지운 오더) / `after`(지운 오더). 실패 = `"kept": { "known": false, "reason": "check_failed" }`.
- 옛 리뷰웹(이 PR 전)은 미리보기 404 · 응답에 `kept` 없음 → IN-B 는 「확인하지 못했습니다」로 그린다(「없음」 금지).

## 완화 금지
- ★★ **조회 실패·시간 초과를 「남는 공고 없음」(빈 목록·known:true)으로 접지 않는다** — 이번 사고가 바로 「아무 말 없음」이었다. 모르면 `known:false`.
- ★★ **남는 공고를 역방향 짝 함수(`liveCampaignForWorkOrders`)로 찾지 않는다** — 그 함수는 `w.deleted_at IS NULL` 조건이라 **오더를 지운 뒤** 오더 쪽 연결(`linked_campaign_id`)로만 이어진 공고를 못 본다 → 삭제 응답이 「없음」으로 오보한다(가드가 함정을 재현해 둔다).
- ★★ **작업보드 예측은 실제 정리와 같은 함수(`_untouchedReasons`·`_moneyRows`)·같은 스위치만** — 예측용 판정을 따로 쓰지 않는다. 결정 254 판정 SQL 은 이 기능 때문에 옮기거나 좁히지 않는다(범위 단일 출처화는 별도 PR RW-A0).
- ★ 미리보기 주소의 열쇠는 헤더만 · 시간 일정 비교만(주소 열쇠는 접속 기록에 남는다).
- ★ 응답 칸은 허용 목록만(공고 5칸 · 작업보드 5칸) — 신청자·리뷰어·직원 이름을 싣지 않는다.
- ★ 자동 정리는 응답 **뒤**(setImmediate) 그대로 — `kept` 계산 때문에 정리를 앞당기거나 기다리게 하지 않는다.
