# ★★ 리뷰 미작성 알림톡 — 같은 리뷰어·같은 회차를 두 요청이 동시에 보내도 공급자는 한 번만 · 발송 실행부(`sendOne`)가 그 주문의 상태 줄을 잠그고 「미리보기 뒤 바뀐 것」을 다시 본 뒤 원장 줄을 넣는다 · 공급자 호출은 잠금 밖 · 둘째 요청은 「다른 담당자(또는 자동 알림)가 방금 이 회차 알림톡을 보냈습니다」 (2026-11-10 · 스키마 변경 0 · 결정 364 「하지 않은 것」 둘째 줄)

## 무슨 일이었나
- 작업보드 [문자·알림톡 보내기]의 알림톡(결정 196)과 자동 알림(결정 160·194 · 크론 `/review-reminders/run`)은 같은 발송 실행부 `reviewReminder.service` `sendOne` 을 쓴다. 보내기 전 판정(회차·결과 확인 중·재시도 6시간 대기)은 **미리보기**(`_summarizePreview`)가 하고, `sendOne` 은 그 판정을 믿고 원장(`review_reminder_deliveries`)에 'accepted' 줄을 넣은 뒤 공급자(솔라피)를 부른다.
- 미리보기와 원장 줄 넣기 사이에 **잠금이 없었다.** 두 담당자가 같은 줄을 동시에 보내거나(결정 364 의 키가 서로 다름), 구버전 화면(키 없음) 두 창, 또는 크론과 담당자가 동시에 같은 줄을 만나면 둘 다 「보낼 수 있음」을 본다. 그 뒤:
  - ㉮ 앞 줄이 아직 'accepted' → migration 160 의 부분 유일 색인(`uq_review_reminder_delivery_open`)·`UNIQUE(주문, 회차, 시도)` 가 둘째 INSERT 를 23505 로 던짐 → 둘째 요청이 **통째로 서버 오류**(같이 고른 다른 줄도 안 나감), 키 경로면 선점 줄이 '대기'로 남아 그 키는 계속 「처리 중」, 크론이면 그 회 실행이 통째로 멈춤.
  - ㉯ 앞 요청이 공급자에게 바로 거절(failed) → 색인이 안 막음 → 둘째가 또 공급자를 부름(재시도 대기 무시).
  - ㉰ 앞 요청이 그 사이 「도착」 확인(delivered) → 둘째가 **같은 회차를 또 보냄**(돈 두 번 · 실측: 고치기 전 테스트에서 공급자 2번).
- 결정 364 는 「같은 키」 다시 보내기만 막는다(키별 선점). 키가 다르거나 없는 동시 발송은 364 「하지 않은 것」에 남아 있었다.

## 규칙
1. **`sendOne` → `_claimDelivery`** (발송 실행부 한 벌 — 담당자 수동·크론 둘 다 탄다):
   - ① 짧은 트랜잭션: `BEGIN` → `SET LOCAL lock_timeout = '5s'` → 상태 줄 upsert(`ensureState`) → `SELECT … FROM review_reminder_states WHERE order_submission_id=$1 FOR UPDATE`. 직렬화 지점 = **주문(리뷰어 참여)당 한 줄인 상태 줄(PK)** — 스키마 변경 0, 새 색인 0.
   - ② 잠금 안에서 **「미리보기 뒤 바뀐 것」만** 다시 본다(판정 규칙 사본을 만들지 않는다 — 규칙은 미리보기 한 벌):
     - 상태가 'pending' 이 아님 → `review_not_pending_before_send`(종전 사유 재사용)
     - 회차(`reminder_count`)가 미리보기 때와 다름 · 이 회차 원장 줄이 'accepted'/'delivered' · 이 회차의 마지막 시도 시각이 미리보기가 본 것보다 새것 → `sent_by_other_before_send`
   - ③ 아니면 원장 줄 INSERT('accepted' = 이 회차 선점) → `COMMIT`. **공급자 호출은 COMMIT 뒤**(잠금을 외부 호출 동안 잡지 않는다 — 크론·다른 담당자를 공급자 응답 시간만큼 막지 않는다). 364 와 같은 「선점 → 호출」 모양.
   - ④ 잠금 대기 5초 초과(55P03) → `reminder_busy_before_send` · 원장 INSERT 유일 충돌(23505) → `sent_by_other_before_send` — 둘 다 **보내지 않음**(fail-closed · 던지지 않음). 그 밖 DB 오류는 종전처럼 던진다(공급자 0).
   - 잠금 순서: 이 트랜잭션은 상태 줄 → 같은 주문의 새 원장 줄만 건드린다. 결과 확인(`reconcileAccepted`)은 원장 → 상태, 취소·종결은 주문 → 상태 순서지만, 이쪽은 'accepted' 줄이 보이면 INSERT 하지 않으므로 유일 색인 대기가 생기지 않는다(교착 없음 · 그래도 5초 상한).
2. **화면 문구**(`manualMessage.service` `SEND_REASON` — 화면은 종전처럼 `reason` 을 결과 목록에 그린다 · 화면 코드 수정 0):
   - `sent_by_other_before_send` = 「다른 담당자(또는 자동 알림)가 방금 이 회차 알림톡을 보냈습니다 — 두 번 나가지 않게 이번에는 보내지 않았습니다. 창을 다시 열면 결과가 보입니다」
   - `reminder_busy_before_send` = 「같은 리뷰어에게 다른 알림톡을 보내는 중입니다 — 두 번 나가지 않게 이번에는 보내지 않았습니다. 잠시 뒤 창을 다시 열어 확인해 주세요」
3. **결정 364 와의 관계** — 키 경로는 그대로: 진 쪽은 `sent:false` → 기존 `_release` 가 선점을 푼다(이번에 넣은 줄은 지움 · 364 ⑥). 같은 키 다시 보내기 · 결과 모름 다시 안 보냄 · 일부 다시 보내기 수정 0.
4. **순서대로 하는 정당한 다음 회차는 그대로** — 새 요청은 새 미리보기를 하므로 「바뀐 것 없음」 → 보낸다(담당자가 날짜 전 회차를 앞당겨 보내는 규칙 불변).

## 소비처 전수
- `sendOne` 호출 2곳(`run` · `sendManual`) · `ensureState` 1곳(이제 트랜잭션 안) · `reminder.sendManual` 호출 2곳(`manualMessage` 키 경로·키 없는 경로) · 사유 코드 소비 1곳(`SEND_REASON` → `workdesk.html` 결과 목록 `r.reason`).
- 기존 가드 스텁(`manualMessageSend.test.js` 정규식 db)은 시도 번호 문장(`COALESCE(MAX(attempt_no)`) 모양을 유지해 수정 없이 통과(검사 의미 불변).

## 배포 순서
- 구버전 화면 + 새 서버: 키가 없어도 서버 `sendOne` 에서 막힌다(이 변경의 목적).
- 새 화면 + 구버전 서버: 종전 그대로(화면 변경 없음).
- 스키마 변경 0 → 마이그레이션 실패·순서 문제 없음. 되돌리기 = 코드만 되돌리면 종전(잠금 없음).

## 완화 금지
- **원장 줄 INSERT 를 잠금 밖으로 빼거나, 잠금 안 재확인을 지우지 않는다** — 두 요청이 둘 다 「보낼 수 있음」을 보고 둘 다 공급자를 부른다(같은 회차 두 번 · 돈 두 번).
- **공급자 호출을 잠금(트랜잭션) 안으로 넣지 않는다** — 공급자 응답(최대 수십 초) 동안 그 리뷰어의 크론·다른 담당자 발송·취소·종결이 멈춘다.
- **잠금 대기 초과·유일 충돌을 「보냄」 이나 서버 오류로 접지 않는다** — 보내지 않음 + 한국어 사유(같이 고른 다른 줄은 계속 나간다).
- 가드: `server/tests/reviewReminderConcurrentSend.test.js`(PGlite 실제 SQL · 실제 서비스 · 공급자 흉내로 호출 수 · 정적 순서 가드 · `REMINDER_LOCK_NATIVE_PG_TEST=1` 이면 실제 PostgreSQL 에서 둘째가 잠금을 실제로 기다리는지 `pg_blocking_pids` 로 확인).

## 하지 않은 것 · 남은 판단
- **문자(SMS)** — 키가 다른 두 요청은 둘 다 보낸다. 그러나 문자에는 「이 사람에게 이미 보냈으면 막는」 규칙이 원래 없다(같은 사람에게 순서대로 두 번 보내도 둘 다 나가는 것이 현재 규칙) → 확인과 기록 사이의 경합이 아니라 **정책의 부재**라 이 장치로 고칠 대상이 아니다. 막으려면 사업 판단: ㉮ 그대로(권장 — 문자는 담당자가 매번 글을 쓰는 연락 수단) ㉯ 같은 사람·같은 글을 N분 안에 다시 보내면 막기(키와 무관 · 서버 판정 추가) ㉰ 확인 화면에 「방금 다른 담당자가 이 사람에게 문자를 보냈습니다」 경고만.
  - **(2026-11-10 사장님 결정 = ㉯ → 결정 [366](366-작업보드-문자-같은번호-같은글-10분-다시보내기-막기-번호잠금-2026-11-10.md) 에서 고침)** — 같은 번호·같은 글 10분(설정) 안 다시 보내기를 키와 무관하게 막는다 · 번호 advisory 잠금으로 동시 두 요청도 공급자 1번.
- 잠금 대기 5초 상한은 정상 경로(ms)와 무관한 안전판이다. 운영에서 「보내는 중」 안내가 자주 보이면 원인(긴 트랜잭션)을 먼저 찾는다.
