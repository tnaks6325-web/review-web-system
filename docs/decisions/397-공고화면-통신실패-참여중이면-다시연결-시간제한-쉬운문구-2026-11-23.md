# ★★ 공고 화면 통신 실패 — 참여 중이면 끊겨도 참여 전 화면으로 보내지 않는다(「다시 연결하는 중 · 참여는 유지돼요」 + 다시 시도) · 모든 서버 호출에 시간 제한(_campFetch 15초) · 첫 로딩 실패에 [다시 불러오기] · 영어 오류 문구 대신 쉬운 한국어 · [참여하기] 응답만 끊겨도 서버 자리로 이어서 (2026-11-23 · 스키마 변경 0 · 서버 변경 0)

## 무슨 일이었나 (공고→참여→구매양식 코드 점검 2026-11-21 · H1·M2·M3·M4·L2)
- **H1** 참여한 뒤 쇼핑 앱에서 돌아와 공고 화면이 다시 열릴 때 작업 내용 조회가 한 번 끊기면(예외) `enterJoined` 의 `catch` 가 곧장 `renderPre()` — 자리는 살아 있고 20분 시계는 흐르는데 화면은 **[참여하기]** 로 돌아가고 영어 「불러오기 오류: Failed to fetch」(아이폰 「Load failed」)만 떴다. 서버가 돌아와도 구매양식으로 돌아오지 않았다. 바로 위의 「토큰 보존 + 자동 재시도」는 **응답이 온 5xx** 에만 탔다. 블로그 승인 대기의 30초 확인도 같은 `catch` 로 끊겼고, 첫 로딩이 429 면 1분 뒤 재시도가 공고만 다시 불러 자리 복원을 하지 않았다.
- **M2** 첫 로딩 실패 = 😥 + 영어(`Failed to fetch` · `Unexpected token '<'…`)만, 다시 시도 버튼·자동 재시도 없음(문구도 이스케이프 없이 innerHTML).
- **M3** [참여하기]·개수·옵션 바꾸기·취소·본인 확인·Q&A·일반 모집 목록이 `'오류: ' + e.message`(영어). 사유 없는 502 는 「지금은 참여할 수 없어요」(거절처럼 읽힘).
- **M4** 화면의 `fetch` 18곳 모두 시간 제한 0 — 느린 망에서 「확인 중…」이 몇 분씩 멈춤.
- **L2** 한 명의 [참여하기]의 응답만 끊기면(자리는 잡힘) 오류만 — 여러 명의(`_applyMany`)에만 있는 복구(`recoverActiveHolds`)가 없었다.

## 규칙
1. **호출 도우미 하나 `_campFetch(url, opts, {timeoutMs})`** (campaign.html 안, 마커 `결정 397 — 공고 화면 서버 호출 도우미` ~ `결정 397 도우미 끝`). 화면의 서버 호출 18곳이 모두 이것을 지난다(맨 `fetch(` 는 도우미 안 한 곳).
   - 요청 주소·본문·머리는 부르는 쪽이 준 그대로 — `signal` 만 더한다. 기본 15초(본문 읽기까지 덮는다) · 자리 복원 조회 10초 · Q&A 제출 30초.
   - 응답이 오면 `{ ok, status, headers, j, bad }`(j = 읽은 JSON, 못 읽으면 `{}` + `bad:true`) — 성공 응답의 뜻은 종전과 같다(`r.json().catch(()=>({}))` 와 같은 j).
   - 서버에 닿지 못함·시간 초과는 던진다 — `e.transport`(·`e.timeout`) · 메시지는 결정 359 문구(「인터넷 연결이 불안정해요…」 「응답이 늦어지고 있어요…」).
   - `_campTempFail(r)` = 못 읽은 응답 또는 **사유 없는** 5xx → 「서버에 일시적인 문제가 있어요…」. 사유(reason)가 있으면 서버의 진짜 판정이라 종전 문구 그대로.
   - 화면 문구는 `_campErrText` → api.js `apiFriendlyErrorMessage`(단일 출처) · 옛 api.js 면 같은 한국어로 접는다.
2. **참여 중(이 기기에 자리 토큰)인데 작업 내용을 못 받으면 참여 전 화면으로 보내지 않는다** — 끊김·시간 초과(예외)와 5xx 가 같은 함수 `_detailTempFail` 로 간다.
   - 구매양식을 보던 중이면 그 화면 그대로 + 종전 안내·6번 재시도. 예약된 다시 시도는 **제출 중이면 틀을 다시 열지 않고 2초 뒤 다시 본다**(`_retryEnterJoined` — 결정 351 「제출 중은 끊지 않음」). 승인 대기 화면이면 그대로 + 30초 확인 다시.
   - 그 밖(처음 열기·완료 화면에서 다른 명의로 등)이면 새 화면 `#vReconnect` 「다시 연결하는 중이에요 · 참여는 그대로 유지돼요 · (남은 시간 약 N분)」 + [지금 다시 연결하기]. 일시 장애는 3·3·8·8·8·8초 뒤 15초마다 **계속** 다시 묻고, 화면 복귀(visibilitychange)·`online` 때 바로 묻는다. 사유 없는 4xx 는 6번까지만 자동.
   - **토큰은 서버가 `expired`·`no_hold` 라고 답할 때만 지운다(결정 356)** — 이번 변경은 지우는 곳을 하나도 더하지 않았다.
3. **처음 열 때 자리가 있으면** 확인이 끝날 때까지 「참여 중인 구매양식을 여는 중…」(참여 전 화면을 비추지 않는다). 참여 전 화면의 15초 갱신(`_preRefreshTick`)은 이 기기에 자리가 있고 열린 창이 없으면 `enterJoined` 로 다시 들어간다. 첫 로딩 429 의 1분 뒤 재시도는 시작 경로(`_campInit` — 공고 → 자리 복원 → 구매양식) 전체를 다시 탄다.
4. **첫 로딩 실패** = 「공고를 불러오지 못했어요」 + 쉬운 문구(이스케이프) + [다시 불러오기] + 끊김·서버 일시 오류면 5→10→20→30초 자동으로 다시(429 는 서버가 정한 시간 뒤 한 번 — 종전 `_scheduleCampaign429Retry`). 자리가 있으면 「이미 참여한 자리는 그대로 유지돼요」. 시작은 한 번만 끝난다(`_campBooted`).
5. **[참여하기] 응답만 못 받음(L2)** — 끊김·시간 초과·사유 없는 5xx 면 `_applyLostRecover`: `recoverActiveHolds(그 명의)` 한 번 → **그 명의** 자리가 서버에 있으면 「참여가 확인됐어요 — 구매양식을 이어서 열게요」 + `enterJoined`. 없으면 쉬운 말 + [참여하기] 되살림. **다시 보내지 않는다**(자리를 하나 더 잡지 않는다 — 결정 353). 여러 명의도 사유 없는 5xx 를 「연결 오류」로 세어 같은 복구를 타고, 하나도 못 잡았는데 복구로 고른 명의 자리가 확인되면 이어서 연다.

## 완화 금지
- 🚫 `enterJoined` 의 실패(예외·5xx)를 `renderPre()`·`clearHold()` 로 접지 않는다 — 자리가 살아 있는데 [참여하기] 화면이 되면 리뷰어가 「참여가 날아갔다」고 떠나고, 산 물건의 구매양식을 못 낸 채 만료된다. 토큰은 서버의 `expired`·`no_hold` 로만 지운다(결정 356).
- 🚫 공고 화면에 시간 제한 없는 맨 `fetch(` 를 다시 들이지 않는다 — 서버 호출은 `_campFetch` 로만(가드가 센다).
- 🚫 사유 없는 5xx·못 읽은 응답을 「지금은 참여할 수 없어요」 같은 거절 문구로, 끊김을 영어 `e.message` 로 보이지 않는다.
- 🚫 [참여하기] 응답을 못 받았을 때 `/apply` 를 자동으로 다시 보내지 않는다 — 서버 자리를 받아 오기만 한다(고른 수까지만 · 결정 353).

## 하지 않은 것 / 확인 못 한 것
- 옵션·개수 바꾸기·취소가 시간 초과로 끝났을 때 서버에서는 반영됐을 수 있다 — 화면은 쉬운 안내만 하고 다음 확인(10초 확인)이 맞춘다(옵션 바꾸기 결과를 틀에 다시 싣는 것은 종전처럼 다음 `enterJoined` 때).
- 참여 전 화면 15초 갱신이 [참여하기] 요청이 걸려 있는 동안 버튼을 되살리는 종전 동작(연타 가능)은 그대로다(시간 제한으로 최장 15초).
- 실제 휴대폰·운영 서버(Railway 502 페이지의 CORS 머리 유무)는 확인하지 않았다 — 가짜 서버(rw-fake) + 크롬·웹킷 390×844 로만 실측.
