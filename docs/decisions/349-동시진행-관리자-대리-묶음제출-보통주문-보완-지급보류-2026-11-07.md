# 네이버·쿠팡 동시진행 — 관리자 대리 묶음 제출 입구 · 수동제출로 들어간 보통 주문 보완 · 묶음 아닌 줄 지급 보류 (2026-11-07 · 스키마 변경 0)

## 무슨 일이 있었나

- 동시진행(한 사람이 옵션 없는 같은 상품을 네이버·쿠팡에서 각각 구매 — 부모 주문 1·구매처 기록 2·작업표 줄 1·리뷰비 1, `base.pay` = 두 금액 합)이 운영에 켜져 있다(결정 341).
- 결정 344 가 외부모집 수동제출을 동시진행 작업표에서 막기 **전에** 수동제출로 들어간 보통 주문 3건이 운영에 있다(`source='admin_external'` · `purchase_bundle_version` NULL · 금액 = 한쪽 금액 · 구매캡처 1장).
- 지급 대상 판정은 **묶음 주문 줄만** 동시진행 지급 판정(`dualChannelPayout.evaluateOrderPayoutEligibility`)으로 보냈다(`bundleTargetsForRows` = `purchase_bundle_version='1'`). 묶음이 아닌 줄은 일반 지급 경로로 흘러 **한쪽 금액 + 리뷰비가 그대로 나갈 수 있었다.**
- 관리자가 동시진행 구매를 대신 넣는 입구가 없었다(리뷰어 구매양식 경로는 리뷰어 로그인·신청·홀드·신원 승인·AI 판독 토큰에 묶여 있다).

## ④ 안전망 — 동시진행 작업표의 묶음 아닌 줄은 지급 보류 (먼저 따로 커밋)

- `dualChannelPayout.dualBundleIncompleteRows(db, rows)` — 작업표마다 공용 발견기 `discoverDualScope([{sheetId,tabName,tabGid}])` 로 동시진행 작업표인지 보고, 그렇다면 `bundleTargetsForRows` 로 묶음 줄을 찾아 **묶음이 아닌 줄 전부**(주문 없는 손 기록 줄 포함)를 `dual_bundle_incomplete` 로 돌려준다. 판정 실패는 `dual_bundle_check_failed`(막음 · fail-closed).
- 배선 두 곳: ⓐ 입금 대상 목록(`payment.listPaymentTargets`) — 해당 줄 `payable=false` + 사유. 회차 만들기(`createBatch`)는 이 목록을 다시 계산해 `payable` 만 담으므로 같이 막힌다. ⓑ 이미 만든 회차의 첫 다운로드(`checkBatchReceiptEligibility`) — 보통 항목이 동시진행 작업표 줄이면 막고, 라우트는 `409 dual_bundle_incomplete`(「동시진행으로 보완한 뒤 새 대량이체」 안내)로 돌려준다.
- 동시진행 작업표가 없는 일반 작업은 결과가 종전과 같다(판정 쿼리가 빈 결과 → 통과).

## ①② 직원 대리 묶음 제출 — `POST /api/trackb/manual-order/dual/submit`

- 서비스 `dualStaffSubmission.submitStaffBundle`(새 파일). 입력 = 작업표 좌표(+ 공고 id) · 슬래시 양식 값(`fields`) · 구매처마다 `{orderNum, paidAmount, imageBase64, mimeType, (recipient·phone·address·userId — 없으면 양식 값)}` · 직원(토큰에서).
- 순서: 준비 상태(`assertDualChannelReady('purchase')` → 409 `dual_channel_not_ready`) → 동시진행 판정(`discoverDualScope` · 동시진행 아니면 409 `dual_channel_required` · 판정 실패 막음) → 구매처 정리(`cleanPurchase`) → 명의 판정(`identityVerdict` · 아이디는 달라도 됨 · 다르면 거절) → 캡처 두 장 필수·서로 다른 사진 → 중복(`externalDuplicateGuard` — 수동제출에서 뽑아낸 같은 함수 + 구매처 기록의 같은 주문번호)·재참여(`repurchaseGuard`)·일 정원(`dailyRemainingForCampaign`) → 조건(`conditionForCampaign` · 현금영수증 필요) · 금액 검사(`decideForExpected`) → 리뷰어 등록·연결(`ensureExternalReviewer` 호출만) → Drive 저장(트랜잭션 밖 · 되읽어 SHA 대조) → `withDualLifecycleInTx` 안에서 증빙 SHA 잠금(`dualEvidenceShaLock` — 리뷰 사진과 공용) · 참여 신청 확정(`confirmExternalApplication`) · 부모 주문(`source='admin_external'`) · 구매캡처 2 · `finishBundleInTx`(구매처 기록 2·합계 검사·명의 근거 해시) → 커밋 뒤 작업표 기록(큐 또는 `writeOrderToWorktable` 동시진행 분기 — 리뷰어 묶음과 같은 방식).
- **명의는 언제나 직원 확인 필요** — `purchase_identity_result='uncertain'` · `purchase_identity_review.status='pending'`(+ `staffProxy`). 지급 판정이 `identity_staff_pending` 으로 막고, 기존 직원 명의 확인 창구(`/api/trackb/dual-purchase/identity-review`)에서 확정한다. 리뷰·영수증은 리뷰어 본인이 낸다.
- 같은 내용을 다시 보내면 24시간 중복 판정에 걸리고, 확인 후 강제여도 같은 묶음 해시면 새로 만들지 않는다(`idempotent`).
