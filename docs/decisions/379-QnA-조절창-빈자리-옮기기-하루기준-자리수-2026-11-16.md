# ★★ Q&A 공고 — 모집인원 조절 창에서 빈 자리를 날짜 사이로 직접 옮기기 + 하루 기준을 자리 수 하나로(0명 휴무 판정 제거) (사용자 확정 2026-11-17 「1+2까지만」 · 377 일부 대체 · 스키마 변경 0)

## 무슨 일이었나
- 운영 사례 「11/3더로우 Q/A 50건」(2026-11-17 박은비 보고): 못 채운 1자리가 11/18 에 있고 11/17 은 날짜별 계획 0명(휴무)으로 저장돼 있었다.
  조절 창에서 [기본으로]를 눌러도 「오늘부터」가 뜨지 않았고(일정 끝 결정이 이미 기록돼 팝업 대상이 아님), 자리 숫자도 바꿀 수 없었다.
- 근본 원인 둘:
  - (가) Q&A 하루 인원 = 자리표(`qna_slots.slot_date`)의 그날 자리 수인데, 조절 창에서는 자리를 옮길 길이 없고 일정 끝 팝업 [추가 모집] 한 번뿐이었다.
  - (나) 날짜별 계획의 0명 휴무(`campaign_daily_plans`)와 자리표가 **같은 날짜를 따로 정해 서로 막았다** — 자리가 있어도 0명 계획이면 그날 닫혔다(`rest_day`).

## 사용자 확정 (2026-11-17 「1+2까지만」)
1. 조절 창 Q&A 화면 날짜 줄마다 [−]/[＋] — **빈 자리**를 날짜 사이로 옮긴다(총 자리 수 불변).
2. Q&A 공고는 날짜 기준을 **자리 수 하나**로 — 0명 휴무를 Q&A 판정에서 뺀다.

## 바꾼 것
### 1. 빈 자리 옮기기 (`qnaSlots.moveQnaSlots` · `POST /api/trackb/campaigns/:id/qna-move`)
- **옮기는 것 = 빈 자리** = 못 채운 자리 판정(`_unfilledSql` — open · 제출된 신청 없음 · 줄에 주문 없음) **+ 신청 중(유효 홀드) 아님**(`_movableSql` · 유예 = 신청 홀드 `HOLD_GRACE_SEC` 단일 출처). 신청 중인 자리를 옮기면 그 사람이 받은 날짜·제출 기한이 어긋난다.
- 화면이 보내는 것 = **날짜별 증감** `days:[{date, n(±), movable(빼는 날 — 화면이 본 그날 옮길 빈 자리 수)}]` + 총 자리 수(`total`) (리뷰 반영 — 아래 「리뷰 반영」 ②. 처음 판은 「from → to, n개」 짝 목록이었다). 잠근 뒤 값과 다르면 **409 `qna_move_stale`** → 화면이 최신 자리로 다시 받아 그린다(조절 창의 기존 409 처리와 같은 방식 — 옛 숫자로 계속 409 나는 막다른 길 금지).
- 받는 날 규칙(잠근 뒤 시각 하나로 — 결정 377 리뷰 반영과 같은 규율):
  - 지난 날 = 거절(`qna_move_past`) · 오늘 = 신청 마감 전에만(`qnaTodayStartCheck` — 추가 모집 「오늘부터」와 같은 판정 · `qna_move_today`)
  - 오더 휴무일(`wo.holidays`)·주말 제외 오더의 주말 = 거절(`qna_move_closed_day`) — 판정은 자리표를 만들 때와 같은 `businessDays`
  - 공고 시작일(`start_date`) 전 날 = 거절(`qna_move_before_start` — 리뷰 반영 ③)
  - **상품별 하루 건수** = 자리표를 만든 원천(오더 상품별 하루 건수 · `_unitDailyCap` — 추가 모집과 같은 함수 · 리뷰 반영 ①)를 넘지 않음 · 공개 자리는 그 상품의 그날 공개가 이미 있으면 놓지 않음(공개글 하루 1건 — `qnaCalendar`). 다 못 넣으면 `qna_move_no_room`.
- 하나라도 실패 = **전부 되돌림**(fail-closed). 기록 = `campaign_plan_events` `qna_move`(actor · `{after,total,moved,moves:[{from,to,n,units}]}`) · 조절 창 이력에 「빈 자리 옮김」.
- **같은 코드(사본 0)**: 잠금(`_lockQnaCampaign` — 작업표 advisory → 공고 FOR UPDATE · 연결 재확인) · 자리·줄 날짜 갱신(`_moveSlotRows` — 그 줄의 진행일자만 · 주문 붙은 줄 제외 · 줄이 안 움직이면 throw) · 커밋 뒤 장부 다시 만들기(`_rebuildAfterMove`)를 `applyQnaEnd`(추가 모집)와 함께 쓴다. 차이는 회차(`round`)만 — 추가 모집 +1 · 옮기기 그대로.
- 일정 끝 결정(`qna_extra`)이 이미 있어도 옮길 수 있다.
- 권한 = 조절 창 저장과 같은 내부 직원(`internalMiddleware`) — 결정 378(팝업 받는 사람 규칙)과는 별개: 옮기기는 하루 인원 조절과 같은 급의 일이라 조절 창 권한을 따른다(사용자 명세 기본값).

#### 상품을 어떻게 고르나 — 날짜 단위(가장 작은 안 · 근거)
- 운영 자리표(읽기 전용 조회 2026-11-18): 이 공고는 상품 7개가 날마다 1~2자리씩 함께 깔린다(같은 날에 여러 상품의 자리). 신청은 리뷰어가 고른 상품의 그날 자리로 묶인다.
- 화면은 날짜별 자리 수만 보이고(조절 창의 단위 = 하루 인원), 서버가 고른 날짜 전체를 한꺼번에 배정한다(리뷰 반영 ② — `_assignQnaMoves`). 해가 여러 개면 **비공개 먼저 · 상품 순서 · 상품 안 순번**, 받는 날 하루 건수가 찬 상품은 그날로 보내지 않는다. 무엇이 옮겨졌는지는 저장 뒤 안내(「11/18 → 11/17 벨벳틴 부티크 상품 1개」)와 이력 기록(`units`)으로 남긴다.
- 상품을 사람이 고르는 화면은 만들지 않았다 — 막힌 사례(남은 1자리)는 날짜만으로 풀리고, 상품 고르기는 화면·검사 범위가 크게 늘어난다. 필요해지면 후속 결정으로 연다.

### 2. 하루 기준 = 그날 자리 수 하나 (`campaignState.qnaIgnoresPlans`)
- 판정 단일 출처 = 정원 재료에 오늘 자리 수(`qnaToday`)가 실린 공고 = Q&A(`computeCampaignState` 의 `isQna` 와 같은 재료).
  - `computeCampaignState` 맨 앞: Q&A 면 계획을 비운 재료로 판정 → `rest_day`(0명)·「조절됨」·다음 오픈일의 0명 건너뛰기가 Q&A 에서 사라진다. 그날 자리 0 = 그날 안 열림(종전 `qnaToday` 정원 그대로).
  - `fetchCampaignCounts`: Q&A 공고는 `plans = null` — 이 깔때기를 읽는 다른 곳(주말 게시 판정·카드 등)도 같은 값을 본다.
  - 조회 실패로 `qnaToday` 가 없으면 종전(일반 공고와 같은 판정) — 실제 신청은 자리 묶기(`pickSlotInTx`)가 fail-closed 로 다시 막는다.
- 추가 모집(`applyQnaEnd`·`qnaExtraPlan`·`qnaExtraStartOptions`)·오늘부터 판정(`qnaTodayStartCheck`)의 0명 휴무 거절·건너뛰기를 없앴다(`qnaRestDays` 삭제). 응답의 `skipped` 칸은 빈 목록으로 남긴다(옛 화면이 그대로 읽는다). 오더 휴무일·주말 제외는 그대로 존중.
- 저장값 정리: Q&A 공고의 `campaign_daily_plans` 행은 지우지 않는다(판정에서 무시 — 데이터 변경 0 · 마이그레이션 0).
- 조절 창 저장(`savePlans`): Q&A 공고에 날짜별 인원(set)을 보내면 **409 `qna_plan_set`**(「자리표가 하루 인원을 정합니다 — 새로고침 뒤 [−]/[＋]로 빈 자리를 옮겨 주세요」) — 저장했는데 아무 일도 안 일어나는 막다른 길 금지. 저장값 해제(remove)는 받는다(옛 0명 계획 정리 · 옛 화면의 [기본으로]).
- 화면(`campaign-daily-plan.js`): 서버가 `qna.move` 칸을 줄 때 Q&A 화면은 「휴무」 글자·[기본으로]·휴무 경고 없이 날짜 줄 `[−] 자리 수 [＋]` + 안내만. 뺀 수 ≠ 더한 수면 [확정 저장] 잠금 + 「같아야 저장」 안내. [확정 저장] = `qna-move` 하나(날짜별 계획을 보내지 않는다).
  - 줄 목록 = 오늘 ~ (마지막 날·오늘 중 늦은 날)+14일 전부(자리 0 인 날도 받는 날) + 옮길 빈 자리가 남은 지난 날.
  - [＋] 잠금 = 지난 날 · 쉬는 날(`move.closed`) · 오늘 신청 마감 뒤(`move.today`) / [−] 잠금 = 그날 옮길 빈 자리(`movable`) 없음. 서버가 저장 때 다시 잰다.

## 배포 스큐
- 구버전 화면 + 새 서버: 응답에 칸이 늘 뿐(`movable`·`move`) — 옛 화면은 결정 377 화면(휴무 표시·[기본으로])을 그린다. 그 [기본으로] → remove 는 받는다. 휴무 표시는 실제로는 무시되는 계획이라 화면 말이 틀릴 수 있다 — 화면 파일 버전(`?v=20261118-qnamove`)을 올려 새로고침하면 새 화면.
- 새 화면 + 구버전 서버: `qna.move` 칸이 없으면 [−]/[＋]를 그리지 않고 결정 377 화면 그대로(그 서버는 아직 0명 휴무를 쓰므로 휴무 표시·[기본으로]가 맞는 말이다).

## ★ 완화 금지
- Q&A 공고의 하루 판정에 날짜별 계획(0명 휴무)을 다시 쓰지 않는다 — 자리표와 계획이 같은 날짜를 따로 정해 서로 막는 사고(이번 신고)가 재현된다. 판정은 `qnaIgnoresPlans` 하나.
- 옮기기에서 신청 중(유효 홀드)·제출된·주문 붙은 자리를 옮기지 않는다 · 화면이 본 빈 자리 수·총 자리 수와 다르면 반영하지 않는다(409).
- 받는 날 판정(지난 날·쉬는 날·오늘 마감·상품별 하루 건수)을 화면 값으로 대신하거나 잠금 밖·잠금 전 시각으로 하지 않는다 · 하나라도 실패하면 전부 되돌린다.
- 잠금·줄 날짜 갱신·장부 다시 만들기를 추가 모집과 옮기기에 따로 두지 않는다(`_lockQnaCampaign`·`_moveSlotRows`·`_rebuildAfterMove` 한 벌).
- Q&A 공고에 날짜별 인원(set) 저장을 조용히 받지 않는다(무시되는 저장 = 막다른 길) — 막고 할 일을 말한다.

## 결정 377 과의 관계
- 377 의 「0명 휴무일 건너뛰기」·「오늘 0명 휴무 = 오늘부터 거절」·「Q&A 조절 창에서 [기본으로]를 지우지 않음」은 **이 결정으로 대체**된다(Q&A 는 0명 휴무를 판정에 쓰지 않으므로 건너뛸 날·풀 휴무가 없다). 옛 서버 응답(`qna.move` 없음)일 때의 화면에서만 [기본으로]가 남는다.
- 377 의 나머지(오늘부터 판정 = 잠근 뒤 · fail-closed · 모르는 시작일 거절 · Q&A 조절 창에 일반 [＋]/[−]·이월·차수를 다시 그리지 않음 · `qna` 칸은 서버 판정으로만)는 그대로 유효하다. 이 결정의 [−]/[＋]는 날짜별 인원이 아니라 **자리를 옮기는 버튼**(`cdp-qst`)이다.

### ① 상품별 하루 건수를 바뀌는 자리 날짜에서 다시 재던 것
- 원인: `_unitPerDay` 가 **지금** 자리표의 날짜 분포에서 상품별 하루 최대치를 다시 쟀다. 하루 2칸인 날에서 1개를 다른 날로 옮기면 최대치가 1로 내려가 **되돌리기가 `qna_move_no_room` 으로 막히고**, 같은 계산을 쓰던 추가 모집(`qnaExtraPlan`)의 하루 용량도 함께 줄었다.
- 고친 것: `_unitDailyCap(wo)` — 자리표를 처음 만든 **바뀌지 않는 원천**을 자리표 생성기와 같은 해석으로 읽는다(`qnaCalendar.qnaUnitsFromWorkOrder` 의 상품별 `daily` · 선택지에 없으면 오더 `daily_count` · 단위 키 = `selectionKey` = `qna_slots.unit_key`). 접수 뒤 이 칸은 잠긴다(`_qnaCalendarLocked` · 상품 일건수 바꾸기도 Q&A 는 `option_daily_qna_locked`). 옮기기·추가 모집이 **같은 함수**(단일 출처).
- 원천에 없는 상품(하루 건수 모름) = **거절**(fail-closed): 옮기기 `qna_move_capacity_unknown`(409) · 추가 모집 `qna_capacity_unknown`(종전엔 하루 1건으로 조용히 접었다).
- 추가 모집 동작 차이: 옮기기 전 자리표에서는 분포 최대치 = min(하루 건수, 총 건수)이고 못 채운 수 ≤ 총 건수라 **깔리는 날짜가 같다**. 운영 실측(읽기 전용 2026-11-18 · Q&A 공고 1건 · 상품 7개): 원천 하루 건수(1·1·1·1·1·1·2)가 분포 최대치와 모두 같다. 달라지는 것은 ㉮ 옮긴 뒤(이제 원래 용량) ㉯ 원천을 모를 때(이제 거절) 둘뿐.

### ② 화면이 출발·도착을 날짜 순서로 짝지어 보내던 것
- 원인: 화면(`qmvMoves`)이 뺀 날·더한 날을 날짜 순으로 짝지어 「from → to」로 보냈고, 서버는 그 짝 안에서만 골랐다. 상품 X·Y 가 하루 1건씩일 때 X(11/17)→11/19, Y(11/18)→11/20 짝은 둘 다 받는 날에 이미 하루 1건이라 거절되지만, X→11/20 · Y→11/19 로 보내면 같은 선택이 된다.
- 고친 것: 화면은 **날짜별 증감만** 보낸다(`days:[{date,n,movable?}]` — `qmvDays`). 서버가 잠금 안에서 고른 날짜 전체를 한꺼번에 배정한다(`_assignQnaMoves` — 최소 비용 최대 유량: 빼는 날 정확히 n개 · 받는 날 정확히 n개 · 받는 날 상품별 하루 건수 − 이미 있는 수 · 공개 자리는 그 상품의 그날 공개가 없을 때 1개). **해가 있으면 반드시 찾고**, 같은 입력이면 언제나 같은 결과(결정적). 해가 여러 개면 비공개 → 상품 순서 → 상품 안 순번(비용 = 그날 후보 순서의 묶음 순위). 탐색 상한(간선 완화 200만 회)을 넘으면 `qna_move_too_big`(400 · 나눠서 옮기라는 안내) · 해가 없으면 `qna_move_no_room`(들어갈 수 있는 수 안내) — 둘 다 전부 되돌림.
- 요청 모양 검사(`_normalizeDays`): 같은 날 두 번 · 0 증감 · 뺀 합 ≠ 더한 합 · 빼는 날 `movable` 없음 · 빈 자리보다 많이 빼기 = `qna_move_bad`. 옛 짝 목록(`moves`)은 받지 않는다(`qna_move_empty`) — 아직 운영에 나간 적 없는 기능이라 옛 화면이 없다. 화면 파일 버전 `?v=20261118-qnamove2`.
- 기록(`qna_move`)·응답의 `moves:[{from,to,n,units}]` 모양은 그대로(배정 결과로 만든다) + `days`(보낸 증감)를 함께 남긴다.

### ③ 공고 시작일보다 이른 날로 옮길 수 있던 것
- 원인: 받는 날 검사에 공고 시작일이 없었고, `qnaTodayStartCheck` 가 `preopen` 을 통째로 허용해 **미래 개시 공고의 「오늘」**(날짜 preopen)도 통과했다 — 옮긴 자리는 시작일까지 아무도 잡을 수 없다.
- 고친 것: 모든 받는 날 ≥ 공고 시작일(`dateOnlyStr(start_date)` — 정원 판정 `computeCampaignState` 와 같은 출처) — 아니면 `qna_move_before_start`(422). `qnaTodayStartCheck` 는 `state = preopen` 이면서 `startDate > 오늘`(날짜 preopen)이면 `not_started` 로 거절하고, **오늘 늦은 시각에 여는 공고(시간 preopen)는 종전대로 허용**한다. 같은 판정이 추가 모집 「오늘부터」에도 적용된다(미래 개시 공고 = `today_not_started` 거절 — 확인 결과 거절이 맞다: 오늘 다시 깐 자리를 오늘 아무도 못 잡는다).
- 화면: 옮기기 재료에 `move.start` 를 싣고, 시작일 전 날은 [＋]를 잠그고 이유를 보인다(「공고 시작일(m/d) 전 — 자리를 둘 수 없습니다」 · 칸이 없으면 종전). 승인된 미리보기 사례(시작일 11/03)에서는 보이는 것이 같다.
- 남은 사각지대: 추가 모집 「내일부터」는 시작일을 보지 않는다(정규 일정이 끝난 공고만 대상이라 시작일이 내일 뒤인 경우는 시작일을 뒤로 고친 경우뿐). 시트 일정 스위치(`CAMPAIGN_SHEET_SCHEDULE=1`)를 켜면 정원 판정의 시작일이 시트 최소 날짜가 되는데 옮기기는 `start_date` 를 본다(기본 꺼짐).
