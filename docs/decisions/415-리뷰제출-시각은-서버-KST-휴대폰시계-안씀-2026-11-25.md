# ★★ 리뷰 제출 시각(작업표 「리뷰제출」 칸)은 서버가 KST 로 정한다 — 리뷰어 휴대폰 시계 값은 칸에 쓰지 않는다 · 리뷰어 홈 수정요청 사진 끊김 안내 한 번 (2026-11-25 · 스키마 변경 0)

## 발단 (리뷰 제출 점검 2026-11-24 · L6)
- 리뷰어 제출 화면(`search-app.js` 단건·여러 건 2곳, `campaign.html` 모집공고 리뷰 2곳)이 **기기 시계**(`new Date()`)로
  `M/D HH:MM` 을 만들어 `value` 로 보내고, `POST /api/submit/review` 가 그 글자를 작업표 리뷰제출 칸에 **그대로** 썼다
  (`submitValue = value || '제출'` → `markStatusCell(kind:'submit', value: submitValue)`).
- 휴대폰 시계·시간대가 틀린 리뷰어(해외 체류·수동 시계)는 다른 날짜·시각이 찍힌다. 리뷰비 일정·독촉 판단을 사람이 이 칸으로 한다.
- 같은 종류의 구매일자 문제는 결정 248 로 「항상 서버 오늘(KST)」이 됐고, 직원 수동 리뷰제출·동시진행 묶음 완료는 결정 375 로
  이미 서버 시각(`sheetlessStatus.SUBMIT_TIME_SQL`)을 쓴다 — 리뷰어 웹 제출만 기기 시계였다.

## 결정
1. ★★ `POST /api/submit/review` 의 리뷰제출 칸 값 = **완료 트랜잭션 안에서 `sheetlessStatus.submitTimeValue(completionClient)`**
   (결정 375 의 식 한 벌 `to_char(NOW() AT TIME ZONE 'Asia/Seoul','FMMM/FMDD HH24:MI')` · 사본 금지 · 새 KST 포맷터 금지).
   `NOW()` = 트랜잭션 시각이라 같은 트랜잭션의 `review_submissions.completed_at`·`campaign_participants.updated_at` 과 같은 순간이다.
2. 화면의 `value` 필드는 **계속 받되 쓰지 않는다**. 화면도 그대로 보낸다(아래 배포 스큐).
3. 시각을 만들지 못하면(빈 값) `'제출'` 기본값으로 접지 않고 `REVIEW_BOARD_WRITE_FAILED` → ROLLBACK → 503 재시도 안내(결정 375 ③ 과 같은 방향).
4. 응답의 `submitted` = 실제로 쓴 값(부분 제출 = 칸을 쓰지 않으니 빈 값). 화면에 이 필드를 읽는 곳은 없다(grep 0).
5. 화면 값이 서버 값과 달라도 로그는 남기지 않는다 — 분 단위 시각은 기기 시계 몇 초 차이로도 자주 달라 잡음만 된다(결정 248 은 날짜라 드물었다).

## 칸 값 모양 — 글자까지 같다
- 화면 식 `${M+1}/${D} ${HH}:${MM}`(월·일 0 채움 없음, 시·분 2자리) = 서버 식 `FMMM/FMDD HH24:MI`. 회귀가드 B 가 같은 순간
  5개(자정 경계·연말·한 자리 월일 포함)를 실제 PostgreSQL 로 계산해 화면 식 4곳과 글자 비교한다.
- 그 칸을 읽는 곳(전부 같은 모양을 이미 받는다 — 바뀌는 것 없음): 제출 판정 `columnResolver` → V2 `statusColumnBinding.isV2ReviewSubmitted`(`parseDateToken` + 시·분 범위) /
  구형 `_isSubmittedValue`(`\d{1,2}/\d{1,2}`) · 작업보드 투영 `trackB`(칸이 비었는지만 봄) · 작업보드 표기 `_workdeskStatusKind`/일련번호 표기(결정 137).
  리뷰 미작성 알림·입금 일정이 이 칸 글자를 날짜로 읽는 곳은 grep 으로 찾지 못했다(못 찾음 ≠ 없음 — 있더라도 모양이 같아 영향 없음).

## 그 칸을 쓰는 곳 전수 (4곳 — `markStatusCell(kind:'submit')` 3 + 직접 SQL 1)
| 경로 | 값 | 이 결정 |
|---|---|---|
| 리뷰어 웹 제출 `submit.routes` `/review` | 화면 기기 시계 → **서버 KST** | 고침 |

## 배포 스큐
- 옛 화면 + 새 서버: 옛 화면이 보내는 값(또는 아주 옛 화면의 값 없음)과 상관없이 서버 KST 시각 — 종전 `'제출'` 폴백도 사라진다.
- 새 화면 + 옛 서버: 화면은 바꾸지 않았으므로 종전 그대로 기기 시각이 쓰인다(지금과 같음 · 빈 칸·'제출' 회귀 없음).

## 함께 고친 것 — 결정 410 잔여
- 리뷰어 홈 「리뷰 이미지 수정 요청」(`index.html` `_reEditSubmit`) 업로드가 끊기면 업로드 도구 토스트 + 화면 토스트로 **같은 실패를 두 번** 말했다.
  결정 410 의 리뷰 제출 두 길처럼 `gasPostUpload(…, 120000, { quiet: true })` — 화면 쪽 `_rhErrMsg`(바탕 `apiFriendlyErrorMessage`) 안내 한 번만 남는다.
  옛 `api.js` 캐시는 셋째 인자를 모르니 종전처럼 두 번(회귀 아님).

## 이미 적힌 값
- 이 변경 전에 기기 시계로 적힌 칸은 고쳐지지 않는다(데이터 쓰기 0 · 정정은 별도 판단).

## 완화 금지
- ★★ 리뷰어 웹 제출의 리뷰제출 칸 값을 화면이 보낸 `value`(기기 시계)로 되돌리지 않는다 · 시각 식을 사본으로 만들지 않는다(`submitTimeValue`/`SUBMIT_TIME_SQL` 한 벌) ·
  시각을 못 만들 때 `'제출'`·화면 값으로 접지 않는다 · 리뷰어 홈 수정요청 업로드의 `{ quiet: true }` 를 빼지 않는다(같은 실패 두 번).
