# ★ 작업표 중복 줄 감시망 (2026-08-19)
- **왜**: 같은 구매가 표에 여러 줄로 늘어난 사고(권정현 11줄)를 **아무도 몰랐다** — 사람이 표를 보다 우연히 발견했다. 기록 경로의 2차 중복 판정이 최종 방어지만, **그것이 또 뚫려도 알 길이 없는 상태**를 없앤다.
- **무엇을 보나**: 같은 **표 주문번호 + 명의(phone8)** 로 살아있는 줄이 2개 이상인 묶음. ★ 판정을 새로 만들지 않는다 — 번호는 `utils/tableOrderNum` 공유 조각(중복 정리·주문 기록과 같은 값), 키도 중복 방어와 같다.
- ★★ **읽기 전용** — 줄을 내리지도 주문을 취소하지도 않는다. 정리는 사람이 [♻ 중복 줄 정리]로. 쓰기는 **스냅샷 한 곳**(`app_settings.worktable_dup_watch`)뿐이고 회귀가드가 그 개수를 센다.
- ★ **무시트 탭만** — 시트 기반 탭은 시트가 진실원본이라 같은 번호 여러 줄이 담당자 의도일 수 있고, 이 사고의 발생 경로(빈 슬롯 소비)도 무시트 전용이다. ★ **모르는 것은 세지 않는다**(번호 6자리 미만·명의 없음·삭제된 줄) — 빈 값끼리 뭉쳐 거짓 경보가 되는 것을 막는다.
- ★★ **늑대소년 방지 = 달라졌을 때만 알린다** — 직전 스냅샷과 지문이 같으면 침묵한다. ★ 지문에 **줄 수를 포함**해야 "줄이 하나 더 늘어난 것"을 다시 알린다(빼면 증식이 조용해진다). ★ **스냅샷을 못 읽으면 알린다**(놓치는 쪽보다 한 번 더).
- ★ 알림은 **묶음마다가 아니라 한 건**으로(도배 방지) · `logAbnormal(severity:'warn')` = **시스템 오류로그**(리뷰어 개인 문제가 아니라 데이터 정합 문제라 `reviewer_event_logs` 아님, 관리자 빨간 알림도 아님).
- **크론** `17 * * * *` + `withJobLock('worktable_dup_watch')` · 킬스위치 `WORKTABLE_DUP_WATCH=0` · **크론은 감시망 실패로 죽지 않는다**. **조회 창구** `POST /api/trackb/worktable/dup-watch`(adminOrMaster) — ★ **`record:false`** 라 사람이 눌러 본 것 때문에 다음 크론 알림이 조용해지지 않는다.
- ⚠ **감시망은 임시 대책이다** — 근본은 `(sheet_id, tab_name, order_submission_id)` 부분 유니크로 DB가 막는 것이고, 그건 남은 어긋난 링크를 먼저 정리해야 가능하다.
- 회귀가드 `tests/worktableDupWatch.test.js`(30케이스 — 스텁 pool 로 **실제 실행**: 처음 발견·동일 침묵·증식 재알림·소멸·스냅샷 실패·조회 실패 + 라우터 스택 실검사, **변이시험 8종 검출 확인**).
