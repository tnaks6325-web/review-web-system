## 기준(사용자 확정 2026-10-11)
1. **사람은 리뷰어 계정 고유번호(`reviewers.id`) 하나로만 가리킨다.** 전화번호는 로그인·검색 손잡이일 뿐이다.
2. **명의는 명의 카드 한 장(`reviewer_identity_cards.id`) = 고유번호 하나.** 본인도 카드 1장. 한 사람 안에서 이름+번호가 같은 카드는 1장(가족 같은 번호·다른 이름은 허용).
3. **참여하는 순간 "누구의 어느 카드"를 기록에 새긴다.** 이후 구매양식·제출·주문·입금·리뷰내역은 그 번호만 따라간다 — 이름·번호로 다시 찾지 않는다.
4. **명의를 만들고 고치는 창구는 하나, 규칙도 그 한 곳.** 주문 한 건의 배송지·연락처·계좌는 그 주문의 값이고 명의 정보를 바꾸지 않는다(명의 저장은 리뷰어가 명시적으로 고를 때만).
- 9/24 결정 175 의 "카드는 사본·아무도 읽지 않는다"는 이 기준으로 **원본 승격 방향**으로 바뀐다(5단계에서 완료). 142 코드 명의(`reviewer_identities`)는 계속 쓰지 않는다(결정 175 유지).

## 옮겨 가는 순서
1. **기록 시작(막지 않음)** — migration 182 `participant_card_id`(신청·주문). apply 가 (세션 대조 후) 카드와 유일 소유자를, 원장이 주문에 카드를 새긴다. ← PR #1596 (2026-10-11 배포, 운영 182 적용 확인)
2. **구매양식·제출이 카드 우선** — 카드 번호가 있으면 그 카드만. 없는 예전 참여는 카드와 같은 규칙(본인과 같은 타계정 = 본인 · 합쳐 들어간 카드가 있는 합친 명의 제외)으로 찾는다. ← PR #1597
3. 쓰기 창구 일원화(내정보·가입·번호 변경·입금 보완·자동보강 + 본인 칸 11곳) · 본인 중복/다른 소유자 번호 규칙을 그 한 곳에 · 참여(apply) 로그인 확인.
4. 입금·리뷰내역·검색을 카드로 + 과거 기록 중 확실한 것 채우기 + 신청 없는 주문의 소유자 기록.
5. 카드를 원본으로, `sub_accounts` 는 화면 호환 사본으로.
- 겹친 데이터(교차 등록 76 · 번호 14 등)는 담당자 정리 목록으로 — 자동 합치기 금지(동명이인, 결정 174 ②가 유지).

## 1·2단계 구현 (레드팀·Codex 반영 후)
- `server/migrations/182_participation_card_binding.sql` — 두 표에 NULL 칸 + 외래키 `NOT VALID`(새 칸은 전부 NULL — 큰 표 훑기 회피) + 기록된 행만 부분 색인(카드 삭제 때 SET NULL 이 표를 훑지 않게). `server/index.js` REQUIRED_SCHEMA 는 구매양식이 SELECT 하는 신청 칸만.
- `reviewerIdentityCards.findParticipationCard` — 본인 참여 = **이름(공백 무시)까지 같은** 활성 본인 카드 1장, 타계정 참여 = 이름+번호 8자리 활성 카드 1장. **정확히 하나가 아니면 null**(추측 금지). 타계정 참여를 본인 카드로 접지 않는다(참여 단계가 본인 번호 타계정 참여를 이미 막음).
- apply(`campaign.routes.js`): 홀드 INSERT 뒤 `SAVEPOINT card_bind`. **요청의 서명된 리뷰어 세션 소유자 = 참여 본계정(reg)일 때만** 기록(세션 없으면 기록 안 함 — 번호만 믿으면 타계정 세션·번호 겹침에서 남의 카드가 붙는다).
  - `participant_card_id` = 위 카드.
  - `owner_reviewer_id` 는 이미 내역·입금이 **정답으로 읽는 칸**이라 159 백필과 같은 유일 소유자 판정(다른 소유자 본인·타계정·번호 변경 이력·코드 별칭 어디에도 없음)일 때만, 덮지 않고(COALESCE) 쓴다.
  - `lock_timeout 1s` 는 트랜잭션 범위라 **SAVEPOINT 안에서 원래 값을 읽고 RELEASE 전에 되돌린다**(Codex P1). 실패해도 참여는 계속.
- 원장(`orderLedger.service.js`): `SAVEPOINT card_copy`(같은 잠금 상한·원복 규율). 게이트 결과에 카드가 있으면 **그 카드만**, 게이트 결과에 카드 칸이 없으면 신청행 카드를 — 신청행·주문 소유자가 **둘 다 있고 같을 때만**. 명시적 null 이면 비움. 이미 있으면 덮지 않음. 실패해도 주문 COMMIT.
- **신청 없는 주문의 소유자 기록은 4단계로 미뤘다** — 그 칸을 읽는 내역·입금 판단이 바뀌므로 읽는 쪽을 함께 손볼 때 한다(레드팀 1·2).
- 구매양식(`reviewerOrderIdentity.service.js`): `loadOwnerProfile` 본인에도 `cardId`, 타계정에 `mergedInto`(identityKey 불변 — 승인 토큰·과거 해시 결속 유지). `resolveApplicationIdentity`:
  - 카드 번호가 있으면 그 카드만 — 지금 값이 신청 당시와 달라도 버리지 않는다(고정 번호. 버리고 추측하면 그 번호를 이어받은 다른 사람이 걸린다 — Codex P1). 타계정 연락처는 종전처럼 신청 당시 값. 카드가 지금 목록에 없으면 종전 방식.
  - 코드 명의(`participant_identity_id`)와 카드가 서로 다른 사람을 가리키면 막는다.
  - 종전 방식 폴백은 `foldSameAsSelfAndMerged` — ① 본인과 이름·번호가 모두 같은 타계정 칸 = 본인 ② 합친 명의는 **그것이 합쳐 들어간 카드가 후보에 함께 있을 때만** 뺀다(번호만 같은 다른 이름은 빼지 않는다).
  - 제출 게이트는 고른 카드가 있을 때만 `participantCardId` 를 싣는다(못 골랐으면 칸째 생략 → 원장이 신청행 카드 — Codex P2).
- ⚠ 받아들인 영향: 소유자가 기록된 참여·주문의 리뷰어는 삭제가 막힌다(142 의 `ON DELETE RESTRICT`, 159 백필 행과 같은 동작). 새 삭제 화면은 409 안내, 옛 삭제 경로는 500 — 잘못 가입한 계정 정리 때 유의.

## ★★ 완화 금지
- ① 카드 기록·복사의 SAVEPOINT 격리를 빼지 말 것 — 빼면 기록 실패가 참여·주문을 통째로 되돌린다(주문 손실). 잠금 상한은 SAVEPOINT 안에서 읽고 RELEASE 전에 되돌린다 — 안 되돌리면 홀드 확정까지 1초 상한이 걸린다.
- ①-2 apply 기록의 **세션 대조**와 소유자 기록의 **159 유일 소유자 판정**을 빼지 말 것 — 번호만 믿으면 번호 재사용·교차 등록(76건)에서 남의 소유로 굳고, 내역·입금이 그대로 따라간다.
- ①-3 원장에서 게이트가 고른 카드가 있는데 신청행 카드로 대신하지 말 것 — 주문의 명의 해시와 카드가 다른 사람을 가리킨다.
- ② `findParticipationCard` 가 "정확히 하나"가 아닐 때 고르게 하지 말 것 — 추측이 곧 이번 사고 계열이다.
- ③ 카드 번호가 있으면 이름·번호로 다시 찾지 말 것 — 지금 값이 신청 당시와 달라도(카드가 지금 목록에 없을 때만 종전 방식).
- ④ 접기는 **본인과 이름·번호가 모두 같은 칸**과 **합쳐 들어간 카드가 후보에 함께 있는 합친 명의**만 — 이름이 다른 명의로 넓히지 말 것(결정 174 ③).
- ⑤ `identityKey` 를 카드 번호로 바꾸지 말 것 — 진행 중 승인 토큰·과거 주문 해시가 끊긴다(바꾸려면 4~5단계에서 rebind 와 함께).
