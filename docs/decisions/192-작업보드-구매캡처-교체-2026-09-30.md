# ★★ 작업보드 [🛒 구매캡처 교체] — 직원이 구매캡처를 새 사진으로 바꾼다 (스키마 변경 0, 사용자 확정 2026-09-30)

- **발단**: 리뷰어가 처음 올린 구매캡처가 주문 변경 등으로 달라졌을 때, 직원이 작업보드에서 사진을 바꿀 창구가 없었다(구매캡처를 올리는 곳은 리뷰어 구매양식 화면뿐).
- **사용자 확정 4건**: ① 옛 사진은 **드라이브 휴지통**(30일 복구) ② **내부 직원 전원(AE 포함)** ③ 창구 = **표 우클릭 + 제출물 미리보기 구매 칸** 두 곳, 실행 창은 한 벌 ④ 사진 넣기 = **붙여넣기(Ctrl+V)·끌어놓기만**(파일 선택 창구 없음 — [📎 리뷰 대신 제출]과 같은 규율).
- **API**: `GET /api/trackb/workdesk/purchase-capture`(쓰기 0 · 지금 사진) · `POST /api/trackb/workdesk/purchase-capture/replace` — 둘 다 `authMiddleware + internalMiddleware`(광고주 차단). 실행부 `purchaseCaptureReplace.service`.
- ★★ **줄 → 주문 짝짓기 = 제출물 미리보기(`reviewImagesForTab`)와 같은 규칙** — `order_submissions.sheet_row = 작업표 seq` + (탭 좌표 ∪ 연결 공고 `campaign:<id>` 좌표). `campaign_participants.order_submission_id` 링크는 오염 사례가 있어 **후보가 여럿일 때 고르는 보조로만** 쓰고, 그래도 못 좁히면 **거부**(`ambiguous_order`).
- ★★ **그 사이 바뀜 차단 2겹**: 화면이 열 때 받은 지금 사진(`expectFileId`)을 다시 보내 ① 업로드 **전**에 대조(다르면 파일 0) ② DB 확정 순간 `FOR UPDATE` 로 다시 대조(다르면 UPDATE 0 + 방금 올린 파일 휴지통). 확정은 리뷰어 업로드(`completeCapture`)와 **같은 advisory lock 키**(`purchase_capture:<주문ID>`).
- ★★ **폴더 판정 단일 출처 = `captureFolder.service.resolveCaptureFolder`** — 리뷰어 업로드(`/image-upload`)의 인라인 폴더 로직을 이관했다. 사본을 두면 두 경로가 다른 폴더에 쌓인다.
- ★ **옛 사진은 휴지통만**(영구삭제 금지). 다른 주문·리뷰 원장이 같은 파일을 가리키거나 확인이 실패하면 **지우지 않는다**(fail-closed · `oldKept`).
- ★ 캡처가 없는 주문에는 같은 창으로 **새로 올린다**. 기록은 작업 로그(`reviewer_event_logs` `capture_replaced` · info · 해결됨)에 남는다. 쓰기 표면 = `order_submissions.capture_file_id/capture_uploaded_at/updated_at` + 로그 1행.
- ⚠ **한계**: 캡처에서 읽어 둔 수취인 등 값은 새 사진으로 다시 읽지 않는다(사진만 바뀐다) · 주문이 연결되지 않은 줄은 붙일 수 없다(`no_order`) · 자동분류로 리뷰 원장의 구매캡처 칸에 옮겨진 사진은 이 기능이 건드리지 않는다.
- **완화 금지**: ① 줄→주문 판정을 링크 단독으로 바꾸지 말 것(남의 주문 캡처를 바꾼다) ② `expectFileId` 대조를 빼지 말 것(리뷰어가 방금 올린 사진을 덮는다) ③ 옛 사진 사용 여부 확인 실패를 "안 씀"으로 접지 말 것.
- 회귀가드 `tests/purchaseCaptureReplace.test.js`(19 — 스텁 pool·drive 로 서비스 **실제 실행** + 배선, **변이시험 5종 검출 확인**) + 실 http 오리진 브라우저 실측(팝오버 body 직속 · 붙여넣기 → 교체 → payload `expectFileId` · JS 오류 0). ⚠ `submissionPreview` 가드의 미리보기 칸 패턴을 갱신했다(버튼은 절대배치라 높이 무영향 — 검사 의미 불변).

## 운영 실측 보강 (2026-09-30 · 같은 날)
- 운영 테스트(마감 작업 「6/10_쟈니베어_쿠팡_온열안대_500건」, 교체 → 확인 → 원본 복원)에서 **줄 번호(`sheet_row`) 짝짓기가 남의 주문을 가리키는 것**을 발견했다 — 캡처가 있는 57줄 중 **36줄**이 줄의 사람 ≠ 주문의 사람(시트 시절 줄 재배치 흔적). 기존 제출물 미리보기도 같은 규칙이라 그 줄들에 **남의 구매캡처를 보여 주고 있었다**(별건).
- ★★ **교체는 이제 "이 줄 사람의 주문"으로 확인된 주문만 바꾼다(`orderMatchesRow`)**: 후보 = 줄 번호 ∪ 주문 링크 ∪ 표 주문번호 일치 → 표 주문번호 ↔ 원장 주문번호(둘 다 6자리 이상이면 이것만) → 연락처 뒤 8자리 → 이름. 근거가 없거나 전부 불일치면 `order_mismatch` 로 **거부**(쓰기 0).
- **완화 금지**: 줄 번호 단독 판정으로 되돌리지 말 것 — 남의 주문 캡처를 바꾼다.

## 제출물 미리보기도 같은 판정으로 (2026-09-30 · 사용자 확정 "이어서 고쳐")
- 미리보기 구매캡처 칸(`reviewImagesForTab`)도 `sheet_row` 단독 짝짓기라 줄이 재배치된 작업에서 **남의 구매캡처**를 보여 주고 있었다(위 57줄 중 36줄).
- ★★ **판정 단일 출처 = `utils/rowOrderMatch`**(`orderMatchesRow`·`pickRowOrder`·`matchRowsToOrders`) — 미리보기와 교체가 **같은 함수**를 쓴다(갈리면 "미리보기는 A 사진인데 교체는 B 주문을 바꾼다").
- 미리보기는 탭·공고 좌표의 캡처 있는 주문을 한 번에 읽고, 줄 목록과 **한 번에 짝짓는다**(후보 = 줄 번호 ∪ 링크 ∪ 표 주문번호 → 확인). ★ **확인 못 한 줄에는 싣지 않는다**(남의 사진보다 없는 편이 낫다).
- ⚠ 이 변경으로 옛 규칙("sheet_row 하나로 짝짓는다")을 고정하던 가드 2종(`captureCampaignScope`·`workboardTopC` ④)을 **새 사용자 확정으로 뒤집었다**. 로컬 PG16 으로 실제 SQL 실행 확인(링크가 남의 주문을 가리켜도 표 주문번호로 제 주문을 찾음).
