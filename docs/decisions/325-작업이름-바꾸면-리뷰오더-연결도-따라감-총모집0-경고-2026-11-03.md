# 작업 이름을 바꿀 때 리뷰오더 연결도 새 이름을 따라간다 · 총모집 0 리뷰오더는 막지 않고 이상로그 경고 (2026-11-03 · 스키마 변경 0)

## 무슨 일이었나

운영 읽기 전용 조사(2026-11-03): 업체 화면 총건수가 빈 업체 작업 44건은 전부 7~8월 생성(9월 이후 0건)이지만 재발 경로가 둘 남아 있었다.

1. **작업 이름 변경이 리뷰오더 연결을 끊는다(코드로 확인).** 탭 이름이 바뀌면 `tabRename.renameTabState` 가 장부·공고(`recruit_campaigns.linked_tab_name`, 결정 020)는 새 이름으로 옮기는데,
   리뷰오더 연결 두 곳 — 직접 연결 `work_orders.linked_tab_name` 과 수동 발주 연결 `trackb_work_order_links.tab_name` — 은 **옮기지 않았다**.
   「그 탭의 리뷰오더」 단일 출처 `utils/workOrderLink.workOrderForTabSql` 은 **이름으로만** 찾으므로(gid 폴백 없음) 새 이름에서 0건 → 정원·작업 조건 카드·업체 화면 총건수가 조용히 빈다.
   무시트 재접수(`order.routes` accept, 가상 시트)는 `o.linked_tab_name` 으로 탭을 다시 등록해 옛 이름 탭이 되살아날 수도 있다.
   - 운영 실측: 살아 있는 직접 연결 181건 중 지금 탭 이름과 다른 것 19건 — 그중 **같은 gid 의 탭이 다른 이름으로 있는 것(= 이름 변경으로 끊긴 것) 1건**(7월 생성, 진행 중).
     나머지 18건은 탭 자체가 등록부(`tab_configs`)에 없는 경우(탭 삭제·미등록)라 이름 변경과 무관. 수동 발주 연결 10건은 끊긴 것 0건. **고치지 않았다(보고만)** — 이미 끊긴 것은 다음 이름 변경 때만 따라간다.
2. **총모집 0 을 그대로 받는다.** 인트라넷 접수(`POST /intake` → `_insertWorkOrder`)와 작업 접수(accept)는 `recruit_count` 0 을 막지 않는다.
   작업표 미리보기는 0 이면 막지만(`worktablePlan` `no_total`) 사람이 총 건수를 따로 넣으면 표는 생기고 오더 정원은 0 으로 남는다. 운영 6·7·8월 각 1건.

## 결정

- **① 이름 변경 트랜잭션 안에서 리뷰오더 연결 두 곳도 옮긴다**(`tabRename.service.js`, 같은 트랜잭션 — 실패하면 이름 변경 전체가 되돌아가 다음 빌드에서 다시 감지된다).
  - `work_orders`: **`linked_tab_name` 한 칸만** 바꾼다. 조건 = 같은 시트·옛 이름 · gid 가 비었거나 같을 때(다른 gid 로 적힌 오더는 다른 탭 것이라 둔다). 지운 오더도 옮긴다(「원본 오더 삭제됨」 표시 — 결정 254).
  - ★★ **`sync_version`·`updated_at`·`shared_sync_outbox` 를 건드리지 않는다** — `linked_tab_*` 는 공유 칸(`sharedFields`)이 아니고 전송 대기열은 명시 INSERT 로만 쌓인다(코드 확인). 인트라넷 목록 폴링(`/intake/list`)은 이 칸을 싣지 않고 `updated_at` 도 안 바뀐다(상세 `/intake/:id` 를 열면 지금 이름이 보일 뿐 — 읽기). 그래서 인트라넷 쪽 저장·번호로 흘러가지 않는다.
    기존 관례: 작업 삭제(`workTabDelete`)가 같은 칸을 직접 비우고, 작업 접수가 직접 쓴다. 결정 154 「Track B 는 `linked_tab_*` 를 쓰지 않는다」는 수동 링크가 승인 링크를 **바꿔치기**하지 말라는 규칙이고, 같은 탭의 이름 좌표를 맞추는 것은 그 대상이 아니다(승인 멱등 판정은 gid 로 하므로 동작 불변).
  - `trackb_work_order_links`: 활성·지운 연결 모두 옮긴다. 새 이름에 이미 활성 연결이 있으면(탭당 활성 1개 제약) 옛 활성 연결은 두고 서버 로그에 경고.
- **② 총모집 0 은 막지 않고 경고만 남긴다**(`services/zeroRecruitWarning.service.js`). 인트라넷 접수 저장 직후(기다리지 않음)와 작업 접수 저장 직후, 저장된 오더의 총모집이 0·빈 값이면
  기존 **이상로그(error_logs)** 에 `warn` 한 줄(`admin/zero_recruit_count`, 오더 id 별 한 줄 — 두 단계는 같은 줄의 횟수만 오른다). 작업 접수 응답에는 `recruitCountZero: true` 만 더한다(구 화면은 무시).
  - 거절하지 않는 이유: 인트라넷 정식 접수가 실패하면 원본 번호(`source_revision`)가 어긋나 그 오더는 다시 못 고친다(AGENTS.md `PUT /api/order/intake/source` 규율).
  - 화면(workdesk·홈 오늘 확인할 것)은 이번에 손대지 않았다(병렬 작업 영역).

## 완화 금지

- ★★ **이름 변경에서 리뷰오더 연결 두 곳을 빼지 말 것** — 빼면 「그 탭의 리뷰오더」가 이름으로만 찾는 단일 출처라 총건수·작업 조건이 조용히 빈다. 이 이동에 `sync_version` 올림·전송 대기열 INSERT 를 더하지 말 것(좌표 정리가 인트라넷 수정으로 둔갑한다).
- ★★ **총모집 0 을 거절(4xx)로 바꾸지 말 것** — 경고만. 기록 실패도 접수를 깨지 않는다(throw 금지).
