# 「랜덤」 작업담당은 리뷰웹이 만두·망고로 자동 배정한다(진행 중 작업이 적은 쪽 · 같으면 번갈아) + 보관 공고 작업도 담당자를 바꿀 수 있다 (사용자 확정 2026-11-23 · 스키마 변경 0)

## 요청과 확정

- 사용자(2026-11-23): 인트라넷 작업담당 「랜덤」은 **AE 가 만두·망고 중 누구에게 줄지 못 고를 때 쓰는 선택지**다. 리뷰웹이 알아서 만두 또는 망고로 정해야 한다.
  지금은 랜덤이 리뷰웹에서 「담당자 없음」이 되어 입금관리의 만두·망고 목록에 안 들어온다(입금관리 맨 아래 「담당자 미지정」 줄로만 보인다 — 결정 295).
- 확정 내용
  1. **트리거** = 인트라넷에서 온 작업오더의 작업담당이 정식 미정 값(「랜덤」·「랜덤배정」·「미정」) **정확 일치**일 때 — 새 접수(`POST /api/order/intake`)와, 나중 원본 수정이 작업담당을 **정해진 값 → 랜덤** 으로 바꾼 때. 빈 값은 트리거가 아니다. 「이미정」 같은 사람 이름은 잡지 않는다(결정 311 의 정확 일치).
  2. **이미 랜덤으로 저장된 옛 오더는 소급하지 않는다**(사용자 선택 「앞으로만」). 원래 랜덤·빈 값이던 오더가 다른 칸만 고쳐 다시 와도 배정하지 않는다.
  3. **고르는 법** = 진행 중 작업오더가 **적은 쪽**. 같으면 **마지막 자동 배정의 반대쪽**(기록이 없으면 만두부터).
  4. **보관된 모집공고에 연결된 작업도 담당자를 바꿀 수 있다**(입금이 남아 있을 수 있다). **완료(done) 작업은 그대로 막는다.**

## 종전 규칙을 뒤집는다

- 결정 039 「③ 담당자: 랜덤·미매핑은 빈 값(자동으로 아무나 배정 금지)」, `utils/workManager.js` 머리 주석 「랜덤은 … 자동으로 아무나 고르면 안 되고 관리자가 정해야 한다」 → **폐기**(사용자 확정). 매핑 자체(`mapWorkManager('랜덤') = ''`)는 그대로다 — 바뀌는 것은 「랜덤으로 들어온 오더의 work_manager 를 리뷰웹이 공유 저장으로 박세희/박은비로 바꾼다」 한 가지다.
- 결정 306 「삭제·완료·보관·미연결은 새 담당자 전용 저장에서 거부」 중 **보관**만 뺀다. 삭제·완료·미연결 거부는 그대로다.

## 무엇을 했나 (자동 배정)

- 새 서비스 `server/src/services/autoWorkManager.service.js`
  - `countLoad(db)` — **진행 중** = 지워지지 않음 · 상태가 완료(done)·반려(rejected) 아님 · 보관 공고(정·역방향 연결) 아님 · 🏁 마감 보관함(`trackb_tab_finished`, 판정은 `trackB.finishedTabsMap`/`isTabFinishedIn` 단일 출처) 아님. 결정 311 홈 질문의 「진행 중」 갈래와 같다. 사람은 오더의 `work_manager` 를 `mapWorkManager` 로 읽는다(만두=박세희 · 망고=박은비 · 랜덤·기타·모르는 이름은 어느 쪽도 아님 · 탭 폴백은 안 본다).
    - 접수 대기(submitted·reviewing·revision·await_chatroom)도 센다 — 이미 그 사람에게 갈 일이다. 반려는 진행이 아니다.
    - 마감 조회를 못 하면 **추측하지 않고 배정하지 않는다**(종전처럼 미지정으로 남는다).
  - `pickSide(load, last)` — 적은 쪽 → 같으면 `app_settings['auto_work_manager_last']` 의 반대쪽 → 기록 없으면 박세희.
  - `autoAssignUndecided({workOrderId})` — 쓰기는 **기존 공유 저장 하나** `sharedPatch.applySharedPatch({origin:'rw_manager', managerOnly:true, actor:'자동배정'})`.
    L1·오더 행 잠금·완료 보호·조건부 버전 쓰기(CAS)·스냅숏·담당자 범위 전송 대기(`shared_sync_outbox.view_scope='manager'`)가 그 안에 있다 → 인트라넷에도 박세희/박은비로 간다. 원본 번호(`source_revision`)는 건드리지 않는다(정확히 +1 규칙 불변).
    - **경합**: 잠금 밖에서 먼저 고른 뒤, `preHook`(L1·행 잠금 아래)에서 ① 아직 정확히 랜덤인지 ② `pg_advisory_xact_lock(hashtext('auto_work_manager'))` ③ **다시 세어** 같은 쪽인지 확인한다. 다르면 쓰기 0 으로 물러나 처음부터 다시 고른다(최대 3번 · `manager_version_conflict` 도 다시). 마지막 자동 배정 기록은 `managerCommitHook` — **같은 트랜잭션**.
    - 잠금 순서 = (이중 채널 범위) → L1 → 오더 행 → 자동 배정 전용 잠금. 자동 배정 잠금을 잡은 채 다른 오더의 행·L1 을 기다리지 않으므로 교착이 없다.
  - `scheduleAutoAssign` — 커밋 뒤(`setImmediate`)에 따로 돈다. 절대 throw 하지 않는다(성공 info · 실패 warn 로그만).
- 연결 지점(`order.routes.js`)
  - `POST /intake`: 새 오더 저장·응답 **뒤**, 원본 계약이 있고 작업담당이 정확히 미정이면 예약. 접수 응답은 한 글자도 안 바뀐다(`data.work_manager` 는 '랜덤'). 멱등 재시도·원본 없는 옛 접수는 예약하지 않는다.
  - 원본 수정 `_intakeSourceManager`(담당자 단독)·`_intakeSourceBidir`(ON 공유 저장): 응답 뒤 `changedToUndecided(수정 전, 저장 후)` 일 때만 예약. 응답·`manager_ack_version` 계약 불변. 옛 창(담당자 capability 없음)의 전체 저장은 담당자를 쓰지 않으므로(결정 306) 트리거가 아니다.
  - 관리자가 리뷰웹에서 직접 「미지정」으로 되돌린 경우는 트리거가 아니다(사람의 명시적 선택).

## 무엇을 했나 (보관 공고 담당자 변경)

다섯 곳의 보관 잠금을 **같이** 뺐다(완료 보호는 다섯 곳 모두 유지):
1. `GET /intake/source/:id/shared` 담당자 capability(`manager_edit_capable`·`writable`) — 인트라넷 작업담당 버튼을 여는 곳.
2. `sharedPatch._managerEditProtection` — 담당자 단독 저장·ON 공유 저장의 실제 `f:work_manager` 쓰기.
3. `sharedSyncPush` — 담당자 범위 대기 줄을 보관 공고라는 이유로 `dead` 처리하던 것.
4. `trackB.service.listWorkOrders` · `trackB.routes GET /work-orders/list` 의 `manager_edit_capable`(관리자 수정창 작업담당 알약).
5. `trackB.service.workdeskTab` 작업 조건 카드 빠른 배정(`managerEdit`).
- 입금관리 「담당자 미지정」 줄 → 작업보드 [관리자 수정] › 작업담당 / 빠른 배정이 보관 공고 작업에서도 실제로 저장된다(막다른 길 해소). 관리자 수정(`orderAdminEdit`)에는 다른 보관 잠금이 없다(공유 저장으로만 간다).
- 그대로 둔 것: 작업보드 「*마감 · 열람 전용」 화면(`?archived=1`, 🏁 마감 보관함 작업)은 화면 전체가 읽기 전용이라 빠른 배정 버튼이 없다 — 공고 보관과 다른 개념이라 이번 범위 밖. 홈 「미지정 담당자 질문」은 진행 중 작업만 다룬다(보관되면 질문이 닫히고, 열려 있던 질문의 답은 「바뀐 질문」으로 거절 · 쓰기 0).

## 인트라넷 쪽 확인 (읽기 전용 · inadd-webapp c2f3c0e6)

- 담당자 범위 수신 `reviewOrderReceiveSharedState`: 리뷰오더 행은 인트라넷이 접수를 보내기 **전**에 이미 있다(원본 ID = 그 행). 리뷰웹 연결 ID(`remote_work_order_id`)가 아직 비어 있으면 불일치 검사를 건너뛴다. 아직 접수 응답을 받기 전(`status ≠ 'sent'`)이면 `held` 409 → 리뷰웹 전송기는 `retry`(15초부터 두 배 · 최대 60번)로 다시 보내고, 접수가 `sent` 로 끝나면 `applied` 로 수렴한다. 전송은 15초 주기라 대개 접수 응답보다 늦게 간다.
- 되돌림(왔다 갔다) 없음:
  - 담당자 capability 창이 옛 기준 버전으로 「랜덤」을 다시 보내면 공유 저장의 기준 버전 검사(`manager_version_conflict`)로 막힌다(종전 리뷰웹 수정과 같은 동작).
  - capability 없는 옛 창의 전체 저장은 담당자를 쓰지 않고, 다르면 리뷰웹 값을 담당자 범위로 **다시 보낸다**(`_sourceUpdateWithManagerRepair`).
  - ON 공유 저장은 3방향 비교라 창이 손대지 않은 랜덤(기준과 같음)은 쓰기 0.
  - AE 가 인트라넷에서 **일부러 다시 랜덤**을 고르면 그건 새 요청이라 다시 자동 배정한다(사용자 규칙 그대로). 자동 배정은 리뷰웹→인트라넷 한 방향 전송이라 되먹임 고리가 없다.
- 남는 틈: 인트라넷 접수 전송이 끝내 실패(failed)로 남으면 담당자 전송도 `held` 로 계속 재시도하다 60번 뒤 `dead` 가 된다 — 인트라넷 공식 재전송(`/retry`) 뒤 리뷰웹 쪽은 이미 배정된 값을 갖고 있어 두 시스템 값이 갈린 채 남을 수 있다. 종전 리뷰웹 수동 배정과 같은 성질의 틈이다(이번 변경이 새로 만든 틈은 아니다).

## ★★ 완화 금지

- 자동 배정 쓰기는 **공유 저장(`applySharedPatch` managerOnly) 하나로만** 한다 — 두 번째 담당자 UPDATE·별도 전송 대기 금지(결정 306·311 과 같은 규율). 원본 번호를 건드리지 않는다.
- 트리거는 **정식 미정 값 정확 일치**만 — 포함 비교(`isUndecidedWorkManager`)로 넓히면 「이미정」 같은 사람 이름의 작업이 남에게 배정된다. 빈 값·모르는 이름을 랜덤으로 읽지 않는다.
- 옛 랜덤 오더 소급 금지(사용자 선택) — 「정해진 값 → 랜덤」 변화일 때만.
- 잠금 안에서 **다시 세기**와 자동 배정 전용 잠금을 빼지 않는다(동시 접수가 같은 쪽으로 몰린다).
- 진행 부하를 모르면 배정하지 않는다(추측 금지) · 자동 배정 실패로 접수·원본 수정을 실패시키지 않는다(응답 뒤 따로).
- 보관 잠금을 다시 넣을 때는 다섯 자리를 **같이** 바꾼다(한 곳만 막으면 버튼은 보이는데 저장이 막히거나, 저장은 되는데 인트라넷에 안 간다). 완료(done) 보호는 빼지 않는다.

## 되돌림

코드만 바뀐다(스키마 변경 0 · `app_settings` 키 하나 추가 사용). 되돌리면 랜덤은 다시 미지정으로 남고 보관 공고 작업은 다시 잠긴다. 이미 자동 배정된 오더는 되돌리지 않는다(사람이 바꾼 것과 같은 공유 저장 기록이다).
