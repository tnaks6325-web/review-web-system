# ★★★ 작업표 줄 삭제·리뷰어 참여 취소가 같은 탭에 몰리면 교착(40P01) — 탭 잠금을 첫 잠금으로(공고·줄보다 먼저) · 교착만 통째로 다시(최대 3번) (2026-11-28 · 스키마 변경 0 · 화면 변화 0)

## 무슨 일이었나
- 같은 작업표(탭)에서 **줄 삭제 여러 건이 동시에** 오면 Postgres 가 교착(40P01)을 감지하고 한 건만 남기고 나머지를 끊었다.
  - 담당자 [줄 삭제](`POST /api/trackb/workdesk/hide`) → 200 `{ ok:false, error:'unexpected', pgCode:'40P01' }`
  - 리뷰어 [참여 취소](영수증리뷰 · `reviewerOrderCancel.cancelOrderByReviewer` → 같은 실행부) → 409 「취소하지 못했습니다. 잠시 후 다시 시도해주세요.」
  - 데이터는 정상(통째로 되돌림) · 다시 누르면 된다. **#1897 이전부터 main 에 있던 문제**(영수증리뷰 3단계의 동시성 실측에서 드러남).
- 실측(로컬 진짜 Postgres · 서버 2벌 · 결정 434 하네스 그대로): 연결 풀 10 → 5건 동시에 **첫 시도 1건만 성공**(7장면 모두) · Postgres 로그 교착 28건 /
  풀 1 → 두 서버에 나눠 보낸 장면에서 3/5 · 교착 6건.

## 왜 (잠금 그래프 — Postgres 로그)
- 실행부 `trackB._hideParticipantInTx` 의 잠금 순서가 **내 줄 → 공고 행 → 탭의 모든 줄** 이었다.
  - A: 자기 줄(`campaign_participants … WHERE id=$1 … FOR UPDATE`) 쥠 → 공고 행(`SELECT rc.id … FROM recruit_campaigns rc … FOR UPDATE`) 대기
  - B: 공고 행 쥠 → 탭의 모든 줄(`SELECT seq, tab_gid, row_json … ORDER BY seq FOR UPDATE`) 대기 — 그중 A 의 줄 → **순환**.
- 이 저장소의 잠금 계약은 **탭 잠금(`sheetless_worktable:<시트>:<탭>`)이 트랜잭션의 첫 잠금 → 공고 행 → 줄**이다
  (결정 182 「탭 잠금은 첫 잠금」 · 392/394 「탭 잠금은 공고 행보다 먼저」 · 321 「작업표 → 공고」 · 016 「공고 행 → 신청 행」).
  줄 삭제만 이 계약 밖에 있었다(탭 잠금을 아예 잡지 않음 — 182 는 「중간에 잡으면 뒤집힌다」는 경고만 남겼다).

## 결정
1. **줄 삭제의 모든 트랜잭션은 첫 잠금으로 탭 잠금**을 잡는다 — 동시진행 범위 잠금(lifecycle) 뒤 · 주문 행·내 줄·공고 행·탭 줄 잠금 앞.
   주문 기록(`sheetlessOrder`)·정원 보충·직원 셀/날짜 수정·날짜 맞추기·Q&A 일정 끝과 **같은 키·같은 자리**.
   - 주문 없는 줄(자기 트랜잭션 `_runWorkdeskMutation`): 본문 첫 줄에서 `_lockHideTabFirstInTx`.
   - 주문 있는 줄(주문 취소 트랜잭션 `cancelOrderSubmission`): 새 선택 콜백 **`beforeOrderLock`** — lifecycle·주문 작업 잠금(try · 기다리지 않음) 뒤,
     **주문 행 `FOR UPDATE` 앞**에서 부른다. 넘기지 않는 다른 호출부(`workdeskOrderDelete` 등)는 종전 그대로.
   - 주문이 그새 취소돼 이어서 도는 자기 트랜잭션(`if (!result) runInOwnTx()`)도 같은 함수라 같은 순서.
   - 같은 탭의 줄 삭제끼리는 탭 잠금에서 줄을 선다 → 순환 자체가 생길 수 없다(종전에도 「탭의 모든 줄」 잠금 때문에 사실상 한 줄로 섰다 — 줄 서는 자리만 앞으로 옮김).
2. **추가 방어 한 겹** — 진입점 `hideWorkdeskRow` 하나에서, 결과가 `unexpected` + `pgCode 40P01` 일 때만 **처음부터 통째로** 다시 한다(최대 3번 · 20~100ms×회차 무작위 대기 · 매번 경고 로그).
   - 왜 안전한가: 교착이면 Postgres 가 그 트랜잭션을 통째로 되돌렸다(커밋 전). 커밋 뒤 단계(날짜 맞추기·장부)는 **성공한 시도에서만** 돈다.
     주문 취소는 한 트랜잭션에서 줄 삭제와 함께만 커밋된다(본문이 안 돌면 취소도 없음) → 「주문만 취소되고 다시 시도」는 생기지 않는다.
   - 왜 두는가: 뿌리(1)는 줄 삭제끼리의 순환을 없앤다. 다른 기능과의 드문 역순 쌍(예: 수동 [작업 삭제] — 결정 392 의 R1 ↔ 작업 삭제 1쌍)은 이 변경 범위 밖이라,
     그때 담당자가 「잠시 후 다시」를 누르는 대신 서버가 한 번 더 해 본다. ★ 뿌리 대신이 아니다 — 실측에서 다시 시도는 **0회** 쓰였다(아래).
   - 그 밖의 실패(시간 초과 등)·업무 거절(`row_changed`·`review_submitted`·`not_sheetless`…)은 다시 하지 않는다(종전 그대로 알린다 · fail-closed 불변).

## 완화 금지
- ★★★ **줄 삭제 실행부(`hideWorkdeskRow`)의 모든 트랜잭션은 탭 잠금이 첫 잠금** — 빼거나(→ 교착 재현) 공고·줄 잠금 **뒤로** 옮기지 않는다(→ 구매 기록과 역순 · 결정 182).
- ★★ 주문 취소 길의 탭 잠금은 `beforeOrderLock`(주문 행 앞) — `beforeCancelMutation`·`beforeCancelCommit` 안으로 옮기지 않는다.
- ★★ 다시 시도는 **40P01 만 · 최대 3번 · 진입점 한 곳** — 다른 오류·업무 거절로 넓히지 않는다 · 뿌리(잠금 순서) 대신으로 쓰지 않는다.
- ★ 날짜 맞추기(relay)·장부 재생성을 줄 삭제 트랜잭션 **안**(다른 연결)에서 부르지 않는다 — 자기 탭 잠금을 기다리며 멈춘다.
