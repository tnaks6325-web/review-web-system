# 네이버·쿠팡 동시진행 ①-기반 — 상품 하나 안의 구매처별 조건 검증 · 기존 수신은 기본 닫힘 (2026-11-05 · 로컬 구현, 미배포)

## 승인 범위

사용자가 계획의 Q1~Q5를 전부 A로 확정했다.

- 구매처는 네이버+쿠팡만, 옵션 없는 상품 하나만.
- 배송지가 확실히 다르면 차단, 판정불가·오류면 접수+직원 확인.
- 리뷰비는 한 사람에게 공고 금액 한 번.
- 작업보드는 한 사람 한 줄, 상품비는 두 구매처 합계와 각각의 금액을 표시.

사전 충돌 점검 뒤 「신규 공고부터, 로컬 가짜 데이터에서 단계별 구현, 전체 흐름 검증 전 실제 모집 금지, 기존 참여 공고 전환 제외」를 권장했고 사용자가 「바로시작해」로 착수를 승인했다. 화면 스타일·화면 반영·운영 활성화와 미결 업무 정책까지 승인받은 것은 아니다.

## 이번 구현 단위와 하지 않은 것

이번 변경은 **①단계 전체가 아니라 상품 설정 검증의 첫 기반 단위**다. 공고 편집·DB 저장·양방향 공유 저장·오더↔공고 왕복 비교·구매 제출·리뷰 제출·실제 지급은 아직 완성되지 않았다. 신규 마이그레이션과 운영 데이터 변경은 없다. 아직 배포하지 않는다.

- `server/src/utils/dualChannel.js`: 두 구매처 상품 설정의 순수 검증·정규화.
- `server/src/services/productOptions.service.js`: 구형/v2 분기 전에 같은 규칙을 태우고, 기존 오류 계약 `ProductOptionsError`로 변환.
- `server/src/routes/order.routes.js`: 정규화를 생략하던 옛 신규 수신·직접 수정·직원 관리자 수정의 세 갈래도 `channels`가 있으면 같은 검증을 탄다. 원본 계약이 있는 신규 수신·번호 수정은 이미 정규화를 사용한다.
- `server/src/services/sharedPatch.service.js`: 잠근 현재 상품·요청 상품과 병합 완료 상품의 기본 닫힘. 정상 동시진행 저장을 구현한 것이 아니라, 준비중 설정이 공유 저장에서 잘못 처리되지 않게 거부한다.

## 상품 설정의 모양

상품 객체 하나의 `channels`에 `naver`와 `coupang`을 고정 키로 둔다. 각 구매처는 `url`, `pay`, `inflow_type`, `guide:{text,images}`다. 상품·정원은 복제하지 않는다.

- `base.pay`는 **1인당 두 구매처 결제금액의 합계**이고 `base.count`는 사람 수다. 합계가 다르면 조용히 다시 계산해 덮지 않고 거부한다. 오더 전체 `pay_amount`와 주문의 `price`는 서로 다른 계약이므로 이번 순수 검증에서 바꾸지 않는다(결정 161·275).
- 구매처·가이드의 알 수 없는 키와 자료형, 구매처 누락, 다른 구매처, 옵션 상품·다상품·구매수량 단계가 섞인 입력은 거부한다.
- 금액은 0 이상 정수, 인원은 1 이상 정수로 검증한다. 검증 범위 상한은 현재 상품 단계 규칙을 따른다. 문자열 정수는 숫자로 정규화하되 Boolean·빈 값·소수·음수·지수 문자열을 숫자로 꾸미지 않는다.
- 상품 URL과 가이드 사진은 로그인 정보 없는 http/https 주소만 허용한다. 단축 주소를 위해 호스트를 특정 쇼핑몰로 제한하지 않으며, 검증 과정에서 네트워크로 열지 않는다. 주소 철자는 앞뒤 공백만 제거한다.
- 구매처별 `inflow_type`은 명시된 `guide`/`link`만 받는다. 부모 상품·공고 값을 대신 쓰지 않는다. 가이드유입은 해당 구매처의 글 또는 사진이 필요하다. 사진 상한은 기존 `guideCanon.GUIDE_IMG_MAX`를 재사용한다. 링크유입에서 생략한 가이드만 빈 가이드로 채운다.
- 기존 상품에 own `channels` 키가 없으면 입력 배열 참조를 그대로 반환한다. 기존 구형 상품 원문의 들여쓰기·값·바이트를 바꾸지 않는다. 새 설정도 입력 원본을 수정하지 않는다.

## 기본 닫힘 — 완화 금지

- 기존 `normalizeProductOptionsJson`은 `allowDualChannels === true`를 **호출 코드가 명시한 내부 검증**에서만 새 설정을 정규화한다. 기본값은 false이며 `dual_channel_not_ready`로 거부한다.
- HTTP 본문에 같은 이름의 true나 능력 표시를 넣어도 열리지 않는다. 실제 수신 처리기는 이 옵션을 본문에서 전달하지 않는다.
- 정규화 결과는 요청 본문의 `_normalized_product_options_json` 같은 이름을 신뢰하지 않고 **서버 모듈 전용 WeakMap**에 요청 객체별로 보관한다. 전체 저장과 부분 수정은 같은 읽기 함수를 사용한다. 외부 예약 필드로 검사를 우회하는 길을 다시 열지 않는다.
- 공유 저장도 현재 저장본·요청·최종 병합 상태에 새 설정이 있으면 같은 준비중 코드로 되돌린다. 설정을 누락·삭제하는 요청으로 일반 상품으로 바꾸지 않는다. 실제 동시진행 공유 저장을 열 때는 금액 변경 뒤 두 구매처 합계 검증을 최종 상태에서 수행해야 한다.
- 검증이 붙었다고 현재 수신기에 동시진행을 허용하지 않는다. 설정 저장·옛 화면 보존·공유 저장·비교·실제 모집의 모든 입구 및 구매·리뷰·정산이 완성되고 검증된 뒤 다음 단계에서 이 경계를 설계한다.
- 공고 임시저장은 기존 운영 작업과 연결되면 최신 구매처 검수 등에서 부수효과가 있으므로, 로컬 가짜 데이터 밖에 초안을 만들지 않는다.
- 기존 NC 두 카드의 별도 제출 경로와 같은 주문의 보충 구매캡처(결정 288)를 동시진행 완료 경로로 재활용하지 않는다.

## 실제 검증

- 상품 정규화에 잘못된 합계를 넣었을 때 기존 코드가 예외 없이 통과함을 먼저 확인했다. 정규화·숫자 표준화·상품 범위 검사가 없던 상태에서 5개 중 기능 검사 4개가 실패하고 기존 원문 보존 1개는 통과했다.
- 준비중 차단을 추가하기 전 검사 4개 중 기능 검사 3개가 실패했다. 구현 후 전부 통과했다.
- 실제 수신 처리기에 가짜 DB를 주입한 6갈래 검사에서 옛 세 경로가 쓰기를 시도하는 실패를 먼저 확인했고, 조건을 확장한 뒤 여섯 갈래 모두 거부·업무 데이터 쓰기 0을 확인했다. 런타임 스키마 보강은 대역에서만 처리했고 실제 DB에는 접속하지 않았다.
- 공통 모듈 단위검사 243개는 부모가 재실행해 통과를 확인했다. 전체 시험과 독립 검토의 최종 결과는 계획 문서의 현재 진행 기록에 남긴다.
- 메모리 사본에서 정규화, 기본닫힘, 옛 경로 보호를 각각 뺀 변이 세 종류는 대응 검사가 실패했다. 실제 작업 파일을 되돌리거나 덮어쓰지 않았다.

## 독립 검토에서 찾은 세 경계와 보완

1. 외부 `_normalized_product_options_json` 우회: 실제 신규 수신 처리기에서 정상 원문 `[]` 대신 합계가 잘못된 숨은 상품 원문이 INSERT 인자로 가는 실패를 재현했다. 검증 결과 보관을 서버 전용 WeakMap으로 바꾼 뒤 정식 원문만 쓰는 것을 확인했다. 인증 우회가 아니라 인증된 수신 요청의 내부 필드 신뢰 문제였다.
2. 공유 저장 합계 파괴: 실제 서비스와 PGlite에서 네이버 9,000원·쿠팡 10,000원인 저장본의 기본 금액만 1원으로 바꾸면 합계 3원이 저장되는 실패를 재현했다(가짜 인원 3명). 현재 설정·입력 설정·병합 결과 기본 닫힘을 추가했다. 기존 단일구매 금액 변경은 성공하고, 새 설정 수정·누락·추가와 병합 중 새 설정 삽입은 모두 거부되며 대상 원문·금액·버전·스냅숏·전송 대기열이 그대로임을 PGlite로 확인했다. 병합 삽입은 실제 서비스의 VM 사본에 결함을 주입한 시험이며 제품 파일은 바꾸지 않았다.
3. 상품명 유실: `|`만 있는 이름과 200자 초과 이름이 구형·v2에서 다르게 통과하던 경계를 막았다. 기존 소비처의 구분자 제거 뒤에도 이름이 남아야 하며 200자 이하여야 한다. 정상 200자 상품은 두 규격에서 기존 금액 추출까지 통과한다. 키 없는 기존 상품 원문 보호는 그대로다.

- 보완 뒤 관련 **265개 검사 통과·실패 0·생략 0**. 전체 자동검사 재실행은 **701개 파일 통과·실패 0**(85.5초). 최초 700개 통과 결과는 보완 전 실행이다.
- 보완 보호를 없앤 메모리 변이도 각각 실패했다: 요청 본문 신뢰로 되돌림 1개, 상품명 검사 제거 1개, 공유 저장 입력 검사 제거 2개, 최종 병합 검사 제거 1개. 문법·모듈 적재 오류로 실패한 것이 아니라 대응 행동 단언의 실패다.
- 세 보완에 대한 최종 독립 대조에서 세 결함의 해결과 새 차단급 결함 미발견을 확인했다. 독립 재실행도 관련 **265개 통과·실패 0**이다. 이 결과도 화면·두 시스템 왕복·운영 활성화 완료를 의미하지 않는다.

## 남은 검증·업무 결정

첫 기반 단위의 로컬 구현·관련 검사·전체 자동검사·독립 대조까지 완료했다. 화면은 기존 공고 편집 모양 유지안을 제안한 상태이며 사용자 선택을 기다린다. 아직 푸시·PR·배포는 하지 않았다. 정상 동시진행 DB 저장·다중 연결 경합·두 시스템 왕복·화면·AI 배송지 판정·실제 지급은 이 변경의 검증 범위가 아니다. PGlite의 차단·되돌림 검증을 그 범위의 완료로 확대하지 않는다. 블로그 포함 여부·한쪽 품절/취소·두 구매 아이디·자리 유효시간·현금영수증은 아직 미결이며 해당 단계 전에 확인한다.
