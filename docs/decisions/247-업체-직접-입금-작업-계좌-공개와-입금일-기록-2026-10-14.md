# ★★ 업체 직접 입금 작업 — 소유 업체 대표 링크에 송금 계좌를 보이고, 업체가 입금일을 기록한다 · 우리 입금관리에서는 뺀다 (사용자 확정 2026-10-14 · migration 189)

## 발단
- 스마트윈 페이백 작업처럼 **업체가 참여자 페이백을 직접 보내는** 작업이 생겼다. 종전에는 우리가 입금했으므로
  업체 화면에서 은행·계좌번호·예금주 열을 응답에서 아예 뺐고(`trackB.service._isAdvertiserRestrictedHeader`),
  입금 칸은 내부 담당자만 [💰 입금수정] 달력으로 고칠 수 있었다(`/workdesk/deposit-date` = internalMiddleware).
  → 업체는 계좌를 볼 수도, 입금했다는 기록을 남길 수도 없었다.

## 결정 (사용자 확정 2026-10-14 "모두 권장")
1. **작업마다 스위치 하나** — `tab_configs.advertiser_payout`(+ `_by`·`_at`, migration 189). 기본 꺼짐. 내부 작업보드 › 작업 조건 › **입금 주체**에서 관리자(master/admin)만 바꾼다(`POST /api/trackb/payment/advertiser-payout`).
   - 켤 때 막는 경우: 시트 기반 작업(`not_sheetless` — 입금일 기록 창구가 무시트 전용) · 소유 업체 없음(`no_advertiser`). 끄기는 언제든.
   - 저장은 `advertiserPayout.service` — `payment.service`(M1 본체)는 payment_* 표에만 쓴다는 규율(paymentBatch 회귀가드)을 지킨다.
2. **계좌 세 칸(은행·계좌번호·예금주)** — 그 작업을 **소유한 업체의 대표 링크**에만(`workdeskTab` 업체 분기).
   - 값 = **우리가 입금할 때 쓰는 바로 그 계좌**(`payment.advertiserPayoutAccounts` → `listPaymentTargets` 판정 단일 출처: 결정 157·231·233).
     시트에 처음 적힌 계좌를 따로 읽으면 "고쳤는데 옛 계좌로 이체"(2026-10-13)가 업체 쪽에서 다시 난다.
   - 대상 = **리뷰 제출이 끝났고 아직 입금이 안 된 줄만**(사용자 확정 1번 권장). 입금일을 기록하면 대상에서 빠져 계좌도 가려진다.
   - 차단 목록(`_isAdvertiserRestrictedHeader`)은 **그대로** — 원본 열은 계속 빠지고, 세 칸은 판정 결과로만 채운다.
   - 세 칸은 입금 칸 바로 앞에 둔다(보고 → 보내고 → 기록하는 순서).
   - 줄 번호(seq)에 더해 **명의(phone8)까지** 같을 때만 싣는다 — 장부가 늦은 사이 빈 줄이 재배정되면 남의 계좌가 보이는 것을 막는다.
   - 우리가 이미 이체에 실패한 계좌(결정 231 `failed_account`)는 은행 칸에 "⚠ 이체 실패 이력"을 붙인다.
   - 노출 조건에 무시트 작업(`meta.sheetless`)도 건다. 업체 로그인 계정(아이디·비밀번호)도 대표 링크와 같은 업체 세션이라 함께 보인다.
   - 업체 응답의 `meta` 에서 내부 정산 값(입금명·리뷰비·이체은행·입금 주체)을 뺀다(종전부터 새던 값 — 리뷰에서 발견).
3. **업체 입금일 기록** — 내부와 **같은 창구**(`setWorkdeskDepositDate` · 우클릭 [💰 입금일 기록] 달력). 그래서 리뷰어 페이백 표시·입금완료 수가 똑같이 움직인다.
   - 라우트: 브랜드 링크 세션 403(사용자 확정 3번 권장) · 소유 스코프 `_ensureThreadScope`(송장 편집·스레드와 같은 게이트).
   - 서비스(잠근 행과 **같은 트랜잭션**): ① 스위치 켜짐 ② 우리 이체 회차(pending/paid)에 살아 있는 줄 아님(`our_payout`) ③ 칸에 값이 있으면 **업체가 넣은 값**일 때만 고치거나 지움(`not_own_entry` — 사용자 확정 2번 권장).
   - "업체가 넣은 값" = 활성 편집기록(`participant_edits` col:<입금열>)의 `created_by` 가 **`업체#<그 업체 id>:<이름>`** 으로 시작하고 **지금 칸 값과 같을 때**(업체 id 로 가른다 — 한 작업에 업체가 여럿 연결되거나 이름이 같아도 남의 업체 기록을 고치지 못한다).
   - 새 날짜는 **리뷰 제출이 끝난 줄에만**(`review_not_submitted` — 의무 투영 → 없으면 리뷰 칸 분류, 미작성 종결 줄 제외). 비우기는 막지 않는다.
   - 화면 입금 칸(`findPaymentColumnIndex`)과 서버 기록 칸(`statusHeaderForTab('paid')`)이 다르면 업체 기록 창구를 전부 잠근다(`column_mismatch`).
   - 기록 형식 = 날짜만(사용자 확정 4번 권장) — 종전 입금 칸 표기(`utils/depositStamp`) 그대로.
4. **이중 입금 차단** — 스위치 켠 작업의 입금 대상은 맨 앞 사유 `advertiser_pays`(이체 불가). 입금관리 목록에서는 빼고 `advertiserPaidExcluded` 건수로 한 줄 알린다. `createBatch` 는 `includeAdvertiserPaid:true` 로 다시 계산해 그 사유로 건너뛴다.
   - `createBatch` 는 줄을 잠근(FOR UPDATE) 뒤 **다시** 본다: 그 사이 스위치가 켜졌으면 `advertiser_pays`, 작업표 입금 칸에 이미 날짜가 있으면(업체가 기록했는데 장부 재생성이 밀린 경우) `already_paid` 로 그 건만 건너뛴다.
   - 스위치를 **끌 때** 확인을 받는다 — 입금일이 기록 안 된 줄이 바로 우리 입금 목록으로 돌아오므로(업체가 보냈는데 날짜만 안 적은 줄을 또 보내면 이중 입금). 켤 때는 저장 뒤 계좌가 보이는 업체 이름을 모두 말한다(한 작업에 업체가 여럿일 수 있다).

## Codex 리뷰 반영 (2026-10-14)
- **주인 업체 판정 = `advertiserForTab`(탭 지정 > 시트 전체)** — 계좌 노출·입금 기록 라우트·스위치 저장이 모두 같은 판정. `canAccessTab` 은 시트 전체 소유를 먼저 통과시켜, 탭을 다른 업체로 옮기면 옛 주인에게도 계좌가 보였다.
- **업체 새 날짜 = 입금 대상 줄(계좌가 보이는 줄)만** — 화면은 `no_account` 로 잠그고, 서버는 트랜잭션 앞에서 `advertiserPayoutAccounts` 를 계산해 잠근 행과 명의까지 맞춘다(`not_payout_target` · 계산 실패 `lookup_failed`).
- **스위치 조회는 `FOR SHARE`**(업체 기록·회차 만들기 양쪽) — 스위치 저장(UPDATE)과 직렬화해, 끄는 중에 들어온 업체 기록은 꺼진 값을 보고 거부된다.
- **켰는데 주인 업체가 사라진 작업 = `advertiser_pays_orphan`** — 우리 목록에서 빼지 않고 보류로 남겨 "입금 주체 확인"을 말한다(아무도 못 보내고 조용히 빠지는 막다른 길 방지 · 업체가 이미 보냈을 수 있어 바로 보내지도 않는다).

## ★ 변경 (사용자 요청 2026-10-15) — 「입금 주체」 스위치를 없애고 **이체은행 선택지 「업체입금」**으로
- 사용자: "입금주체를 없애고 모집공고설정에서 이체은행에 자동/하나/케이 + 업체입금 선택지로 작동하게".
- **저장소 = 이체은행 하나** — 모집공고 `recruit_campaigns.transfer_bank='advertiser'` / 탭 설정 `tab_configs.transfer_bank='업체입금'`(탭은 한글 라벨 관례).
  판정 = `payment.advertiserPaysFrom(공고 값, 탭 값)` — **이체은행과 같은 순서**(공고가 하나/케이를 명시하면 탭의 업체입금은 무시), 공고는 대상 계산과 같은 공고(`campaignForTab`/`_loadCampaigns` = 연결 탭의 가장 최근 공고).
  `normalizeBankChoice` 는 그대로 kbank|hana 만 — 업체입금이 이체 파일 은행으로 새지 않게.
- 고르는 곳: 모집공고 설정(세 가지 모양 모두) · 작업 조건 › 이체은행(공고 없는 작업의 탭 설정 창). 작업 조건 카드의 「입금 주체」 행·`POST /payment/advertiser-payout`·`_cndPayerModal` 제거.
- 고를 수 있는 작업 = 시트 없는 연결 작업 + 주인 업체(`advertiserPayout.checkAdvertiserPayoutAllowed`) — 모집공고 생성·수정(업체입금으로 **바꿀 때만**, `ADVERTISER_PAYOUT_NOT_ALLOWED`)과 탭 이체설정(`saveTransferSetting`)이 같은 검사.
- 업체입금에서 다른 값으로 바꿀 때 확인(미기록 줄이 우리 입금 목록으로 돌아온다 — 이중 입금 주의).
- 잠금 안 재확인(업체 기록·회차 만들기) = `payment.advertiserPayoutLocked` — 탭 설정·공고 이체은행을 **FOR SHARE** 로 읽는다(공고 수정·탭 저장과 직렬화).
- 탭 설정 조회 실패(`_loadTabMeta.failed`) = 탭의 업체입금을 모름 → 전 건 `advertiser_payout_unknown`(fail-closed).
- migration 189 의 `tab_configs.advertiser_payout*` 칸은 **쓰지 않는다**(운영 실측 2026-10-15: 켠 작업 0건이라 옮길 데이터 없음 · 칸은 남겨 두고 부팅 필수 목록에서만 뺐다).

## ★★ 완화 금지
- **업체 응답의 계좌 세 칸에 소유 판정(`advOwnsTab`)과 브랜드 세션 제외를 빼지 말 것** — 작업보드 표는 `allowAllWorkdesk` 로 **모든 업체가 열람**한다. 빼면 남의 업체·퍼진 브랜드 링크에 참여자 계좌가 보인다.
- **계좌 값을 원본 시트 열·구매양식에서 따로 읽지 말 것** — `listPaymentTargets` 판정과 갈리면 업체가 옛 계좌로 보낸다(2026-10-13 사고의 재현).
- **업체입금 여부를 모를 때 "우리 입금"으로 접지 말 것** — `_classifyAdvertiserPayout` 실패·탭 설정 조회 실패 = 전 건 `advertiser_payout_unknown`(보류). 업체도 보내고 우리도 보내면 되돌릴 수 없다.
- **`normalizeBankChoice` 가 업체입금을 은행으로 돌려주게 바꾸지 말 것** — 이체 파일 서식 판정이다.
- **업체입금을 따로 저장하는 두 번째 칸(스위치)을 되살리지 말 것** — 이체은행과 갈리면 화면·입금관리·업체 노출이 서로 다른 값을 본다.
- **업체 입금 기록의 세 가지 재확인(스위치·우리 회차·업체가 넣은 값)을 라우트로만 옮기지 말 것** — 잠근 행과 같은 트랜잭션 안이어야 끄기 직후·회차 생성 직후의 경합을 막는다.
- **잠금 재료 조회 실패 시 업체 기록 창구를 여는 쪽으로 바꾸지 말 것**(`lockAll` → 전 줄 `unknown`).
- **업체 기록 소유 판정에서 업체 id 를 빼고 `업체:` 같은 공통 접두어로 되돌리지 말 것** — 여러 업체가 연결된 작업에서 남의 기록을 고친다.
- **`createBatch` 의 잠근 뒤 재확인(스위치·입금 칸)을 빼지 말 것** — 목록 계산과 회차 생성 사이의 경합이 그대로 이중 입금이 된다.
- **계좌 칸을 줄 번호만으로 짝짓지 말 것**(명의 phone8 대조 유지).
- **주인 업체 판정을 `canAccessTab`(소유 범위)로 되돌리지 말 것** — 탭 이관 시 옛 주인에게 계좌가 보인다(`advertiserForTab` 유지).

## 위험 · 남은 것
- ⚠ **업체 링크는 로그인 없이 열린다**(로그인 요구를 다시 켤 수 없게 막혀 있다 — migration 118). 스위치를 켜면 링크를 가진 사람은 대상 줄의 계좌를 본다. 그래서 켜는 창에서 그 사실을 그대로 말한다. 참여자에게 "입금은 업체가 직접 하며 계좌가 업체에 전달된다"는 안내가 필요한지는 운영에서 판단(법률 판단 아님).
- 업체가 입금일을 기록하면 우리 쪽 이체 결과·원장(payment_*)에는 남지 않는다 — 작업표 칸·편집기록·장부 파생(리뷰어 화면)만 바뀐다(우리가 보낸 돈이 아니므로 정상).
