## 최초 동시성 RED 재현 기록 (후속 보강은 아래)
PGlite 단일 연결의 성공을 실 PostgreSQL 경합 증명으로 보지 않고, 자격증명 없는 별도 로컬 PostgreSQL 16.15 클러스터를 만들어 두 연결로 추가 검사했다. 운영 DB/Drive에는 연결하지 않았다.

실제 삭제 서비스의 추가사진 tombstone INSERT SQL을 추출해 다음 순서를 실행했다.
1. 삭제 연결이 트랜잭션을 열고 기존 추가사진의 좌표를 tombstone에 복사한다.
2. 다른 연결이 해당 주문을 `FOR UPDATE`로 잠그고 새 추가사진을 INSERT 후 COMMIT한다.
3. 삭제 연결이 주문을 DELETE 후 COMMIT한다(추가사진 원장은 FK CASCADE).

결과: 기존 사진의 tombstone은 남지만, 2번의 `new-photo-during-delete`는 추가사진 원장에서도 지워지고 tombstone에도 없다. 파일은 남아도 연결 좌표가 소실될 수 있다. 검사 exit 1로 재현했다. 클러스터는 검사 직후 중지했다.

- 재현은 실제 PostgreSQL의 두 연결과 생산 tombstone SQL을 사용하지만, 전체 앱/권한 흐름을 두 연결로 실행한 E2E는 아니다.
- 당시 삭제 전용 advisory lock과 추가사진의 주문별 lock은 같은 열쇠가 아니었다. tombstone 복사와 주문 CASCADE 사이에 새 사진이 들어오는 경로를 막아야 한다.
- 권장안: 기존 lifecycle/업무 잠금 순서를 전수 확인한 뒤 대상 주문을 같은 순서로 잠그고, 좌표 복사 이전에 사진 추가와 직렬화한다. 실제 두 연결로 업로드 선행/삭제 선행을 모두 재검증한다.
- 사용자 「진행해」 승인 후 아래 최소 보강을 적용했다. 운영 배포 승인은 별개다.

## 승인 후 보강·검증 (2026-11-09)
- 레드팀은 주문 행을 먼저 FOR UPDATE로 잠그는 후보가 `tabRename`의 review→order 행 잠금 순서와 새 교착을 만들 수 있음을 지적했다. 블루팀의 동일 범위·별도 statement 조건은 채택하되 조기 주문 행 잠금 후보는 심판 단계에서 거절했다.
- 대신 사진 접수에서 이미 쓰는 `purchase_capture:<UUID>` 트랜잭션 advisory key를 삭제에서도 재사용한다. `utils/purchaseCaptureLock.js`가 정렬·중복 제거·UUID 정규화를 제공하고 core/삭제가 같은 도우미를 호출한다. 기존 원본 제출·직원 교체 키와 호환된다.
- 삭제의 추가사진 조회 범위(직접 작업·확정 dual 주문·연결 공고 좌표)를 한 SQL 조각으로 재사용해 대상 ID를 읽고, ID 순서대로 공통 advisory를 잡은 뒤 별도 INSERT statement로 묘비를 읽는다. 기존 review→order 행 삭제 순서·확인·금융·SAVEPOINT는 바꾸지 않는다. 잠금/새 묘비 오류는 전체 ROLLBACK한다.
- `purchaseCaptureDeleteConcurrency.test.js`: 별도 로컬 PostgreSQL에서 실제 core·전체 삭제 서비스·이름 변경 서비스를 실행했다. 일반/네이버/쿠팡 및 공고 좌표 주문의 추가 선행/삭제 선행/Drive 진행 중 삭제, 이름 변경 겹침, 잠금·묘비 SQL 실패 롤백, 무관 주문 비차단 등 16경우를 통과했다. pg_blocking_pids로 실제 대기를 확인했다. 원래 실패하던 전체 서비스 RED도 보존했다.
- 관련 38개 검사 파일 통과. 테스트 중 생산 소스 3개의 SHA256이 불변임을 확인했다. 로컬 클러스터는 종료했다. 독립 최종 코드 검토도 통과했다(신규 보안/논리 결함 없음). 검토자는 소스를 검토했으며 실제 실행 검증은 부모가 수행했다. opt-in 실제 PG 검사의 CI 상시 실행·다중 주문/묶음 3중 경합 확장은 비차단 후속 제안으로 남겼다. 공고 좌표 주문은 부모의 16경우에 이미 포함되어 있다.
- 이 보강은 COMMIT된 기존 주문의 추가사진 참조를 보호한다. 새 주문 phantom, 전사 잠금의 교착 부재, 원본 묘비의 기존 경합, Drive 완료 후 DB 거절된 미접수 파일 정리까지 해결했다고 주장하지 않는다.
