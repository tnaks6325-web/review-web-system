# ★★ 유입방식도 작업오더 폴백을 본다 — 저장하는 순간 유입가이드가 무력화되던 경로 (2026-08-21)
- **점검 발단**: 작업오더는 `유입방식 : 유입가이드` 인데 모집공고 수정 화면은 `링크유입` 이었다.
- ★★ **인트라넷은 정상이다** — `reviewOrderInflowTypeCode()` 가 `'guide'|'link'` 만 보내고(`inadd-webapp/public/static/js/review-orders.js`), `work_orders.inflow_type` 에도 그대로 저장된다. 작업오더 상세의 `유입가이드` 라벨 자체가 `_INFLOW_LABEL[o.inflow_type]` 에서 나오므로 값이 `'guide'` 라는 증거다.
- ★★ **리뷰어 화면은 이미 폴백을 갖고 있었다** — `GET /:id/work-detail` 과 관리자 미리보기는 `(workDetail && workDetail.inflowType) || (await _lookupInflowType(...))` 로 **연결 작업오더**를 본다. 구멍은 **수정 모달과 관리자 카드 칩 둘뿐**이었다(저장값만 봄).
- ★★★ **그래서 저장이 곧 사고였다** — 모달이 `wd.inflowType === "guide" ? "guide" : "link"` 라 **값이 없으면 무조건 link** 로 열리고, 그대로 저장하면 그 `link` 가 `work_detail` 에 굳어 **리뷰어 화면의 폴백을 이긴다**(`||` 앞이 이긴다) → 가이드유입 공고에 `[🔗 상품 페이지 열기]` 가 노출된다(`campaign-workdetail.js` 가 막으려던 바로 그 사고). **혼합 조합을 고치려고 저장하는 행위가 유입가이드를 무력화**시켰다.
- **수정**: 수정 모달은 **저장값이 없을 때만** 작업오더 값으로 프리필하고 **출처를 문장으로 말한다**(저장해야 굳는다). 저장값이 있으면(`link` 포함) **절대 덮지 않는다** — 사람이 정한 값이다. 관리자 카드 칩도 같은 폴백을 보되 `/admin/list` 가 **배치 1회**(N+1 금지)로 실어 주고, **`work_detail` 을 고쳐 내려보내지 않는다**(별도 필드 `orderInflowType` — 저장 시 굳지 않게).
- ★★ **짝짓기 규칙 사본 0** — 같은 SQL 이 세 벌(단건·배치·`_lookupInflowType`)로 늘어날 참이라 `linkedRecruitQuota` 의 **공유 조각**(`LINKED_WO_ON`/`LINKED_WO_ORDER` + `linkedWorkOrdersForCampaigns`) 한 곳으로 모았다. 정원 폴백·혼합 조합·유입방식이 **같은 작업오더**를 본다. ⚠ 이 통합으로 `_lookupInflowType` 에 **소프트삭제 오더 제외가 추가**된다(종전에는 `deleted_at` 필터가 없어 지워진 오더 값도 썼다) — 레포의 반복 규율과 같은 방향이고, 그 공고의 유입가이드가 있으면 판정은 안전한 쪽(버튼 숨김)으로 떨어진다. ★ 관리자 상세는 혼합 조합·유입방식을 **한 번의 조회**로 가져온다.
- ★★ **혼합 안내가 거짓말하지 않게** — 작업오더 조합 합계가 총건수와 다르면 **저장이 막히는데도**(`validateRecruitReviewTypeMix`) "저장하면 반영됩니다"라고 말했다(실측: 포토 70 + 텍스트 30 = 100건인데 총건수 300건). 이제 `작업오더 조합(합계 100건)이 총건수 300건과 달라 그대로 저장할 수 없습니다 — 총건수에 맞춰 조정해주세요` 로 사실과 다음 행동을 말한다. ★ 합계 불일치 자체는 이미 `.mixed-review-total.is-invalid` 빨간 글씨가 표시하고 있었다(새 경고를 더하지 않는다).
- ★★ **근본 차단은 인트라넷에서 한다 (2026-08-21 · inadd-webapp #377)** — 리뷰웹 접수(`order.routes`)는 여전히 혼합 합계를 검증하지 않는다(`validateReviewTypeMix` 0회). 어긋난 오더가 이미 저장돼 있으면 리뷰웹은 **작업오더를 고칠 수 없어** 그 공고가 영영 저장 불가가 되므로, 값이 태어나는 인트라넷 리뷰오더가 막는다: `reviewOrderReviewMixError` 가 `POST/PUT /api/review-order/source` 에서 400 으로 거부(미전송·형식오류·한 유형·모집인원 0·합계 불일치). ★ **규칙은 리뷰웹 `utils/reviewTypeMix.validateReviewTypeMix` 와 같아야 한다** — 어긋나면 "인트라넷은 통과인데 리뷰웹은 거부"라는 막다른 길이 되살아난다(레포가 갈라져 코드 공유가 불가능하므로 인트라넷 회귀가드가 규칙을 고정한다). ★ **수정(PUT)은 직전 payload 와 병합된 값으로 판정**(본문이 안 보낸 칸은 그대로 리뷰웹으로 간다) · 블로그(`work_kind='blog'`)는 검사 대상 아님 · 옵션별 조합은 인트라넷 화면 전용(서버에서 함께 막으면 옵션 조합이 없던 과거 오더의 제목만 수정까지 거부된다) · **재전송(retry)은 이미 저장된 payload 를 다시 보내는 경로라 게이트를 걸지 않았다**(걸면 전송 실패한 정상 오더가 영영 전달되지 않는다).
- ⚠ **이 배포 이전에 저장된 어긋난 오더는 그대로 남는다** — 그 오더를 인트라넷에서 수정하려면 조합을 먼저 바로잡아야 하고(화면·서버 둘 다 막는다), 리뷰웹 발행 화면은 종전대로 `작업오더 조합(합계 N건)이 총건수 M건과 달라 그대로 저장할 수 없습니다` 로 안내한다.
