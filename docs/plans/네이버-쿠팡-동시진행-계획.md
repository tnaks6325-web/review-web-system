## 1. 사용자 요구 (원문 그대로 · 2026-11-05)

> 네이버/쿠팡 동시진행하는게 있어.
> 1개상품의 작업이지만 동일상품을 네이버에서도 쿠팡에서도 구매하고 동시에 제출해야하는 건이야
> 이때 조건은 참여계정정보가 하나로 통일(배송지까지)인 상태여야해
> Ex)네이버 A배송지 쿠팡 B배송지 사용불가
> 표기상 다를순 있어도 동일주소지여야해.
>
> 인트라넷 리뷰오더에서부터 설정을 이렇게 할수 있어야하고 구매과정도 그렇게 가능해야해.
> 구매캡쳐도 네이버와 쿠팡 각각의 캡쳐본을 동시에 제출해야하고
> 리뷰를 제출할때에도 네이버와 쿠팡의 리뷰를 각각 제출해야해.
>
> 결제금액은 네이버 9,900원 쿠팡 9,900원으로 동일하다면 페이백도 19,800원으로 나가야하지.
> 예를들어 네이버 9000원 쿠팡 10000원 이라면 19,000원으로 합해서 관리되어야하고.
>
> 대신, 작업보드의 표에는 1명당 2행이 아닌 1행만 표기되어야해.
>
> 네이버 링크유입 / 쿠팡 가이드유입 이라면 각각의 가이드를 설정/편집 할 수 있어야하고.

### 요구를 정리하면
| # | 요구 |
|---|---|
| R1 | 인트라넷 리뷰오더에서 「네이버+쿠팡 동시진행」을 설정한다 |
| R2 | 한 상품을 한 사람이 네이버·쿠팡 **둘 다** 구매한다(모집 인원은 사람 수 — 두 배가 되면 안 됨) |
| R3 | 두 주문의 참여 계정 정보(받는 사람·연락처·**배송지**)가 같아야 한다 — 표기는 달라도 같은 곳이면 OK, 다른 곳이면 **사용 불가** |
| R4 | 구매캡처 2장(네이버·쿠팡)을 **동시에** 제출 |
| R5 | 리뷰도 네이버 리뷰·쿠팡 리뷰를 **각각** 제출 |
| R6 | 페이백 = 두 결제금액의 **합계**(9,900+9,900=19,800 / 9,000+10,000=19,000) |
| R7 | 작업보드 표는 **1명당 1행** |
| R8 | 구매처마다 유입방식(링크/가이드)과 가이드를 **따로** 설정·편집(예: 네이버 링크유입 + 쿠팡 가이드유입) |

## 2. 사용자에게 보여 준 계획 (쉬운 말 — 아래 안전 진행안으로 착수 승인)

### 바뀌는 모습
1. **인트라넷 리뷰오더**: 구매채널에 「네이버+쿠팡 동시진행」. 상품 칸 안에 **네이버 줄 / 쿠팡 줄** — 줄마다 상품 주소·결제금액·유입방식(링크/가이드)·가이드. 모집 인원은 사람 수 그대로, 총 상품구입비 = (네이버+쿠팡 금액) × 인원.
2. **리뷰웹 공고**: 같은 설정을 편집할 수 있고, 양쪽이 서로 맞춰진다(양방향).
3. **리뷰어 화면**: 신청은 한 번. 네이버 칸(링크유입이면 [링크 열기] 버튼)·쿠팡 칸(가이드유입이면 가이드 글)이 함께 보인다.
4. **구매양식**: 카드 2장(네이버·쿠팡)을 **한 번에** 낸다. 주문번호·결제금액·구매캡처는 각각. 두 카드의 받는 사람·연락처·배송지가 같은 곳인지 확인 — 다르면 접수 안 함. 금액 검사도 구매처별(쿠팡은 쿠팡 기준, 네이버는 네이버 기준).
5. **작업보드**: 1명당 1줄. 네이버 주문번호·쿠팡 주문번호를 한 줄에, 결제금액은 **합계**.
6. **페이백**: 합계로 나간다.
7. **리뷰 제출**: 「네이버 리뷰」「쿠팡 리뷰」 두 칸 — 둘 다 내야 제출완료.

### 진행 순서 (한 단계씩 · 각 단계 전 사전 충돌 점검 보고)
| 단계 | 내용 | 운영 영향 |
|---|---|---|
| ① | 리뷰웹: 구매처별 칸 저장 + 공고 편집 화면 | 화면 변경 → 로컬 전·후 캡처 + "좋다" 후 반영 |
| ② | 리뷰웹: 리뷰어 화면에 구매처 두 칸 표시 | 화면 변경 → 시안 후 반영 |
| ③ | 리뷰웹: 구매양식 두 장 동시 제출 · 같은 주소 확인 · 작업보드 1줄 · 합계 페이백 | **돈이 걸린 단계** — 레드·블루·심판 검토 |
| ④ | 리뷰웹: 리뷰 두 칸 제출 | |
| ⑤ | 인트라넷 리뷰오더 설정 + 양방향 맞춤 | 화면 변경 → 시안 후 반영 |
| ⑥ | 내 컴퓨터에서 두 시스템 실테스트(가짜 데이터) | 운영 무접촉 |

- 동시진행을 켜지 않은 기존 공고·오더는 **하나도 바뀌지 않게 하는 것이 목표**다(새 칸이 없으면 종전 동작). **「배포 순서 무관」은 철회한다** — 코드 점검상 리뷰웹의 받기·보존·비교를 먼저 준비해야 하며, 새 기능은 양쪽 지원과 전체 흐름 시험이 끝나기 전 활성화하지 않는 안을 제안한다. 아직 보장되거나 승인된 동작이 아니다.
- 규모: 결정 333(상품마다 유입방식, 4단계)보다 2~3배.

## 4. 조사 결과 (개발자용 — 경로는 2026-11-05 main 기준)
리뷰웹 = `~/dev/wt/rw-dualchannel`(main 955607b4 시점), 인트라넷 = `~/dev/wt/inadd-dualchannel`(main e0ef5b3c 시점). 줄 번호는 그 시점 기준이라 새 세션은 다시 확인할 것.

### 4-1. 가장 큰 제약 — "한 사람 = 한 신청 = 한 주문 = 한 줄 = 금액 하나"
- 신청: 상품이 있으면 `optionKey` 정확히 1개 필수(`campaign.routes.js:2279-2300`) · 활성 홀드 공고+phone8 유일(`127_blog_approval.sql:60-62`) · `campaign_applications.option_key` 단일 TEXT(061) · `order_submission_id` 단일 UUID(045:24).
- 홀드 게이트: 홀드에 살아 있는 주문이 있으면 두 번째 POST 는 `alreadySubmitted`(`submit.routes.js:556-623, 879-893`) → **두 번째 카드를 별도 주문으로 넣는 길은 막혀 있다.**
- 작업보드 줄: `campaign_participants` 1행 = `order_submission_id` 1개. 두 번째 주문을 같은 줄에 쓰면 링크를 빼앗는다(`sheetlessOrder.service.js` ~887-893 · `requireEmptyOrSame` 654-659). 줄에 안 묶인 홀드 주문은 복구 작업이 **새 줄을 만든다**(`recoverUnwrittenSheetlessOrders` 1144-1187).
- 헤더 매핑: '금액' 포함 헤더 전부에 `orderData.price`, '주문번호' 포함 헤더 전부에 `orderNum`(`orderLedger.service.js:296,298`) → 「네이버 주문번호」「쿠팡 주문번호」 칸이 같은 값을 받는다. ID 칸은 하나일 때만 채움(247-250, 290 · 256-258 은 NC 탭 두 ID 칸을 둘 다 비운다고 명시).
- 작업보드 표시·편집 기준 주문 1개(`trackB.service.js:85, 3836-3844, 4083, 4151-4157`).
- **권장 저장 모양(조사 에이전트 결론)**: 홀드 1개 = `order_submissions` 1행(price = **합계**) + 쿠팡 쪽을 그 행의 추가 칸(`coupang_order_num`·`coupang_price`·`coupang_capture_file_id`·쿠팡 수령인/연락처/주소 등)으로. 전용 헤더로 매핑해 일반 '금액'·'주문번호' 규칙이 건너뛰게. → 위 "한 주문" 불변식을 하나도 안 깬다.
  - 대안(홀드당 주문 2행)은 홀드 게이트·단일 링크·복구 작업과 충돌.

### 4-2. 페이백
- 지급 항목은 줄당 1개(`payment_batch_items` (sheet_id, tab_name, row_index) 활성 유일 · 086:49-81).
- 상품비 = 작업보드 금액 우선(`payment.service.js:484-493` · `paymentWorkboardAmount.service.js:27-38` · `utils/paymentAmount.js:20-37` — 결제금액/결제금/금액/결제 **정확히 일치** 먼저, 다음 '금액' 포함 첫 헤더).
  - → 「결제금액」 칸과 `order_submissions.price`를 합계로 유지하면 기존 지급 경로를 재사용할 수 있는 후보이다. **지급 코드 무변경은 미확정**이다. 「네이버 금액」「쿠팡 금액」 칸 선택, 직원의 금액 수정, 두 리뷰 제출 전후 지급 가능 여부까지 실제 시험한 뒤 판단한다.
  - `order_submissions.price` 에 네이버 금액만 두면 `priceMismatch`(493)가 모든 줄에서 뜬다.

## 7. ①단계 구현 전 영향 점검 — 코드 확인 완료, 안전 진행안 착수 승인

기준: 리뷰웹 HEAD `955607b4`(점검 착수 시 `origin/main`과 일치). 병렬 읽기 전용 조사 두 건을 합쳤으며, 부모 작업자가 아래 핵심 위험 코드를 직접 다시 읽었다. 관련 제품 파일 목록은 중복 제거 51개이고 경로 존재를 프로그램으로 확인했다. **51개 모두 수정한다는 뜻은 아니다.** 실행 시험·운영 조회·기능 구현·푸시·PR·배포는 하지 않았다. 계획 문서의 답변·조사 상태만 갱신했다.

### 확인된 충돌과 설계 주의점

1. **상품을 네이버·쿠팡 두 선택지로 만들면 안 된다.** 참여는 선택지 하나만 고르는 구조이고 같은 이름의 두 번째 줄은 버려진다(`server/src/routes/campaign.routes.js:239-295,2279-2301`). 상품·모집 인원은 하나로 유지하고 그 안에 고정 구매처 하위 설정을 두는 안을 권장한다. `channels.naver`/`channels.coupang` 같은 모양은 설계 후보이며 확정하지 않았다.
2. **옵션 없는 단일 상품에는 선택지 줄이 없을 수 있다.** `campaign_options`의 새 칸만 추가하는 설계로 끝내지 않는다(`frontend/js/index-recruit.js:2389-2418,3190-3192`; `server/src/utils/woCampaignPrefill.generated.js:221-232`). 줄 유무와 무관한 저장 위치를 설계해야 한다.
3. **공유 저장·발행·대조·옛 화면 보호를 함께 확장해야 한다.** 상품 하위 객체는 현재 통째로 비교하고(`server/src/utils/sharedPatchPlan.js:89-92`), 상품 목록에 빠진 키는 삭제로 판정한다(`:132-145`). `channels`를 허용목록에 더하기만 해서는 실제 적용·공고 투영이 완성되지 않는다. 기존 옛 화면 보존은 `inflow_type` 전용이다(`server/src/utils/unitInflow.js:56-74`). 새 기능 지원 표시와 미전송 값 보존을 별도로 설계한다. 프리필은 원본 `frontend/js/work-order-detail.js`를 수정한 뒤 생성기를 사용하며 서버 사본을 손수 고치지 않는다.
4. **저장부터 허용해도 곧바로 모집을 열면 위험하다.** 현재 신규 공고는 본체 저장 후 상품조건 저장 실패를 경고로 처리한다(`server/src/routes/campaign.routes.js:3627-3648`). 두 구매처 조건을 모두 저장하지 못한 동시진행 공고가 모집중으로 남는 길은 별도 방어가 필요하다.
5. **운영 작업에 연결한 임시저장도 안전하지 않다.** 리뷰 기대 구매처는 상태·보관 여부를 거르지 않고 연결 탭의 최신 공고에서 읽는다(`server/src/services/reviewInspect.service.js:848-870`). 초안 하나가 기존 리뷰 검사에 영향을 줄 수 있으므로 기존 운영 작업에 붙여 시험하지 않는다. 숨김 표시만으로 격리를 대신하지 않는다.
6. **옛 NC 제출 경로는 재사용하지 않는다.** 두 카드를 따로 제출하고 주소가 달라도 이름·전화 일치로 통과하는 갈래가 있어 이번 원문 요구와 맞지 않는다(`frontend/js/search-app.js:6034-6058,6095-6119,9281-9367`). 외형·안내문만 참고 후보이다. 기존 구매캡처 두 장은 같은 주문의 주사진·보충사진이므로 쿠팡 주문 사진으로 임의 전용하지 않는다(결정 288).
7. **주소 AI 오류를 다른 주소로 단정하는 경로를 분리해야 한다.** AI 응답을 읽지 못하면 현재 `ok:true, isSamePerson:false`가 되고(`server/src/services/gemini.service.js:524-540`), 호출부는 이를 불일치로 바꾼다(`server/src/services/identity.service.js:147-153`). 이번 확정 정책은 판정불가 접수+직원확인이므로 그대로 연결하면 안 된다. 비교 대상은 두 주문 사이 정보이며, 등록 프로필 주소와 같아야 한다는 추가 제한으로 넓히지 않는다(결정 219).
8. **금액·주문번호 전용 기록이 필요하다.** 현재 '금액'이 들어간 모든 칸에는 같은 금액, '주문번호'가 들어간 모든 칸에는 같은 번호를 쓴다(`server/src/services/orderLedger.service.js:296-298`). 열 이름만 늘리지 않고 각각의 실제값과 합계를 나눠 기록해야 한다. 기존 지급 경로 재사용 가능 여부는 실제 시험 전까지 미확정이다.

### 안전하게 재사용할 후보와 미검증

- 기존 공유 저장의 버전·잠금·트랜잭션·실패 시 되돌림을 확장한다. 새 직접 쓰기 경로를 만들지 않는다.
- 기존 유입방식 정규화·가이드 검사·리뷰 슬롯 완료 판정·한 줄 지급 구조를 재사용 후보로 삼는다. 현재 코드에 있다는 사실과 동시진행에서도 실행 통과했다는 것은 다르다.
- **기존 자동검사 통과 여부, 실제 화면·DB 저장·동시 편집·AI 정확도·지급 결과·두 시스템 왕복·배포 시차는 전부 미검증**이다. 구현 승인 뒤 격리된 로컬 가짜 데이터로 검증한다.
