# 업체 작업 링크·홈 첨부·담당자·알림·수정권한 개선

## 승인과 현재 단계

2026-11-05~06 사용자 요청 다섯 가지와 선택 답변을 보존한다. 1번 작업별 업체 링크와 3번 홈 첨부의 시안을 검증·전달했고, 사용자 **“좋다”**로 시각 승인을 받았다. 실제 구현·격리 전체 검사·독립 검토·PR #1774 미리보기 전달 후 사용자가 **“확인했어 운영에 반영해”**로 실제 화면 확인과 두 기능의 운영 반영을 승인했다. 현재는 정확한 머지·운영 배포를 확인하는 단계다. 나머지 세 요구나 실제 알림 발송의 승인이 아니다.

- 업체 링크: 해당 작업부터 열며 같은 업체의 다른 작업 열람은 유지한다.
- 담당자: 기존 버튼 방식(C스타일)을 유지하고 블로그 작업에 `기타`를 지원한다. 빈 값·랜덤으로 숨기지 않는다.
- 홈 첨부: 입금관리로 이동하지 않고 홈에서 결과 파일을 선택/놓는다.
- 알림: 사이트 알림함과 카카오 알림톡. 당일 예정 인원 구매 완료, 전체 작업 리뷰 제출 완료, 리뷰어 본인 취소, 품절, 상품 금액 변경을 구분한다.
- 수정권한: 인트라넷과 리뷰웹이 같아야 하며 진행 자료 보호용 기존 잠금을 유지한다.

### 2026-11-06 추가 답변 — 취소된 이전 질문보다 우선

1. **1.A**: 작업별 링크·홈 첨부 시안부터 진행한다. 기타·수정권한은 양쪽을 함께 보완하며 기존 알림 개발본은 재사용한다.
2. **2.B**: 리뷰비와 **리뷰어 통장표시 및 인트라넷 업체입금명 둘 다** 만두·망고 수정 전용이다. 서로 다른 두 입금명 값이나 지급방식을 하나로 합치지 않는다. 이름/별명만으로 권한을 증명하거나 admin/master 예외를 임의 추가하지 않는다.
3. **3.B**: 첫 유효 품절·가격 신고는 `의심`으로 알린다. 실제 조치·조건 변경이 반영되면 별도로 알린다. 신고를 확정 사실처럼 표현하지 않는다. 기존 직원 공통 경고를 없애지 않는다.

### 시각 승인 후 실제 연결 착수

- 사용자 `좋다`는 전달한 작업별 업체 링크·홈 첨부 시안의 승인이다. 기존 선택 1A·2B·3B를 유지하며 다시 묻지 않는다.
- 최신 `origin/main`을 다시 받아 현재 작업 기준 `955607b42135db7944331ae40faf970eb2f5b8fb`과 차이 없음, 작업 브랜치 및 기존 시안·증거 파일 보존을 확인했다.
- 실제 앱 수정 전에 두 독립 읽기 전용 점검을 시작했다. 하나는 광고주 접속 열쇠·작업 지정·소유권·기존 공유의 전체 소비처, 다른 하나는 특정 홈 카드의 은행 결과 반영·다른 대량이체 거부·입금관리 전체 로딩 부작용 분리다. 부모만 공용 화면 파일을 수정한다.
- 기존 보호 검사 세 파일을 다시 실행했고 모두 종료0이다. 실제 소켓·HTTP·fetch·PostgreSQL 연결을 차단하고 운영 자격을 상속하지 않은 로컬 가짜 자료 검사다. 새 기능의 RED/GREEN·저장·전체 검사 완료로 확대하지 않는다.
- 사전 점검 결과를 보고한 뒤 원인별 실패 시험부터 구현한다. 실제 기능 미리보기는 별도로 사용자 확인을 받으며, 실제 알림 발송 활성화는 계속 금지한다.

### 실제 연결 중간 기록 — 전체 완료 아님

- 작업별 업체 링크: 기존 대표 주소는 유지하고 작업 좌표만 추가한다. 접속 열쇠 보존, 소유 목록 안의 작업만 선택, 명시 작업 우선, 조회 실패와 대상 없음 구분, 로그아웃 시 예약 초기화, 홈 버튼과 기존 직원 공유 분리를 구현했다. 관련 7개 집중 스크립트는 모두 종료0이다.
- 홈 첨부: 부모는 화면·파일 선택/드롭·조회 연결을 수정한다. 서버 새 입구와 전용 처리 모듈은 파일 소유권을 나눠 위임했다. 다른 작업폴더는 수정하지 않는다. 설계 심판의 조건부 통과는 실행 통과가 아니다.
- 화면 연결 검사는 기존 카드에 첨부가 없는 실패를 먼저 확인하고 수정했다. 파일 선택 전 회차 고정, 여러 파일 거절, 입금관리 전체 로더 미호출, 저장 후 재조회 전달, 늦게 도착한 이전 로그인 응답 폐기를 포함한 8개가 통과했다. 실제 앱 컴포넌트를 브라우저에서 누른 검사는 아래 별도로 기록한다.
- 목록 조회 실패는 기존 질문을 보존하고 `확인 불가`를 명시한다. 일반 홈 초기화를 예외로 끊지 않으면서 `{ok:false}`를 반환하도록 별도 실패를 재현했다. 전용 모듈의 이 반환값 처리 누락도 추가 실패 후 수정했고, 금융 결과를 유지한 채 목록 갱신 경고를 표시한다.
- 이전 입금 성공 후 질문 갱신만 실패한 경우, 같은 파일 재첨부에서 `pending===0`이어도 질문을 다시 계산해야 한다. 서버 위임에 반례를 포함했다. 금융 기록을 재등록하거나 질문을 강제로 완료 처리하지 않는다.
- 기존 전송 위치 검사 실패는 실제 공통 전송 함수와 모듈을 실행해 종전 범용 POST 주소·본문·1회 호출을 검증하도록 강화했다. 목록 갱신의 `{ok:false}`를 놓치는 경우와 다른 이체 파일 거절을 설명하지 못하는 경우도 실제 실패 후 수정했다. 현재 전용 처리 모듈 21개·서버 입구 15개·화면 연결 8개가 통과한다. 담당자 질문·작업표 빈 줄 질문까지 포함한 부모 집중 14개 스크립트가 모두 종료0이다. 전체 검사 통과는 아니다.
- 실제 앱의 확인카드·하단 창·결과창을 HTTP 로컬 서버에서 실행했다. Chromium/WebKit, PC 1440·휴대폰 390의 총 32개 검사 통과, 페이지 오류0이다. 실제 파일 선택창과 FileReader를 거쳐 정확한 홈 회차 URL 1회 전송·기존 입금관리 로더 미호출·계좌 원문 미보관/미표시·목록 갱신 실패 시 결과 보존·중복 보류를 확인했다. API 응답은 명시적 가짜 자료이며 운영 인증·은행 파일 해석·실제 SQL·전체 홈 화면 검증이 아니다. 외부 요청 12개는 브라우저에서 전부 차단했다.
- 휴대폰 결과 제목의 은행명이 두 줄로 쪼개지는 문제를 글자 Range 측정으로 실패 재현하고, 새 홈 결과창에만 적용되는 스타일로 수정했다. 두 엔진 재측정과 전후 캡처는 `docs/reports/client-workflow-20261106/app-home/`에 보존했다. 운영 배포본 정렬 확인으로 보고하지 않는다.
- 실제 금융 처리기+PGlite 격리 SQL 보존7개를 부모도 재실행해 통과했다. 같은 파일 재첨부 추가 입금0·기존 paid 상태/잠금·파일 실패/누락 실패·증빙 잠금·후행 리뷰 거절 시 앞선 입금 롤백을 확인했다. 방어만 뺀 메모리 사본은 원장2건을 저장해 실패했다. 단일 연결 직렬화/좁은 advisory 대체이며 작업보드·안내는 격리했으므로 실제 PostgreSQL 여러 연결 경합·운영 입금·외부 발송으로 확대하지 않는다.
- 업체 작업 진입도 실제 앱의 홈 표14열·복사 버튼·boot·업체 작업 렌더러·다른 작업으로 돌아가는 버튼/행 클릭을 두 엔진 × 두 폭의28개 로컬 검사로 확인했다. 휴대폰의 숨겨진 옆 목록 때문에 이동이 막히는 실패를 재현해 기존 전체 작업 목록을 여는 버튼만 추가했다. 인증/API/클립보드는 가짜다. 전체 홈 모든 메뉴·운영 인증 검증은 아니다.
- 이후 최신 main `b2f78871d843d56f2d7c18c1f80b1ee0c36df2ce`를 안전하게 반영했다. 이 작업의 제품3파일은 반영 전후 바이트가 같았고 뒤처짐0이었다. 전체 검사는703개 파일 모두 통과(0실패·296.1초)했다. 수정 전701개 중2개가 실패한 기록도 보존하며, 두 검사 모두 기존 보호 의미를 유지한 채500자 제한 제거·실제 의존성과 승인된14열로 맞췄다.
- 최초 전체 독립 검토는18개 파일을 읽고 보안/논리 오류 없이 통과했다(`deleg_e4ad6fd6`). 이후 휴대폰 이동 버튼과 검사2개의 추가분도 독립 검토 통과, 보안/논리 오류0이다(`deleg_bc31f33e`, 원문 수신 완료). 로그아웃 추출 정규식이 인접 함수까지 포함하는 비차단 개선 제안은 남겼다. 현재 두 정리문은 실제 로그아웃 안에 있어 현재 보호 의미는 유지되며, 후보를 불필요하게 바꾸지 않는다. 실제 PR 미리보기 승인·머지·배포와 별개이며 실제 알림 발송은 계속 미활성화다.

## 순서와 경계

1. 기존 모양을 재사용한 1·3번 동작 시안 → PC/휴대폰 검증 → 사용자 시각 확인.
2. 승인된 시안의 실제 앱 구현: 원인별 실패 시험 → 최소 수정 → 집중/전체 검사 → 독립 검토 → 안전한 테스트 미리보기 확인. 실제 저장과 단순 시안 동작을 구분한다.
3. 기타 정식 값의 양방향 지원과 전체 화면 표시·재저장·질문 재발 방지. 원본 연결은 공유 저장, 원본 없는 작업은 기존 빈 탭칸 저장 규칙을 유지한다.
4. 실제 계정 식별자·모든 쓰기 입구를 확인한 뒤 수정권한을 통일한다. 원본 작성자와 실제 편집자를 혼동하지 않는다. 동일값 재전송으로 일반 저장을 막거나 과거 참여·이체 기록을 바꾸지 않는다.
5. 기존 알림 작업의 최신 통합·검증을 확인하고 재사용한다. 새 품절/가격 의심 및 실제 반영 사건은 중복·수신권한·문안·설정 세대를 검증한다. 실제 수집/발송 활성화·템플릿 변경·고객 발송은 별도 승인 사항이다.

## 조사 근거와 재사용 주의

- 최초 조사 RW `eb7f1ffa`, 인트라넷 `5b9180f5`. 2026-11-06 시안 기준 RW `955607b4`로 최신화했다. 최근 가격 신고·블랙리스트·리뷰어 내역 변경은 보존한다.
- `resolveWorkManager`: 실제 호출 4줄/3파일. `기타` 오더+옛 탭 `망고`가 망고로 표시되는 현재 동작을 가짜 자료로 재현했다.
- 기존 `_consumeGo`는 주소의 광고주 접속 부분을 지운다. 해당 기능을 그대로 합쳐 기존 공유·새로고침 계약을 깨뜨리지 않는다.
- 기존 `_pmUploadResultAny`는 `_pmLoad`를 호출하고 다른 회차의 과거 입금일 보완까지 실행할 수 있다(실제 기존 함수를 가짜 자료로 재현). 서버의 파일 해석·대조·반영은 재사용하되 홈의 완료 갱신과 입금관리 전체 로딩을 분리한다.
- 기존 관련 검사 3파일은 최초 조사 기준에서 통과했다. 새 요청 구현이나 새 기준 전체 검사 통과로 확대하지 않는다.
- 담당자·권한 감사는 정적 조사이며 계정 대응·모든 소비처 분류·운영 저장은 미검증이다.
- 알림은 다른 작업폴더에서 3종을 개발 중이다. 이 작업에서 그 폴더를 수정/실행/배포하지 않는다. 현재 main의 migration 214와 미공개 알림 번호의 충돌도 해당 작업 통합 때 다시 확인해야 한다.

## 시안 완료 조건

- `시안 · 실제 앱 미적용`과 가짜 자료임을 명시한다. 실제 고객/계좌/접속 열쇠를 사용하지 않는다.
- 작업 링크가 선택한 작업을 열고 같은 업체의 나머지 작업도 열 수 있다. 직원 세션을 주소에 넣지 않는다.
- 시안 전용 결과 파일로만 선택·끌어놓기·다른 파일 거절·중복 방지·완료 갱신을 확인한다. 실제 은행 파일 해석/반영을 했다고 보고하지 않는다.
- PC 1440과 휴대폰 390 너비에서 페이지 오류·문서 가로 넘침·가려진 동작 버튼을 검사한다. 실제 http 주소로 검증하고 전후 캡처를 보존한다.
- 운영 앱·입금·사진·담당자 배정·알림 발송은 변경하지 않는다.
