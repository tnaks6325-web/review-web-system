# 구글 시트 API 쿼터 사고 분석 및 DB(SQL) 이관 근거 보고서

> 작성: 2026-06-25 · 대상 시스템: 리뷰 관리 시스템(Node.js Express + PostgreSQL, 구글 Sheets 연동)
> 근거: 운영 DB `error_logs` / `sync_queue` / `slot_locks` 직접 조회 + 문제 시트 실측
> 사고 시트: `1JqV25Q1VtkhvY_A8gCrTA22ZrQRkIR9TvbZpqMe0ZKI` / 탭 `6/25(공영쇼핑)시크릿에이지_선크림+아이크림 200건`

---

## 1. 한 줄 요약

**구매·리뷰 제출이 매 건 구글 시트를 "읽어서 빈 행을 찾는" 구조라, 아침 동시 제출이 몰리면 구글 Sheets API의 분당 읽기 쿼터가 고갈된다.** 쿼터가 막히면 시트 쓰기가 15초 타임아웃 → 백그라운드 큐 적체 → 같은 빈 행 경합 → **중복 행 증식(실측 14.6%)** 과 **리뷰폼 이름 지연 → 재제출**로 이어진다. 이 병목은 코드 튜닝으로 완화는 되나 **근본 제거는 시트 의존을 끊고 DB(SQL)를 1차 원장으로 삼아야 가능**하다.

## 3. 쿼터 오류 3종 — 무엇이, 왜

운영 `error_logs`에서 확인된 실제 메시지와 누적 횟수.

### 3-1. 읽기 쿼터 초과 — `Quota exceeded for quota metric 'Read requests'`
- **누적 24회** (시스템 14 + 구매양식 9 + 리뷰제출 1), 6/25 06:37~06:57 집중.
- 구글 Sheets API v4 **기본 한도**: 프로젝트당 **읽기 300회/분**, 사용자당 60회/분(쓰기도 동일). 초과 시 HTTP 429 + `RESOURCE_EXHAUSTED`.
- **왜 터지나**: 제출 1건마다 빈 행을 찾으려 탭 전체(`A1:ZZ500`)를 읽는다. 아침 홈쇼핑 오픈(06:30~) 동시 제출 N건이 각자 수 회씩 읽기를 일으켜 **분당 300회 한도를 순식간에 소진**.

### 3-2. 자원 고갈 — `Resource has been exhausted (e.g. check quota)`
- **누적 8회**, 6/25 06:52 동시 발생.
- 위 읽기 쿼터 초과의 또 다른 표현. 쿼터가 바닥나 **API가 아예 요청을 거부**하는 상태. 이 시점엔 읽기뿐 아니라 쓰기·후속 호출까지 연쇄 실패.

### 3-3. SA 저장공간 쿼터 — `Service Accounts do not have storage quota` (403)
- **누적 1회**(6/25 03:15), 같은 시트의 이미지 업로드 경로.
- 성격이 다른 쿼터: 서비스계정(SA)은 **Drive 저장 용량이 0**이라 SA로 파일을 만들면 403. (OAuth 위임/공유드라이브 필요 — 이미 코드에 OAuth 우선 폴백이 있으나 이 건은 SA로 샘.)

## 4. 결과 사슬 — 쿼터 한 번이 부른 연쇄

```
아침 동시 제출 폭주(홈쇼핑 06:30~)
   │
   ▼  탭 전체 읽기 × N건 동시
구글 Sheets API 분당 읽기 한도(300/분) 고갈
   │  → 429 Quota exceeded / Resource exhausted   [실측 quota 32회]
   ▼
빈행 탐색 읽기 실패 → 시트 쓰기 15초 타임아웃        [실측 timeout: 구매58 + 리뷰63]
   │
   ▼  DB엔 저장됐으나 시트 반영은 백그라운드 큐로 밀림
sync_queue 적체 (중복 차단 없던 경로)
   │
   ▼  3분 캐시 기반 빈행 스캔이 동시 요청에서 같은 행 선택
같은 빈 행(예: 58번) 경합·덮어쓰기                    [실측 "동시 제출 감지" 276회]
   │
   ├─▶ 시트에 중복 행 증식                            [실측 29행 / 199행 = 14.6%]
   │
   ▼  시트 반영 지연 → 리뷰제출 폼에 본인 이름 안 뜸
사용자가 "실패한 줄 알고" 재제출 (2~3회)             [카톡 다발]
   │
   ▼  중복 행 더 증가 → 관리자 수동 삭제 시 캐시·인덱스 충돌
운영 렉 / 데이터 신뢰도 저하
```

**핵심**: 쿼터 고갈은 단일 오류가 아니라 **타임아웃 → 큐 적체 → 행 경합 → 중복 → 재제출 → 렉**의 출발점이다. 즉 이번 사고의 거의 모든 증상이 "시트를 읽어야만 동작하는 구조" 한 곳에서 파생됐다.

## 5. 왜 코드 튜닝만으로는 한계인가

이미 적용/가능한 완화책과 그 한계:

| 완화책 | 효과 | 한계 |
|---|---|---|
| 3분 탭 데이터 캐시 | 읽기 횟수 감소 | 캐시가 stale일 때 **같은 빈 행 경합**(58번행 문제) 유발 |
| 15초 타임아웃 + 큐 재시도 | 사용자 대기 제거 | 쿼터가 풀릴 때까지 **반영 지연**은 그대로, 큐 적체 |
| 지수 백오프(큐) | 쿼터 회복 대기 | 처리량 자체가 **시트 API 한도에 묶임** |
| 행 점유 락(이번 PR #116) | 중복·덮어쓰기 제거 | 여전히 **빈행 후보를 시트에서 읽어야** 함 |

→ 모두 "시트 API를 덜·늦게 쓰자"는 우회일 뿐, **분당 한도라는 천장**은 그대로 남는다. 동시 사용자가 늘수록 같은 사고가 재발한다.

## 6. 근본 해법 — DB(SQL)를 1차 원장으로

**현재**: 시트가 원본 → 제출마다 시트를 읽고/쓴다 → 쿼터·동시성·지연이 시트 API에 종속.
**전환 후**: PostgreSQL이 원본(원장) → 제출은 **DB 트랜잭션**으로 즉시 확정 → 시트는 **표시·백업용으로 비동기 단방향 미러링**.

### 6-1. 쿼터 문제 소멸
- 빈 행 탐색·중복 검사·이름 조회가 전부 **DB 쿼리**로 바뀌어 **구글 읽기 쿼터를 소비하지 않는다.** 분당 300회 천장이 사라진다.
- 시트 반영은 큐가 **묶음(batch)** 으로 한가할 때 쓰므로 쓰기 호출도 급감.

### 6-2. 동시성·중복 근본 해결
- "다음 빈 행"을 `INSERT ... RETURNING` / 시퀀스 / 유니크 제약으로 **원자적으로** 배정 → 58번행 경합 불가.
- 주문번호 유니크 제약 → **중복 행 구조적으로 불가**(이번 PR의 `sheet_row_claims`가 이 방향의 1차 적용).

### 6-3. 즉시성
- 제출 즉시 DB 확정이므로 리뷰폼 이름 조회가 **지연 0** → "이름 안 떠서 재제출"의 방아쇠 제거(이번 PR의 ⓒ가 1차 적용).

### 6-4. 추가 이점
- 트랜잭션·정합성, 인덱스 기반 빠른 검색, 감사 로그, 백업/복구 용이, 비용·외부 의존 감소.

## 7. 이관 전략 (점진적·비파괴)

한 번에 끊지 않고 단계적으로:

1. **DB 우선·시트 미러(현재 진행형)** — 제출은 DB에 즉시 확정(이미 `order_submissions`), 시트는 비동기 미러. 빈행/중복/이름 조회를 **시트 읽기 → DB 쿼리로 교체**(읽기 쿼터 제거의 핵심).
2. **행 번호 배정을 DB로** — 시트의 "빈 행 찾기"를 DB 시퀀스/배정 테이블로 대체(이번 `sheet_row_claims`를 자연스러운 원장 배정으로 승격).
3. **조회 화면을 DB 기반으로** — 관리자/AE/리뷰어 화면이 시트 대신 DB(`review_index` 등)를 본다(상당수 이미 그러함).
4. **시트는 표시·공유·백업 채널로 격하** — 시트 쓰기는 묶음·저빈도. 실패해도 DB가 원본이라 데이터 손실 없음.
5. **RAW 미러로 양방향 검증** — 기존 `raw_sheet_mirror`로 DB↔시트 정합 점검 후 시트 의존 제거.

> 주의: 일부 사용자는 여전히 구글 시트를 직접 편집할 수 있으므로, **시트→DB 역방향 반영(수동 편집 흡수)** 정책을 먼저 합의해야 한다. 이 부분의 설계 선택(시트 편집을 허용할지/읽기전용으로 둘지)이 이관 범위를 좌우한다.

## 8. 부록 — 근거 데이터(운영 `error_logs`/실측)

**쿼터(quota) — 6종 시그니처, 누적 33회**
- `Quota exceeded for quota metric 'Read requests'` — 시스템 14 / 구매양식 9 / 리뷰제출 1 (24회)
- `Resource has been exhausted` — 시스템 5 / 구매양식 3 (8회)
- `Service Accounts do not have storage quota` (403) — 이미지 업로드 1회

**타임아웃(timeout) — 3종, 누적 149회** (쿼터 고갈의 직접 결과)
- 리뷰제출 시트쓰기 15초 타임아웃 — 63회
- 구매양식제출 시트쓰기 15초 타임아웃 — 58회
- AI 이미지분석 Gemini 9초 타임아웃 — 28회

**다운스트림 — 동시성·중복**
- "동시 제출 감지 — 큐에서 재시도" — 누적 276회(전부 사고 시트)
- 문제 탭 실측 중복: 25개 주문 중복 / **잉여 29행 = 데이터 199행의 14.6%**

**현재 미해결 오류 분포(요약)**: open 15건 — quota 6 / timeout 3 / network 3 / unknown 2 / not_found 1.

---

### 결론
이번 사고의 **중심은 구글 시트 API 읽기 쿼터의 구조적 고갈**이며, 타임아웃·중복·재제출·렉은 모두 그 파생이다. 코드 튜닝은 천장을 미룰 뿐 제거하지 못한다. **DB(SQL)를 1차 원장으로 삼고 시트를 비동기 미러로 격하**하면 쿼터 천장 자체가 사라져 동시성·중복·지연이 근본적으로 해소된다. 진행 중인 SQL 이관은 이 사고가 가리키는 정확한 방향이다.
