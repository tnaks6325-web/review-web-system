옵션별 유입링크 — 링크유입 작업은 옵션마다 상품 URL이 다르다

모집공고에 옵션이 여러 개인데 유입 링크가 1개여서, 리뷰어가 자기가 고른 옵션과 다른 상품 페이지로 들어가는 구조를 고칩니다. 더불어 리뷰웹 진행상품 블록과 인트라넷 리뷰오더 상품/옵션/금액 블록의 입력 조건을 맞춥니다.

PRD v0.9 (착수 전 · 결정 대기) · 대상 저장소 = review-web-system + inadd-webapp · 작성 2026-08-10

⚠ 이 문서는 아직 확정본이 아닙니다. §08의 결정 사안 D1~D6을 골라 주셔야 구현에 들어갈 수 있습니다. 각 항목에 권장안을 표시해 두었고, 카드를 클릭하면 맨 아래에 고른 결과가 모입니다. 화면 모양은 와이어프레임 시안에서 실제로 눌러 보실 수 있습니다.

01지금 무엇이 잘못되어 있나

리뷰어가 옵션을 고르고 참여하면 작업내용 카드에 [🔗 상품 페이지 열기] 버튼이 뜹니다. 그런데 그 버튼이 여는 주소는 공고 전체에 하나뿐인 값(recruit_campaigns.landing_url)입니다.

결과 — 옵션이 「블랙 / 화이트 / 베이지」 3종인 링크유입 작업에서, 화이트를 고른 리뷰어도 베이지를 고른 리뷰어도 전부 같은 한 개의 상품 페이지로 들어갑니다. 옵션마다 상품 페이지(또는 딥링크)가 다른 채널에서는 리뷰어가 다른 상품을 구매하거나, 링크를 벗어나 직접 검색해 들어가 유입 성과가 깨집니다.

왜 지금까지 이런 구조였나 (실측)

  • 인트라넷 리뷰오더는 상품 URL을 상품 단위로 한 칸만 받습니다(review-order-product-url-*). 옵션 행에는 옵션1/옵션2/결제금액/건수만 있고 URL 칸이 없습니다. 링크유입 안내문도 "상품 URL에 입력한 링크를 그대로 사용합니다" 한 줄뿐입니다.
  • 인트라넷이 리뷰웹으로 보내는 구조 신호 product_options_json 의 계약이 [{ name, url, base:{pay,count}, options:[{label,pay,count}] }] — 옵션 항목에 url 이 없습니다.
  • 리뷰웹 진행상품 표에는 URL 칸이 아예 없고, 랜딩 URL은 [모집 조건] 카드의 rf_landing_url 한 칸입니다.
  • 옵션 원장 campaign_options 에도 URL 컬럼이 없습니다(opt_key·금액·정원·일건수·상태뿐).

즉 어느 층에도 "옵션별 링크"를 담을 자리가 없습니다. 데이터 모델부터 화면까지 한 줄로 이어서 뚫어야 합니다.

04데이터 모델

리뷰웹 — migration 101

  • campaign_options.landing_url TEXT DEFAULT '' — 컬럼 추가만 · 백필 0 · DB CHECK 없음 (087 리뷰타입 · 099 work_kind 와 같은 규율). 빈 값 = 지금 동작 100% 불변(옵트인).
  • (D1에서 "공고에 유입방식 칸" 채택 시) recruit_campaigns.inflow_type TEXT DEFAULT '' 동반.
  • ★ FK 없음 — 이 테이블은 이미 campaign_id TEXT REFERENCES recruit_campaigns(id)를 갖고 있고, 082의 42804(FK 타입 불일치로 파일 전체 롤백) 사고를 재현하지 않기 위해 새 FK를 만들지 않습니다.
  • ★ REQUIRED_SCHEMA 등록 — 옵션 저장 INSERT 목록에 들어가므로 컬럼이 없으면 공고 발행·수정이 전면 42703이 됩니다. 부팅 프리플라이트에서 막습니다(082·085 규율).

인트라넷 — 스키마 변경 0

  • product_options_json 계약 확장: options:[{ label, pay, count, url }].
  • ★ 양방향 가산적 · 배포 순서 무관(088 계약건 · 099 work_kind 와 같은 성질) — 리뷰웹만 먼저 배포되면 url이 안 실려 와 종전 동작, 인트라넷만 먼저면 리뷰웹이 그 필드를 버립니다.
  • 상품 단위 URL(url)은 그대로 둡니다 — 옵션 없는 상품의 링크이고, 옵션 URL이 비면 폴백입니다.

06화면

① 인트라넷 리뷰오더 — 상품/옵션/금액

  • 옵션 행 끝에 [상품 URL] 칸 추가(단일옵션 4칸 → 5칸 / 이중옵션 5칸 → 6칸).
  • 유입방식이 가이드유입이면 옵션 URL 칸을 회색 비활성 + "가이드유입은 링크를 쓰지 않습니다" 안내. ★ 숨기지 않고 비활성으로 남깁니다 — 칸이 사라지면 유입방식을 바꿨을 때 왜 칸이 생겼는지 알 수 없습니다(레포의 폴더 버튼 규율과 동일).
  • 비활성 상태의 값은 전송하지 않습니다(가이드유입 오더에 링크가 딸려가 리뷰웹에서 링크유입으로 오독되는 것 차단).
  • 상품 단위 URL 칸은 그대로 — 라벨을 "상품 URL (옵션 없을 때 사용)" 로 바꿔 역할을 화면이 말합니다.
  • 시트참조 모드는 적용 제외 — 옵션 구조 자체를 만들지 않는 흐름입니다(reviewOrderOptionsPayload 가 undefined 반환).

② 리뷰웹 발행·수정 모달 — 진행상품

  • 표에 URL 칸 추가(위치는 D3). 표가 진실원본이라는 기존 규율은 그대로 — _syncPreviewFromOptRows 가 이미 작업내용 원문·정원을 표에서 파생하듯, 랜딩 URL도 같은 함수에서 파생합니다.
  • 작업오더에서 발행하면 옵션별 URL이 자동 프리필(_woOptionRows 확장) — 담당자는 확인만.
  • 가이드유입이면 URL 칸 비활성 + 안내. 링크유입이면 빈칸에 빨간 테두리 + 자동점검 항목 추가.
  • ★ URL 칸이 없는 화면에서 저장해도 기존 URL이 지워지지 않습니다 — 옵션표·리뷰타입과 같은 "UI 있는 화면에서만 전송" 원칙(리뷰어앱 인라인 수정 모달 등 축약 화면 보호).

③ 리뷰어 화면

  • 참여 후 작업내용 🧭 유입가이드 카드의 [🔗 상품 페이지 열기]가 고른 옵션의 URL을 엽니다.
  • 버튼 위에 "내가 고른 옵션: 화이트" 한 줄을 붙여 어느 상품으로 가는지를 말합니다 (옵션이 여러 개인 작업에서 링크 하나만 있으면 리뷰어가 확인할 방법이 없습니다).
  • 옵션 변경(change-option) 시 enterJoined() 재조회로 URL도 함께 바뀝니다 — 추가 배선 없음.
  • ★ 옵션 URL이 비면 공고 랜딩 URL로 폴백 — 이미 발행된 공고는 지금과 똑같이 동작합니다.

별도 칸 없이 "옵션 URL을 채웠다 = 링크유입"으로 추정합니다. 칸은 안 늘지만 가이드유입인데 참고용으로 URL을 넣은 경우를 링크유입으로 오판합니다.
고른 값: — 미선택 —

D2 — 링크유입 + 옵션 있는 작업인데 URL이 비면 어떻게 할까요?

이미 발행된 옛 공고는 옵션 URL이 전부 비어 있습니다(그 공고를 열어 다른 값만 고치는 흐름을 막으면 안 됩니다).

게시(active) 저장만 차단 권장
임시저장·비게시 상태는 경고만 하고 저장 허용, [게시] 상태로 저장할 때만 차단합니다. 리뷰어에게 노출되는 공고는 반드시 URL을 갖고, 옛 공고 수정은 막히지 않습니다. 서버도 참여형 활성화 게이트(_participationActivationErrors)와 같은 자리에서 재검증합니다.
저장 자체를 하드블록
상태와 무관하게 저장 버튼이 잠깁니다. 가장 강하지만 옛 공고의 긴급 정정(리뷰비·정원)까지 통째로 막힙니다.
경고만 (게시 허용)
빨간 경고만 띄우고 막지 않습니다(레포의 옵션 칸 자동점검·정리 도우미와 같은 방식). 오탐으로 정상 발행이 막히는 일은 없지만 누락이 그대로 리뷰어에게 나갑니다.
고른 값: — 미선택 —

D3 — 옵션 없는 작업의 상품 URL은 어디에 두고, 기존 [랜딩 URL] 칸은 어떻게 할까요?

진행상품 표에 URL 칸을 만들면 [모집 조건]의 랜딩 URL 칸과 같은 값을 두 곳에서 관리하게 됩니다.

진행상품 표가 진실원본 권장
표에 URL 칸을 두고(옵션 없는 작업 = 상품 행 / 옵션 있는 작업 = 옵션 행), [랜딩 URL] 칸은 표에서 자동 파생되는 읽기전용으로 바뀝니다. 지금 정원·작업내용 원문이 표에서 파생되는 규율과 같아 어긋날 수가 없습니다.
옵션 있는 작업만 표에 URL
옵션 없는 작업은 지금처럼 [랜딩 URL] 칸을 그대로 쓰고, 옵션 있는 작업만 옵션 행에 URL을 둡니다. 변경 범위는 최소지만 URL 입력 위치가 작업 종류에 따라 두 곳으로 갈립니다.
둘 다 두고 옵션 URL 우선
[랜딩 URL]을 편집 가능한 채로 남기고 옵션 URL이 있으면 그것이 이깁니다. 같은 값을 두 곳에서 관리하게 되어 나중에 어긋납니다.
고른 값: — 미선택 —

D4 — 인트라넷 옵션행과 리뷰웹 옵션행의 칸을 어디까지 똑같이 맞출까요?

지금 다른 것: 이중옵션(인트라넷만) · 일건수(리뷰웹만) · 시트참조(인트라넷만).

URL만 맞추고 나머지 현행 유지 권장
양쪽 옵션 행에 URL 칸을 넣는 것까지만 통일합니다. 이중옵션은 인트라넷에서 입력하고 리뷰웹으로는 「블랙 + 라지」 합친 라벨 하나로 넘어오는 지금 계약을 유지하고, 일건수는 모집 운영값이라 리뷰웹 전용으로 둡니다.
리뷰웹에도 이중옵션 2칸 도입
리뷰웹 옵션 행도 옵션1/옵션2로 나눕니다. 다만 시트 옵션열 기입값(opt_key)은 결국 한 문자열이라 저장 시 다시 합쳐야 하고, 기존 발행분과 표기가 갈릴 수 있습니다.
인트라넷에도 옵션별 일건수 추가
인트라넷 옵션 행에 일건수를 넣어 리뷰웹과 완전히 같은 칸 구성으로 맞춥니다. 지금 인트라넷은 작업 전체 일건수 1칸만 받고 있어 개념이 바뀝니다(발주 담당자 입력 부담 증가).
고른 값: — 미선택 —

D5 — 옵션은 없는데 상품이 2개 이상인 작업은 어느 URL을 쓸까요?

리뷰웹 진행상품 표는 옵션 없는 작업에서도 [상품 추가]로 여러 줄을 만들 수 있는데, 그 경우 리뷰어에게는 고를 선택지가 없습니다(옵션 원장이 비어 있음).

첫 상품 URL 사용 + 경고 권장
첫 줄의 URL을 공고 랜딩 URL로 쓰되, 상품이 2줄 이상이고 URL이 서로 다르면 "리뷰어는 하나만 보게 됩니다 — 옵션으로 나누시겠어요?" 경고를 띄웁니다.
옵션 있는 작업으로 전환 유도
URL이 서로 다른 다상품은 사실상 옵션 작업이므로 [옵션 있는 작업]으로 바꾸라고 안내하고 그 전에는 저장을 막습니다. 데이터는 깔끔해지지만 기존 다상품 공고 운영이 막힙니다.
지금처럼 1칸만 · 경고 없음
옵션 없는 작업은 URL 1개라는 현행을 그대로 둡니다. 가장 단순하지만 다상품 링크유입의 오유입은 그대로 남습니다.
고른 값: — 미선택 —

D6 — 리뷰어 화면에 "내가 고른 옵션"을 링크 버튼 옆에 표시할까요?

옵션마다 링크가 다르면 내가 맞는 상품 페이지로 가는지를 리뷰어가 확인할 방법이 필요합니다.

버튼 위에 옵션명 한 줄 권장
"내가 고른 옵션: 화이트" + [🔗 화이트 상품 페이지 열기]. 잘못 고른 것을 여기서 알아챌 수 있습니다. 작업내용 카드에 이미 상품·옵션 정보가 있어 중복이지만 클릭 직전 위치라 의미가 다릅니다.
버튼 라벨에만 옵션명
줄을 늘리지 않고 [🔗 화이트 상품 페이지 열기] 로만 표시합니다. 옵션명이 길면 버튼이 잘립니다.
지금 그대로 (표시 없음)
버튼 문구를 바꾸지 않습니다. 화면 변경 0이지만 리뷰어는 링크가 자기 옵션 것인지 알 수 없습니다.
고른 값: — 미선택 —

09단계 · 순서

앞 단계가 뒤 단계의 전제입니다(스키마 → 저장 → 화면 → 연동 순).

  1. 1M1 — 그릇 · migration 101(campaign_options.landing_url + D1 채택 시 inflow_type) · REQUIRED_SCHEMA 등록 · utils/optionLanding.js 판정 함수. 이 단계만으로는 화면 변화 0.
  2. 2M2 — 리뷰웹 입력·저장 · 진행상품 표 URL 칸 · readOptRows/_saveCampaignOptions 확장 · 유입방식 연동 비활성 · 자동점검 항목(D2 수준) · 발행 모달 미리보기 반영.
  3. 3M3 — 리뷰어 화면 · work-detail 응답에 옵션별 URL 반영 · 관리자 미리보기 동일 적용 · [상품 페이지 열기] 옵션 표기(D6).
  4. 4M4 — 인트라넷 · 옵션 행 URL 칸 · product_options_json 에 url 동봉 · 폼/서버 검증 · 리뷰웹 _woOptionRows 프리필 확장. M4는 M2와 독립 — 어느 쪽이 먼저 배포돼도 안전.

회귀가드 (신설 tests/optionLandingUrl.test.js)

  • 판정 순수함수 실행 — 옵션 URL → 공고 URL → 빈 값 순서 · 킬스위치 · 잘못된 스킴 거부.
  • 스텁 pool 로 저장·조회 실제 실행 — INSERT 컬럼 수 ≡ 자리표시자 수 ≡ 파라미터 수 계수 (099에서 실제로 깨졌던 자리) · 미전송 시 기존 값 보존.
  • 공개 응답에 URL 부재 고정 — _publicOptionView 가 URL을 싣지 않음.
  • 미리보기 = 실제 화면 — 두 경로가 같은 resolver를 태우는지 실행으로 대조.
  • 인트라넷 조립 실행 — 가이드유입이면 url 미전송 · 시트참조 모드 미전송.
  • 변이시험으로 각 단언이 실제로 잡는지 확인(레포 관행).

10미리 밝혀 두는 한계

  • 이미 참여한 리뷰어는 참여 시점의 옵션으로 잠겨 있고, 나중에 관리자가 그 옵션의 URL을 고치면 다음에 열 때부터 새 URL이 열립니다(리뷰비처럼 참여 시점 스냅샷을 뜨지 않습니다 — 링크는 "지금 어디로 가야 하는가"라 최신값이 맞습니다).
  • 구매양식(시트 기입)에는 URL이 들어가지 않습니다 — 이번 범위는 유입 안내까지입니다.
  • 이중옵션은 D4 결정 전까지 리뷰웹에서 합친 라벨 하나로 다뤄집니다.
  • 인트라넷 시트참조 모드는 옵션 구조 자체가 없어 옵션별 링크를 담을 수 없습니다(담당자가 시트로 관리).
