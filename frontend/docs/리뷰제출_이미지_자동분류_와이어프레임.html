1구현 가능 여부 — 필요한 부품 대 이미 있는 부품

결론부터: 구현 가능하다. 필요한 9개 부품 중 6개가 이미 운영 중인 코드라 그대로 재사용하고, 신설은 3개(구매캡처 판별 종류·이동 이력 원장·슬롯 정합 보강)뿐이다. 특히 AI 호출 순증이 0이다 — 업로드 시점에 이미 verifyCapture가 이미지 종류를 판별하고 있어서(2026-07 도입, 현재는 경고만), 이 시스템은 그 판정값을 그대로 재사용해 "경고"를 "이동"으로 승격하는 것이다.

지금도 리뷰 자리에 현금영수증을 올리면 시스템이 알고 있다(AI 확신 90%+ 면 관리자 빨간 알림까지 발생 — 좌측 스크린샷의 "리뷰 화면이 아닌 것으로 판정됨" 카드가 그것). 다만 알기만 하고 아무것도 옮기지 않는다. 이 계획은 그 판정 뒤에 ①이동 ②중복반려 두 동작을 붙이는 것이라, 판별 정확도·호출량·검수 타이밍은 전부 검증된 현행 그대로다.

2분류·이동 규칙 매트릭스 (제출된 자리 × AI 판정 → 동작)

이동은 정의된 전이만 한다(아래 표 밖의 조합은 전부 현행 유지 = 경고만). AI 확신도 90% 이상(sure)에서만 이동하고, 70~90% 구간은 지금처럼 경고만 한다.

3처리 흐름도 — /review-upload 파일 루프 확장

① 리뷰어가 캡처 첨부 → 제출1차 필터(첨부 즉시 review-precheck)는 현행 그대로 — 여기선 변경 없음
② Drive 업로드 + SHA-256 지문 기록현행 그대로 (review_submissions.file_hash)
③ AI 검수 verifyCapture현행 그대로 — 캐시 히트라 AI 콜 순증 0
④ 신설 routeDecision(판정, 탭 슬롯 구성)이동 전이표 대조 + 대상 폴더 확보 가능 여부 + 모드(끔/관측/자동)
✓ 형식 일치 / 판정불가 / 애매(70~90%)현행 그대로 종료 — 일치면 통과, 애매면 경고+알림만. 아무것도 옮기지 않는다.
↗ 불일치 · 확신 ≥90% · 전이표 有⑤ 대상 슬롯 중복 검사(해시)로
✕ 불일치인데 대상 폴더 없음(비현영 탭에 영수증 등) 이동 안 함 — 현행 경고+알림 유지.
⑤ 신설 대상 슬롯 중복 검사같은 행·같은 리뷰어·대상 슬롯 원장에서 같은 file_hash + 다른 file_id 조회 (DB 1쿼리)
중복 없음 → 이동moveFile → slot_key·이동이력 갱신 → 대표이미지·완료판정 재계산 → 응답에 moved:{from,to} → 리뷰어 화면 "옮겨 드렸어요" 안내 + 관리자 이동 알림(info)
중복 있음 → 반려방금 파일 trashFiles(휴지통) → 원장 소프트 취소 → 응답에 rejected:'duplicate' → 리뷰어 화면 "이미 제출된 파일" 안내 + 그 칸 재첨부 요구 → 관리자 알림(warn)
비용 계산 — AI 콜 +0 (기존 판정 재사용) · Drive 콜 = 오제출 파일당 이동 1회(또는 휴지통 1회) + 폴더 확보 0~1회 · DB = 중복 검사 1쿼리 + 갱신 2~3쿼리. 오제출은 예외 상황이라 총량이 작고, 시트 API는 일절 건드리지 않는다(쿼터 무영향).

5안전장치 — 완화 금지 목록 (레포 규율 정합)

  • ★★ 제출 차단의 유일 근거는 결정적 판정(SHA-256 정확 일치)뿐이다. AI 판정으로는 절대 반려하지 않는다 — 1차 필터의 "차단은 other+90% 한 갈래뿐, 오탐 = 참여 소각" 규율을 그대로 계승. AI가 하는 일은 이동까지다(이동은 가역, 반려는 비가역적 사용자 경험이라 근거의 급이 달라야 한다).
  • ★★ 삭제는 휴지통(trashFiles)만 — 영구삭제 API를 쓰지 않는다. 30일 복구창 + 관리자 카드 [휴지통에서 복구] 버튼. 되돌리기 어려운 파괴는 시스템이 하지 않는다는 레포 원칙.
  • ★★ 이동은 전이표에 정의된 조합만 — 표 밖 조합(예: other 판정, 대상 폴더 없는 탭)은 전부 현행 유지. "확인 불가 = 옮기지 않음"(옵션 칸 blank-only와 같은 fail-closed 방향).
  • ★★ 이동 이력 없는 이동 금지 — 모든 이동은 routed_from_slot/routed_at을 남기고 관리자 알림(info)을 발생시킨다. 조용한 자동수정 금지(슬래시양식 보정 배지와 같은 규율). 되돌리기는 이 이력이 유일한 재료다.
  • ★ fail-open 불변 — AI 미설정·장애·타임아웃·저확신·중복검사 쿼리 실패는 전부 "아무것도 안 함"(현행 동작). 자동 분류가 죽어도 업로드·제출은 산다.
  • ★ 카카오메이커스 채널 제외 — 별점 없는 피드형 화면이 공존해 리뷰 판정 자체가 흔들리는 채널(REVIEW_PRECHECK_EXEMPT와 같은 목록)은 자동 이동 대상에서 뺀다.
  • ★ 킬스위치 3단 — AUTO_FILE_ROUTE=0(전체 끔) / AUTO_FILE_ROUTE=dry(관측) / AUTO_FILE_ROUTE_REJECT=0(이동은 하되 반려만 끔). 기본값 = 끔(opt-in — 배포 순간 동작 불변).
  • ★ 대표 이미지·완료 판정 정합 — review 슬롯에서 파일이 나가면 review_file_*을 남은 리뷰 파일로 재계산(없으면 비움 — 업체 뷰어 미리보기가 영수증을 리뷰로 보여주는 사고 방지). 이동 결과는 업로드 응답에 실려 프론트가 슬롯 충족을 재계산한다.
  • ★ 구매캡처 kind 추가 시 기존 판정 보존 — 프롬프트는 줄 추가만(기존 3줄 불변), 캐시 접두 classify4: 상향(옛 캐시가 새 종류를 모른 채 히트하는 것 차단). 087 2차가 밟은 길 그대로.

6단계별 구현 계획

M1 — 판별 확장 + 관측 1차 배포

  • kind order_capture 신설(gemini.service 프롬프트 줄 추가 + 캐시 classify4:)
  • routeDecision 순수함수 + 전이표(utils/captureRoute.js 단일 출처)
  • 관측 모드: 이동 계획을 로그·관리자 알림으로만 (AUTO_FILE_ROUTE=dry)
  • 마이그레이션: review_submissions에 routed_from_slot/routed_at/routed_by
  • 구매캡처 판별 예시이미지 슬롯(설정탭 aisamples 패널 확장, 캐시 지문 접두 분리)

M2 — 자동 이동 관측 검증 후

  • review-upload에 이동 실행 배선(moveFile + slot_key·이력·대표이미지 갱신)
  • 업로드 응답 moved 동봉 → 프론트(search-app.js) 슬롯 재계산 + ④-1 안내
  • 관리자 카드 [원위치로 되돌리기](역이동 + 이력 reverted)
  • 완료 판정 재평가 — 이동으로 필수 슬롯이 비면 제출 버튼 잠금

M3 — 중복 반려 최후 단계

  • findSlotDuplicate(같은 행·같은 리뷰어·대상 슬롯 해시 대조 — 기존 findDuplicate와 분리)
  • 중복 시 trashFiles + 원장 소프트 취소 + 응답 rejected:'duplicate' + ④-2 안내
  • 관리자 카드 [휴지통에서 복구]
  • 회귀가드: 전이표 실행 검증 + 반려는 해시 일치에서만 발생(AI 단독 반려 부재를 변이시험으로 고정) + 스텁 pool로 업로드 루프 실제 실행 + 기존 captureSlotVerify·reviewInspect 가드 패턴 동반 갱신
왜 3단계인가 — 이동(가역)과 반려(사용자 경험상 비가역)는 리스크 급이 다르다. 관측 모드로 실제 오제출 분포·AI 오탐률을 확인한 뒤 이동을 켜고, 이동이 안정된 뒤에야 반려를 켠다. 각 단계는 킬스위치로 독립적으로 되돌릴 수 있고, 기본값이 전부 "끔"이라 배포 자체는 무영향이다.

7잔여 위험 · 사용자 결정 필요 항목

항목내용제안 기본값
🔴 구매캡처 ↔ 구매확정 화면 구분 둘 다 "주문 관련 화면"이라 AI가 헷갈릴 수 있는 가장 약한 고리. 구매확정 리뷰타입 탭에서는 구매캡처 이동을 잘못 발동하면 정상 제출이 옮겨진다. 구매확정(confirm) 리뷰타입 탭은 구매캡처 자동 이동 제외 + 예시이미지 등록 후 활성화
출시 모드 관측(dry)으로 시작할지, 바로 자동 이동으로 켤지. 관측 2주 → 자동 이동 (오탐률 근거 확보)
반려 문구·재첨부 유도 반려가 리뷰어에게 "제출 실패"로 읽히면 문의가 늘어난다. 문구는 "이미 제출돼 있어요"(안심) 톤으로. ④-2 목업 문구
과거 오제출 소급 정리 이 시스템은 새 제출부터 적용. 이미 잘못 들어가 있는 파일은 별도 배치(2차 검수 스윕에 이동 제안 추가)로 — 범위 밖, 필요 시 후속. 1차 범위 제외
비현영 탭의 영수증 제출 영수증 슬롯이 없는 탭이라 이동 대상 폴더가 없다. 요구사항("폴더가 있는 경우")대로 이동하지 않고 경고만 — 폴더를 즉석 생성하지 않는 이유는 그 탭의 슬롯 구성(완료 판정)이 바뀌기 때문. 경고만 (현행 유지)
