01 배경 — 지금은 무엇이 없나

택배발송대행 작업은 그날의 송장번호를 그날 광고주에게 넘겨야 출고가 밀리지 않는다. 지금은 등록 파일도 손으로 만들고, 택배사가 준 결과 파일의 송장번호도 사람이 한 줄씩 옮겨 적는다.

코드를 전수 조사한 결과, 송장번호를 담을 칸이 시스템 어디에도 없다는 것이 확인됐다.

찾아본 곳결과
work_orders (migration 019)courier_proxy BOOLEAN — 택배대행 여부만 있고 송장 컬럼 없음
전 마이그레이션송장/운송장 컬럼·테이블 0건
작업표 표준 열 ROLE_META역할 16종에 송장 없음 → 열을 만들어도 "매칭되지 않습니다"로 분류
컬럼 감지 columnResolver송장 키워드 0건 → row_json에 원문으로만 담김(검색·집계 대상 아님)
작업유형 트리거이미 있음 — WORK_TYPE_TRIGGERS의 courier_proxy ("택배대행이 '예'일 때")
반면 내보낼 재료는 이미 다 있다 등록 양식이 요구하는 받는사람 · 전화번호 · 주소는 order_submissions에 전용 컬럼(recipient / phone / address)으로 이미 저장돼 있다. 시트 row_json을 파싱할 필요가 없다. 즉 이 기능은 "내보내는 재료는 있고, 받아 적을 칸을 새로 만드는" 작업이다.

그리고 똑같은 모양의 흐름이 이미 완성돼 있다 — 입금관리(migration 086 M1 / 100 M2): 대상 추출 → 회차 다운로드 → 결과 업로드 → 자동 반영. 이 PRD는 그 뼈대를 그대로 본뜨되, 아래 §02의 결정적 차이 하나를 다르게 설계한다.

02 ★ 입금 자동화와 결정적으로 다른 점 — 매칭 키가 없다

업로드해주신 실측 파일 2종을 열어 대조한 결과다.

등록용 양식 (A타입) — 6열, 35건

수량(A 타입) | 우편번호 | 상품명1 | 받는사람 | 전화번호1 | 주소 | | 장수돌만두 | 서규환 | 010-8258-4882 | 경기도 하남시 신장로205번길 30, kcc스위첸 101동 203호

수량·우편번호는 전 행이 비어 있었다(선택 항목). 우리 고유번호를 실을 칸이 없다.

두 파일을 짝지을 수 있는 것

후보 키쓸 수 있나실측 근거
전화번호없음결과 파일 48열에 전화번호 열 자체가 없다
주소불가상세주소가 법정동으로 축약된다. 경기도 하남시 신장로205번길 30, kcc스위첸 101동 203호 → 경기 하남시 덕풍동 — "덕풍동"은 원본 주소에 아예 없는 글자다
주문번호비어 있음결과 파일에 열은 있으나 이번 파일은 전 행 공란(A타입 양식에 그 칸이 없어 못 실어 보냄)
관리번호불가7989707275 — 택배사가 접수 시점에 부여. 우리가 미리 정할 수 없다
수하인명가능35건 전부 일치, 이번 배치엔 동명이인 없음. 다만 동명이인은 언제든 생길 수 있다
행 순서가능업로드 1~35행 ↔ 결과 NO 1~35가 35/35 완전 일치
입금 자동화(M2)의 짝맞추기
  • 키 = (계좌 숫자, 금액)
  • 둘 다 결과 파일에 그대로 들어 있다
  • 순서가 뒤바뀌어도 정확히 찾는다
  • 같은 키가 여럿이면 순서로 가르고 고지 — 실측상 같은 사람·같은 작업이라 손해가 없다
택배의 짝맞추기
  • 키 = 이름 + 다운로드 당시 행 순서
  • 이름은 중복 가능, 순서는 택배사가 바꿀 수 있다
  • 어긋나면 남의 집 송장번호가 내 줄에 적힌다
  • 그건 배송 사고이자 개인정보 사고이고, 화면상으로는 정상으로 보인다
★★ 그래서 이 기능의 최상위 규칙 (완화 금지) 이름과 순서가 둘 다 맞을 때만 자동으로 기록한다. 하나라도 어긋나면 그 줄부터 자동 배정을 멈추고 확인 화면에 모아 사람이 짝을 고른다.
순서만 믿고 밀어 넣지 않는다. 택배사가 한 건을 빼거나 정렬을 바꾸면 그 아래 전원이 한 칸씩 밀린다. 34건이 조용히 잘못 기록되는 쪽이, 35건을 사람이 5분 확인하는 쪽보다 훨씬 비싸다.
주소는 자동 배정을 막는 근거로 쓰지 않는다 (경고 전용) 법정동 축약 때문에 정확 대조가 불가능한 데다, 실측 파일에 전남광주시 남구 회재로…(리뷰어가 시/도를 잘못 적은 행)가 실제로 있었다. 결과의 광주 남구 주월동과 시/도가 어긋나지만 같은 사람이 맞다. 주소로 잠그면 멀쩡한 건이 무더기로 막힌다.
→ 비교는 시군구 토큰 하나만(위 예시는 "남구"로 일치) 하고, 어긋나도 경고 표시까지만 한다.
미래 대비 — 고유번호가 생기면 그것이 최우선 결과 파일에 주문번호 열이 이미 존재하므로, 나중에 그 칸이 있는 양식(B/C타입 등)을 쓸 수 있게 되면 우리 회차 항목 번호를 실어 보내고 그대로 되받아 100% 정확 매칭이 된다. 판정 함수의 1순위 규칙으로 미리 넣어 두되, 값이 비어 있으면 발동하지 않으므로 지금 동작에는 아무 영향이 없다.

03 사용자 확정 사항 12건

#항목확정 내용
1등록 양식지금 A타입 그대로 사용 → 이름 + 순서 매칭, 안전 우선 설계
2대상 추출 기준택배대행 작업 중 구매일자가 오늘인 행
3발송 단위리뷰어 1명 = 1박스
4상품명옵션까지 반영 (예: 장수돌만두 - 고기만두)
5택배사지금은 한 곳, 늘어날 예정 → 택배사별 형식 표 구조로 만들어 둠
6기록 칸둘 다 — 기존 '택배' 칸 자동 인식 + 작업표 표준 열에 '송장번호' 정식 추가
7광고주 제공3종 전부 — 뷰어 표 노출 + 광고주가 직접 엑셀 다운로드 + 업로드 즉시 알림
8재다운로드다운로드한 행은 잠근다. 송장이 안 들어오면 풀 수 있다
9불일치 처리자동 배정을 멈추고 사람이 확인
10권한AE도 자기 담당 작업만 처리 가능
11결과 없는 건그대로 두고, 사람이 [다시 대상으로]를 누를 때만 잠금 해제
12재발송칸을 두 개로 — 송장번호 / 재발송송장
13취합 시점담당자가 필요할 때 버튼을 누른다 (자동 실행·마감 시각 없음)

STEP 2 · 사람

STEP 3 · 사람

STEP 4 · 사람
⬆ 결과파일 올리기
확인 화면에서 자동/확인필요/결과없음을 보고 [이대로 반영]
STEP 5 · 시스템
송장 기록 + 알림

시스템 밖 구간(STEP 3)이 있다는 것이 설계의 전제 택배사 시스템과 API 연동이 아니라 사람이 파일을 나르는 구조다. 그 사이에 파일이 편집되거나, 일부만 접수되거나, 순서가 바뀔 수 있다. §08의 짝맞추기 규칙은 전부 이 전제 위에서 설계됐다.

05 데이터 모델 (migration 101)

입금관리(086)와 같은 모양이다. 신규 3테이블 + 컬럼 추가 0. 라이브 테이블은 읽기만 한다.

-- 회차 (한 번의 다운로드 = 한 회차)
CREATE TABLE parcel_batches (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  seq            BIGSERIAL,                 -- 화면 표기용 회차번호
  courier        TEXT NOT NULL,             -- 택배사 키 (지금은 1종, 늘어날 예정)
  status         TEXT NOT NULL DEFAULT 'downloaded'
                 CHECK (status IN ('downloaded','cancelled','applied')),
  item_count     INT  NOT NULL DEFAULT 0,
  created_by TEXT, created_at TIMESTAMPTZ DEFAULT NOW(),
  download_count INT DEFAULT 1, last_downloaded_at TIMESTAMPTZ, last_downloaded_by TEXT,
  cancelled_at TIMESTAMPTZ, cancelled_by TEXT,
  applied_at   TIMESTAMPTZ, applied_by   TEXT
);

-- 회차 항목 = 파일 한 줄. 보낸 값과 파일 순번을 그대로 박제한다
CREATE TABLE parcel_batch_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  batch_id   UUID REFERENCES parcel_batches(id) ON DELETE CASCADE,
  sheet_id   TEXT NOT NULL, tab_name TEXT NOT NULL, row_index INT NOT NULL,
  campaign_id TEXT REFERENCES recruit_campaigns(id) ON DELETE SET NULL,  -- ★ TEXT (082 규율)
  seq_in_file INT NOT NULL,        -- ★★ 파일 몇 번째 줄로 나갔는가 = 결과 매칭 앵커
  reviewer_name TEXT, recipient TEXT, phone TEXT, address TEXT,
  product_name  TEXT, qty INT DEFAULT 1,
  tracking_no   TEXT,                -- 결과 반영 시 기록
  is_resend     BOOLEAN DEFAULT FALSE,  -- 재발송송장 칸으로 갔는가
  matched_by    TEXT,                   -- order_no | name_seq | manual
  result_seq    INT,                    -- 결과 파일 몇 번째 줄과 짝지었나
  status TEXT NOT NULL DEFAULT 'pending'
         CHECK (status IN ('pending','shipped','released','cancelled')),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- ★★ 중복 접수 최종 방어선: 살아있는 항목은 한 행에 하나뿐
CREATE UNIQUE INDEX uq_parcel_items_active
  ON parcel_batch_items (sheet_id, tab_name, row_index)
  WHERE status IN ('pending','shipped');

-- 업로드 감사 원장 (파일 자체는 저장하지 않는다)
CREATE TABLE parcel_result_uploads (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  batch_id UUID REFERENCES parcel_batches(id) ON DELETE CASCADE,
  courier TEXT, file_name TEXT, file_format TEXT,
  row_count INT, auto_matched INT, needs_check INT, no_result INT,
  applied BOOLEAN DEFAULT FALSE, summary JSONB,
  uploaded_by TEXT, uploaded_at TIMESTAMPTZ DEFAULT NOW()
);
★ 되풀이하면 안 되는 실측 사고 3종을 미리 막는다 ① FK 타입 — recruit_campaigns.id는 TEXT다. UUID로 선언하면 PG가 42804로 FK를 거부하고 그 마이그레이션 파일 전체가 롤백되며, 그 오류코드는 "적용됨" 기록 대상이 아니라 배포마다 같은 자리에서 실패한다(082 실사고).
② 부팅 프리플라이트 — REQUIRED_SCHEMA에 parcel_batch_items.tracking_no를 등록한다. 없으면 화면이 통째로 42703으로 죽는데 서버는 정상 부팅해 무신호 전면 장애가 된다.
③ 상태값 released — 확정 11번(결과 없는 건은 사람이 [다시 대상으로]를 눌러야 풀림)을 위해 부분유니크 밖의 종결 상태를 따로 둔다. cancelled와 구분해야 "회차 취소"와 "송장 미발급"이 이력에서 갈린다.

06 오늘 발송 대상 추출

판정 단일 출처 = utils/parcelTarget.js. 화면·다운로드·결과반영이 같은 함수를 쓴다(화면엔 뜨는데 다운로드에선 빠지는 불일치를 구조적으로 차단).

대상 조건 (전부 AND)

#조건판정 재료
①택배대행 작업연결된 작업오더 work_orders.courier_proxy = true (접수 시 tab_configs로 전파된 값 사용)
②구매일자 = 오늘(KST)작업표 날짜 칸 → utils/koreanDate.parseDateColumn
③수취인·연락처·주소 있음order_submissions.recipient / phone / address → 없으면 row_json 폴백
④송장 칸이 비어 있음utils/parcelColumn.js가 해석한 칸의 현재 값
⑤살아있는 회차 항목 없음NOT EXISTS (… status IN ('pending','shipped')) — 확정 8번
★★ parseDateColumn에 fallbackAnchor를 반드시 넘긴다 작업표의 구매일자는 8 / 10 (월)처럼 연도가 없다. 앵커를 안 넘기면 전 행이 null이 되어 "오늘 대상 0건"으로 조용히 죽는다. 이 레포에서 이미 두 번(063 시트 일정, 작업보드 오늘 참여현황) 밟은 자리다. 회귀가드는 실제 표기 M / D (요일) 픽스처로 고정한다 — ISO 문자열로 검증하면 앵커를 빼도 통과해 버린다.

15 잔여 위험 · 미결

#항목내용과 대응
1매칭 키가 근본적으로 약하다이름+순서는 택배사가 파일을 편집하면 깨진다. 이 PRD는 깨졌을 때 자동을 멈추는 것까지만 한다. 근본 해결은 등록 양식에 주문번호 칸을 쓰는 것이며 택배사 확인이 필요한 미결 사항이다
2우편번호를 못 채운다리뷰어 입력에 없다. 택배사가 주소로 자동 판정하는 현재 방식에 의존한다(실측 파일도 공란). 택배사가 우편번호를 요구하기 시작하면 리뷰어 입력 항목 추가가 필요하다
3합포장 미지원확정 3번(1명 = 1박스)에 따라 합포장여부·합포장키는 쓰지 않는다. 한 사람이 여러 건을 받는 작업이 생기면 별건
4택배사 1종형식 표(COURIER_SPECS) 구조는 만들어 두되 실제 항목은 1개. 두 번째 택배사는 실물 파일을 받아 픽스처로 추가해야 한다(추측으로 열 이름을 넣지 않는다)
5반품·재발송 3회차 이상칸이 2개라 세 번째 송장은 담을 곳이 없다. 그때는 기존 값을 확인 필요로 보고하고 사람이 정리한다
6배송 상태 추적 없음이 기능은 송장번호를 넘기는 것까지다. 배송완료 여부·반송 조회는 택배사 API가 필요한 별건
