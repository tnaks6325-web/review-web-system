01

배경 — 왜 블로그 작업 행이 사라졌나

블로그체험단은 구매일자를 미리 정할 수 없다(체험단이 모집되면 그때그때 실제 구매일자를 입력하는 운영). 그런데 무시트 이관·슬롯 백필의 "준비 행" 판정이 구매일자가 날짜로 해석되는 행만 인정한다.

누락 메커니즘 (실측 확정)

  • sheetSlotSync.service.js readPreparedRows(L98–111): 구매일자 파싱 성공 행만 prepared. 값은 있는데 파싱 실패면 datelessFilled로 세지만, 칸 자체가 빈 행은 어느 카운터에도 안 잡힌다 = 완전 무음 누락.
  • 이관 점검표 ①(sheetlessCutover.service.js _checkSheetRows)도 같은 판정을 쓰므로 점검표가 초록인 채로 이관됐다 — 바를참스킨 0804는 구매일자·이름이 있는 행만 시스템표(campaign_participants)로 넘어가고 2~10번 등 빈 행은 통째로 빠졌다.
  • 보조 요인: 검색인덱스 파서(columnResolver.js:235 if (!name) return null)는 이름 없는 행을 버리므로, 준비 행은 원래부터 시스템표 백필(slot-backfill)로만 들어올 수 있었다.

사용자 확정 사항 · 가정

항목확정 내용상태
분류 체계리뷰체험단/블로그체험단은 별도 축(작업유형 work_kind). 기존 리뷰타입(포토·텍스트·구매확정·별점·혼합)은 리뷰체험단 안에서만 쓰는 하위 값으로 유지 — 블로그 작업엔 리뷰타입 없음.확정
구매 흐름블로거도 상품을 직접 구매하고 구매양식을 제출한다(간소화). 다른 점 = 결과물이 리뷰캡처 대신 포스팅URL.확정
모집·배정관리자 수기 배정뿐 아니라 리뷰웹 참여형 모집공고로도 모집(블로거 직접 참여)까지 이번 범위에 포함.확정
결과물 제출포스팅URL만 제출 — 리뷰캡처 첨부 없음. URL 제출 = 리뷰제출 완료 처리.확정
준비 행 기준바를참스킨 0804 = 번호 1~50. 앞으로의 블로그 작업 = 리뷰오더에서 입력한 총원(recruit_count)이 준비 행 수의 기준(구매일자 무관).확정
바를참스킨 1회 동기화별도 전용기능(범용 도구·화면) 구현 없이, 그 작업 하나만 1회 동기화한다.확정
구매양식 간소화 범위가정: 1차는 리뷰체험단과 동일 칸 구성(+블로그URL 자동 기록). 칸 축소(예: 아이디 제외)는 운영해 보며 후속 결정.가정
블로그URL 입력 주체가정: 공고 참여 시 블로거가 필수 입력(홀드에 저장 → 구매양식 제출 시 시트/작업표 블로그URL 열에 자동 기록). 관리자 수기 배정 시엔 관리자가 작업보드 그리드에서 직접 입력.가정

⚠ 가정 2건은 구현 착수 전 확인이 필요하면 그 단계(M4·M5) 시작 시점에 재질문한다. 가정이 뒤집혀도 모델(work_kind 축·전파 경로)은 불변.

M2 — 블로그 작업의 준비 행 = 리뷰오더 총원 (판정 보정)

리뷰체험단의 "준비 행 = 구매일자 날짜 행" 판정은 그대로 두고, work_kind='blog'인 탭만 총원(recruit_count) 기준으로 갈라탄다. 사용자 확정: "앞으로의 블로그작업은 리뷰오더에서 총원 입력 시 총원이 준비 행의 기준".

  • 신규 작업(무시트 접수 F1·작업표 생성): 이미 recruit_count만큼 행을 만드는 구조(buildWorktablePlan → createSlotsFromSheetRows)라 행 수는 문제 없음. 블로그면 구매일자 분배를 하지 않는다 — 구매일자 칸은 빈 칸으로 생성(모집되면 그때 기입), 달력 프리필(sheetlessDailyPlan.prefillFromWorktable)은 스킵(날짜가 없으므로 unparsable로 조용히 죽는 대신 블로그 사유로 명시 스킵). 공고 정원은 발행폼 daily_limit/recruit_total 경로.
  • 시트 기반 블로그 탭의 슬롯 백필·점검표 ①: readPreparedRows에 blog 분기 — 준비 행 = 헤더 아래 1행부터 총원 N행까지(연결 작업오더의 recruit_count, 시트에 값이 있는 행은 rowJson 동반). sheetlessCutover._checkSheetRows(점검표 ①)·slot-audit·slot-backfill·sweepPreparedRows는 전부 readPreparedRows 한 곳을 쓰므로 분기 지점은 한 곳(사본 0). 총원을 모르면(오더 미연결·0) 판정 불가로 정직하게 보고(0으로 꾸미지 않는다).
  • 구매일자 빈 행 무음 누락 자체도 고친다: readPreparedRows가 리뷰 작업에서도 "구매일자 빈 행 N건"을 dateEmpty로 세어 화면에 고지(지금은 datelessFilled만 보임) — 판정은 불변, 보고만 추가(조용한 누락 금지 규율).
  • URL 열 하이재킹 방지(즉시 위험 수리): columnResolver.js:174 urlKeywords가 'url' 부분일치·첫 매칭 승이라 「블로그URL」·「포스팅URL」 열이 상품URL보다 왼쪽이면 review_index.product_url이 참여자 블로그 주소로 덮인다(리뷰어 화면 상품 링크로 노출). → URL 열 판정에서 '블로그'·'포스팅' 포함 헤더 제외. 블로그 열 도입 전 선행 필수.

M4 — 포스팅URL 전용 제출 (리뷰캡처 대체)

열 2종의 위치 (요구 3)

  • 블로그URL = 참여자 신원 열(이 블로그의 주인이 참여). 구매양식 제출 매퍼(mapOrderToSheetRow)에 '블로그' 포함 헤더 규칙 추가 — 값이 있을 때만 쓰고(null 반환 = 안 씀·안 지움), 라이브 셀이 비어 있을 때만(blank-only — 관리자 선기입 보존, 옵션 칸 규율과 동일). 현재 매퍼는 이 헤더를 어느 규칙에도 안 태워 null이므로 기존 주문 경로 무회귀.
  • 포스팅URL = 결과물 열. 기존엔 「비고(닉네임)」 열을 대용해 왔다 — 제출 경로는 이미 존재: POST /api/submit/review가 memo를 /비고/ 우선 → /포스팅/ 폴백으로 시트에 쓴다(submit.routes.js:607–622). 블로그 탭은 이 우선순위를 뒤집는다(/포스팅/ 우선 → 없으면 /비고/ 폴백 = 바를참스킨 기존 시트 호환). 신규 블로그 작업표 표준 열에는 「블로그URL」·「포스팅URL」 열을 기본 포함.

URL만으로 제출 완료 (요구 3-2)

  • 리뷰어 화면(search-app.js): blog 탭(/api/search 응답에 workKind 동봉)이면 리뷰캡처 드롭존 대신 「포스팅URL」 전용 입력창을 그린다. 이미지 1장 이상 필수 게이트(:3102)는 blog에서 URL 존재로 대체. 다건·슬롯 경로 포함 첨부 경로 전부 같은 분기(사본 금지 규율 — 기존 csMemo/mrMemo 입력칸을 URL 입력으로 승격, placeholder의 "블로그체험단인 경우 포스팅URL (선택)"이 blog 탭에서는 "포스팅URL (필수)").
  • 서버(POST /api/submit/review): blog 탭이면 memo(=포스팅URL) 필수 + http(s) URL 형식 검증, 파일 0건 허용. 완료 판정 = URL 존재 → review_index.is_submitted=TRUE + submit_col 시각 기입(기존 Step1·Step3 경로 재사용). 무시트 탭은 sheetlessStatus.markStatusCell을 포스팅 칸(row_json 병합)까지 확장(submit_col 기록과 같은 패턴 — 장부 재생성에도 보존되는 W3-a 규율).
  • 기존 버그 동시 수리: 큐 재시도(syncQueue.service.js:570–598 review_submit 핸들러)가 payload의 memo를 안 읽어 재시도 시 포스팅URL이 유실된다 — 핸들러가 memo를 소비하도록 수정(블로그 무관하게도 현행 버그).
  • 검수·AI 격리: blog 작업은 캡처가 없으므로 1차 필터(precheck)·2차 검수(reviewInspect)·캡처 슬롯 파생·리뷰 이미지 미리보기 대상에서 제외(work_kind='blog' skip — 판정 실패는 현행 경로 = fail-open). 포스팅URL의 내용 검수(포스팅 실존·본문 검사)는 범위 밖(후속).
  • 리뷰어 홈: 완료 카드는 기존 isSubmitted 흐름 그대로(제출일 = submit_col 기입 시각). 완료 카드에 포스팅URL 링크 표시는 후속(완료 행은 row:{}로 비워 반환되므로 별도 필드 필요).

M5 — 블로그 모집공고 (블로거 직접 참여)

  • 공고: recruit_campaigns.work_kind='blog'(발행 프리필 = 작업오더 work_kind). 카드에 「블로그」 배지, 공고 모달은 리뷰타입 카드 숨김 + 버튼군 UI 있는 화면에서만 전송(축약 화면이 저장해도 설정이 안 풀리는 기존 원칙). 정원·홀드·리뷰비·기간별리뷰비 등 참여형 인프라는 전부 그대로 재사용(분기 최소).
  • 참여(apply) 시 블로그URL 필수 입력(가정 A2): campaign_applications.blog_url(migration 099) — blog 공고에서 미입력이면 403 blog_url_required(자리 미점유, 내정보 게이트와 같은 위치). campaign.html에 입력 시트(옵션 바텀시트 패턴 재사용). URL은 http(s) 형식 검증 + 길이 상한.
  • 구매양식 → 시트 기록: 제출 시 홀드 서버권위(_authoritativeHold)가 blog_url을 함께 읽어 orderData.blogUrl로 전달 → 매퍼의 '블로그' 헤더 규칙(M4)이 그 행 블로그URL 칸에 기입(blank-only). 홀드 없는 제출(레거시·수기)은 값이 없어 안 쓴다(지움 사고 0).
  • 관리자 수기 배정: 작업보드 그리드 편집(오버레이)으로 블로그URL·구매일자를 직접 입력 — 기존 participant_edits 경로 그대로, 신규 코드 0.
  • 블로거 신원·검색 매칭은 기존 phone8 체계 그대로(블로그URL은 표시·기록용 열이지 매칭 키가 아니다 — 매칭 키를 늘리면 무인증 검색 보안 게이트가 흔들린다).
