1. 지금 무슨 일이 벌어지고 있나

증상 — 8월부터 리뷰비를 1,000원 → 1,500원으로 올렸더니, 7월에 이미 참여를 마친 리뷰어의 “리뷰 내역” 카드에도 1,500원이 뜹니다. 리뷰어는 “1,500원이라고 적혀 있는데 왜 1,000원만 들어왔냐”고 문의합니다.

원인 — 리뷰비는 값이 하나뿐이고, 화면은 “지금 값”을 실시간으로 읽는다

리뷰비는 공고 한 건당 recruit_campaigns.review_fee 딱 한 칸입니다. 리뷰어 화면은 참여 이력을 그릴 때마다 그 칸의 현재 값을 다시 읽습니다 — 참여 당시 금액을 어디에도 적어두지 않기 때문에, 값을 고치면 과거·현재가 한꺼번에 바뀝니다.

위치하는 일지금 결과
recruit_campaigns.review_fee공고당 리뷰비 1개 저장기간 개념 없음
/api/reviewer/review-earnings리뷰 내역 카드의 리뷰비 배지 + 누적/받을예정 합계탭에 연결된 최신 공고의 현재 값으로 전건 계산
참여상품 정보 팝업 · 공고 카드리뷰비 표기동일하게 현재 값
돈이 걸린 부분 — 이 값은 화면 표기만이 아니라 리뷰어의 “누적 금액” 합계에도 들어갑니다. 과거 건이 1,500원으로 계산되면 리뷰어가 보는 정산 예상액 자체가 틀립니다.

왜 “공고를 새로 하나 더 만들기”로는 안 되나

  • 리뷰비는 탭(작업 시트)에 연결된 공고를 따라 붙습니다. 같은 탭에 공고를 하나 더 만들면 과거 건까지 새 공고 쪽으로 붙어 결과가 같아집니다(탭당 최신 1건을 봅니다).
  • 작업·정원·관제가 공고 단위라 공고를 쪼개면 모집 현황이 둘로 갈라집니다.
  • 실제로 필요한 건 “다른 캠페인”이 아니라 같은 캠페인의 기간별 단가입니다.

2. 해결 모델 — 구간표 + 참여시점 고정

두 가지를 같이 넣습니다. 하나만으로는 안 됩니다.

① 기간 구간표 신규

공고에 “언제부터 얼마” 줄을 여러 개 등록합니다.
7/1부터 1,000원 · 8/1부터 1,500원
→ 앞으로 어떤 금액을 줄지를 관리자가 미리 예약해 둘 수 있습니다.

② 참여시점 고정(스냅샷) 신규

리뷰어가 참여를 확정하는 순간 그때의 금액을 그 건에 새겨 둡니다.
→ 나중에 구간표를 어떻게 고쳐도 이미 참여한 건의 표기는 절대 안 바뀝니다.

왜 둘 다인가 — 구간표만 있으면 “7월 구간을 실수로 지우거나 날짜를 고쳤을 때” 과거 표기가 또 흔들립니다. 스냅샷만 있으면 “다음 주부터 올릴 금액”을 미리 잡아둘 수 없고, 스냅샷이 없는 과거 데이터를 설명할 방법이 없습니다. 구간표 = 앞으로 줄 금액 / 스냅샷 = 이미 준 금액으로 역할을 나눕니다.

리뷰비를 정할 때 보는 순서 (한 건에 대해)

1순위참여 건에 새겨진 금액
스냅샷 → 2순위그 건의 구매일로 구간표 조회
과거 데이터 구제 → 3순위오늘 기준 구간
아직 참여 전 → 폴백기존 review_fee
구간 미설정 공고
기존 공고는 아무것도 안 바뀝니다 — 구간을 하나도 등록하지 않으면 폴백(기존 review_fee)만 동작합니다. 즉 기능을 켜지 않은 공고는 지금과 100% 동일합니다(참여형 스위치·타계정 허용과 같은 opt-in 방식).

7월 건을 1,000원으로 되돌리는 방법 (이번 사고 수습)

과거 참여 건에는 스냅샷이 없으므로 2순위(구매일 → 구간표)가 구제합니다. 관리자가 이 공고에 7/1 = 1,000원 / 8/1 = 1,500원 두 줄만 등록하면, 7월에 구매한 행은 다음 조회부터 자동으로 1,000원으로 표시됩니다. 데이터 수기 정정 불필요.

ALTER TABLE campaign_applications ADD COLUMN review_fee_snapshot INTEGER;

종료일을 저장하지 않는 이유 — 시작일·종료일을 둘 다 받으면 관리자가 7/31과 8/1 사이에 빈 하루를 만들거나 구간을 겹치게 입력할 수 있고, 그날 참여한 건은 금액이 없어집니다. 시작일만 받으면 구조적으로 빈틈·겹침이 불가능합니다(레포의 “판정 단일 출처” 규율과 같은 맥락).

기준일(어느 구간에 속하는가)을 정하는 순서

순위기준근거 · 비고
1참여 건의 review_fee_snapshot참여 확정(홀드 확정 / 구매양식 제출) 시 기록. 있으면 무조건 이 값 — 구간표를 나중에 고쳐도 불변
2연결된 주문의 제출일(KST)스냅샷 이전에 접수된 건 구제. 실제로 산 날

4오늘(KST)아직 참여 전 — 공고 카드·목록의 “지금 참여하면 받는 금액”
—구간 0개면 recruit_campaigns.review_fee기존 동작 그대로(폴백)
완화 금지선 — 스냅샷이 있는 건에 “구간표가 더 최신이니까”라는 이유로 구간값을 덮어씌우면 이번 사고가 그대로 재현됩니다. 1순위는 항상 스냅샷이고, 이미 지급한 금액을 정정해야 할 땐 관리자가 그 건을 지목해 고치는 별도 조치(감사 로그 동반)로만 처리합니다.

계산은 한 곳에서만 단일 출처

utils/campaignFee.js에 resolveReviewFee({schedules, snapshot, orderDate, sheetDate}) 순수함수를 두고, 소비처(리뷰 내역 API·팝업·카드·작업내용)는 전부 이 함수만 부릅니다. 표시 규칙을 화면마다 따로 만들면 “카드는 1,000원인데 합계는 1,500원”으로 갈라집니다.

5. 리뷰어 화면 — 무엇이 달라지나

지금 (7월 참여자 화면)

항목표시
7월 참여 카드리뷰비 1,500원 ❌
누적 금액1,500 × 3건 = 4,500원 ❌
실제 입금1,000 × 3건 = 3,000원

→ “1,500원이라면서 왜 3,000원만 들어왔죠?” 문의 발생

변경 후 (7월 참여자 화면)

항목표시
7월 참여 카드리뷰비 1,000원 ✅
누적 금액1,000 × 3건 = 3,000원 ✅
8월 신규 참여리뷰비 1,500원 ✅

→ 화면 = 입금액. 문의 자체가 안 생김

참여 전 리뷰어에게도 인상 예고를 보여줄 수 있음 선택

[쿠팡] 영양제망고 7·8월 리뷰

상황동작
구간을 하나도 등록 안 함지금과 완전히 동일(기존 review_fee). 이 기능은 opt-in

기능 장애킬스위치 CAMPAIGN_FEE_SCHEDULE=0 → 전건 기존 review_fee로 즉시 복귀
배포 직후 한 번은 눈으로 확인할 것 — 리뷰어의 누적 금액이 바뀌는 변경입니다. 구간을 등록하기 전(= 폴백 상태)에 합계가 배포 전과 동일한지 먼저 확인한 뒤, 문제의 공고부터 구간을 넣는 순서를 권장합니다.

8. 확정된 결정 · 구현 결과

질문확정구현
기준 날짜참여(구매)한 날 참여(홀드) 시점에 금액을 새기고, 스냅샷이 없는 과거 건은 주문 제출일 → 시트 구매일자 순으로 판정
7·8월 과거 표기 정정정정함 그 공고에 7/1=1,000 · 8/1=1,500 두 줄만 등록하면 7월 건이 자동으로 1,000원으로 표시됨(데이터 수기 정정 없음)
인상 예고 노출안 함 리뷰어 카드에는 오늘 적용 금액 하나만 표시. 예고 배지 미구현
상품비 기간별불필요 상품비는 실제 주문 금액에서 오므로 범위 밖. 옵션 결제금액도 종전 그대로

운영 순서 (권장)

  1. 배포 직후, 구간을 등록하기 전에 리뷰어 누적 금액이 배포 전과 같은지 확인(구간 0개 = 기존 동작).
  2. 문제의 공고를 통합 작업대 › 모집공고에서 열고 📅 기간별 리뷰비를 켠 뒤 두 줄 입력 → 저장.
  3. 7월 참여자 화면에서 1,000원으로 표시되는지 확인. 8월 신규 참여는 1,500원.
이후 참여자는 참여 시점 금액이 새겨집니다 — 배포 이후의 참여 건은 나중에 구간을 고쳐도 표기가 바뀌지 않습니다. 반대로 배포 이전의 과거 건은 스냅샷이 없어 구간표를 고치면 표기가 따라 바뀝니다(이번 정정이 가능한 이유).
문제가 생기면 — Railway 환경변수 CAMPAIGN_FEE_SCHEDULE=0 하나로 전건이 기존 review_fee로 즉시 복귀합니다(구간 데이터는 남습니다).
