PRD · Implementation — v1.1 (방향 확정 · M1 착수)

작업표 생성
통합작업대에서 업체별 작업을 바로 만든다

지금은 100건짜리 작업을 시작하려면 1번부터 100번까지 행이 미리 준비된 구글시트를 만들어 작업오더에 첨부해야 합니다. 이 문서는 그 시트 준비를 없애고, 통합작업대가 100건짜리 작업표를 자동으로 만들어 주는 방식의 기획(PRD)과 구현 방법을 담은 시안입니다. 비개발자도 읽을 수 있게 썼고, 개발 참고용 각주는 회색 상자로 분리했습니다.

통합작업대 (workdesk) 작업오더 연동 시트 의존 축소 Track B 확장 M1 배포됨 2026-08-04
01

지금은 어떻게 일하고 있나

작업 하나를 시작하는 데 구글시트 준비가 항상 먼저입니다. 100건짜리 작업이면 누군가 시트에 100줄을 만들고, 날짜를 나눠 적고, 옵션을 줄마다 배정한 뒤 그 URL을 작업오더에 붙여야 시스템이 일을 시작할 수 있습니다.

① 시트 수작업 준비
100행 생성 · 날짜 분배 · 옵션 배정 · 서식 복사 (사람 손)
→
② 작업오더 제출
AE가 시트 URL 첨부 (URL 없으면 제출 불가)
→
③ 관리자 접수
접수 시점에 탭이 시스템에 등록됨
→
④ 시스템이 시트를 읽음
읽은 내용으로 검색·제출·모집공고가 활성화
  • 준비 시간이 든다 — 작업마다 시트 100줄을 만들고 날짜·옵션을 손으로 나눈다.같은 일을 매번 반복. 서식이 담당자마다 조금씩 달라 시스템 인식률도 흔들린다.
  • 시트가 단일 장애점 — 직원이 행을 삭제하면 아래 기록이 전부 밀리고, 수기 입력과 시스템 기록이 경합해 "유령 기록" 사고가 났던 이력이 있다.이를 막으려고 시트 상단 경고문, 사후검증, 자동복구 같은 방어 장치를 계속 덧대 왔다.
  • 구글 읽기/쓰기 한도(쿼터)를 계속 관리해야 한다 — 분당 호출 수를 나눠 쓰는 장치가 이미 여러 겹이다.작업이 늘수록 이 한도가 성장의 상한이 된다.
02

무엇으로 바꾸나 — 한 문장 요약

"100건 작업이면, 통합작업대가 100건짜리 작업표를 미리 만들어 준다." 작업오더에 적힌 모집인원·일건수·옵션만으로 표의 뼈대가 자동으로 완성되고, 담당자는 미리보기에서 확인·조정만 하면 됩니다.

① 작업오더 제출
시트 URL 없이도 제출 가능 (인원·일건수·옵션이 재료)
→
② 작업표 자동 생성
100행 + 날짜 분배 + 옵션 배정 + 표준 컬럼이 자동 완성
→
③ 미리보기 · 확인
담당자가 열/행/날짜를 눈으로 확인, 필요하면 수정 후 [생성]
→
④ 즉시 작업 시작
모집공고 발행·리뷰어 제출·정산이 이 표 위에서 진행
핵심 원칙 — 새로 짓지 않고, 이미 있는 것을 잇는다

통합작업대에는 이미 작업별 명단 표(참여자 원장), 발주 기준 빈 슬롯 생성 기능, 행별 메모·커스텀 열, 편집 기록 원장이 돌아가고 있습니다. 작업표 생성은 이 부품들을 "작업 시작 시점"으로 앞당겨 꿰는 일이지, 별도 시스템을 새로 만드는 일이 아닙니다.

참고(개발): campaign_participants(명단 원장) · prepareRosterFromWorkOrder/prepareRosterSlots(발주 기준 gap-fill 빈 슬롯 생성 — 이미 구현) · participant_edits(오버레이 편집) · trackb_custom_columns(커스텀 열) · trackb_work_order_links(발주↔탭 링크)
03

어떤 항목이 고정이고, 어떤 항목이 변칙인가 — 근거 데이터

"표에 어떤 열이 필요한가"는 추측할 필요가 없습니다. 시스템에는 이미 운영 중인 모든 시트 탭의 열 구성 스냅샷과 열 의미 판정 기록이 쌓여 있어, 실제 데이터로 고정/변칙을 분류할 수 있습니다.

이미 쌓여 있는 학습 재료 3가지

  • 전 탭 열 구성 스냅샷 — 5분마다 모든 시트를 복제해 두는 장치(RAW 미러)가 탭마다 "감지된 헤더 목록"을 보관 중.수십 개 탭의 헤더를 집계하면 "거의 모든 탭에 있는 열"과 "일부 탭에만 있는 열"이 통계로 갈린다.
  • 열 의미 판정 기록 — 어떤 헤더가 수취인·연락처·결제금액 등으로 판정됐는지의 매핑 원장과 판정 근거 기록.헤더 이름이 탭마다 달라도("연락처"/"전화번호"/"핸드폰") 같은 의미로 묶을 수 있다.
  • 제출·기입 실적 — 어떤 열이 리뷰어 제출로 채워지고, 어떤 열은 관리자가 미리 적어 두는지(작업지시)의 실사용 기록."시스템이 쓰는 칸 / 사람이 미리 적는 칸 / 끝까지 비는 칸"을 구분하는 근거.
참고(개발): raw_sheet_tabs.detected_headers(탭별 헤더 스냅샷) · tab_column_mappings + index_master.detect_source(컬럼 판정 SoT/관측) · mapOrderToSheetRow 키워드 표(제출이 채우는 칸의 단일 출처) · optionWriteColumns(작업지시 칸 판정)

분류 결과 — 3계층 템플릿

코어(고정) — 거의 모든 작업에 공통 자동 채움 — 생성 시 시스템이 값까지 넣는 열 작업별(변칙) — 채널·작업 유형에 따라 붙는 열
번호 구매일자 옵션 / 리뷰옵션 주문자 수취인 쿠팡ID · 네이버ID 연락처 배송주소 은행 계좌번호 예금주 결제금액 주문번호 리뷰제출 입금 비고 회차/차수 현금영수증 관련 커스텀 메모 열
계층무엇이 결정하나예시생성 시 동작
① 코어(고정) 없음 — 항상 포함 주문자·수취인·연락처·주소·은행·계좌·예금주·결제금액·주문번호·리뷰제출·입금·비고 빈 칸으로 준비. 리뷰어 구매양식 제출이 채운다.
② 채널 레이어 구매채널 (상품 URL로 자동 판정 — 이미 있는 기능) 쿠팡→쿠팡ID열, 네이버→네이버ID열, 동시진행(NC)→두 열, 현영 탭→현금영수증 슬롯 채널에 맞는 열만 자동 추가.
③ 작업 레이어 작업오더 내용 + 담당자 추가 옵션열(옵션 2종 이상일 때), 리뷰형태(포토리뷰/텍스트 — 작업지시 선기입), 회차, 자유 메모 열 작업오더에서 자동 제안 → 미리보기에서 담당자가 추가·삭제.
학습은 "제안"까지만, 확정은 사람이

헤더 통계로 만든 템플릿은 미리보기의 기본값일 뿐입니다. 실제 표 생성은 담당자가 미리보기에서 확인하고 누른 뒤에만 일어납니다. 자동 분류가 틀려도 잘못된 표가 조용히 만들어지는 일이 없게 하는 안전장치입니다. (옵션 칸이 "상품옵션"인지 "작업지시"인지 헤더만으로 구분되지 않는다는 운영 교훈이 이미 문서화되어 있습니다.)

04

작업표는 이렇게 만들어진다 — 행 자동 채움 규칙

열(템플릿)이 정해지면, 행은 작업오더의 숫자 3개(모집인원 · 일건수 · 옵션표)로 자동 완성됩니다. 지금까지 사람이 시트에 손으로 하던 배분을 규칙으로 옮긴 것입니다.

행 수 · 번호

모집인원이 100이면 1~100번 행 100줄이 생성됩니다. 번호는 시스템이 매기고 바뀌지 않습니다.

구매일자 자동 분배

일건수가 20이면 1~20행 = 1일차, 21~40행 = 2일차 … 식으로 날짜가 자동 배정됩니다. 시작일·휴무 요일(예: 주말 제외)을 미리보기에서 고르면 실제 달력 날짜로 환산됩니다.

모집 일정과 자동으로 한 몸이 된다

지금도 시스템은 "시트의 날짜 칸"을 읽어 그날 모집 정원을 정합니다(시트 일정 자동 인식). 작업표가 날짜를 직접 만들면 그 규칙이 역방향으로 그대로 재사용되어, 날짜별 정원·이월·휴무일 처리가 별도 개발 없이 이어집니다.

옵션 배정

작업오더의 옵션표(옵션명·수량)가 있으면 옵션별 수량만큼 행에 나눠 적습니다. 예: 골라담기 40 / 콰이어트 30 / 어나더 30 → 해당 행의 옵션 칸에 미리 기입.

작업지시 선기입

"포토리뷰" 같은 리뷰형태(작업지시)는 전 행에 미리 적어 둘 수 있습니다. 시스템은 값이 있는 옵션 칸은 절대 덮어쓰지 않는다는 기존 규칙(blank-only)을 그대로 따르므로, 선기입 값이 제출 과정에서 지워지는 사고는 구조적으로 차단됩니다.

나머지 칸

주문자·수취인·연락처 등 코어 열은 빈 칸으로 두고, 리뷰어의 구매양식 제출이 실시간으로 채웁니다(지금과 동일한 경로).

참고(개발): 날짜 분배는 campaignSchedule.service(063)의 파생 규칙("그 날짜의 행 수 = 그날 정원")을 생성 방향으로 재사용 · 옵션 배정은 prepareRosterSlots의 라운드로빈 로직 확장 · 선기입 보호는 orderLedger.filterOptionWritesBlankOnly 기존 불변식 그대로

06

구현 방식 — 기존 시스템과 어떻게 이어지나

가장 중요한 설계 결정은 "시트를 언제까지, 어떻게 두는가"입니다. 한 번에 끊지 않고, 작업 단위로 안전하게 넘어가는 3개 모드를 둡니다.

모드작업표(작업대)구글시트언제 쓰나
A. 하이브리드
(출시 기본값)		 작업표가 먼저 생성됨 (화면·편집의 기준) 시스템이 같은 구성의 시트를 자동 생성해 뒤에서 동기화 — 주문 기록·정산 등 기존 파이프라인은 시트 경유 그대로 전환기 전체. 기존 파이프라인(행 배정·사후검증·백업)을 한 줄도 안 바꾸고 "시트 준비 수작업"만 없앤다.
B. DB 원본 작업표가 유일한 원본 보기용 사본 (시스템이 써 주기만 함) Track B 전환 스위치(source_of_truth)가 'db'로 플립된 작업 — 이미 만들어진 게이트(불일치 0 검증)를 그대로 통과해야 한다.
C. 시트 없음 작업표만 존재 생성 안 함 최종 단계. 광고주 열람도 통합작업대 광고주 링크로 대체된 뒤.

하이브리드(A)가 기본값인 이유

  • 주문 기록 경로가 시트 복제본(RAW 미러)을 기준으로 행을 배정한다 — 시트가 있는 한 이 검증된 경로를 그대로 쓴다.라이브 핫패스를 건드리지 않는 것이 이 저장소의 제1 원칙.
  • 백업·재해복구 리허설이 시트/Drive 기준으로 이미 구축돼 있다.
  • 광고주·외부 공유가 아직 시트 습관이다 — 습관 전환은 강제하지 않고 광고주 링크 기능이 흡수한다.

새로 만드는 것 (최소 구성)

  • 템플릿 원장 — 작업표의 열 구성을 저장하는 표 1개 (업체·채널별 기본값 + 작업별 확정본).신규 테이블 1~2개. 기존 테이블 변경 없음(추가만 — Track B 3원칙).
  • 헤더 학습 리포트 — 미러된 전 탭 헤더를 집계해 고정/변칙 통계를 내는 조회 기능 (읽기 전용).
  • 생성 API + 미리보기 화면 — 발주 기준 빈 슬롯 생성(이미 있음)에 날짜 분배·옵션 배분·선기입을 얹은 확장판.
  • 시트 자동 생성(모드 A) — '새 시트생성' 기능(이미 있음)에 템플릿 헤더 + 행 선기입을 추가.
참고(개발): 모드 A의 시트 생성은 기존 create-campaign-sheet 경로 재사용(시트/탭 생성·SA 권한부여 유지, DB 등록은 접수 시점 이연 규칙 그대로) · 선기입 행 쓰기는 배치 1회(쿼터 계산: 100행 ≈ 쓰기 1~2콜) · 날짜 칸 선기입은 063 시트 일정 인식이 그대로 읽어 모집 일정으로 파생 — 즉 시트를 받아 쓰던 기존 규칙과 완전 호환 · 모드 B 게이트는 부품6 source_of_truth + parity real=0 기존 장치 재사용
건드리지 않는 것 (안전선)

① 구매양식 제출 경로(주문원장 → 행 배정 → 시트 기록)는 무변경 — 작업표는 그 결과를 "보여주는 표"에서 출발한다. ② 기존 작업(이미 시트로 진행 중)은 아무 영향 없음 — 이 기능은 신규 작업의 선택지다. ③ 옵션 칸 blank-only, 행 배정 신원 가드, 사후검증 등 사고 재발방지 장치는 전부 그대로 살아 있다.

07

단계별 로드맵

각 단계는 독립적으로 배포·검증 가능하며, 앞 단계가 끝나야 다음이 의미를 갖습니다.

M1
헤더 학습 리포트 (읽기 전용)  ✓ 배포됨
미러된 전 탭의 열 구성을 집계해 고정/변칙 통계 화면을 만든다. 이 문서의 3계층 분류를 실데이터로 확정. → 통합작업대 [작업표] 탭. 함께 작업오더 시트 URL 필수 해제(Q2 확정) 적용.
남은 것: 관리자가 리포트를 보고 "우리 표준 코어 열"을 확정 → M2 기본 템플릿으로 고정
M2
템플릿 원장 + 생성 미리보기 + 작업표 생성 (모드 A)
작업오더 펼침행 [작업표 생성] → 미리보기 → 100행 생성 + 동일 구성 시트 자동 생성·동기화. 신규 작업 1~2건으로 파일럿.
완료 기준: 시트 수작업 0으로 작업 1건이 모집→제출→정산까지 완주
M3
운영 확대 + 학습 고도화
업체·채널별 기본 템플릿 자동 추천(직전 작업 복사 포함), 인원 변경 시 증설(gap-fill)·축소 처리, 작업오더 폼에서 시트 URL을 선택 항목으로 완화.
완료 기준: 신규 작업의 절반 이상이 작업표 생성으로 시작
M4
시트 축소 (모드 B → C)
Track B 전환 게이트(불일치 0)를 통과한 작업부터 DB 원본 플립. 광고주 열람은 광고주 링크로 대체. 시트는 보기용 → 생성 안 함 순으로 축소.
완료 기준: 신규 작업 기본값이 "시트 없음"
08

리스크와 방어

위험무슨 일이 생기나방어
템플릿 오분류 학습이 "옵션" 칸을 잘못 읽어 필요한 열이 빠지거나 불필요한 열이 생김 학습은 제안까지만 — 생성은 항상 미리보기에서 사람이 확정. 생성 후에도 커스텀 열 추가/숨김으로 교정 가능.
인원 변경 100건으로 생성했는데 120건으로 증액, 또는 80건으로 축소 증액 = 부족분만 추가 생성(이미 있는 gap-fill 방식·중복 없음). 축소 = 빈 행만 숨김 처리(제출 있는 행은 보호), 이력 보존.
이중 관리 혼선 (모드 A) 작업표와 시트가 어긋난 걸 늦게 발견 이미 운영 중인 대조 검증(parity)·사후검증이 그대로 감시. 어긋나면 관측 대시보드에 불일치로 표시.
날짜 분배 실수 휴무일 설정을 빼먹어 주말에 모집이 열림 미리보기에 날짜 분배 전체를 보여주고 합계 검증(≠ 총건수면 생성 잠금). 생성 후에도 날짜 칸 수정 = 즉시 일정 반영(기존 시트 일정 규칙과 동일).
권한 아무나 표를 만들거나 지움 생성·수정은 작업오더 편집 명단과 같은 권한(마스터는 항상 허용, 명단 조회 실패 시 읽기 전용 — 기존 fail-closed 규칙). 광고주는 읽기 전용 그대로.
기존 파이프라인 회귀 주문 기록·검색 등 라이브 경로가 영향받음 모드 A에서 라이브 경로 무변경(시트 병행). 회귀가드 테스트 신설 + 레드-블루-심판 검증을 거쳐 배포(저장소 표준 절차).
09

확정된 방향 (2026-08-04)

착수 전 4개 결정 사항이 모두 확정되었습니다. 아래가 이 프로젝트의 기준선입니다.

항목확정의미
Q1. 출시 모드 A. 하이브리드 (시트 자동 생성·병행) 주문 기록·행 배정 등 라이브 경로는 한 줄도 바뀌지 않는다. 없어지는 것은 "시트를 사람이 준비하는 일"뿐.
Q2. 시트 URL 필수 해제 즉시 해제 (M1과 함께 배포) AE 작업오더 제출에서 시트 URL이 선택 항목이 되었다. 아래 "지금 적용된 것" 참조.
Q3. 템플릿 소유 단위 채널별 기본 (쿠팡/네이버/올리브영/카카오메이커스) 업체별 원장은 만들지 않는다. 채널이 열 구성을 결정하고, 작업별 차이는 미리보기에서 조정.
Q4. 광고주 열람 광고주 링크로 즉시 전환 하이브리드 기간에도 광고주에게 시트를 새로 공유하지 않는다. 업체별 고유 접속 링크(통합작업대)가 창구.
Q2 즉시 해제의 실제 동작 — 제출은 선택, 접수는 여전히 탭이 필요

접수(接受)는 그 탭을 시스템에 등록하는 단일 관문이라, 등록할 탭이 없으면 접수가 성립하지 않습니다. 그래서 제출 단계의 필수만 풀고 접수 게이트는 그대로 뒀습니다 — 이 덕분에 "접수된 오더는 연결 탭 정보를 항상 갖는다"는 기존 전제(모집공고 자동 채움이 여기에 의존)가 깨지지 않습니다. M2 전까지 시트 미첨부 오더는 관리자가 시트탭 주소를 채워 접수하고, M2가 오면 그 자리를 [작업표 생성]이 대신합니다.

10

지금 적용된 것 (M1 배포분)

① 작업오더 시트 URL — 선택 항목으로

  • AE 오더 제출 화면에서 시트 URL 옆의 * 표시가 사라졌다. 비워두고 제출할 수 있다.
  • 내가 보낸 오더 목록에서 시트를 안 붙인 건은 "시트 미첨부 — 접수 시 작업표 생성"으로 표시된다(빈 값이 조용히 "-"로 숨지 않는다).
  • 인트라넷에서 넘어오는 오더도 동일(서버 검증 해제).
  • 접수 화면은 시트가 없으면 "시트탭 주소를 입력하거나 작업표를 생성한 뒤 접수해주세요"로 안내한다.

② 설정 › 작업표 표준 열 — 리포트 + 우리 표준 열 확정

  • 어디에 있나: 통합작업대 설정 탭, 그리고 관리자 대시보드 설정 탭 — 같은 화면 한 벌이라 어느 쪽에서 바꿔도 결과가 같다. 관리자·마스터만 보인다.
  • 표준 코어 열 편집: 항상 들어갈 열을 추가·삭제·순서변경한다. 순서가 그대로 표의 열 순서가 된다. [통계에서 불러오기]를 누르면 우리 시트들이 실제로 가장 많이 쓰는 이름(번호·구매일자·주문자·수취인·연락처…)으로 한 번에 채워진다.
  • 열마다 "시스템 인식: ○○" 표시 — 그 이름으로 만들면 구매양식 제출이 무엇을 채우는지 즉시 보인다. 이름이 곧 동작을 정한다(‘연락처’로 만들어야 전화번호가 들어간다). 같은 역할이 두 칸이면 경고가 뜬다.
  • 채널별 추가 열: 쿠팡·네이버·올리브영·카카오메이커스 각각에 그 채널일 때만 붙는 열(예: 쿠팡ID).
  • 헤더 학습 리포트(펼치기): 전 탭 열 구성을 코어 후보 / 작업별·채널별 / 미분류로 집계 + 비율 + 실제 헤더 이름 변형 + ⚠ 상태칸 겹침 경고. 읽기 전용이고 구글시트 재읽기 0(미러 스냅샷만).
  • 여기서 저장한 표준 열이 M2 작업표 생성 미리보기의 기본값이 된다.
분류 규칙을 사람이 적어 넣지 않았다 — 제출 코드에서 파생한다

"이 헤더가 수취인인가 연락처인가"의 판정은 리뷰어 제출이 실제로 어느 칸에 쓰는지를 결정하는 바로 그 코드를 실행해 되읽는 방식으로 얻습니다(각 항목에 표식을 넣어 어느 열에 꽂히는지 관측). 판정 규칙을 따로 베껴 두면 "제출은 A열에 쓰는데 작업표는 B열을 만드는" 어긋남이 조용히 생기기 때문입니다. 회귀 테스트가 이 파생 관계를 고정합니다(39개 검사).
