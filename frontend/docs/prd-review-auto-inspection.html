리뷰 자동검수 시스템 구현계획서

리뷰어가 제출한 리뷰 캡처가 업체(광고주)에게 전달되기 전에, 시스템이 진짜 리뷰인지 · 우리 상품 리뷰인지 · 재탕/중복이 아닌지를 자동으로 검수한다. 현재 리뷰이미지 제출 로직과 구글드라이브 폴더 구조를 그대로 활용하며, 이미 운영 중인 AI 검수(3단계 캡처 검수) 인프라를 확장하는 방식으로 설계했다.

#검수 조건(요구)구현 방식판정 재료비용
1 실제 리뷰파일 여부
네이버 빨강별점 / 쿠팡 노란별점 예시이미지 첨부 저장		 ★ 1차 = 첨부 즉시(§4 경로 0) — 제출 전에 그 자리에서 판별해 잘못된 파일을 되돌린다. 기존 AI 판별(classifySubmissionImage)을 종합검수 프롬프트로 확장 — 리뷰화면 여부 + 채널(네이버/쿠팡/기타) 판별. 관리자 설정탭에서 채널별 별점 예시이미지를 등록(현금영수증 발행방법 이미지와 동일 패턴)하면 판정 시 참조 이미지로 함께 전송(few-shot). AI 비전 1콜
(기존 콜 대체 = 순증 최소)		 낮음
2 상품명 대조
작업오더 상품명 vs 리뷰이미지 속 상품명 OCR		 같은 AI 콜에서 이미지 속 상품명 텍스트를 OCR 추출 → 기대 상품명과 정규화 유사도 비교. 기대 상품명 우선순위: ① 탭 검수설정 수동입력 → ② 연결된 작업오더(work_orders)의 상품정보. 작업오더가 없으면 관리자 UI에서 직접 입력. AI 비전(동일 콜) + 텍스트 매칭 낮음
3 제출자명 ↔ 리뷰어명
(사용자도 필요성 불확실)		 1단계에서는 판정 제외 권고. 리뷰 화면의 작성자 표시는 마스킹(홍**, a***1)·닉네임이라 실명과 정확 대조가 불가능하고 오탐이 크다. 다만 OCR로 작성자 표시 텍스트는 수집만 해 두고, 데이터가 쌓인 뒤 유용성을 재평가한다. OCR 수집만(판정 OFF) 보류
4 동일 파일 검사(중복) 업로드 시점에 SHA-256 파일 해시를 계산·저장(base64를 이미 쥔 시점 = 추가 비용 0). 같은 해시가 다른 행·다른 리뷰어·다른 탭에서 재등장하면 중복 판정. 과거 파일은 배치로 Drive에서 내려받아 해시 백필. 파일 해시(DB 대조, AI 불필요) 낮음
5 텍스트 유사도 90%+
중복의심/불량리뷰 분류		 같은 AI 콜에서 리뷰 본문 텍스트를 OCR 추출·저장 → PostgreSQL pg_trgm(이미 설치·검색에서 사용 중)으로 기존 제출 본문과 3-gram 유사도 계산. 0.9 이상 = 중복의심 분류(비교 범위는 같은 탭 우선, 전역은 옵션). OCR(동일 콜) + SQL 유사도 중간
설계 원칙 4줄 요약 — ① 검수는 두 층: 1차 = 첨부 즉시 리뷰어 화면에서(리뷰 화면인가·어느 채널인가), 2차 = 제출 후 관리자 화면에서(상품명·중복·글 겹침). ② 판정 재료는 AI 1콜로 한 번에 뽑고, 이미지 해시 캐시 덕에 1차에서 쓴 결과가 2차에서 재사용된다(콜 순증 0). ③ 중복·유사도는 저장된 해시·텍스트만으로 DB에서 계산한다(이미지 재다운로드 0). ④ 차단은 “리뷰 화면이 아님”이 확실할 때 하나뿐이고, 그마저 2회 후 우회로가 열린다. 판정 불가는 언제나 통과(fail-open).

1현재 구조 분석 (As-Is)

1-1. 리뷰이미지 제출 흐름

1
리뷰어 제출 — 리뷰어 홈/구매양식 화면(search-app.js)에서 캡처 첨부 → POST /api/image/review-upload(diag.routes.js)로 base64 전송. 페이로드에 sheetId · tabName · reviewerName · rowIndex · slotKey(리뷰/현금영수증 슬롯) 포함.
2
폴더 확보 — tab_configs.folder_url이 있으면 그대로, 없으면 ensureReviewFolderPath가 시트제목 → 탭명 → [리뷰] 경로를 자동 생성 후 DB에 저장. 폴더 확보 실패 시 업로드 중단(루트로 새는 것 방지 가드).
3
Drive 업로드 — 파일명 {리뷰어명}_{순번}_{yyyyMMdd_HHmmss}.{확장자}로 업로드(OAuth 우선 → SA 폴백, 소유자 tnaks 보정).
4
기존 AI 검수(3단계) — captureVerify.verifyCapture → Gemini classifySubmissionImage가 리뷰/영수증/기타 형식만 판별. 불일치면 리뷰어 인라인 경고 + reviewer_event_logs(capture_mismatch, 확신도 0.9+는 critical 빨간 알림). fail-open: AI 장애·저확신은 통과, 제출 차단 없음.
5
DB 기록 — 대표 1장은 review_index.review_file_*(031, 'review' 슬롯만), 모든 파일은 review_submissions 원장(032, file_id 유니크 업서트, slot_key 포함)에 적재. 주문 원장(order_submissions.capture_file_id)과도 연결.

② 상품명 대조 (OCR ↔ 작업오더)

판정 목표: 리뷰이미지에 표기된 상품명이 이 탭(작업)의 상품과 일치하는가 — 타 상품 리뷰 제출을 잡는다.

  • OCR 추출: 같은 AI 콜 응답에 productName(이미지에 보이는 상품명 표기, 없으면 빈 값) 필드 추가.
  • 기대 상품명 소스(우선순위):
    1. 탭 검수설정 수동 입력 — 신규 tab_configs.inspect_product_names(TEXT, 줄바꿈 구분 복수 허용). "작업오더에 상품명이 없다면 별도로 입력"하는 요구를 이 칸이 담당. 검수 탭 UI에서 바로 입력.
    2. 연결된 작업오더 — 탭 ↔ 오더 링크로 work_orders.title / product_option / product_options_json에서 상품명 후보 파생(공고 프리필 파서 parseProductLinesToRows 재사용 — "옵션 없음/단일" 서술어 제외 규칙 포함).
  • 매칭 규칙: 정규화(공백·특수문자·괄호 제거, 소문자화) 후 ⓐ 포함 관계 ⓑ 토큰(브랜드·모델명 단위) 일치율로 1차 판정, 애매하면(부분 일치) Gemini에 "같은 상품인가" 텍스트 질의 보조(주소 유사도 검증 verifyAddressMatch와 같은 패턴). 쇼핑몰 화면의 상품명 축약·말줄임(…)을 감안해 부분 포함도 일치로 인정.
  • 기대값이 아예 없으면: 대조 안 함(unverified) — 오탐으로 막는 것보다 "설정하면 검사해 준다"를 UI에서 유도. 판정 불가를 불량으로 취급하지 않는다(fail-open).

③ 제출자명 ↔ 리뷰어명 검수 — 1단계 보류 권고

보류 이유(요구사항에도 "필요한지 잘 모르겠음"으로 명시):

  • 네이버/쿠팡 리뷰 화면의 작성자 표시는 마스킹(홍**, a***1) 또는 닉네임이라 시스템의 리뷰어 실명과 정확 대조가 구조적으로 불가능하다.
  • 가능한 검사는 "첫 글자·길이가 아예 다르면 타인 계정 의심" 정도인데, 닉네임 사용자가 많아 오탐(정상 제출을 의심 처리)이 크다 — 오탐은 막으려던 사고보다 나쁘다는 이 시스템의 규율(캡처 검수·신원게이트와 동일)에 어긋난다.

대신 이렇게: OCR로 작성자 표시 텍스트(authorMask)를 수집·저장만 해 둔다(같은 콜, 비용 0). 데이터가 쌓이면 "같은 작성자 마스킹이 여러 리뷰어의 제출에 반복 등장" 같은 계정 재사용 패턴 분석에 쓸 수 있다 — 판정 ON 여부는 그때 다시 결정(설정 REVIEW_INSPECT_AUTHOR=0 기본 OFF).

④ 동일 파일 검사 (중복파일)

  • 해시 계산 시점: 업로드 핸들러가 base64를 이미 쥐고 있는 시점에 SHA-256 1회 — 추가 다운로드·AI 비용 0. review_submissions.file_hash(신규 컬럼)에 저장.
  • 중복 판정(전부 DB 대조): 같은 해시의 기존 행이
    • 같은 (시트·탭·행·리뷰어) → 재제출/교체로 정상 처리(중복 아님 — Drive는 재업로드마다 새 file_id를 만들므로 이 케이스가 흔하다).
    • 다른 행·다른 리뷰어·다른 탭 → 중복 제출. 상대 파일(어느 탭 누구의 제출인지)을 판정 근거에 함께 저장해 UI에서 나란히 보여준다.
  • 과거분 백필: 기존 review_submissions에는 해시가 없다 → 배치 스윕이 Drive에서 파일을 내려받아(downloadFile) 해시를 채운다. 사이클당 건수 제한(§4)으로 Drive 부하 통제, 최근 제출분부터 역순.
  • 2단계(선택): 완전 동일 파일이 아니라 살짝 수정한 재사용(크롭·밝기 조정)은 지각 해시(dHash 64bit + 해밍거리)로 확장 가능 — 로드맵 M4.

⑤ 리뷰 본문 텍스트 유사도 (중복의심 / 불량리뷰)

  • 본문 추출: 같은 AI 콜 응답의 reviewText(이미지 속 리뷰 본문 전문) — 별도 OCR 엔진 없이 Gemini 비전이 담당.
  • 유사도 계산: PostgreSQL pg_trgm의 similarity()(3-gram) — 한글에서 이미 검색용으로 검증된 확장. 0.90 이상 = 중복의심(env REVIEW_INSPECT_SIM_THRESHOLD, 기본 0.9).
  • 비교 범위: 기본 = 같은 탭 내 기존 제출 본문(같은 상품에 같은 글 복붙이 가장 흔한 불량). 전역(리뷰어가 여러 캠페인에 같은 글 돌려쓰기) 비교는 GIN 인덱스 + % 연산자로 가능하나 비용이 커 옵션(§8 확정 필요 ②).
  • 가드: 본문이 너무 짧으면(기본 30자 미만) 유사도 판정 제외 — "맛있어요 재구매의사 있습니다" 같은 관용구는 누구나 비슷해 오탐이 된다. 같은 리뷰어의 같은 행 재제출은 비교 대상에서 제외(자기 자신과의 유사도).

3데이터 모델 (migration 081 · 비파괴)

기존 테이블은 컬럼 추가만, 판정 결과는 신규 테이블 1개에 격리한다(라이브 핫패스 무접촉 — Track B와 같은 "추가만" 원칙).

-- 081_review_inspections.sql (전부 idempotent)

-- ① 제출 원장에 파일 해시 (업로드 시 즉시 계산, 과거분은 배치 백필)
ALTER TABLE review_submissions ADD COLUMN IF NOT EXISTS file_hash TEXT;
CREATE INDEX IF NOT EXISTS idx_review_sub_hash ON review_submissions(file_hash);

-- ② 탭별 기대 상품명 수동 입력 (작업오더에 상품명이 없을 때)
ALTER TABLE tab_configs ADD COLUMN IF NOT EXISTS inspect_product_names TEXT DEFAULT '';

-- ③ 검수 결과 원장 (파일 1장 = 1행, review_submissions.file_id 기준)
CREATE TABLE IF NOT EXISTS review_inspections (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  file_id         TEXT NOT NULL,            -- review_submissions.file_id (유니크)
  sheet_id        TEXT NOT NULL,
  tab_name        TEXT NOT NULL,
  row_index       INTEGER,
  reviewer_name   TEXT,
  status          TEXT NOT NULL DEFAULT 'pending',
                  -- pending(미검수) | pass | suspect(의심) | fail(확실 불량)
                  -- | unverifiable(판정 불가) | resolved(관리자 확인 종결)
  checks          JSONB DEFAULT '{}'::jsonb, -- 항목별 판정 상세(§아래)
  channel         TEXT,                      -- naver | coupang | etc (판별 결과)
  ocr_product     TEXT,                      -- 이미지 속 상품명 표기
  ocr_text        TEXT,                      -- 리뷰 본문 전문 (유사도 재료)
  ocr_author      TEXT,                      -- 작성자 마스킹 표기 (수집만)
  ai_confidence   REAL,
  ai_model        TEXT,
  inspected_at    TIMESTAMPTZ,               -- AI 판정 완료 시각
  resolved_at     TIMESTAMPTZ,               -- 관리자 확인 시각
  resolved_by     TEXT,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_review_inspect_file ON review_inspections(file_id);
CREATE INDEX IF NOT EXISTS idx_review_inspect_tab
  ON review_inspections(sheet_id, tab_name, status);
CREATE INDEX IF NOT EXISTS idx_review_inspect_status
  ON review_inspections(status) WHERE status IN ('pending','suspect','fail');

-- ④ 예시이미지·설정은 app_settings 키로 (테이블 불필요)
--    review_inspect_sample_naver / review_inspect_sample_coupang = 이미지 프록시 URL

checks JSONB 구조 (항목별 판정 상세)

{
  "format":     { "verdict": "pass|warn|fail|skip", "kind": "review", "channel": "coupang",
                  "expectedChannel": "coupang", "confidence": 0.94 },
  "product":    { "verdict": "pass|warn|fail|skip", "ocr": "히말라야 핑크솔트 400g",
                  "expected": ["히말라야 핑크솔트"], "source": "work_order|manual|none" },
  "duplicate":  { "verdict": "pass|fail|skip", "matchFileId": "…", "matchTab": "…",
                  "matchReviewer": "…" },
  "similarity": { "verdict": "pass|warn|skip", "score": 0.93, "matchFileId": "…",
                  "matchReviewer": "…", "scope": "tab" },
  "author":     { "verdict": "skip", "ocr": "김**" }          // 1단계는 항상 skip
}

종합 status 산출 규칙: 하나라도 fail → fail / fail 없이 warn 있음 → suspect / 전부 pass·skip → pass / AI 판정 자체를 못 함 → unverifiable(제출엔 영향 없음). 관리자가 [확인] 처리하면 resolved로 종결(원판정은 checks에 보존).

4검수 파이프라인 — 사전 필터 + 인라인 + 배치 3경로

경로 0 — 첨부 시점 사전 필터 1차 · 리뷰어 화면

목적: 잘못된 파일이 Drive에 올라가고 제출로 기록되기 전에 되돌린다. 사후 보완 요청(교체요청 → 리뷰어 재제출)은 왕복 비용이 커서, 그 자리에서 바꾸게 하는 편이 양쪽 모두 싸다.

  • 삽입 지점: search-app.js의 _csAddFiles() — 지금은 base64로 읽어 S.filesBySlot에 담기만 하고 서버를 부르지 않는다. 여기에 신규 POST /api/image/review-precheck(무인증, imageApiLimiter) 호출을 얹는다. Drive 업로드 0 · DB 쓰기 0 — 순수 판정만 반환.
  • 판정 범위(1차 한정): kind(review/receipt/other) + channel(naver/coupang/etc) + 탭 기대 채널과의 일치 여부. 상품명·중복·유사도는 넣지 않는다 — 상품명은 기준 미등록 탭이 많아 오탐 위험이 크고, 중복·유사도는 저장된 다른 제출과 대조해야 나오는 판정이라 첨부 시점에는 비교 대상이 없다.
  • ★ AI 콜 순증 0: gemini.service의 캐시 키가 이미지 해시(_getCacheKey('classify:' + base64))라, 첨부 때 판정한 결과가 제출 시 review-upload에서 캐시 히트된다(TTL 10분, 첨부→제출 간격은 통상 그 안). 첨부에서 한 번 쓰고 제출에서 아끼는 구조.

차단 강도 — 3단 (완화·강화 모두 신중히)

판정동작근거
kind='other' AND 확신 ≥ PRECHECK_BLOCK_CONFIDENCE(0.9) 제출 잠금 슬롯에 재첨부 안내 + 제출 버튼 비활성 주문내역·상품사진·빈 화면 = 사람이 봐도 100% 재요청 대상. 그 자리에서 막는 편이 서로 싸다.
채널 불일치 (탭 기대 채널 ≠ 판별 채널) 경고 + 확인 체크 체크하면 그대로 제출 ★ 탭 채널은 상품 URL 호스트로 추정한 값(WO_CHANNEL_HOSTS)이라 우리 데이터가 틀릴 수 있다. 우리 오류로 리뷰어를 막지 않는다. 채널 정보가 없는 탭은 대조 자체를 생략.
AI 미설정·오류·타임아웃·확신 < 0.9 무판정 통과 화면에 아무것도 표시하지 않음 기존 captureVerify fail-open 규율 그대로 — 판별 불가가 제출을 막는 사유가 되면 안 된다.
★★ 탈출구는 반드시 유지(제거 금지) — 같은 슬롯에서 2회 연속 차단되면 “제가 올린 게 맞습니다” 체크가 열리고 제출이 통과된다. AI 오판으로 리뷰어가 제출 자체를 못 하는 상태는 참여 소각이라, 불량 1건을 놓치는 것과 비교가 안 되는 사고다. 우회 통과 건은 reviewer_event_logs critical로 남겨 관리자가 반드시 본다(우회가 조용해지면 차단이 무의미해진다).

킬스위치 REVIEW_PRECHECK=0(사전 필터 전체 OFF — 첨부 동작이 현행으로 복귀) · REVIEW_PRECHECK_BLOCK=0(판정은 하되 잠그지 않고 경고만 — 운영 초기 관측 모드 권장).

경로 A — 업로드 인라인 (신규 제출) 2차

  • review-upload 핸들러에서 ① SHA-256 해시 계산·저장 ② 기존 verifyCapture 콜을 종합검수 콜로 교체(응답에서 슬롯 형식 판정 + 검수 재료를 동시에 얻음 — 콜 수 순증 0) ③ review_inspections에 결과 upsert.
  • 중복·유사도는 이 시점에 DB 대조만(해시 equality + 같은 탭 trgm) — 수 ms 수준.
  • AI 실패·타임아웃 → status='pending'으로만 남기고 업로드는 정상 완료(fail-open). 배치가 재시도.
  • 리뷰어 화면: 기존 슬롯 불일치 인라인 경고는 그대로(경로 0이 죽어 있었을 때의 백스톱). 2차에서 새로 나온 판정(상품 불일치·중복·유사)은 리뷰어에게 표시하지 않고 관리자 검수 탭으로만 — 이 판정들은 사람이 봐야 확정되므로, 리뷰어를 붙잡는 대신 관리자가 [다시 받기]를 눌렀을 때만 통지한다.
  • ★ 경로 0에서 우회 통과된 건(2회 차단 후 리뷰어가 밀고 들어온 건)은 여기서 checks.format.overridden=true로 기록하고 critical 알림을 남긴다.

경로 B — 배치 스윕 (재시도 + 과거 백필)

  • cron 주기(기본 */5) + withJobLock('review_inspect_sweep')(멀티 인스턴스 직렬화 — 기존 락 유틸 재사용).
  • 대상: pending 건 + 검수 이력이 없는 과거 review_submissions(최근분부터 역순).
  • 사이클당 REVIEW_INSPECT_BATCH(기본 20)건 — 건당 Drive downloadFile 1회 + AI 1콜. 시트 API lane 무접촉(쿼터 영향 0), Drive·Gemini 부하는 캡으로 통제.
  • 연속 실패 건은 재시도 상한 후 unverifiable로 종결(무한 재시도 금지 — 스마트빌드 실패 시트 처리와 같은 규율).

알림 연계 (기존 체계 승계 — 새 채널 없음)

판정노출근거(기존 규율)
fail 확실 불량(중복 파일, 확신도 0.9+ 비리뷰 화면)reviewer_event_logs critical → 관리자 대시보드 빨간 알림 + SSE + 검수 탭capture_mismatch의 sure 승격과 동일 기준
suspect 의심(유사도 90%+, 상품명 부분 불일치, 채널 불일치)검수 탭 + 리뷰어 로그(warn)만 — 빨간 알림 없음애매한 판정까지 알리면 급한 건이 묻힌다(늑대소년 방지)
pass / skip·unverifiable검수 탭 집계에만 반영조용한 정상(도배 금지)

도배 방지: 같은 (탭·행·파일)의 미해결 알림이 있으면 새로 쌓지 않고, 교체 업로드로 판정이 pass가 되면 자동 해결(auto:reinspected) — captureVerify의 도배 방지·자동해결 패턴 그대로.

상세

화면 구성 요소

  • 필터 바: 탭 선택(작업 목록 — staff는 담당 탭만) · 상태(의심+불량 기본) · 사유별 칩. 상단에 탭별 검수현황 요약(통과/의심/불량/미검수).
  • 카드: 썸네일(/api/drive/image/:id 프록시) + 리뷰어·행 + 판정 배지 + 근거 한 줄. 클릭 → 상세 패널.
  • 상세 패널: 원본 이미지 + OCR 본문 + 판정 항목별 상세(checks). 중복/유사 건은 상대 파일과 나란히 보기(두 이미지 + 본문 diff 하이라이트).
  • 액션:
    • [통과 처리] — 오탐 확인 시 resolved 종결(원판정 보존, 열려 있던 알림 자동 정리).
    • [교체요청] — 기존 이미지 교체요청 + C/S 카드 통지 흐름으로 연결(리뷰어에게 사유와 함께 재제출 안내 — 신규 통지 채널을 만들지 않는다).
    • [⚙ 검수설정] — 탭별 기대 상품명 입력(inspect_product_names) + 채널별 별점 예시이미지 등록(관리자 설정탭과 동일 위젯 재사용).

6구현 로드맵 (4 마일스톤 · 각각 독립 배포 가능)

M0

1차 사전 필터 — 첨부 시점 채널·리뷰 판별 최우선

잘못된 제출을 애초에 줄이는 단계라 효과가 가장 크고, 기준 등록(상품명 등) 없이도 바로 동작한다. 신규 테이블 없이 배포 가능.

  • gemini.service.classifySubmissionImage에 channel 판별 추가(기존 응답 필드는 상위 호환 유지 — 기존 슬롯 검수 시맨틱 불변)
  • 신규 POST /api/image/review-precheck — Drive·DB 무접촉 순수 판정, imageApiLimiter
  • 프론트 _csAddFiles에 판별 호출 + 슬롯 상태 3종(통과/경고+확인/차단) + 2회 차단 시 우회 체크
  • 회귀가드: 차단 조건이 'other'+확신 0.9로 한정되는지 · AI 실패 시 통과인지 · 우회로가 살아 있는지를 고정(이 셋이 풀리면 참여 소각 사고)
M1

데이터 기반 + 2차 인라인 검수 (신규 제출부터 쌓기 시작)

이 단계만 배포해도 신규 제출은 전부 검수 재료가 쌓인다. 화면 없이도 DB로 확인 가능.

  • migration 081 (review_inspections + file_hash + inspect_product_names)
  • 업로드 핸들러: 해시 계산 + 종합검수 프롬프트(M0의 확장 콜 재사용 — 캐시 히트) + 판정 upsert + 중복/유사도 DB 대조
  • 신규 서비스 reviewInspect.service.js (판정 규칙·상태 산출·알림 연계 — captureVerify 규율 승계)
  • 회귀가드 tests/reviewInspect.test.js (판정 순수함수 + 스텁 pool 핸들러 실행 + fail-open 고정)
M2

배치 스윕 + 과거분 백필

  • cron 스윕(withJobLock, 사이클 캡, 재시도 상한) — pending 재시도 + 과거 review_submissions 해시/OCR 백필
  • 백필 범위 기본: 최근 30일(§8 확정 필요 ⑤) — 전량 백필은 Drive·AI 비용 산정 후
  • 알림 배선(critical/warn 2단 + 도배 방지 + 자동 해결)
M3

통합작업대 "리뷰검수" 탭 UI

  • workdesk nav 탭 + 필터/카드/상세/나란히 보기 + 미확인 뱃지(폴링 — workdesk엔 SSE 없음)
  • [교체요청] → 기존 reviewEdit + csBridge 연동 / [통과 처리] → resolved 종결
  • 검수설정: 탭별 기대 상품명 + 채널별 별점 예시이미지 등록(관리자 설정탭 위젯 재사용)
  • 회귀가드: 라우터 스택 실검사(권한 미들웨어 체인 — authMiddlewareChain 패턴) + 프론트 배선
M4

선택 확장 (운영 데이터 본 뒤 결정)

  • 지각 해시(dHash)로 "수정한 재사용" 탐지 / 전역 텍스트 유사도(GIN 인덱스)
  • 제출자명 검수 ON(수집 데이터 유용성 검토 후) / 광고주 화면 검수 요약 노출
  • 탭 마감 시 검수 리포트(통과율·불량 목록) 자동 생성 — 마감자료(closeout) 파이프라인에 합류

7운영·보안 원칙 (완화 금지선)

원칙내용
fail-open — 판정 불가는 통과AI 장애·미설정·타임아웃·저확신이 업로드·제출을 막는 일은 없다(captureVerify·신원게이트와 동일 규율). 모르면 통과가 원칙.
차단은 1차의 한 갈래뿐제출을 잠그는 경우는 “리뷰 화면이 아님”을 AI가 확신(≥0.9)할 때 하나다. 채널 불일치·상품명 불일치·중복·유사도는 절대 차단하지 않는다(경고 또는 사후 분류). ★ 차단 조건을 넓히면 오탐이 곧바로 참여 소각이 되므로, 확대는 운영 데이터로 오탐률을 확인한 뒤에만.
탈출구 상시 유지2회 차단 시 “제가 올린 게 맞습니다” 우회가 열린다(제거 금지). 우회 건은 critical 알림으로 관리자에게 전달 — 막는 길과 뚫는 길을 함께 둔다. 자동 반려는 여전히 없다 — 불량 확정은 항상 사람이 누른다.
API 비용 통제인라인은 기존 형식판별 콜을 확장·대체(순증 0), 배치는 사이클 캡(기본 20건). Gemini 캐시(동일 파일 재업로드 상각)·타임아웃 9초 골격 재사용. 시트 API lane 무접촉(검수는 시트를 한 번도 읽지 않는다).
Drive 부하다운로드는 배치 백필에서만(신규 제출은 base64를 이미 쥐고 있음). 사이클 캡 + 최근분 우선. 이미지 재업로드·이동 없음(읽기 전용).
PIIOCR 본문·작성자 표기는 내부 전용(광고주 미노출, 1단계). 검수 API는 전부 인증 + 역할 스코프(staff 담당 탭 강제). 이미지 접근은 기존 무인증 프록시의 추측불가 fileId 모델 유지.
킬스위치REVIEW_INSPECT=0(인라인+배치 전체 OFF — 업로드는 기존 형식판별만으로 동작), REVIEW_INSPECT_SWEEP=0(배치만 OFF). 판정 임계 env: REVIEW_INSPECT_SIM_THRESHOLD(0.9) · REVIEW_INSPECT_MIN_TEXT(30자) · REVIEW_INSPECT_BATCH(20).
기존 동작 불변슬롯 형식 검수(capture_mismatch)의 판정·알림 시맨틱은 그대로 유지 — 종합 프롬프트는 기존 응답 필드(kind/confidence/businessNo/amount)를 포함하는 상위 호환으로 설계하고, 회귀가드가 기존 필드 계약을 고정한다.
롤백 용이신규 테이블 + 컬럼 추가만(비파괴). 되돌리기 = env OFF + (원하면) 081 드롭. 라이브 핫패스(주문 원장·시트 쓰기·검색)는 한 줄도 건드리지 않는다.

8구현 착수 전 확정 필요 사항

  1. 1차 차단 범위 — 권고안: “리뷰 화면이 아님”(확신 0.9+)만 제출 잠금, 채널 불일치는 경고+확인 체크로 통과. 채널까지 잠그면 탭 채널 정보(URL 호스트 추정)가 틀렸을 때 정상 제출이 막힌다.
  2. 1차 우회로 — 권고안: 2회 차단 후 “제가 올린 게 맞습니다” 체크로 통과 + critical 알림. 우회로를 없애면 AI 오판 시 리뷰어가 제출을 못 해 참여가 소각된다.
  3. 제출자명 검수(조건 ③) — 본 계획은 "1단계 보류 + OCR 수집만"을 권고. 이대로 진행해도 되는지? (마스킹·닉네임 때문에 오탐이 크다는 판단 — §2-③)
  4. 텍스트 유사도 비교 범위 — 기본 "같은 탭 내"로 시작 권고. 리뷰어가 다른 캠페인에 같은 글을 돌려쓰는 것까지 잡으려면 전역 비교가 필요(비용↑) — 어느 범위로 시작할지?
  5. 불량/의심 시 리뷰어 통지 — 권고안: 자동 통지 없음, 관리자가 [교체요청] 버튼으로 확정한 건만 기존 C/S 카드로 통지. 의심 단계에서 리뷰어에게 바로 보이게 하면 오탐 마찰이 크다.
  6. 광고주(업체) 노출 — 1단계는 내부 전용 권고. 이후 "검수 통과율" 같은 요약만 광고주 작업대에 노출할지?
  7. 과거분 백필 범위 — 최근 30일 권고(그 이전은 이미 업체 전달이 끝난 작업이 대부분). 전량 백필이 필요하면 Drive 다운로드·AI 콜 비용을 별도 산정.
확정되면 M1(마이그레이션 + 인라인 검수)부터 착수한다. M1은 화면 없이도 배포 가능하고, 배포 즉시 신규 제출부터 검수 데이터가 쌓이기 시작한다 — M3 UI가 열리는 시점에는 이미 판정 이력이 차 있는 상태가 된다.
