🚫 모집공고별 참여가능 리뷰어 관리 (블랙리스트 건별 관리)

유저플로우 · 와이어프레임 시안 v1.0 — 직원 아이디어(캡처 2장) 기반 구현계획 · 2026-08-05 · 시안 단계(구현 전 확인용)

1. 아이디어 파악 — 무엇을 만드는가

한 줄 요약: 모집공고 편집 화면에서 "이 공고에 참여할 수 없는 리뷰어"를 건별(공고별)로 지정하고, 차단된 리뷰어가 참여를 시도하면 관리자가 고른 안내 메시지(마감 위장 / 사유 고지)를 보여준다.

캡처에서 읽은 요구사항

캡처 항목해석
공고별 관리 ("건별")블랙리스트여도 이 공고에서는 참여 허용이 가능해야 한다 — 모집이 안 구해지는 공고엔 블랙리스트 리뷰어라도 참여시켜야 하기 때문. 반대로 평소 정상 리뷰어를 이 공고만 차단도 가능.
2000여명 전부 불러오기 ❌전체 명단 로드·전체 저장 금지. 검색해서 찾은 사람만 표에 띄우고, 설정을 바꾼 사람만 저장한다.
"2000명 전체체크가 기본"기본값 = 전원 참여가능. 즉 차단 목록(deny-list) 방식 — 체크를 해제한(차단한) 사람만 DB에 행이 생긴다. 전원 체크 상태를 저장할 필요가 없다.
체크박스 해제 → 참여불가검색 결과 표에서 체크 해제 + [선택 적용] = 그 리뷰어들 이 공고 참여 차단.
안내 메시지 설정 2종차단된 리뷰어가 참여 시도할 때 보일 문구를 관리자가 선택: ① "공고가 마감되었습니다"(마감 위장 — 차단 사실을 드러내지 않음) ② "이전 리뷰 미작성 & 리뷰 기한 경과로 인해 공고 참여가 불가합니다"(사유 고지).
검색 = 이름 / 전화번호 뒤4자리 / 닉네임 + 등록 계좌번호노란 메모 "+등록 계좌번호" — 같은 사람이 이름·번호를 바꿔 등록해도 계좌번호로 추적해 찾겠다는 의도로 해석.
이전 리뷰 상태 표시 (리뷰 미작성 N건 · 기한 경과 N건 · 정상)차단 여부를 판단할 근거를 표에서 바로 보여준다. 기존 데이터(참여 확정 이력 + 리뷰 제출 이력)에서 파생 가능.
필터 (전체/참여가능/블랙리스트/리뷰미작성/기한경과) · 엑셀 다운로드 · 관리 이력보조 기능 — 단계(M2~M3)로 나눠 구현.

기존 시스템과의 연결점 (코드 확인 완료)

  • 전역 블랙리스트는 이미 있다: blacklist 테이블(001, phone UNIQUE·사유·등록자) + /api/blacklist 관리 API. 단 현재 참여(apply) 게이트에서 강제되지 않는다(GAS 시절 이관만 된 상태).
  • 참여 게이트 자리도 이미 있다: POST /api/campaign/:id/apply가 등록 리뷰어 검증(not_registered) → 내정보(profile_missing) → 당일 이력(already_today) 순서로 사유코드를 돌려주는 구조 — 여기에 사유코드 하나를 추가하는 방식이라 홀드·정원 로직 무접촉.
  • 리뷰 미작성/기한 경과 판정 재료: 참여 확정(campaign_applications.submitted / order_submissions) 대비 리뷰 제출(review_index.is_submitted·review_submissions) — 새 수집 없이 파생.
  • 캡처의 S/A/B/C 등급은 현 시스템에 없다 → 1차에서는 등급 대신 "이전 리뷰 상태"로 대체하고, 등급제는 별도 기획(후속)으로 분리 제안.

2. 핵심 설계 결정 (구현계획의 뼈대)

② 저장 모델 — "차단한 사람만 저장" (deny-list)

2000명 문제의 해법: 전원 체크(참여가능)가 기본이므로 DB에는 예외만 저장한다. 신규 테이블 campaign_reviewer_gates 1개 — 공고당 행 수 = 차단/허용 예외 인원수(보통 0~수십 명).
컬럼내용
campaign_id TEXT공고 FK — ★ recruit_campaigns.id가 TEXT이므로 반드시 TEXT(082에서 UUID로 선언했다 마이그레이션 파일 전체가 영영 안 붙은 42804 사고 재발 방지 — 기존 회귀가드가 자동 대조).
phone8판정 키 — 홀드·검색·타계정과 같은 명의 키. 이름이 아니라 번호로 키잉(동명이인 오차단 방지).
modeblock(이 공고 참여 차단) | allow(전역 블랙리스트지만 이 공고는 허용 — "건별"의 핵심).
message_typeblock일 때만: closed(마감 위장) | policy(사유 고지). allow는 NULL.
reviewer_name, created_by, created_at, released_at표시용 이름 스냅샷 + 감사 이력. 해제는 소프트(released_at) — 삭제하지 않아 "관리 이력"이 그대로 나온다. 활성 행 부분유니크 (campaign_id, phone8) WHERE released_at IS NULL.

② 판정 규칙 — 우선순위 3단 (완화 금지)

  1. 공고별 allow 있으면 → 통과 (전역 블랙리스트보다 우선 — "이 공고는 참여시킨다")
  2. 공고별 block 있으면 → 차단 + 그 행의 message_type 문구
  3. 전역 blacklist에 있으면 → 차단 (기본 문구 = 사유 고지형) — ★ 단 이 3단계는 env 옵트인(CAMPAIGN_REVIEWER_GATE_GLOBAL=1)으로만 켠다. 전역 블랙리스트는 지금까지 참여를 막지 않았으므로, 배포 즉시 강제하면 기존에 잘 참여하던 리뷰어가 조용히 막히는 회귀가 된다. 1차 출시는 공고별 게이트만.
★ 판정 단일 출처: 위 3단은 순수함수 utils/reviewerGate.js(가칭) 하나에만 둔다. 소비처(apply 게이트 · 관리 표의 "참여 상태" 배지 · 관제)가 각자 규칙을 만들면 "표에는 참여가능인데 실제 참여는 거부"로 갈라진다 — 리뷰비 resolveReviewFee와 같은 규율.

③ 적용 지점 — apply 게이트 1곳 (+ 위장 마감의 한계 고지)

  • 차단 판정은 POST /api/campaign/:id/apply의 등록 리뷰어 검증 직후, 홀드 생성 전에 넣는다 → 자리 미점유(정원 무오염), 403 + reason:'reviewer_blocked' + 설정된 안내 문구.
  • 마감 위장(closed형)은 응답 문구·화면만 마감처럼 보여준다: campaign.html이 이 응답을 받으면 기존 마감 화면과 동일한 UI를 렌더.
⚠ 위장의 한계(화면에도 고지할 것): 공고 목록 카드는 무인증·개인 무관 렌더라 차단 리뷰어에게도 "모집중"으로 보인다. 위장이 완전해지려면 목록까지 사람별로 달라져야 하는데 그건 목록 캐시(5초)·무인증 구조와 충돌 → 1차 범위 밖. 실제 동선은 "카드 탭 → 참여하기 → '공고가 마감되었습니다'"로, 위장 목적(차단 사실 비노출)은 달성된다.

④ 관리 UI — 검색 기반, 전체 로드 없음

  • 진입: 모집공고 카드 [🚫 참여 리뷰어] 버튼(관제 📡 옆) → 전용 모달. 창구는 리뷰웹시스템[3버전] 모집공고 탭 + 관리자 대시보드 공용(공유 모듈 js/campaign-reviewer-gate.js 한 벌 — 모달 사본 금지).
  • 검색 API: GET /api/campaign/admin/:id/reviewer-search?q= — 이름 부분일치 ∪ 전화 뒤4자리 ∪ 닉네임 ∪ 계좌번호 숫자 부분일치. 서버 LIMIT 50(더 있으면 "N건 더 — 검색어를 좁혀주세요"). 응답에 리뷰어별 이전 리뷰 상태 + 현재 판정(위 단일 출처 함수) 동봉.
  • 이미 차단/허용된 인원은 검색 없이도 보이도록 "이 공고의 예외 목록"이 모달 기본 화면(= 저장된 행만, 보통 0~수십 건).

⑤ 권한·보안

  • 관리 API 전부 authMiddleware + adminOrMaster. 계좌번호로 검색되는 화면이므로 등록리뷰어DB와 같은 판단으로 AE(staff)·광고주 차단, 결과 표의 연락처는 뒤4자리·계좌는 뒤4자리만 표시(전체값 미반환 = 데이터 최소화).
  • 리뷰어앱 공고수정 스코프 토큰(via:'reviewer_campaign')·인트라넷 토큰은 이 경로에 도달 불가(기존 격리 유지) — 차단 목록 조회·변경은 권한 상승 표면이라 화이트리스트에 넣지 않는다.
  • Track B 경로(/api/trackb/campaigns/:id/reviewer-gate)는 _delegate 프록시로 동일 핸들러 재사용(인트라넷 SSO 관리자용 — 단 adminOrMaster 동일).

확인이 필요한 결정 (구현 착수 전 답 주시면 반영)

Q1. 차단 시점에 이미 잡혀 있는 홀드/확정 건은 그대로 두는 것으로 설계했습니다(신규 신청만 차단). 기존 홀드도 강제 취소해야 하나요? (강제 취소는 결제 진행 중인 리뷰어의 자리를 뺏는 파괴 동작이라 기본 제외 권장)
Q2. 안내 메시지 2종은 고정 문구로 시작합니다. 공고별 자유 문구 입력까지 필요한가요? (자유 문구는 리뷰어에게 그대로 나가는 외부 노출 텍스트라 검수 부담 증가)
Q3. 전역 블랙리스트(기존 blacklist 테이블)의 apply 강제는 옵트인 후속으로 뺐습니다. 1차부터 켤까요?
Q4. "리뷰 미작성 / 기한 경과" 판정 기준: 미작성 = 참여 확정 후 N일(기본 14일) 경과했는데 리뷰 미제출, 기한 경과 = 제출은 했으나 기한 이후 — 이 기준으로 괜찮은가요? 기한 일수 설정이 따로 필요한가요?

6. 잔여 위험 · 한계 (문서화)

  • 목록 카드는 위장되지 않는다 — 차단 리뷰어도 카드에서는 모집중으로 보이고 [참여하기]에서 마감 안내를 받는다(§2-③). 완전 위장은 무인증 목록 구조와 충돌해 1차 범위 밖.
  • phone8 키잉의 귀결 — 리뷰어가 다른 번호로 재가입하면 차단이 따라가지 않는다. 계좌번호 검색(노란 메모)이 이를 추적하는 보조 수단이며, 계좌 기반 자동 차단은 오차단 위험(가족 공용 계좌 등)이 있어 사람이 검색해 확인 후 수동 차단까지만.
  • 타계정 참여와의 관계 — 차단 판정은 명의 phone8 기준이므로, 차단된 본인이 타계정 명의로 신청하면 1차에서는 막히지 않는다. 소유자(owner_phone8) 합산 차단은 후속(§09 타계정 규칙과 정합 검토 필요).
  • 사유 고지형 문구의 정확성 — "리뷰 미작성·기한 경과" 문구를 실제로는 다른 사유(단순 관리 차단)에 붙이면 리뷰어 항의 소지가 있다 → 적용 확인(S3)에서 그 리뷰어의 실제 이전 리뷰 상태와 문구가 안 맞으면 ⚠ 경고 표시(차단은 막지 않음).
