01 · OVERVIEW

무엇을, 왜 만드는가

지금은 AE가 올린 작업오더를 관리자가 접수하고, 모집공고를 만들어도 리뷰어는 "참여 신청"까지만 가능합니다. 실제 작업내용(상품·옵션·결제금액·유입가이드)은 카톡방에서 수동으로 전달되고, 구매양식 제출은 별도 링크로 진행됩니다. 이 기능은 그 수동 구간을 시스템 안으로 끌어들입니다.

목표

  • 참여 셀프서비스 — 리뷰어가 공고 카드에서 직접 신청하고, 신청 즉시 작업내용을 확인해 바로 구매·제출까지 완료한다.
  • 시간대 자동 운영 — 구매시간대·일일진행건수 기준으로 공고가 스스로 열리고 닫힌다(오픈예정 타이머 → 모집중 → 금일완료 → 종료). 관리자가 매일 손으로 켜고 끌 필요가 없다.
  • 의미 있는 카운터 — "5/20"이 실제 진행 인원을 반영하도록, 신청은 시간제한 홀드(미제출 시 자동 반환)로 관리한다.
  • 운영 안전 — 오픈 러시(정각 신청 폭주)에도 시트 쿼터·행배정 사고가 나지 않도록 신청은 DB에만 기록하고, 시트 기록은 기존 구매양식 제출 경로(DB-first + 큐)만 사용한다.

#한계해결 방향
1신청 ≠ 진행 — 신청만 하고 구매하지 않아도 current_slots가 계속 차 있어 카운터가 무의미시간제한 홀드 + 만료 자동 반환 (§03-C)
2시간대 수동 운영 — time_range가 자유 텍스트라 기계 판정 불가, 켜고 끄는 건 관리자 몫구조화 시간창 + 서버 상태엔진 (§03-B)
3작업내용 전달이 시스템 밖 — 유입가이드·결제금액이 카톡 수동 전달신청 게이트 뒤 전용 상세 페이지 (§03-D)

5무인증 상세 API가 SELECT * — GET /api/campaign/:id가 전 컬럼 반환. 여기에 작업내용을 넣으면 신청 없이 유출공개 필드 화이트리스트 + 신청 검증 API 분리 — 구현 1단계에서 선행 (§08)
03 · POLICY

핵심 정책 — 상태·시간·홀드·카운트·공개

모든 판정의 단일 기준은 서버입니다. 카드의 타이머·버튼은 표시일 뿐, 신청 가능 여부는 서버가 최종 판단합니다(클라이언트 시계 불신).

A. 공고 노출 상태머신 (서버 계산값, 저장하지 않음)

preopen 오픈예정
오늘 시간창 시작 전. 카드 노출 + 회색 필터 + 흰색 굵은 카운트다운
→
open 모집중
시간창 내 & 일일한도 미달. "n/20" 카운터 + 참여신청 가능
→
open·cutoff 신청마감
종료 10분 전~종료. 신규 신청만 차단, 진행 중 홀드는 제출 계속 가능
→
daily_done 금일완료
일일한도 충족 또는 시간창 종료. "금일 모집완료 · 내일 14:00 오픈" — 비노출 아님
→
closed 종료
총 모집인원 소진 or 관리자 종료. 마감 섹션으로 이동

daily_done → (다음 날 window_start) → preopen/open으로 매일 자동 순환. 상태는 저장하지 않고 매 요청 시 계산하므로 드리프트·크론 누락이 없습니다.

B. 시간 규칙

구매시간창
window_start ~ window_end (TIME, KST 고정)
발행 시 작업오더 purchase_time("2시~4시") 텍스트를 프리필로 보여주고 관리자가 구조화 값으로 확정 입력. 자정 넘김(예 23:00~01:00)은 v1 미지원(발행 폼에서 차단)
신청 마감 버퍼
종료 10분 전 신규 신청 차단
close_buffer_min 기본 10, 공고별 조정. "종료 시각까지 구매 완료" 기준이므로 막판 신청은 물리적으로 제출 불가 → 선차단
오픈 전 노출
숨기지 않고 회색 필터 + 카운트다운
오픈예정 타이머는 굵은 흰 글씨 실시간(HH:MM:SS). 서버 응답의 serverNow와의 오프셋으로 보정 — 기기 시계가 틀려도 정확
일일 리셋
KST 자정 기준 집계, 오픈은 window_start
"오늘"의 신청·제출만 일일 카운터에 포함. 자정~window_start 사이는 preopen

C. 홀드(시간제한 신청) 규칙

① 신청
서버 원자 검사: 시간창·버퍼·일일한도·총잔여·중복 → 통과 시 홀드 생성
→
② 홀드 활성
status=applied, expires_at = min(now+30분, window_end). 카운터 즉시 +1, 작업내용 열람 가능
→
③-a 제출 확정
TTL 내 구매양식 제출 → status=submitted (order_submissions와 링크). 자리 확정
→
③-b 자동 만료
TTL 경과·미제출 → status=expired. 자리 반환·작업내용 접근 종료·재신청 가능
  • TTL 기본 30분 (hold_ttl_min, 공고별 조정). 상세 페이지 상단에 남은 시간 타이머 상시 표시.
  • 만료 스윕: 매분 크론이 expires_at 경과 + 미제출 홀드를 expired 처리(withJobLock으로 다중 인스턴스 직렬화). 만료 판정 직전 order_submissions 링크 존재를 재확인해 "제출했는데 만료" 경합을 차단.
  • 중복 방지: 캠페인당 phone8 기준 활성(applied)·확정(submitted) 신청은 1건. expired/cancelled 후 재신청 허용.
  • 신원: 리뷰어 홈 세션(이름+전화 뒷 8자리, 기존 reviewer/verify) 필수. 미확인 사용자는 신청 버튼에서 본인확인 → 이어서 신청.
  • 취소: 리뷰어 스스로 "참여 취소" 가능(홀드 즉시 반환). 노쇼 반복 시 제재는 v2 검토(§09).

D. 카운트 규칙

카운트계산식노출
일일 카운터 "n/20" n = 오늘의 유효 홀드(applied·미만료) + 오늘의 제출확정(submitted) · 분모 = daily_limit 리뷰어 카드·상세에 실시간(폴링 15초, 서버 5초 캐시). 홀드가 만료되면 n이 내려가고 자리가 다시 열림
총 소진 판정 누적 submitted + 현재 유효 홀드 ≥ recruit_total → closed 총 모집인원·누적치는 리뷰어에게 미표시(요구사항). 관리자 화면에만 표시
잔여일 반영 마지막 날 잔여 < daily_limit이면 분모를 잔여로 축소 표시 (예 "3/7") 총원 노출 없이 자연스럽게 마감 유도
왜 홀드를 카운트에 포함하나? "제출 수만 세는" 방식은 오픈 직후 여러 명이 동시에 구매를 진행하다 정원을 초과 구매하는 사고(구매했는데 자리 없음)를 만듭니다. 홀드 포함 카운트는 초과 구매 방지와 노쇼 자동 정리를 동시에 만족하는 티켓팅 방식입니다.

06 · DATA & API

데이터 모델 · API 설계

모델 축은 recruit_campaigns 확장입니다. 작업오더(work_orders)는 내부 인테이크로 남기고, 발행 시점에 공개용 스냅샷을 캠페인으로 복사합니다 — 내부 필드(작업시트 URL 등)가 구조적으로 공개면에 존재하지 않게 하기 위함입니다.

B. 상태 판정 (서버 단일 함수, 의사코드)

function campaignState(c, now /*KST*/) {
  if (c.status !== 'active')                        return 'closed';
  const used  = countSubmittedAll(c) + countActiveHolds(c);      // 누적 제출 + 유효 홀드
  if (c.recruit_total > 0 && used >= c.recruit_total) return 'closed';   // 총 소진
  const t = timeOfDay(now);
  if (t <  c.window_start)                          return 'preopen';    // 회색 + 카운트다운
  if (t >= c.window_end)                            return 'daily_done'; // 내일 재오픈
  const today = countTodaySubmitted(c) + countTodayActiveHolds(c);
  if (today >= dailyQuota(c))                       return 'daily_done'; // 금일완료
  if (t >= c.window_end - c.close_buffer_min)       return 'cutoff';     // 신규신청만 차단
  return 'open';
}
// dailyQuota = min(daily_limit, recruit_total - 누적확정)  ← 마지막 날 잔여 축소
// 응답에 serverNow·opensAt·closesAt 포함 → 클라 타이머는 오프셋 보정만 담당

D. 인라인 구매양식 — 재사용 방식

  • 채택: 동일오리진 iframe 임베드. 구매양식(search.html)은 9,600줄 search-app.js에 결합된 화면이라 부분 이식이 불가하고, 프론트가 같은 오리진(Cloudflare Pages)이라 X-Frame-Options SAMEORIGIN·localStorage 세션이 그대로 통합니다. AI 캡처 자동입력·다건 카드·검증 로직을 재구현 없이 100% 재사용합니다.
  • 진입 파라미터: 기존 s/g/t/d(공고의 linked_sheet_id/gid/tab_name/display_name) + 신규 app=신청ID&embed=1. embed=1이면 헤더·중복 UI 숨김(임베드 전용 모드).
  • 완료 통신: 제출 성공 시 postMessage({type:'order-submitted'}) → 부모(campaign.html)가 확정 화면 전환·카운터 갱신. iframe 높이는 postMessage 자동 조정.
  • 폴백: iframe 로드 실패 시 "구매양식 열기(새 창)" 버튼으로 동일 URL 직행 — 흐름은 유지.
  • v2 검토 임베드 UX 실측 후 필요 시 경량 전용 폼(원장 API 직접 호출)으로 교체 — 로드맵 §09.

08 · EDGE & SECURITY

엣지케이스 · 보안 · 운영 리스크

선행 보안 수정 (구현 1단계 첫 커밋)

GET /api/campaign/:id 의 SELECT * 축소가 모든 작업의 선행 조건입니다. 작업내용(work_detail)·카톡URL을 컬럼에 추가하기 전에 공개 필드 화이트리스트를 먼저 배포해야, 중간 배포 시점에도 비공개 데이터가 무인증으로 새지 않습니다.
분류시나리오방어
동시성오픈 정각 러시 — 마지막 1자리에 동시 신청단일 SQL 원자 조건부 INSERT(한도 검사 포함, 트랜잭션) — 애플리케이션 레벨 검사·증가 분리 금지. 구현 시 레드-블루-심판 프로세스 적용 대상
동시성만료 스윕 vs 막판 제출 경합스윕이 expired 확정 직전 order_submissions 링크 존재 재확인 — 제출 우선
동시성멀티 인스턴스(rolling 배포) 이중 스윕withJobLock advisory lock (기존 패턴 재사용)
시간클라이언트 시계 오차 — 타이머 조작/오표시모든 응답에 serverNow 포함, 클라는 오프셋 보정 표시만. 신청 가부는 서버 재검사
시간TTL이 시간창 종료를 넘어감 (15:50 신청 + 30분)expires_at = min(now+TTL, window_end) — 종료 시각까지 구매 완료 원칙 유지
시간자정 넘는 시간창v1 발행 폼에서 차단(명시적 제약). 수요 확인 후 v2
데이터참여신청만으로 시트에 행 생성 → 행배정 충돌신청 시트쓰기 폐지 — 시트 기록은 제출 경로만. 기존 신원링크 원칙("쓰기 성공 후")도 그대로 유지
보안미신청자가 work-detail URL 직접 호출phone8+활성홀드 서버 검증, 만료 403. 카드·목록 API에는 작업내용 자체가 없음
보안유입가이드 HTML XSS서버 sanitize(태그·속성 화이트리스트) 후 저장·반환. href/src 프로토콜 검사(https·프록시만)
보안phone8 무차별 대입으로 타인 홀드 열람work-detail은 (campaign_id × phone8) 정확 일치 + rate limit. 응답에 타인 식별정보 미포함
부하오픈 직후 목록 폴링 스파이크목록 응답 서버 5초 캐시 + 폴링 15초 + 상세만 10초. SSE는 도입하지 않음(과잉)
UX구매하러 나갔다 돌아왔더니 만료TTL 사전 고지(신청 전 안내) + 상세 상단 상시 타이머 + 만료 화면에서 원탭 재신청(잔여 시)
운영발행 후 작업오더 수정이 공고에 미반영(스냅샷)의도된 동작 — 공고 수정 모달에서 "작업오더에서 다시 불러오기" 버튼 제공
09 · ROADMAP

구현 로드맵 · 미결 사항

종속성 순서대로 4개 마일스톤. 각 단계는 독립 배포 가능하며 기존 공고 동작(participation_mode=false)을 깨지 않습니다.

단계범위완료 기준
M1 · 기반 ① /:id 화이트리스트 축소(선행) ② 마이그레이션(스키마 §06-A) ③ 상태엔진+list 확장 ④ apply 원자화·시트쓰기 폐지 ⑤ 홀드 스윕 cron ⑥ work-detail API 단위테스트: 상태판정 표준 케이스 + 동시신청 경합 + 만료/제출 경합 (레드-블루-심판 적용)
M2 · 리뷰어 화면 공용 카드 모듈(4상태+타이머) → index.html·recruit.html 적용, campaign.html 상세(참여 전/후), iframe 인라인 제출(embed 모드+postMessage), my-status applied 스테이지 모바일 실기기에서 여정 1~8 완주, bfcache 복귀·새로고침 시 상태 복원
M3 · 관리자 발행 폼 확장(시간창·한도·홀드·썸네일 저장·작업내용 스냅샷), 관제 위젯(오늘/누적/노쇼) 작업오더→발행→자동 운영 1사이클 무개입 통과
M4 · 다듬기 노쇼 데이터 리포트, 임베드 UX 개선(필요 시 경량 폼 전환 판단), recruit.html 구페이지 정리 KPI 첫 측정 리포트

미결 사항 (v2 검토 — 구현 차단 아님)

  • 노쇼 제재 — 만료 반복 리뷰어의 신청 제한(예 3회 만료 시 당일 차단). M3의 노쇼 데이터로 기준 결정.
  • 경량 인라인 폼 — iframe UX가 모바일에서 불편하면 원장 API 직결 전용 폼으로 교체.
  • 자정 넘김 시간창 — 실제 수요 확인 후.
  • 알림 — 오픈 10분 전 PWA 푸시(이미 푸시 인프라 있음) — 오픈 러시를 키우는 부작용도 함께 검토.
  • 차수(회차) 연동 — 같은 탭의 2차·3차 진행 시 공고 재사용 vs 신규 발행 규칙.
