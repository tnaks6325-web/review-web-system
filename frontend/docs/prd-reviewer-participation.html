01 · OVERVIEW

무엇을, 왜 만드는가

지금은 AE가 올린 작업오더를 관리자가 접수하고, 모집공고를 만들어도 리뷰어는 "참여 신청"까지만 가능합니다. 실제 작업내용(상품·옵션·결제금액·유입가이드)은 카톡방에서 수동으로 전달되고, 구매양식 제출은 별도 링크로 진행됩니다. 이 기능은 그 수동 구간을 시스템 안으로 끌어들입니다.

목표

  • 참여 셀프서비스 — 리뷰어가 공고 카드에서 직접 신청하고, 신청 즉시 작업내용을 확인해 바로 구매·제출까지 완료한다.
  • 시간대 자동 운영 — 구매시간대·일일진행건수 기준으로 공고가 스스로 열리고 닫힌다(오픈예정 타이머 → 모집중 → 금일완료 → 종료). 관리자가 매일 손으로 켜고 끌 필요가 없다.
  • 의미 있는 카운터 — "5/20"이 실제 진행 인원을 반영하도록, 신청은 시간제한 홀드(미제출 시 자동 반환)로 관리한다.
  • 운영 안전 — 오픈 러시(정각 신청 폭주)에도 시트 쿼터·행배정 사고가 나지 않도록 신청은 DB에만 기록하고, 시트 기록은 기존 구매양식 제출 경로(DB-first + 큐)만 사용한다.

03 · POLICY

핵심 정책 — 상태·시간·홀드·카운트·공개

모든 판정의 단일 기준은 서버입니다. 카드의 타이머·버튼은 표시일 뿐, 신청 가능 여부는 서버가 최종 판단합니다(클라이언트 시계 불신).

A. 공고 노출 상태머신 (서버 계산값, 저장하지 않음)

preopen 오픈예정
오늘 시간창 시작 전. 카드 노출 + 회색 필터 + 흰색 굵은 카운트다운
→
open 모집중
시간창 내 & 일일한도 미달. "n/20" 카운터 + 참여신청 가능
→
open·cutoff 신청마감
종료 10분 전~종료. 신규 신청만 차단, 진행 중 홀드는 제출 계속 가능
→
daily_done 금일완료
일일한도 충족 또는 시간창 종료. "금일 모집완료 · 내일 14:00 오픈" — 비노출 아님
→
closed 종료
누적 제출확정 ≥ 총 모집 or 관리자 종료. 마감 섹션으로 이동 — 종착(되돌아오지 않음)

daily_done → (다음 날 window_start) → preopen/open으로 매일 자동 순환. preopen~daily_done은 저장하지 않고 매 요청 시 계산(드리프트·크론 누락 없음). 단 closed만은 예외로 영속화합니다: 누적 제출확정이 총 모집에 도달하는 순간 status를 실제 closed로 저장 — 홀드 만료로 카운트가 내려가도 마감 섹션에서 되살아나는 플립을 차단.

  • 역전이 규칙 — 일일한도 충족형 daily_done은 홀드가 만료 반환되면 open으로 복귀합니다(자리가 다시 열림 — 정상 동작이며 카운터도 함께 내려감). 시간창 종료형 daily_done은 다음 날까지 복귀 없음.
  • soft_full (잔여 대기) — "누적 제출확정 + 유효 홀드 ≥ 총 모집"이면 신청만 차단(apply 409 사유 soft_full)하고 표시는 daily_done 계열("잔여 대기")로 처리. 홀드가 만료되면 다시 열립니다. closed(종착)와 명확히 구분 — closed는 제출확정 기준으로만 판정.
  • 참여형 공고에만 적용 — participation_mode=false(기존 공고)는 이 상태머신을 타지 않고 현행 status(active/closed)+max_slots 로직을 그대로 유지.

C. 홀드(시간제한 신청) 규칙

① 신청
서버 원자 검사: 시간창·버퍼·일일한도·총잔여·중복 → 통과 시 홀드 생성
→
② 홀드 활성
status=applied, expires_at = min(now+15분, window_end). 카운터 즉시 +1, 작업내용 열람 가능
→
③-a 제출 확정
TTL 내 구매양식 제출 → status=submitted (order_submissions와 링크). 자리 확정
→
③-b 자동 만료
TTL 경과·미제출 → status=expired. 자리 반환·작업내용 접근 종료·당일 재신청 불가(내일 가능)
  • TTL 기본 15분 (hold_ttl_min, 공고별 조정), expires_at = min(now+TTL, window_end). 제한시간에는 구매뿐 아니라 구매양식 제출 완료까지 포함된다(제출 완료 시각 기준 판정). 안내는 "15분"이 아니라 절대시각 동적 표기: apply 응답의 expires_at 기준 "14:15까지(15분) 제출 완료" — 창 막판 신청자가 "15분 준다더니 잘렸다"고 느끼지 않게.
  • 유효 홀드 판정은 시각 기준: 모든 카운트·게이트 쿼리는 status='applied' AND expires_at > now(). 만료 스윕(매분 크론, withJobLock)은 정리용일 뿐 — 크론이 죽어도 만료 홀드가 자리를 점유하지 못함.
  • 만료는 확정적(유예 없음): 만료 후 도착한 제출은 자동 재확정하지 않는다. 단 주문 자체는 원장에 정상 수용(롤백 금지 — 실물 구매 손실 방지)하고 홀드는 초과분으로 표기 + 관리자 관제 알림(§06-E). 이미 구매한 리뷰어의 구제는 관제 위젯의 운영자 수동 확정으로 처리.
  • 만료 스윕 경합 차단: expired 확정 직전 order_submissions 링크 존재를 재확인 — 제출 우선(만료 시각 전에 도착한 제출 보호).
  • 중복 방지 + 재신청 0회: 캠페인당 phone8 기준 활성(applied)·확정(submitted) 신청은 1건. 만료(expired)·취소(cancelled) 후에도 같은 캠페인에는 당일 재신청 불가(상태 무관, 당일 신청 이력이 있으면 409 — 다음 날 재시도 가능). 홀드 스쿼팅·방치 반복 점유가 원천 차단된다.
  • 신원 = 등록 리뷰어만: 신청 시 서버가 (이름, phone8) 리뷰어 등록 여부를 검증(기존 reviewer/verify 로직 서버측 재사용). 미확인 사용자는 신청 버튼에서 본인확인 바텀시트 → 성공 시 구매양식과 동일 키·포맷(rapp_reviewer_auth: name/phone8/verified/expAt)으로 세션 저장 — 인라인 iframe에서 2차 로그인이 뜨지 않게 하는 필수 조건(§06-D).
  • 남용 방어: phone8당 동시 활성 홀드 상한(전 캠페인 합산 2건) + phone8·IP 단위 apply rate limit + 신청 성공 시 1회성 holdToken 발급(랜덤, DB 저장) — work-detail·cancel의 공통 열쇠로 사용해 phone8만 아는 제3자의 열람·강제취소를 차단.
  • 취소: 리뷰어 스스로 "참여 취소" 가능(홀드 즉시 반환, phone8+holdToken 필요, 이벤트 로깅). 단 취소해도 같은 캠페인 당일 재신청은 불가하므로 취소 확인 다이얼로그에 이를 고지. 계정 단위 노쇼 제재(다캠페인)는 M3 노쇼 데이터 확보 후 v2 확정(§09).

D. 카운트 규칙

카운트계산식노출
일일 카운터 "n/20" n = 오늘의 유효 홀드(applied AND expires_at>now) + 오늘의 제출확정(submitted) · 분모 = 오늘의 dailyQuota(아래) 리뷰어 카드·상세에 준실시간(≤20초) — 목록 폴링 15초+서버 캐시 5초, 상세 폴링 10초. 단 자기 액션(신청 성공·만료 감지)은 응답의 최신 카운트로 즉시 갱신. 홀드가 만료되면 n이 내려가고 자리가 다시 열림
일일 분모 (dailyQuota) dailyQuota = min(daily_limit, recruit_total − 전일까지의 누적 제출확정) — KST 일 시작 시점에 고정, 장중 불변 오늘 제출분을 분자·분모 양쪽에서 빼는 이중차감 방지(마지막 날 잔여의 절반에서 조기 마감되는 결함 차단). 분모가 장중에 "0/7→2/5"처럼 흔들리지 않음. recruit_total≤0(무제한)이면 dailyQuota=daily_limit, daily_limit은 발행 검증에서 ≥1 강제
총 소진 판정 2단 ① soft_full: 누적 submitted + 현재 유효 홀드 ≥ recruit_total → 신청만 차단("잔여 대기", 홀드 만료 시 재개) ② closed(종착): 누적 submitted ≥ recruit_total → status 영속 저장 총 모집인원·누적치는 리뷰어에게 미표시(요구사항). 관리자 화면에만 표시

왜 홀드를 카운트에 포함하나? "제출 수만 세는" 방식은 오픈 직후 여러 명이 동시에 구매를 진행하다 정원을 초과 구매하는 사고(구매했는데 자리 없음)를 만듭니다. 홀드 포함 카운트는 초과 구매 방지와 노쇼 자동 정리를 동시에 만족하는 티켓팅 방식입니다.

B. 상태 판정 (서버 단일 함수, 의사코드)

// 유효 홀드 = status='applied' AND expires_at > now()   ← 스윕은 정리용, 판정은 항상 시각 기준
function campaignState(c, now /*KST*/) {
  if (!c.participation_mode)                        return legacyState(c); // 기존 공고: status+max_slots 현행 로직
  if (c.status !== 'active')                        return 'closed';       // closed는 영속값(제출확정 도달 시 저장)
  const t = timeOfDay(now);
  if (t <  c.window_start)                          return 'preopen';      // 회색 + 카운트다운
  if (t >= c.window_end)                            return 'daily_done';   // 내일 재오픈
  const today = countTodaySubmitted(c) + countTodayActiveHolds(c);
  if (today >= dailyQuota(c))                       return 'daily_done';   // 금일완료 (홀드 만료 시 open 복귀)
  const softFull = countSubmittedAll(c) + countActiveHolds(c) >= c.recruit_total;
  if (c.recruit_total > 0 && softFull)              return 'soft_full';    // 잔여 대기 — 신청만 차단, 종착 아님
  if (t >= c.window_end - c.close_buffer_min)       return 'cutoff';       // 신규신청만 차단
  return 'open';
}

D. 인라인 구매양식 — 재사용 방식

  • 채택: 동일오리진 iframe 임베드. 구매양식(search.html)은 9,600줄 search-app.js에 결합된 화면이라 부분 이식이 불가하고, 프론트가 같은 오리진(Cloudflare Pages)이라 X-Frame-Options SAMEORIGIN·localStorage 세션이 그대로 통합니다. AI 캡처 자동입력·다건 카드·검증 로직을 재구현 없이 100% 재사용합니다.
  • 진입 파라미터: 기존 s/g/t/d(공고의 linked_sheet_id/gid/tab_name/display_name) + 신규 app=신청ID&embed=1. embed=1이면 헤더·중복 UI 숨김(임베드 전용 모드).
  • 세션 선행 조건(필수): 구매양식은 localStorage rapp_reviewer_auth(name/phone8/verified/expAt, 12시간) 부재 시 자체 로그인 화면을 띄운다(search-app.js 실코드 확인). campaign.html 본인확인 성공 시 동일 키·동일 포맷으로 세션을 기록해 iframe 2차 로그인을 차단하고, embed 모드에서 세션 부재·만료가 감지되면 iframe 자체 로그인 대신 postMessage로 부모에 위임 → 바텀시트 재호출.
  • 입력값 복원: 외부 쇼핑몰(쿠팡 앱 전환 등)에 다녀오는 동안 모바일 브라우저가 탭을 리로드해도 폼 값이 살아나도록, iframe 폼 입력을 sessionStorage에 자동 저장하고 app=신청ID 재진입 시 복원 (M2 완료기준).
  • 표시 vs 제출값 우선순위: 상세 페이지의 상품/옵션/결제금액은 표시=공고 스냅샷, 제출값=폼(연결 탭 라이브) — 불일치 시 폼 기준. 공고 수정 모달의 "다시 불러오기"에서 라이브 값 대조 표시.
  • 완료 통신: 제출 성공 시 postMessage({type:'order-submitted'}) → 부모(campaign.html)가 확정 화면 전환·카운터 갱신. iframe 높이는 postMessage 자동 조정.
  • 폴백: iframe 로드 실패 시 "구매양식 열기(새 창)" 버튼으로 동일 URL 직행. 새 창 제출은 postMessage가 닿지 않으므로 부모 상세 페이지가 10초 폴링(홀드 상태 조회) + visibilitychange 복귀 시 즉시 1회 재조회로 submitted 전환을 감지해 확정 화면으로 자동 전환.
  • 카톡 인앱브라우저(recruit.html 공유 진입): localStorage·새 탭 동작이 불안정하므로 인앱 감지 시 "기본 브라우저로 열기" 유도 배너 + 외부 링크는 새 탭 대신 현재 탭 이동 정책.
  • v2 검토 임베드 UX 실측 후 필요 시 경량 전용 폼(원장 API 직접 호출)으로 교체 — 로드맵 §09.
