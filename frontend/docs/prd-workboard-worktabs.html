📑 작업보드 작업탭 워크플로우 — 구현계획(PRD)·와이어프레임 v1.0

2026-08-04 · 대상: 리뷰웹시스템[3버전](workdesk) 내부인 화면(관리자·AE) · 목적: "브라우저에 시트 탭을 여러 개 열어두고, 진행 중인 것은 앞에, 끝난 것은 뒤로 보내던" 직원의 실제 워크플로우를 작업보드 안에서 그대로 할 수 있게 한다.

1. 배경 — 지금 직원은 이렇게 일한다

실제 화면 관찰 + 직원 인터뷰로 확인한 시트 시절의 워크플로우와, 이번 계획에서 각각 무엇으로 바뀌는지의 대응표입니다.

진행 중인 작업 시트를 브라우저 탭으로 여러 개 열어둔다㉮ "열린 작업" 줄 — 작업보드 상단 맨 위에 내가 열어둔 작업이 탭처럼 나란히. 계정에 저장되어 다른 PC에서 로그인해도 그대로 유지(브라우저보다 좋아지는 점)

즉 이번 계획의 부품은 셋: ㉮ 열린 작업 줄(개인별) · ㉯ 완료 상태(전사 공통) · ㉰ 홈 작업 목록 블록.

💡 현재 작업보드의 문제(코드로 확인): 상단 바가 "1단 = 업체 세그먼트, 2단 = 그 업체의 탭들"이라 작업을 바꿀 때마다 업체를 거쳐야 하고, 목록에 순서·진행/완료 개념이 전혀 없으며(서버 고정 정렬), 끝난 작업도 계속 같은 줄에 섞여 나옵니다. 또 작업보드 목록에는 담당자·제출·입금 수치가 없어 관리자 대시보드의 "작업 중인 탭 목록" 같은 한눈 훑기가 불가능합니다.

2. 확정된 결정 4가지 사용자 확정 2026-08-04

① 완료 기준 = 수동 완료 + 자동 후보 배지 담당자가 [✅ 완료] 버튼을 눌러야 완료됩니다(시트에서 탭을 뒤로 옮기던 그 행동). 시스템은 데이터가 다 찬 작업에 ✓ 완료 후보 배지만 붙여 알려줄 뿐, 자동으로 완료 처리하지 않습니다. (제안은 시스템, 확정은 사람)
② 완료 보관 = 가벼운 완료 상태만 완료는 작업보드 화면에서만 분리되는 표시입니다. 리뷰어 검색·인덱스·기존 아카이브 등 다른 시스템 동작은 전혀 건드리지 않아, 되돌리기(진행중 복귀)가 클릭 한 번입니다. 기존 아카이브([마감으로 보내기])는 종전대로 관리자 대시보드에서 별도 진행합니다.
③ 작업 목록 나열 = 홈 화면에 블록 추가 직원이 좋아했던 "작업 목록 나열"(담당자·인원/제출·입금이 보이는 표)은 홈 화면 히어로 아래에 둡니다. 작업보드는 탭(여닫기) 중심으로 유지합니다.
④ 탭바 = 기존 유지 + 열린 작업 줄 추가 업체 세그먼트(1단)·그룹 탭(2단)은 그대로 두고, 맨 위에 "열린 작업" 줄을 추가합니다(총 3단). 기존 습관(업체별 탐색·즐겨찾기)을 깨지 않으면서 브라우저 탭 방식이 얹힙니다.

7. 추가로 정하면 좋은 것 4가지 권장안 제시 — 이대로 진행해도 무방

㉠ "완료 후보 ✓" 배지의 판정 기준
권장
인원 충족 + 전건 제출 + 전건 입금 — 관리자 대시보드에서 이미 "완료(핑크 행)"로 칠하는 기준과 동일. 기준이 두 벌이 되지 않습니다.
대안
인원 충족 + 전건 제출(입금 제외) — 배지가 더 일찍 뜨지만, 입금이 남은 작업을 완료해 버리는 실수를 유도할 수 있습니다.
㉡ 홈 "작업 목록" 블록의 위치
권장
히어로 바로 아래 · 전체폭 — 접속하자마자 보이고 표 컬럼(담당·게이지·입금)이 좁아지지 않습니다. 기존 타일·브리핑 레일은 그 아래로 내려갑니다.
대안
타일 그리드 옆(좌측 열) — 첫 화면 구성이 덜 바뀌지만 표 폭이 좁아져 컬럼을 줄여야 합니다.
㉢ 완료 처리 권한
권장
관리자 전체 + AE는 담당 업체 작업만 — 기존 작업보드 편집 범위 규칙 그대로. 복귀가 클릭 한 번이라 위험이 낮습니다.
대안
편집 허용명단(workdesk_editors)만 — 작업오더 접수·공고 발행과 같은 명단으로 조입니다. 완료가 잦은 일상 동작임을 감안하면 과한 마찰일 수 있습니다.

8. 구현 단계 제안

단계내용배포하면 바로 좋아지는 것
M1
완료+목록		 완료 상태(전사 공통) 저장소 + [✅ 완료]/[↩ 복귀] + 완료 후보 배지 + 홈 작업 목록 블록(진행 중/완료 보관함 서브탭, 담당자·인원/제출·입금 표) + 작업보드 1·2단에서 완료 작업 제외 "작업보드에 진행 중만 남는다" + "관리자 대시보드식 나열"이 홈에 생긴다 — 직원 요청 2건이 먼저 해결
M2
열린 탭		 "열린 작업" 줄(0단) — 계정별 서버 저장, 열기/닫기/드래그 순서, 완료 시 자동 정리, [＋ 작업 열기] 브라우저 탭 워크플로우 완성 — 업체를 거치지 않는 작업 전환

M1·M2는 독립 배포 가능하며 순서를 바꿔도 됩니다. 두 단계 모두 기존 화면·데이터에 대해 추가만 하므로(아래 9절) 되돌리기가 쉽습니다.

9. 개발 부록 개발자용 — 건너뛰어도 됩니다

데이터 모델 · API · 기존 코드 재사용 지점 (클릭해서 펼치기)

새 저장소 (migration 088, 두 테이블 — 관용구: IF NOT EXISTS·soft delete·되돌리기 주석)

  • trackb_tab_done — 완료 상태(전사 공통): (sheet_id, tab_name) 키 + tab_gid + done_at/done_by + deleted_at(복귀 = soft delete, 이력 보존). 부분 인덱스 WHERE deleted_at IS NULL. Track A 무접촉 — tab_configs·index_master에 컬럼을 추가하지 않는다(그쪽은 아카이브·마감(is_closed)이 이미 쓰는 표면).
  • trackb_workdesk_worktabs — 열린 작업 줄(개인별): trackb_workdesk_favorites(060)와 동일 형태 (owner_key TEXT PK, tabs JSONB '[]', updated_at). 키 = sheetId␟tabName␟tabGid(즐겨찾기 _favKey와 동일 규약), 배열 순서 = 탭 순서. ⚠ 즐겨찾기 원장에 접두(@open␟)로 얹지 않는다 — 즐겨찾기는 Set으로 재직렬화되어 순서가 보존되지 않는다.

API (전부 /api/trackb/* — 인트라넷 SSO 토큰 격리 범위 안)

  • GET/POST /api/trackb/workdesk/worktabs — favorites 라우트(trackB.routes.js:85-94)와 동일 골격(authMiddleware, _by(req) owner key, 서버측 정규화·상한).
  • POST /api/trackb/workdesk/tab-done {sheetId, tabName, done:true|false} — _ensureEditScope(master/admin 전체 · staff 담당 탭 canAccessTab · advertiser 차단). done=false = 복귀(soft delete 해제가 아니라 새 상태 행 or deleted_at 세팅 — 이력 보존 방식은 구현 시 확정).
  • 목록 확장 — GET /api/trackb/tabs 응답에 done 주석을 항상 동봉(LEFT JOIN trackb_tab_done, fail-soft) + ?stats=1일 때만 담당자·인원/제출/입금 수치 동봉(tab_configs·index_master·입금 서브쿼리 — 관리자 대시보드 /api/tab/dashboard의 집계식(tabconfig.routes.js:1312-1339) 재사용, 목록 쿼리 실패 시 stats만 비우고 목록은 반환). ★ 스코프의 단일 출처 = scopedActiveTabs(trackB.service.js:1538-1561) — 홈 목록·작업보드·완료 보관함이 전부 이 한 경로를 태워야 AE 담당 범위가 갈라지지 않는다. /api/tab/dashboard를 _delegate 프록시로 뚫지 않는 이유 = 그 응답은 전 탭(스코프 없음)이라 staff에게 담당 밖 데이터가 샌다.

프론트 재사용 지점 (workdesk.html)

  • 열린 줄 저장/동기화 = 즐겨찾기 패턴 복제(:1641-1671 — 로컬 즉시 반영 + 서버 비동기 push + 부팅 시 서버 원본 동기화). 탭 키 규약 _favKey(:1647) 재사용.
  • 홈 목록 줄 클릭 → 작업 열기 = STATE.pendingTab + switchView('workdesk') 기존 계약(:1286-1296, :1446-1460) 그대로 — 히스토리 "중간 항목 금지" 규칙과 자동 정합.
  • 완료 후보 판정식 = 광고주 뷰 _awStatus(:1474-1479, 인원 충족+전건 제출)와 관리자 대시보드 핑크 행 판정(제출+입금 100%, index-app.js:12978-12981) 중 ㉠ 결정에 따름 — 판정은 서버 수치로 클라이언트가 파생(표에 보이는 숫자와 같은 재료 = 배지와 표가 어긋날 수 없음).
  • 작업보드 그룹핑 _wGroups(:1680-1694)에 done 필터 추가(완료 탭 제외), 검색 wSearch(:1749)는 완료 포함하되 "완료" 표기.
  • 홈 블록 삽입 자리 = .hm-hero와 .hm-wrap 사이(:3726-3747). 홈 히어로 "진행 중 작업" 숫자(:3753-3758)는 같은 응답을 쓰므로 진행 중 기준으로 자동 일치.

격리·안전 (Track B 3원칙 준수)

  • 추가만 — 신규 테이블 2 + 신규/확장 라우트, 기존 테이블 스키마 무변경. 시트 쓰기 0 · Track A 핫패스(검색·주문원장·인덱스빌드) 참조 0. 되돌리기 = 라우트 미마운트 + DROP TABLE 2.
  • 완료는 표시 계층 — index_master.status·아카이브·is_closed와 독립. 아카이브된 탭은 활성 목록에서 빠지므로 보관함에서도 사라짐(화면 고지).
  • 배포 스큐 — 구백엔드 응답에 done/stats 필드가 없으면 프론트는 종전 화면 그대로(필드 부재 = 기능 미표시, 조용한 오작동 금지).
  • 회귀가드(구현 시) — tests/workboardWorktabs.test.js: 라우터 스택 실검사 + 스텁 pool로 tab-done 스코프(staff 담당 밖 403) 실행 + scopedActiveTabs 단일 출처(사본 SQL 부재) + 프론트 배선(vm 렌더 — 프리변수 함정 대비) + 완료 제외가 업체 칩 개수에도 반영.

10. 이번에 하지 않는 것

  • 아카이브 자동 실행 — 완료 ≠ 아카이브. [마감으로 보내기]는 종전대로 관리자 대시보드에서(사용자 확정 ②). 완료 보관함에 아카이브 연결 버튼을 두는 것은 추후 별건.
  • 구글시트·리뷰어 화면 변경 0 — 완료/열린 탭은 내부 화면 분류일 뿐.
  • 광고주 화면 변경 0 — 광고주 전용 레이아웃은 이번 범위 밖.
  • 작업 자동 완료 — 데이터 조건 충족 시 자동 처리하지 않음(사용자 확정 ①).
  • 관리자 대시보드(admin.html) 변경 0 — "작업 중인 탭 목록"은 그대로 유지(폐기 예정 트랙이지만 이번 작업이 건드리지 않음).
